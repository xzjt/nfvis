## 4. 本轮教训（入册，接手必读）

1. **veth 是成对设备，一端消失即整对消失**（容器 netns 销毁 ⇒ 容器端消失 ⇒ 宿主端一起没了）。
   「停容器把宿主端留着」在内核里做不到——正确口径是「宿主端随**声明**由网络侧幂等补建、
   随**声明消失/删除**清空」。（R5-2）
2. **应用段序与「释放不再声明的成员」会互相咬**：容器 veth 宿主端必须「先建接口（vnf-if 段）、
   后由 bridge-domain 段 enslave」；恢复重放的 veth 段还要**前置**于交换机段，否则交换机段的
   「释放不在声明里的成员」会把运行中容器的宿主端从 bridge 上摘掉。交换机段要用
   `SwitchMembersOf(cfg,…)` 当声明集单一真源。（R5-0）
3. **清场命令不要只看 `tail -1`**：R6-1 首报时错误原文正好被截断窗口吞掉，误以为删除成功。
   核对面：`show configuration | display set | grep <对象>`、`ip -br link`、`show alarms active`。
4. **「空壳」有两类坑**：vpp 段删叶子留**非 nil 空壳**（判「是否为空」要按**内容**，R4-1）；
   删光一个配置族留空壳会让 `display set` 回放自校验报内部错误——修复走既有**登记制**
   （`pruneEmptySingleton` 逐族登记，**未登记的容器不动**，R4-3）。
5. **容器 `args` 是单个参数元素**（`args "sleep 3600"` ⇒ `exec: "sleep 3600": executable file not found`）；
   跑长命令用 `command /bin/sleep` + `args 3600`。（既有语义，两数据面一致。）
6. **单测全绿挡不住真机（又一次实证）**：本轮多条真机发现（段序、veth 语义、两类空壳、
   `ip tuntap del` 被持有 EBUSY）**全部**是单测/子智能体自检抓不到的；每条都已回灌成守护
   （按**真机形状**——真机抓到的字段/命令/报文形态必须喂进用例）。
7. **内核模式删对象要在内核模式下做**（切回 vpp 后再删，内核侧 teardown 不跑 ⇒ 留孤儿 bridge/tap/VRF；
   必要时手工 `ip link del`）。切回 vpp 前先删干净，或按 §6 配方切过去删。
8. **子智能体的「偏差」清单要先读再验收**：本轮两个子智能体各报出 1~2 条真问题（入桥段序、
   停容器巡检抖动），全部采纳并回灌；其中一个还自行发现「恢复重放的交换机段会摘掉运行中容器的宿主端」。
9. **`ip tuntap del` vs `ip link del`**：前者是 TUNSETIFF detach，要求设备**未被任何进程持有**——
   而产品按设计长期持有内核 DHCP tap（carrier 来自持有者）；删被持有的 tap 用 rtnetlink（`ip link del`）。

## 6. 工作方式（照旧，必须遵守）

- **契约先行**：每个特性先写规格书附录 A 决策（含 由来/口径/不改/落点/测试/真机）+ `AGENTS.md` 决策计数同步
  （`contrib/scripts/check_decisions_count.sh` 守护，现 **344**），再写代码。
- **实现派子智能体**（每批 ≤3 并发、**同一文件只让一个会话改**、逐条**红-绿**）；主会话做审查 + 真机 + 提交。
- **用户可见文本不写决策号**（`internal/archtest` 的 `user_text` 守护会拦）。
- **提交前 `make check`**（七项）全绿；提交信息写清「改了什么 + 真机怎么验的」；推送 `origin v3`。
- **真机验证坚持独立事实源**（`ip`/`bridge`/`nft`/`ss`/`tcpdump`/`journalctl`/docker/virsh/浏览器黑盒），
  **不拿被测代码自己的读视图当 oracle**；清场后核对残留为 0；每条「未验证/未实现/未复现」如实登记。
