## D. 技术方案（已设计，待实现）

### D-1 govpp v0.13.0 stats 限制的解决（三层，建议按顺序）

**实测事实**：govpp pinned v0.13.0（上游最新仅 v0.14.0-alpha）；statsclient 能正确解码接口计数/内存/线程，**只有 buffer 池与 ACL 受影响**；**VPP 自带 `/usr/bin/vpp_get_stats` 可用**（同版本解码保证正确，支持 `dump|ls|poll` + `machine` 格式 + 路径 pattern），实测 `/buffer-pools/default-numa-0/{used,available,cached}` 数值正确。

1. ✅ **第一层（已完成，决策 #68）**：`statstool.go` 新增 `StatsTool` 接口 + 纯函数解析器
   （`ParseStatsMachine`/`BufferPoolsFromDump`），`Buffers()` 在 statsclient 解码失败/全零时改调
   `vpp_get_stats socket-name <stats.sock> dump machine '/buffer-pools/*'`；
   `state.Buffers` 增 `Source`/`Reason`，`/vpp/status` 增 `buffers_source`/`buffers_unavailable`，
   `/metrics` 增 `source` 标签与 `nfvis_vpp_buffer_stats_available`，`show vpp [buffers]` 打印来源与原因
   ——**不静默省略**。真机证据 `docs/evidence/m5/d1-stats-fallback.txt`（可用路径 available=430184；
   停 VPP 后给出来源+原因；重启 VPP 自动恢复）。
2. ⛔ **第二层（ACL 计数，实测不可安全落地 → 正式降 V2）**：`acl_stats_intf_counters_enable`
   **无法经 govpp v0.13.0 调用**——VPP 26.06 消息表 `135/136` 为该消息及其应答，govpp 解析应答 ID 正确
   （136），但实际应答为 `acl_del_reply`（ID 108）：二者 CRC 同为 `e8d4e804`（均为仅含 retval 的应答），
   请求被 VPP 当作 `acl_del`(107) 执行。**不但无效、且可能误删 ACL，故不接线**（不宜"先调用失败再兜底"）。
   另实测绑定后 stats 段无 `/acl-plugin/<名>/...` 逐规则计数（仅默认的 `/err/acl-plugin-*` 错误计数）。
   → 按 D-1 既定规则**正式降 V2**，规格书 §4.3/§12 与决策 #34 已标注（未改为解析 `vppctl` 文本）。
3. **第三层（中期，V2 候选）**：升级 govpp（仅 alpha，牵动全部 binapi，升级前须在 nfvis-vm 跑全量 `make integration`）；或自解析 stats segment（格式自描述、跨版本稳定，~300 行 + 单测，去掉 statsclient 与子进程依赖）——**ACL 命中计数若要恢复，须走此层**。
