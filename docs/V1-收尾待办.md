### 1. ✅ 已完成（2026-09-18 第二十四轮）：`make integration` **全绿**

   231 条断言 PASS / **0 FAIL** / 0 SKIP（`test/integration` 781s；`make integration` 内已显式 `-timeout 45m`）

三条原失败用例的**根因是两条，且都不是「窗口太短」这么简单**（证据
`docs/evidence/v1-closeout-round24-integration-green.txt`）：

- **RC1：产品把 NoCloud seed 挂成 SATA 光盘，而 guest 内核缺 `ahci` → seed 不可见 → cloud-init
  `notfound=disabled` 静默自我禁用**（不是超时，是压根没跑）。四条证据：宿主 `virsh domblklist`
  里 seed 挂着 / guest `lsblk` 只有 `vda*`、无 `/dev/sr0` / guest 内核日志只有 `virtio_blk`、
  `ahci|libata` 命中 0 / guest 的 `ds-identify.log` 写着
  `FS_LABELS=` + `ISO9660_DEVS=` + `No ds found [mode=search, notfound=disabled]. Disabled cloud-init [1]`。
  镜像侧对照：`debian-12-genericcloud` 有 `ata_piix`/`isofs`/`sr_mod` 但**无 `ahci`**；
  **⚠️ 更正上一轮 #17 的结论——genericcloud 不可能通过**，可用的是**完整内核**的
  `debian-12-generic-amd64.qcow2`（已按产品路径 `request images upload` 导入，sha512 与官方一致）。
- **RC2：测试的 `runcmd` 把 guest 网卡写死成 `eth0`，而 guest 里实际是 `enp1s0`**（systemd 可预测网名；
  产品模型里的 `eth0` 只是 VPP 侧 socket 的逻辑名）。证据：guest 串口
  `ci-info: | enp1s0 | ...` + `Cannot find device "eth0"` + `cc_scripts_user.py[WARNING]` +
  `cloud-final FAILED`；同一条日志里的 `Datasource DataSourceNoCloud [seed=/dev/sr0]` 证明 RC1 已修好。
- 另有一层**时间基线**：guest 的地址由 cloud-init **final 阶段**配，而该阶段 `After=network-online.target`，
  本用例的 BD 上没有 DHCP → `systemd-networkd-wait-online` 约 120s 才放行 → guest 到 **uptime ~135s**
  才有地址（串口实测 `modules:final ... Up 134.15 seconds`）。原先按 alpine 定的 60s/150s 窗口必然误判。

修法全在**测试侧与 Makefile**（未改产品）：镜像选取改为「只从已确认可用的镜像里挑，否则跳过并说明要求」
（`testVMImage`/`usableVMImage`）；5 处硬编码核池 `{1,2,3}` 改为按真机事实派生（`vmIsolatedCores`，即 #18）；
`runcmd` 改为按实际存在的非 lo 网卡配地址；等待窗口按上述实测基线放大；串口诊断改为与 ping 等待**并行持续回读**、
失败时把整段 guest 串口带进错误信息。

**新登记、需决策（本轮未动产品）**：#22 seed 以 SATA 光盘交付，缺 `ahci` 的 guest 内核看不到且 cloud-init
静默自禁（Debian cloud 内核、Alpine virt 内核都属此类，正是 NFV 常用精简镜像）；#23 模型接口逻辑名（`eth0`）
与 guest 内核网名（`enp1s0`）不一致，手册宜加一句说明。详见 §2.13。

跑法（现在可直接复跑，全套约 13 分钟）：

```bash
ssh nfvis-vm 'systemctl stop nfvis; systemctl restart vpp; sleep 8'   # 避免两个 actor 驱动 VPP（§3.6）
ssh nfvis-vm 'cd /root/src && GOPROXY=https://goproxy.cn,direct make integration'
ssh nfvis-vm 'systemctl start nfvis'                                   # 跑完把服务起回来
```
⚠️ 跑前确认 **1G 大页 free ≥ 1**（`cat /sys/kernel/mm/hugepages/hugepages-1048576kB/free_hugepages`）：
残留 VM 会占着它，导致 VM 起不来报 `Cannot allocate memory`（我为此白跑过一轮）。
⚠️ 镜像须是「guest 内核有 `ahci` + `iso9660`」的那种：本机用 `debian-12-generic-amd64.qcow2`（缺省自动选中）；
`alpine.qcow2` 与 `debian-12-genericcloud-amd64.qcow2` **都不可用**（缺 `ahci`），选定它们只会得到超时。

### 3.4 网卡 DPDK 绑定（决策 #72；重启后会丢）

> ⚠️ **动手前必读**（2026-09-18 自锁门外的教训）：
> 1. **`ens160` 是管理口**（承载默认路由与 SSH）——`bind-dpdk` **绝不能碰它**。
>    `internal/orchestrator/network/dpdkbind.go` 的 `Bind/Unbind` **没有任何管理口守卫**，
>    文档只是"声明约束"；候选里也会出现管理口（发现 #7）。**先用内核事实确认哪个不能碰**：
>    `ip route show default`、`echo $SSH_CONNECTION`、`ip -o -4 addr show`。
> 2. **先 `modprobe vfio-pci`**（无 IOMMU 时还要 `echo Y > /sys/module/vfio/parameters/enable_unsafe_noiommu_mode`），
>    否则 `bind-dpdk` 直接失败（发现 #6；手册把它放在"CLI 不可用时"的方式 B，实际是**前置条件**）。
> 3. **绑定成功后端口不会自动进 VPP**：需把它**声明进配置**（`set interfaces <口>` + `set vpp dpdk dev <口>`
>    → commit → `request vpp restart`），见 §3.3 与用户手册 §3.3。
>    ✅ **2026-09-18 决策 #100 起产品路径已走通**（此前只能带外手写 startup.conf、且 `request vpp restart`
>    会把口弄丢）：口名→PCI 记在 `/var/lib/nfvis/dpdk-bindings.json`；`request vpp restart` 现在会按
>    committed + 该记录重生成 startup.conf，且对「已接管但未声明」的口**先告警**（掉口防呆）。
>    当前这台机器上 ens192/ens224 **都已由产品声明**（committed 的 `vpp.dpdk.per_dev`）。
> 4. 一旦失联：**带外 `reboot`** 即可恢复（vfio 绑定不跨重启）。

```bash
# 产品命令（会中断流量，须 --yes）
nfvis-cli -c "request interfaces 0000:13:00.0 unbind-dpdk to-driver vmxnet3 --yes"
nfvis-cli -c "request interfaces ens224 bind-dpdk --yes"
```
带外手工（CLI 不可用时；M3 交接文档有原文）：

```bash
modprobe vfio-pci; echo Y > /sys/module/vfio/parameters/enable_unsafe_noiommu_mode
for d in 0000:0b:00.0 0000:13:00.0; do
  echo $d > /sys/bus/pci/drivers/vmxnet3/unbind 2>/dev/null || true
  echo vfio-pci > /sys/bus/pci/devices/$d/driver_override
  echo $d > /sys/bus/pci/drivers/vfio-pci/bind
done
systemctl restart vpp; sleep 8; vppctl show interface
```
**实测平台行为**：① 绑定后内核网卡消失 → 只能按 PCI 定位，且须**按 PCI 回读驱动**；
② 清空 `driver_override` + `rescan` **不足以**让内核重探原生驱动 → 必须给 `to-driver`。

### 3.5 ⚠️ 默认 HTTPS（决策 #72，易踩）

- nfvisd **默认自动生成自签证书并启用 HTTPS**（`/var/lib/nfvis/tls/`）。
  - 开发/测试要明文：**必须显式 `-allow-plaintext`**（该开关是权威的，会忽略已装/自签证书）。
  - `curl` 用 https 需 `-k` 或 `--cacert /var/lib/nfvis/tls/server.crt`。
  - **`nfvis-cli` 零参数即可连**（缺省 `https://127.0.0.1:443` 且自动固定本机证书，决策 #78）；
    口令可用 `-p` / `NFVIS_PASSWORD` / **交互式提示**（决策 #80⑤）。
  - `make e2e` 用 `NFVIS_API=https://…`（证书经 `NFVIS_E2E_CA` 固定，缺省同上路径）。
- **监听地址收敛**：`-listen` 为通配且已配置管理口地址时收敛为管理口地址（未配在本机时不收敛）。

### 3.6 ⚠️ 跑集成测试前必须重置 VPP（踩过两次）

真机验证若在 VPP 里建过对象（BD/VRF/端口），**跑 `make integration` 前必须 `systemctl restart vpp`**，
否则残留拓扑会污染用例（曾遗留 3 个 bridge domain 导致 `TestE2EFlow` 的 VRF ping 0 received；
决策 #37 亦记过"同挂一个 BD 致 NAT 不回 ICMP"）。

### 3.7 ⚠️ cross-connect 环路（真机踩到，整机失联）

`cross-connect` 是**二层直通、无 MAC 学习、无环路保护**。把**同一广播域**内的两个端口直通
（本环境 ens192/ens224 与 ens160 同在 VMnet8）会形成**物理二层环路/广播风暴**——实测导致
**整机 load 21、内核 soft lockup、网络完全不可达**（详见 §5.6）。两端必须属于**不同**广播域。

### 3.8 其它环境事实

- VPP **不自启**（`systemctl start vpp`）。
- nfvis-vm 直连 proxy.golang.org 不通；`git push` 需 ssh key（开发机已配）。
- **开发机（Windows/Git Bash）内存限制**：commit 限额约 2 GB，`go test ./...`（并行编译）会
  `fatal error: out of memory`；用 `go test -p 1 ./...`。CI 不受影响。
- 开发机装了 `python`（无 `python3`）；`ssh-keygen -R <host>` 清陈旧 host key（VM 重装/回滚后会出现）。
- 部分命令输出中文在 Git Bash 下可能乱码（终端编码），不影响判定。

### 3.9 ⚠️ 动包管理**之前先备份 `/var/lib/nfvis`**（2026-09-16 事故后的新流程）

2026-09-16 发布 v1.1.4/v1.1.5 期间，已装实例的配置库 `/var/lib/nfvis/nfvis.db` **被重置**：

## 5. 踩坑记录（勿重蹈）

1. **口令哈希泄露**：commit 的审计详情是完整 diff，而 `/audit-logs` 只需 `ClassReadOnly` →
   read-only 账号可取他人哈希。**教训**：脱敏要覆盖"日志/审计/视图"全链路，且须在**渲染层**
   （放进 `Flatten` 会让"仅改口令"被判为无变更）。
6. **`pkill -x nfvisd` 杀不掉改名后的进程**：开发态实例若叫 `/tmp/nfvisd-old`（进程名 `nfvisd-old`），
   `-x` 精确匹配**不命中**，于是「杀掉旧的、起新的」实际是「旧进程还在占用 18443，新进程绑定失败」——
   后续所有请求都打到**上一个**实例上。本轮因此得到过一组「新旧二进制结果完全一样」的**假对比**
   （还据此差点写错结论）。**教训：换二进制前先 `for p in $(pgrep -f nfvisd); do readlink -f /proc/$p/exe; done`
   确认到底谁在服务**；`pgrep -f` 连路径一起匹配。
7. **管道会吞掉退出码，量退出码必须不经管道**：`$CLI -c ping … | grep -v 连接; echo $?` 拿到的是 **grep 的** 0，
   不是 CLI 的；`OUT=$(cmd | grep …)` 之后 `$?` 同理是 grep 的。本轮据此误判过「ping 退出码 0」。
   **教训：量退出码就单独执行、重定向到文件，别进管道。**（假绿之外，还有一类「假证据」。）
8. **上一轮自己造成的回归要回头查**：决策 #88 那次编辑把 `## 附录 B：…` 标题当成锚点替换掉了（新串里没带回来），
   于是 **v1.1.8 的包内规格书少了附录 B 标题**——守护全绿、测试全过，因为**没人检查文档结构**。
   本轮已补回。**教训：拿标题/锚点做替换时，改完要 `grep` 一次锚点还在不在。**
2. **"声明了但无实现/静默无效"反复出现**（最高频缺陷类型）：`sriov.vf-count`、`max-sessions`、
   `facility/severity`、`management ip address`、物理口 link 告警、**8 处 CLI 语句**都属此类。
   **教训**：命令树/契约里声明的东西若执行器未映射会**静默无效**，比缺功能更危险。
   决策 #79 后由 `DisallowUnknownFields` + `contractStatements` 清单双重兜底——
   **新增契约语句必须同时补进该清单**，否则它永远不会被执行到。
3. **契约与实现漂移**：`/audit-logs` 声明 `offset` 却静默忽略；LLDP `system_name` 在 govpp 里取不到；
   `request api token revoke` 在契约里被放在顶级（决策 #76⑧）。
4. **复核要用"证伪"而非采信标签**：15 条降级里 6 处措辞/证据不准，1 处是真缺陷
   （"无真机证据"的 IPv6 实际藏着 v6 路由不可见的 bug）。
5. **`pkill -f` 会杀掉自己的 ssh 会话**（命令行含匹配串时）。括号技巧（`pkill -f "[u]dp_listen"`）
   **只保护 pkill 自己的 argv，保护不了调用它的那个 shell**：2026-09-15 我在**同一个** `ssh host '<脚本>'`
   里既 `pkill -f "[1]27.0.0.1:18443"` 又写着 `-listen 127.0.0.1:18443`，远端 bash 的 cmdline 含该串
   → 整个会话被自己杀掉，**命令零输出**（排查了半天）。
   可靠做法：① 把脚本落成文件再跑（`bash /tmp/x.sh`，远端 bash 的 cmdline 就只有文件名）；
   ② 或按监听端口反查 PID 再 kill：`pid=$(ss -ltnp | sed -n 's/.*127.0.0.1:18443.*pid=\([0-9]*\).*/\1/p')`。
6. **⚠️ 我自己踩的：`git checkout <file>` 会丢掉该文件的全部未提交改动**。验证红-绿时我用它撤临时改动，
   结果把 `cliexec.go` 的整份改动退回 HEAD。**教训**：红-绿要撤的是"注入的坏代码"，
   应该 `cp` 备份后用 `sed` 改回，别用 `git checkout`。
7. **6 核 VM 上跑重负载会触发内核 soft lockup 而整机失联**：`watchdog: BUG: soft lockup - CPU#3 stuck for 52s`
   （`drain_vmap_area_work` → `flush_tlb_kernel_range` → `smp_call_function_many_cond`，
   即 CPU 饱和下 vmap 回收的跨 CPU TLB flush 长时间自旋）。当时 VPP 轮询线程占着隔离核，
   又在上面跑 Docker/镜像/容器定义。**教训**：验证时避免让 VPP 轮询与重负载同时在 6 核机上跑满；
   失联后可从 `journalctl -b -1` 取证据（重启不会丢上一 boot 的日志）。
8. **CLI 前端与服务端是两条路径**：守卫/校验只加在 HTTP handler → CLI 能绕过
   （`api.cliExecutor` 直调 Provider）。新增任何前置校验必须落在**两侧共同依赖处**（决策 #75）。
9. **⚠️ 交互行为只用管道（非 TTY）演示 → 交互缺陷全部漏网**（决策 #81）。`printf 'show ?\n' | nfvis-cli`
   这类演示里 `term.MakeRaw` 失败、退化 `readPlain`，于是「raw 模式下裸 `\n` 不回车导致的错位」与
   「`?` 必须回车」**都不会出现**——M2 的 `?` 演示记录正是这么跑的，`V1-验收检查表` 据此把
   FR-CLI-001/002/003 判了「通过」，而 Tab **从未实现过列出候选**、`?` **必须回车**。
   **教训**：交互行为必须在 **pty** 下验证——`script -qec '<cmd>' /dev/null`，并用 `cat -A`
   核对行尾是 `^M$`（CRLF）而不是裸 `$`（LF）；且「响铃并列出」这类措辞要**逐词**对照契约，不能只看「补全能用」。
   可复跑的手动冒烟：`contrib/scripts/cli-pty-smoke.sh`（10 项断言，修复前失败 7 项、修复后全绿）。
10. **⚠️ heredoc 会吞掉反斜杠与中文**（本会话被咬三次）：`python - <<'PY'` 里的 `'\\'` 变成 `'\'`（直接语法错误）、
   含 CJK 的匹配串被改坏（**`grep` 匹配不到却报 0 命中，看着像「已清理干净」**）。
   **教训**：脚本/提交信息一律**先 Write 落文件再执行**（`python build/x.py`、`git commit -F 文件`），
   别把带转义或中文的逻辑塞进 heredoc；发现「异常干净的 0 命中」要换个工具复核。
11. **⚠️ 工具/脚本自身出错会制造假红**（比假绿更伤信任，决策 #85）：语义校验脚本先后踩了三次——
    终端文本解析脆弱（把 `ens192` 截成 `192`）、`show l2fib` 空表按行数计得 1、
    **前置条件没校验**（`CLI_BIN=/tmp/nfvis-cli` 已被删 → 所有经 CLI 的断言退化成空输出 → 3 通过/6 失败，
    看着像产品大面积回归，实际完全正常）。**教训**：这类脚本必须**先校验前置条件并 `exit 1` 说清原因**，
    且结论采信前先做「已知正确 → 判 PASS、已知错误 → 判 FAIL」的自校准。
12. **deb 不是逐字节可复现的**：同一棵源码树连续 `make deb` 两次，哈希就不同（打包层 tar 成员 mtime + 压缩）。
   **教训**：别用「重打包 → 比哈希」来验证源码一致；发布校验只能以**发布件自身**的 sha256 为准
   （构建端与回下载件一致即可）。要做可复现构建需给 `dpkg-deb` 设 `SOURCE_DATE_EPOCH`（见 §2.7）。
13. **测试会把缺陷固化成期望**（决策 #84/#86 各出现一次）：`TestDynamicCandidatesEndpoint` 曾断言
    「已配置的接口名**应成为候选**」（正是 #83 的 bug 本身）；5 处断言曾要求消息里**含 `FR-NET-021`** 等内部编号。
   **教训**：断言写**契约语义**（「修改需先关机」「跨 NUMA」），不写实现细节；改行为时若既有测试大面积变红，
   先分辨「产品或测试谁错了」。
14. **收尾必须还原环境**：本会话多次起开发态 `nfvisd`（`/tmp` DB）并扰动 VPP。收尾动作：
