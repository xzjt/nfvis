### 新登记（2026-10-02，round124~126 真机；round126 实证后重写）

- **R140-1（中，round140 真机复现）relay 撤销后 UDP/67 的 proxy 处理残留，域内 DHCP 包被静默吞掉**：
  产品路径配 relay（`set virtual-switches <vs> dhcp-relay server <ip>`）后再删（`delete …`），
  `vppctl show dhcp proxy` 已空，但域内客户端的 DHCP 包仍被 dhcp-proxy 节点按
  `dhcp-proxy-to-server · no dhcp server configured` 丢弃（punt 收不到；同端口重新注册 punt 可夺回）。
  影响：relay 用过又删的域里 DHCP 静默失效；将来 DHCP server 的 punt 注册若只在启用边沿做，也会被它吞掉。
  修法方向：punt 注册在 relay 变化后重申（或巡检自愈）；证据 `docs/evidence/v2-round140-dhcp-server-spike.txt` §5。
  **server 侧已按硬口径规避（#359）**：DHCP 服务器的 punt 注册**每次收敛都重申**（先撤再注，幂等），
  relay 残留夺不走 server 的处理权；**relay 自身的残留吞包（域内无 server 在场时）仍开放**（#359 明确不改 relay 语义）。

- **VPP 的 main heap 占用 1 个 1G 大页**（讨论口径：**1G 只给 VNF、VPP 用 2M**）——**已由决策 #347 部分收口并如实重定性**：
  内核启动基线的默认大页尺寸改为**恒 2M**，并把大页池 sysctl 钉值判据改为取「即将生效基线」（避免
  过渡期把声明值喂错池）；但 **main heap 的 1G 占用无法消除**——round126/127 实测其**偏好最大可用页尺寸**，
  VPP 与内核的相关配置键都改不了（附录 A #347），故「1G 池只给 VNF」的目标**被真机否决**，改为明示边界
  「1G 池声明 N ⇒ VNF 可用 N−1」。以下为原登记（round126 smaps 实证）：
  VPP 进程有一个 **1G 的 hugetlb 映射** `/memfd:seg_0-0`（`VmFlags` 含 `ht`），即它的 main heap；
  `vppctl show memory` 的 `page stats: page-size 2M, total 512` 只是 VPP **内部**把这一页 1G 切成 512 个
  2M subpage 的记账，**不代表内核层面用的是 2M 页**。后果：1G 池（本项目声明 2 页）被 VPP 占 1 页，VNF
  只能再用 1 页 ⇒ **第二个 VNF 起不来**（round124 实测 `cli-vm`/`dns-vm` 均报 `Cannot allocate memory`）。
  **后续路线**：让 VPP 的 main heap（及数据面其它 arena）**避开 1G 挂载点**——用 2M，或给 VPP 指定独立的
  hugetlbfs 挂载点；产品生成的 `startup.conf` 的 `memory` 段与宿主 `/dev/hugepages` 的 pagesize 要一起看。
  动前先按**实测**确认 VPP 26.06 的 `main-heap-page-size` 语义与挂载点选择规则（别按配置名猜）。
  证据 `docs/evidence/v2-round126-*.txt` §2。
- **2M 池大量「预留未用」页**（round126 实测 510 页 ≈ 1GB）——2M 池 `nr=768 / free=235` 的 533 页「在用」
  里只有 23 页有进程/inode 引用，**510 页无任何引用**（smaps/fd/`HugetlbPages` 三向对照），`surplus=0`，
  `vppctl show physmem` 报 `reserved-pages 8192` ⇒ 它们**被进程预留（reserve）但未 fault**。
  **不可用 sysfs 回收**（实测写 `nr_hugepages` 后内核账不变——不在空闲链表上），需从**预留者一侧**释放。
  **后续路线**：核实预留方（VPP/DPDK 的 `reserved-pages 8192` 从哪来、是否可控），并把「预留量」与
  「池声明」对齐（否则池里大半的页被占而 VNF 用不到）。
- ✅ **「重启后现场不自动恢复」的 VPP 半边已由决策 #348 收口**（round129 重启测试达成，PR #278 squash 合并）：

   **后续路线**：a) 补「默认表寻址」能力后再启；b) 待 VPP dns 支持按表/VRF；
   ~~c) 自研域内 DNS 转发器~~ **已按路线 c 落地（决策 #345，round124）：`punt socket` 自研域内转发器，
   全局 + 按域上游，四维真机验证通过**（本行此前仍写「未立项」是**账目漂移**，round138 更正）。
   **余**：管理网侧转发（宿主解析器已覆盖，深化另议）。
4. **IPv6 业务面完整性——余量**（§3-4）——**诊断侧已收口（决策 #330）**；
