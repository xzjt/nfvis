## 一、账面欠款：规格书已承诺推迟、至今未做（10 条；原 11 条中第 11 条已由决策 #305 收口）

### 网络数据面

   （vpp plugins 里 linux-cp 开关已暴露），决策 #6。
2. **VXLAN overlay**（§1-2）——全 0 命中。
3. **VRRP 网关冗余**（§1-3）——全 0 命中。

### 可观测性

6. **ACL 逐规则命中计数**（§1-9）——决策 #68 降 V2 的技术债：govpp v0.13.0 调

   绑定后 stats 段亦无逐规则计数；需升级 govpp 或自解析 stats segment。

### AAA 与安全

7. **管理面主机防火墙策略配置**（§1-12）——0 命中（宿主 nftables 类管理）。

### 系统与运维

### 半成品命令

## 二、已登记未修的缺口（17 条）

（差距分析本节原第 11 条 F1 已由决策 #302 收口移出，其后条目顺延；括注为差距分析原编号。）

1. **R79-1（中）：`POST /logout` 按身份键清候选**（差距分析 §2-1）——同一用户跑任意一条 CLI 命令会
   静默丢弃控制台/脚本侧未提交候选并释放编辑锁（待办 §2.3 有最小复现；决策 #151 只修了
   「一次性事务后交还锁」这一相关面）。根治需会话与身份键分离，契约先行。
2. ~~**VM 启动失败的可诊断性**（§2-2）——vhost-user 初始化失败时 VM 停在 libvirt `paused (starting up)`，
   CLI/控制台只回「已受理」，失败原因仅 libvirt 层可见（round80 登记；恢复办法 = `request vpp restart` + `start`）。~~
   **已收口（决策 #311）**：启动受理后在可配置探测窗口内回读域状态，落在 `paused`/`crashed`/`shutoff`
   等非预期态时透出域状态 + reason、libvirt 日志摘录与恢复建议（CLI `%%` / REST 500 + `detail[]` /
   Web 详情页经既有错误通道可见），正常启动路径与耗时不变。
3. **operator 角色粒度**（§2-3）——决策 #145 只做「只读 vs 有写」两档，operator 仍会看到声明为
   super-user 的入口并得 403；需服务端下发权威 class（契约先行）。
4. **「秘密出口」全量复查**（§2-4）——决策 #149 只脱敏了诊断归档，同类出口未系统扫过。
5. **自助改密连带提交配置页候选**（§2-5，round77 观察项）。
6. **1G 大页池「无主占用」无回收路径**（§2-6）——round88 #199/#201 只收掉了 vpp 包 sysctl 撑大机制，
   池回收本身仍开口。
7. ~~**CLI 引号内 `|` 被当管道切分、多行引号值只取首行**（§2-7）——多行 user-data 须走文件路径规避。~~
   **已收口（决策 #313）**：引号内的 `|`/`#` 不参与切分（管道切分早已 #155 收口，本轮统一词法到
   `internal/cliparse`）；脚本（`-c`/`-f`）与交互 REPL 支持**跨行引号值**（值内保留换行），
   多行 user-data 可内联；只该单行的值由提交校验明确拒绝、不静默取首行。
8. **R84-16：VNF 声明的端口不在交换机配置读视图**（§2-8）——不出现在
   `show virtual-switches <vs> ports`；物化进 `vs.Ports` 需先决策（会改配置库形状）。
9. ~~**R84-18：cross-connect 端口数不足时静默无操作**（§2-9）——既有测试把「缩减到 1 端口」定义为合法。~~
   **已收口（决策 #308）**：调查结论为 applier 的**合法无操作**（`cross_connect=true` 且端口数 <2 →
   `desiredMembers` 有意返回空挂接集合、`takeStale` 摘除旧成员），触发路径是「先建两点直通、再删一个端口」；
   合法性不变，改由提交期结构化警告（`CommitResult.Warnings`）如实报出「本次提交不会建立直通」。
10. **R84-22：恢复收敛顺序**（§2-10）——vNIC 置入 L3 VRF 可能早于建表 ⇒ `No such FIB / VRF (-3)`
    未收敛项，需重放一次才成功。
11. **COMMIT_COMPENSATION_FAILED 无自动消解路径**（§2-12）——对非 VRF 表类残渣不消警；且告警表
    进程内、重启丢历史（round87 §8 已知限制）。
12. ~~**容器镜像目录名 ≠ Docker tag 时镜像不可用**（§2-13）——§12 原第 30 项、决策 #76 §4①。~~
    **已收口（决策 #312，运行时缺陷实为 #160 已修）**：导入时按目录项名重打标签 `<名>:latest`，
    目录项名即唯一可用名；#312 再读出 tar 内嵌 tag 记入 `Image.source_tags` 并在导入输出/详情回显
    （重命名不再静默），并加守护测试保证候选与实际可用同源；README/命令全表/规格书 §12 的旧限制已更正。
13. ~~**console 断开后空闲阻塞在 `Read`**（§2-14）——需按键才退出（FR-CMP-014 伴随缺陷，决策 #70⑤ 待修）。~~
    **已收口（决策 #310）**：根因是客户端的**单点阻塞式读**（主循环直接阻塞在 stdin `Read`，
    服务端断开的 `done` 收不到）；改为本地输入独立协程 + `select` 同时等待，断开即退出、无需按键，
    见用户手册 §8 与规格书附录 A #310。
14. **`request vpp restart` 返回后立即查询偶发 broken pipe**（§2-15）。
15. ~~**deb `Recommends` 未补 `qemu-utils, cloud-image-utils`**（§2-16，原 #20，低）——
    缺 qemu-img/cloud-localds 时 VM 定义失败/测试跳过。~~
    **已收口（决策 #306）**：`Makefile` 的 deb `Recommends` 追加 `qemu-utils, cloud-image-utils`
    （只补 Recommends、不动 Depends）；离线/安装器路径本就显式含这两包，无需改动。
16. ~~**NFR-006 告警侧缺 `time_synced` 三态字段**（§2-17）——审计侧已实现、告警侧未加。~~
    **已收口（决策 #307）**：抽 `internal/clocksync.Mark` 为单一事实源，审计与告警共用；
    告警在创建/重新激活时打标三态，`show alarms`/`GET /alarms`/Web 告警卡同源展示。
17. ~~**VPP 不可用时 `start` 阻塞到客户端超时**（round95 §3 新登记）——`systemctl stop vpp` 后
    `request virtual-machine-functions <n> start` 的请求在到达决策 #311 的 3s 探测窗口**之前**
    就阻塞在 libvirt `DomainCreate`（等 vhost-user socket），直到客户端 90s 超时，且域停在 `paused`。~~
    **已收口（决策 #314，同时是 #311 的验收前提）**：在启动路径**最早可行点**（`p.api.Start` 之前）
    做数据面前置判定——复用既有 `network.Manager.StatusView`（与 `/vpp/status` 同源），VPP 未连接即
    **秒级失败**并给出「数据面（VPP）当前不可用，未启动虚拟机 <n>；request vpp restart（自查：show vpp）」，
    不进入会阻塞的 vhost-user 准备、**不产生 paused 残域**；覆盖 `start` 与 `restart` 的 off→start 分支
    （#311 曾登记 restart 分支未纳入，本条一并覆盖）；REST 走既有 Error 形状 503 `UNAVAILABLE`。

### 未验证（6 条，环境受限，与上列缺陷分开看待）

- **SR-IOV 全链路**（FR-NET-004/021）——nfvis-vm 为 vmxnet3，无 PF/VF 硬件；
  附带：`request sriov delete-vfs` 忽略 `vf <n>` 参数（决策 #94 已「诚实化」）。
- **LLDP 邻居表**（FR-NET-018）——环境无 LLDP 对端（启用与命令已验）。
- **容器 memif 通流**（T0-3 / FR-NET-022 容器侧）——离线无自带 memif 客户端的容器镜像。
- **真人 `Ctrl-]`**（T0-4 / FR-CMP-014）——需运行 VM + 真实交互 TTY。
- **§10 吞吐/容量类基准**——10GbE ≥14Mpps、vhost-user ≥8Gbps、≤10 VM/≤20 容器、恢复 ≤30s/≤3min；
  需流量发生器与目标硬件。
- **硬件健康极端场景**（FR-SYS-012）——VM 无 IPMI/温度传感器/smartctl（降级路径已验证）。

## 三、新发现：文档零登记、但同类产品标配的空白（8 条）

（差距分析本节原编号 6、8、10、11、12 已移入 v3；以下括注原编号。）

1. **DHCP server / relay**（差距分析 §3-1）——全仓库 0 命中（仅两处注释提及 guest DHCP 场景）。
   BVI/L3 网关是产品自己的核心场景，VNF 拿地址只能靠 cloud-init 或外部 DHCP；至少 DHCP relay 该有。
2. **L2 环路防护（STP/RSTP，或至少环路检测）**（§3-2）——0 命中，且 CLI 全表对 cross-connect 场景
   明文警告「无环路保护」；自定位「虚拟交换机」却无任何防环手段。
3. **DNS 转发/代理**（§3-3）——`set dns server` 只是宿主解析器配置；无 dnsmasq 类转发服务供
   VNF/容器/管理网使用。
4. **IPv6 业务面完整性**（§3-4）——地址与静态路由已双栈，但 NAT / ACL 五元组 / 诊断命令
   （ping6/traceroute6）的 v6 覆盖未见证据（待专项核实）；「IPv6 仅管理面 + 静态路由」只能算半双栈。
5. **QoS 深度**（§3-5）——仅单速 cir/cbs 且只支持 ingress-policy 绑定；无 egress 方向、
   无层级 shaper / 优先级队列 / 丢弃策略。
6. **历史时序数据**（§3-7）——`/metrics` 是即时快照、无时序存储；Web 总览 5s 轮询同样没有趋势图
   数据底座，容量规划与事后回溯无从谈起。
7. **`/metrics` 覆盖面**（§3-9）——`internal/metrics` 只采集宿主运行态（/proc 等）；
   VPP / VNF / 容器指标是否进 /metrics 未见证据（待专项核实）。
8. **ping / traceroute 不支持指定 VRF / 源地址 / IPv6**（§3-13）——命令树里 `ping` 仅 VPP 数据面
   IPv4；排障高频细项。
