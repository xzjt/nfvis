## 二、已登记未修的缺口

**本节原 29 条已全部收口**（含 1 条误判撤回）——索引见 [`docs/v2已做.md`](v2已做.md) §二。
本节仅保留**环境受限、尚未取得证据**的项：

### 新登记（2026-10-02，round124~126 真机；round126 实证后重写）

- **VPP 的 main heap 占用 1 个 1G 大页**（讨论口径：**1G 只给 VNF、VPP 用 2M**）——**已由决策 #347 部分收口并如实重定性**：
  内核启动基线的默认大页尺寸改为**恒 2M**，并把大页池 sysctl 钉值判据改为取「即将生效基线」（避免
  过渡期把声明值喂错池）；但 **main heap 的 1G 占用无法消除**——round126/127 实测其**偏好最大可用页尺寸**，
  VPP 与内核的相关配置键都改不了（附录 A #347），故「1G 池只给 VNF」的目标**被真机否决**，改为明示边界
  「1G 池声明 N ⇒ VNF 可用 N−1」。以下为原登记（round126 smaps 实证）：
  VPP 进程有一个 **1G 的 hugetlb 映射** `/memfd:seg_0-0`（`VmFlags` 含 `ht`），即它的 main heap；
  `vppctl show memory` 的 `page stats: page-size 2M, total 512` 只是 VPP **内部**把这一页 1G 切成 512 个
  2M subpage 的记账，**不代表内核层面用的是 2M 页**。后果：1G 池（本项目声明 2 页）被 VPP 占 1 页，VNF
  只能再用 1 页 ⇒ **第二个 VNF 起不来**（round124 实测 `cli-vm`/`dns-vm` 均报 `Cannot allocate memory`）。
  **后续路线**：让 VPP 的 main heap（及数据面其它 arena）**避开 1G 挂载点**——用 2M，或给 VPP 指定独立的
  hugetlbfs 挂载点；产品生成的 `startup.conf` 的 `memory` 段与宿主 `/dev/hugepages` 的 pagesize 要一起看。
  动前先按**实测**确认 VPP 26.06 的 `main-heap-page-size` 语义与挂载点选择规则（别按配置名猜）。
  证据 `docs/evidence/v2-round126-*.txt` §2。
- **2M 池大量「预留未用」页**（round126 实测 510 页 ≈ 1GB）——2M 池 `nr=768 / free=235` 的 533 页「在用」
  里只有 23 页有进程/inode 引用，**510 页无任何引用**（smaps/fd/`HugetlbPages` 三向对照），`surplus=0`，
  `vppctl show physmem` 报 `reserved-pages 8192` ⇒ 它们**被进程预留（reserve）但未 fault**。
  **不可用 sysfs 回收**（实测写 `nr_hugepages` 后内核账不变——不在空闲链表上），需从**预留者一侧**释放。
  **后续路线**：核实预留方（VPP/DPDK 的 `reserved-pages 8192` 从哪来、是否可控），并把「预留量」与
  「池声明」对齐（否则池里大半的页被占而 VNF 用不到）。
- ✅ **「重启后现场不自动恢复」的 VPP 半边已由决策 #348 收口**（round129 重启测试达成，PR #278 squash 合并）：
  nfvisd 启动时若 VPP 未运行即由它发起拉起（发起式 `--no-block`、绝不阻塞自身启动），就绪由既有连接重试
  接管——实测 `reboot` 后**单次启动即 active**（无 90s 超时循环），journal「检测到 VPP 未运行，发起拉起
  （不等待）」→「已连接 VPP」→「恢复收敛完成」，幂等路径「VPP 已在运行，无需拉起」同场验证，无
  `VPP_AUTOSTART_FAILED`。②「VNF 不自启」属**设计行为**——负载需声明 `autostart true` 才随系统自启；
  libvirt 层 autostart 软链由产品按声明建立（sem-vm 实测开机即被 libvirt 拉起）。本项余量只剩 R129-2（见下）。
  证据 `docs/evidence/v2-round129-d348-reboot-verified.txt`。
- ✅ **「VPP 不在时 nfvisd 启动超时」（round128 登记，#348 前置）与「`probeOnce` 只看 api.sock 存在会误判
  陈旧 socket」均已收口**：round129 SIGQUIT 全栈定根——超时的真因是 **R129-1**（libvirt 连接无界阻塞，
  与 VPP 无关），由决策 **#349** 有界化修复；`probeOnce` 现为硬超时 + **真实 binary API 连通判定**
  （#348 实现，`vpp.go` probeRunning）。证据 `docs/evidence/v2-round129-startup-hang-rootcause.txt`。

- **R129-2（中，round129 登记）开机竞态：nfvisd 对 libvirt 的启动降级是永久性的（不自动重连）**——
  libvirtd「Started」后要先做完 sem-vm 的 libvirt autostart（1G 大页 prealloc + mem-lock）才服务客户端
  握手（实测 >10s），nfvisd（unit 有 `After=libvirtd.service` 但记账早于实际可服务）10s 有界等待内连不上
  ⇒ 按 #349 口径降级 NoopCompute 且不自动重连 ⇒ **每次开机后 VM 编排（生命周期动作）需人工
  `systemctl restart nfvis` 恢复**（降级以 `COMPUTE_UNAVAILABLE` 如实呈现）。VNF 本身由 libvirt
  autostart 拉起、数据面由 #348 自动拉起，均不受影响。**候选修法（待立项）**：启动期 libvirt 连接失败后
  **有界重试数次**（如 3×10s 退避）再转永久降级，或周期巡检对 COMPUTE_UNAVAILABLE 自动重连（需评估
  Provider 换装的并发安全）。证据 `docs/evidence/v2-round129-d348-reboot-verified.txt` §2。

---

  「实际持有 / 无主占用」两列 + 告警 `HUGEPAGE_POOL_ORPHAN`，能如实告出上面那类页；`reclaim` 只回收
  「内核实际 > 声明且**空闲**」的多余页（#329 原范围），**不触无主页**（机制不成立：那类页不在空闲链表，
  写 `nr_hugepages` 释放不了）。证据 `docs/evidence/v2-round126-*.txt` §3~§4。
  （round125 曾据此判断「1G 有一页无主、内核可释放」——**该判断已更正**：1G 两页都被真持有。）
- **1G 池的「数据面固定占 1 页」应进入用户可见口径**（round126/127 实测：VPP 的 main heap 始终占
  1 个 1G 页，且无任何配置键可改——见附录 A #347）——当前 1G 池读数只显示「声明/实际/在用/持有」，
  不体现「数据面已固定占用 1 页、VNF 可用 = 声明 − 1」。**待做**：① `wizard` 声明 1G 池时把这一页
  算进去（按「VNF 可用 = 声明 − 1」校验/展示），并在声明 < 2 时提示「无法再起 VNF」；② 读视图
  （`show system hugepages` / `GET /system/hugepages` / Web 资源池页）考虑给出「可用 = 声明 − 数据面
  占用」一列。证据 `docs/evidence/v2-round126-*.txt` §2、round127 实测（2M 池被收小后 VPP 起不来）。

## 三、新发现：文档零登记、但同类产品标配的空白（原 8 条；**未做 5 条**，其余已收口）

（差距分析本节原编号 6、8、10、11、12 已移入 v3。**编号沿用原清单**；已收口部分见
[`docs/v2已做.md`](v2已做.md) §三——三.1 relay 半边 #335、三.2 环路检测 v1 #337、三.5 QoS 出向 #331、三.8 ping/traceroute #330。）

1. **DHCP server 本体**（差距分析 §3-1 余量）——relay 半边已收口（决策 #335）；
   **余**：DHCP server（租约池/状态机）与跨 VRF 的 server（v1 边界）。
   **附带未竟**：relay 的**端到端租约验证**——测试设备受环境工具链阻塞（guest 串口静默、无 exec、
   1G 大页仅 2 页），需换观测通道（修串口，或以预制带 DHCP server 的镜像）后补做（见 round113 证据 §3）。
2. ~~**L2 环路防护**~~——**已收口 v1（决策 #337）**：检测告警 + learn-limit 缓解；
   STP/RSTP 与自动 blocking 属 v3。
3. **DNS 转发/代理的数据面半边**（§3-3 余量）——`set dns server` 只是宿主解析器配置。**尝试未达已撤回
   （决策 #338，round116 真机实证）**：VPP 26.06 的 dns 插件**只在默认表解析上游**（binapi 无 VRF/fib 字段、
   CLI 无表参数），而产品 L3 域都是 VRF 且**无法在默认表配地址**——实测「客户端查询能到 VPP、VPP 永远发不出
   上游查询」（缓存永久 pending、pcap 无出向流量），配了就是假的。
   **后续路线（未立项）**：a) 补「默认表寻址」能力后再启；b) 待 VPP dns 支持按表/VRF；
   c) 自研域内 DNS 转发器（新服务，大）。**余**：管理网侧转发（宿主解析器已覆盖，深化另议）。
4. **IPv6 业务面完整性——余量**（§3-4）——**诊断侧已收口（决策 #330）**；
   **余**：NAT44 与 ACL 五元组的 **v6 覆盖专项核实**（另可选：v6 的 DHCP/ND 等业务面补齐，视 v3 定）。
5. ~~**QoS 深度**~~——**已收口出向（决策 #331）**；层级 shaper / 优先级队列 / 丢弃策略属 v3。
6. **历史时序数据**（§3-7）——`/metrics` 是即时快照、无时序存储；Web 总览 5s 轮询同样没有趋势图
   数据底座，容量规划与事后回溯无从谈起。
7. **`/metrics` 覆盖面**（§3-9）——`internal/metrics` 只采集宿主运行态（/proc 等）；
   VPP / VNF / 容器指标是否进 /metrics 未见证据（待专项核实）。
8. ~~**ping / traceroute 细项**~~——**已收口（决策 #330）**。

**另：ACL 线的口径提醒**（ACL 相关条目均已收口，见 `v2已做.md`）——ACL 只能绑 **L3 接口**
（网关/端口形态提交期拒绝，决策 #340）；绑定时产品自动放行非 IP/ARP（#341）。若将来底座支持其它形态，
须**先补命令树叶子**（契约先行）再启用（原 R119-1 的结论）。
