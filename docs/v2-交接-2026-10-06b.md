## 4. 本批教训（入册）

1. **账目数字必须"可复算"**：命令全表 §3 的漂移能长期存在，根因是没有一条可执行的复核方法（旧数字按若干轮前的
   现场写成）。本轮把复核写成 `grep -c '^| \`' …` 并逐项注明来源，任何后续轮次都能一键复算。**记账同样要被守护**。
2. **「证据已俱、状态未更新」是账目漂移的主力形态**（12 行 🚫→✅）：交付轮次结束时，**行状态要与证据同一批更新**，
   不能只写证据不翻账。
3. **VPP `packet-generator` 的内联 hex 需要 `0x` 前缀**：`data { hex 0x… }` 可建流；无前缀会报
   `failed to parse packet data …`（在带 `interface` 的组合下还会误导性地先报 `output interface or node not given`）。
   **pcap 载荷**（`pcap <file>` + `limit`，字节可精确构造）是最可靠的注入路线——本轮四相位对照即用此法
   （round167 记录只写了 `data { hex … }`，本轮补齐）。
4. **注释与渲染可能不符，只有真机看页面才知道**（R168-1）：`fill()` 会把 `undefined` 渲染成「—」，
   而注释声称"行不显示"——单测/守护看不见这种偏差；Browser Use 复核的清单里要包含**空态**。
5. **「不建」也是路线，但要有据**：定裁要有①技术可行性事实（spike，证明不是"做不了"）+ ②产品口径依据
   （FR 原文，证明是"不该做"）+ ③将来若需的执行路径与工作量（让推翻成本可知）。
6. **Web 复核的完整口径**＝有数据态 + 空态 + 三方一致（Web/CLI/REST）+ 截图；窄视口的列内换行等**观感项如实登记、不夸大**。
7. **逃生门的用法与登记**：本会话有一次 `NO_VERIFY=1` 提交（**仅文档交接一行**、为跳过慢速全树测试；零代码影响）
   ——**事后已按纪律补跑 `make check`（rc=0）**，在此登记；`NO_VERIFY` 只应用于这种零代码影响的场合，且必须补检。
8. **存量 gofmt 漂移会挡住提交**：pre-commit 检查**全树** gofmt，此前轮次经逃生门提交留下的两处注释行漂移
   （`//（` 缺空格）会卡住后续任何提交——本轮已修（`style:` 提交）；**用 NO_VERIFY 提交前先跑 `gofmt -l internal cmd`**。
