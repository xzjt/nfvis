## 4. 本批教训（入册）

1. **故障注入可能被产品自愈吃掉**：可自愈系统里「注入生效」必须对着失败路径的**日志/计数证据**确认——
   本轮第一次删内核 tap 被 15s 巡检静默重建（TapDump 找不到→TapCreate 重建），注入不成立；
   第二次「删真 tap + 即刻同名 dummy 占位」必须**同一条 shell 原子完成**（15s 窗口必被自愈吃掉）。
2. **「修复后仍失败」要区分「修复没用」与「挂点在更早一环」**：#366 只修握手段时真机仍挂——按链路逐环验证
   （WS 升级在 x/net 层不碰 docker ⇒ 101 即时返回；真挂点是 State/create），据此把有界扩到全路径，
   复验中又抓到 `ContainerExec` 的 State 漏网（`context.Background()` 调用方 ⇒ 幽灵完成）。
3. **跨域资源归属要靠真机对照实验定性**：UDP/67 的本地处理是**全局单槽**（server 的 punt 注册 vs relay 的
   per-FIB 代理共用查找点），代码推理说不清谁抢谁——真机「并存前计数 0 → 并存后持续增长」定案。
4. **可自愈/持久化状态让「删了没删干净」类缺陷易被掩盖**：R140-1 的 proxy 残留本轮再次实证
   （删 relay 后 `show dhcp proxy` 仍在，重启才清）——仍在待做清单。
5. **套件数字变化要归因到现场**：语义 25/26/27 三个读数分别对应「S13 缺现场」「规范现场」「S8 窗口热」——
   记录时必须带现场条件，否则会被误读成回归。
6. **只读代码会漏掉「持有层」这一层**（round158）：#375 的 B8 把「Provider 运行期不可达 ⇒ 503」修好后，
   真机（装包时 docker 停着）才暴露「**Docker 启动时即不可达 ⇒ 持有层 `containerHolder` 未接入 ⇒ 500**」——
   REST handler 的 `s.containers == nil` 分支永不命中（持有层非 nil，只是未接入）。真机验证是唯一出口。
7. **套件偶发失败也要定根，不能当噪声放过**（round158）：`TestMetricsHistoryTruncatedAndLimit` 隔离下 5/5 通过、
   负载下偶发失败——定根为 #372 A8 的收窄锚点取墙钟 `until`（⇒ 丢掉本应保留的旧点），另立 **#376** 修复。
   「偶发」往往是**时序假设**在负载下被放大，背后常是真缺陷。
