## 五、round41 新登记（2026-10-21，v3.0.23 发布件走查）

> 来源：`docs/evidence/v3-round41-clean-install-walkthrough-vpp-kernel.txt`。
> 本轮在**发布件**上完成了 VPP/内核双数据面全功能走查与数据面往返，四套件零失败
> （fulltest 297/0/26、语义 43/0/0、lifecycle 40/0/3、pty 10/10，与 v3.0.22 逐项一致）；
> 以下两条为走查中发现的**口径**项（无功能性缺失，但会让同一事实读出不同数字 / 误判命令失败）。

34. ~~**R41-1（中）交换机「成员端口」同一事实三个数，契约未说明**~~ ——
    **已收口（决策 #495，v3 线第 92 条）**。口径＝① 列表 `ports` **语义不动**（它同时是
    `PUT …/ports` 的回写来源，改它会破坏「读出来改一改写回去」的既有用法），改为**契约如实化 +
    并列计数**：`VirtualSwitch.ports` 补 description（配置声明，成员读视图见 `/ports`，
    并写明「判断某口是否属于本交换机请用 `/ports`」），新增 `ports_declared_count`（＝`ports` 条数）
    与 `ports_total_count`（＝`/ports` 条目数，**与 `/ports` 共用同一实现**
    `switchRuntimePortNames`+`switchPortViews`，两处数字恒相等；运行态不可用时退化为配置派生条数）；
    ② CLI 列表列名 `Ports` → **`Ports(rt)`** 并在表尾给口径注（明示是运行态成员数、与
    `show … ports` 的派生并集不同口径）；③ Web 列表「成员端口」列并列显示**配置 / 读视图**两个数，
    列头与页内说明写明两者口径。
    **原始记录（留档）**：最小复现（rev 187~189）——只配 `set virtual-switches cal-test type l2` +
    `gateway ip 192.168.77.1/24`（产品据此建 BVI），则 `GET /virtual-switches` 该对象 `ports` = **null/0 条**、
    `GET …/ports` = **1 条**（bvi1, source=runtime）、CLI 列表 Ports 列 = **1**、CLI `show … ports` = **1 条**；
    大现场（vs-lan 1 静态 + 2 VNF 派生 + 1 容器派生 + 2 运行态）出现 **CLI 列表 3 / REST 列表 1 /
    ports 端点 6** 三数并存。根因：`handleGetVSwitches` 直接序列化 `model.VirtualSwitch`（其 `ports`
    是配置原始端口），而 `/ports` 与 CLI 走 `switchPortViews`（配置派生 ∪ 运行态、剔内置 DHCP tap）；
    openapi 里该字段无任何 description。
    守护：`TestGetVSwitchesPortCountsMatchPortsEndpoint`、`…RuntimeUnavailable`、`…ZeroWhenNoPorts`、
    `TestShowVSwitchListStatesPortColumnCaliber`（均红-绿验过）。
    真机：VPP 下 `declared=1 / total=2` 且 `/ports`=2；内核下 `1 / 3` 且 `/ports`=3；Web 显示 `1 / 3`。
    **须先定口径再改实现**（改字段名是契约变更，属破坏性）。

    **补充（2026-10-21 追查，用户追问「是不是内核/VPP 不同导致」）**——**主因与数据面无关**，
    但**确有一层与数据面有关**，拆开看：
    · **与数据面无关的两层**（这才是三数并存的主因）：① `handleGetVSwitches` 只序列化配置
      （不碰任何数据面）；② `/ports` 与 CLI 走 `switchPortViews`＝**配置派生 ∪ 运行态**。
      同一份配置在**两个数据面**下 `GET /virtual-switches` 都给同样的「仅配置」结果，
      差异恒为「运行态有多少成员」。实测（VPP 现场，vs-lan 静态口只有 ens192）：
      REST 列表 `1 条（ens192）`、`/ports` `2 条（ens192 + bvi0）`、CLI 列表 **2**、
      `vppctl show bridge-domain detail` 真实成员 `bvi0/ens192/tap0`。
      注：CLI 列表的 `Ports` 列取的是**运行态 BD 成员数**（`len(bd.Ports)`，已剔内置 tap），
      不是 `/ports` 那套派生并集——**CLI 列表与 CLI `/ports` 本身也不是同一口径**
      （前者不含「配置里有、运行态还没建」的 VNF vNIC，后者含）。
    · **与数据面有关的一层（新登记，见 R41-3）**：派生条目的**取名规则**两数据面不对称——
      容器分支按数据面给名（#442），**VNF 分支不看数据面**，内核下仍给 VPP 逻辑名
      `vh-<vm>-<nic>`，而内核侧真实设备是 libvirt 建的 `vnetN`。故内核现场会出现
      「派生 `vh-…`（不对应任何设备）+ 运行态 `vnet0`」**两条并列**，端口表数字偏大，
      且按 `vh-` 名去 `ip link` 找不到设备——R5-1/R7-2 同类问题在 VNF 侧的残留。

36. ~~**R41-3（中）内核数据面下 VNF 的派生端口名仍是 VPP 逻辑名 `vh-<vm>-<nic>`**~~ ——
    **已收口（决策 #495）**，取修法 ①：`AttachedPortName` 的 VNF 分支加数据面判断——内核下
    返回**空串**，调用方按既有约定退回 `<vm>/<nic>` 语义名（不编造数据面里不存在的 `vh-…`）；
    VPP 侧逐字不变。同时把 `SwitchPortView.port` 的**可缺席**语义写进契约（`omitempty`，
    缺席时用 `source`+身份字段寻址）。**不做** tap 名簿记（`vnetN` 由 libvirt 分配且随域重建
    变化，需整套生命周期维护——留作后续候选；见下方 R41-4）。
    **原始记录（留档）**：`switchports.go:197 AttachedPortName` 只有 `PortSourceContainer` 分支读
    `cfg.DataPlaneMode()`（内核→veth 宿主端 `nfvisct…`，#442 修 R5-1），**VNF 分支不看数据面**；
    而内核侧 VNF 的等价设备是 libvirt 的 `vnetN`（round41 §4.4：`interface type='bridge'`，
    宿主 `vnet0` 在 bridge 里 forwarding），产品侧无可靠 tap→VM 映射
    （`netkernel/api_surface.go` 的 `CheckVnfPorts` 注释）。影响：端口表两条并列（`vh-…` 派生 +
    `vnet0` 运行态）数字偏大、按名核对找不到设备、反查 vNIC 被引到不存在的名字。
    守护：`TestAttachedPortNameVNFKernelReturnsEmpty`、`…VNFMemifKernelReturnsEmpty`、
    `TestDerivedSwitchPortsKernelVNFPortEmpty`、`TestSwitchPortViewsKernelVNFLabelFallsBack`
    （红-绿：注回旧实现即精确报红）。
    真机（内核，rev 191 同名现场）：端口表由 `vh-r41v-nic0` + `vnet0` 变为 **`r41v/nic0` + `vnet1`**，
    与 `bridge link show master vs-lan` 的实际成员一一对应；`ip link show vh-…` 的「设备不存在」
    这一误导不再出现。

37. **R41-4（低）`CheckVnfPorts` 在内核数据面恒 no-op，`VNF_PORT_DOWN` 告警族在核下不判**——
    `api_surface.go:161` 明确「产品侧没有可靠的 tap 名映射，故不做判定（如实不报，避免误报）」。
    **这是有意的取舍**（避免误报），不是缺陷；但「切数据面后域仍是旧形态、vhost 口 link down」
    这类**真故障**在核下**不会被告警**，只能靠 `show interfaces`/`show alarms` 人工看。
    #495 取的是「派生名退回语义名」（不做 tap 簿记），故本条**保持现状**：核下继续如实不报。
    **后续若做 tap 名簿记，本条可顺带转成可判**——仍待定裁，不单独立项。


35. ~~**R41-2（中）内核数据面下已配 NAT 规则时 `show nat` 整条命令失败**~~ ——
    **已收口（决策 #495）**：`execShowNat` 在 `natRT.Sessions()` 报错时先过能力哨兵判据
    （`unsupportedCapabilityErr`，与 REST 的 501 映射**同一判据**，不新造第二套）——命中则
    **行内降级**：配置段照给（无配置时给「（无 NAT 配置）」）、追加一行
    「运行态不可用（…不受支持——NAT 会话表）；切回 VPP 数据面后可用」、**不带 `%` 前缀**、
    退出码 0；**真实执行故障仍 `%%` 报失败**（不吞）。结构化视图给

## 七、round44 新登记（2026-10-23，v3.0.26 复测）

42. **R44-1（中）脱离脚本的退出码恒为 0，掩盖了 dpkg 真失败与锁冲突**——
    `installScriptWithResult` 生成的脚本以 `printf` 收尾，`launchShell` 又以 `>>install.log 2>&1`
    追加重定向，故整条命令的退出状态取的是最后一条 `printf` ⇒ **恒 0**。
    后果：`installDeb` 里文档化的「`dpkg frontend lock` 撞锁 6 次重试」**从未真正触发**；
    `dpkg -i` 的失败只能靠后续状态读回兜住（本轮 BUG-17 的修复已让状态判定可靠，故危险性下降，
    但「重试」这条设计意图仍是空转）。
    **修法方向**：让脚本把 `dpkg -i` 的 rc 显式传递出来（如结尾 `exit $rc`，且 launchShell 的重定向
    改成对整段分组 `{ …; } >>log 2>&1`），再按新语义重排 `looksInterrupted` / `installedReport` /
    锁重试三处的依赖——**需要单独一轮红-绿，不要与状态判定一起改**。
