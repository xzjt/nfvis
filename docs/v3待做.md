### 自 v2 第三节「新发现空白」后续声明属 v3 的三条（补记一笔）

> 这三条在 `docs/v2待做.md` 第三节的对应条目里写明「属 v3 / 视 v3 定」，但此前未在 v3 侧落点；

## 三、数据面可切换（决策 #404）的未实现族

> 决策 #404 落地「VPP / Linux 内核网络」双数据面。**已实现**：物理口、bond、L2 交换机、

> 以下族在**内核数据面下提交期直接拒绝**，逐个补齐后从本清单移除（每族都要走契约先行 +
> 真机验证）。

1. ~~**DHCP 中继**~~——**已收口（决策 #437）**：内核侧为 nfvisd 内的**自研用户态中继实例**
   （每台声明了中继的 L2 交换机一个；收 bridge 上的 DHCP 请求 → 源地址重写为 BVI 的 v4 网关地址
   → 单播 server:67，giaddr=0；应答按「请求期 xid → 客户端 MAC」登记表回注以太帧），提交期不再
   拒绝；**真机 DORA 全流程已实证**（见决策 #437 与交接文档）。
2. ~~**DHCP 服务器**~~——**已收口（决策 #438）**：复用既有服务器核心不动，只换内核侧传输面
   （每交换机一条**由产品持有的**内核 tap + 绑 BVI 地址的 UDP/67 socket 收单播续租）；**真机
   完整 DORA 已实证**（OFFER/ACK 租约 192.168.99.100）。
3. ~~**数据面 DNS 代理**~~——**已收口（决策 #439）**：内核侧为 nfvisd 内的**域内转发管理器**——
   落点＝域内 IPv4 地址（L2 的 BVI 网关地址 ∪ 各 VRF 的 l3-interface 地址）上的 **UDP/53 socket**
   （绑具体地址 + `SO_BINDTODEVICE` 绑域 VRF）；按域优先、回落全局，皆空回 SERVFAIL；复用 #345 的
   DNS 报文级核心（SERVFAIL 构造/上游去重/宿主栈查询，单一真源）；全局上游（vpp 段的
   `DNSProxyServers`）在该数据面下同样生效。**真机验证待执行**（设计文档 §3.2d）。
4. ~~**LLDP**~~——**已收口（决策 #440）**：内核侧为 nfvisd 内的**自研 LLDP 收发代理**（每启用接口一个
   AF_PACKET socket，ethertype 0x88CC）：收＝解析基础 TLV 建邻居表（TTL 过期移除）；发＝按间隔
   （缺省 30s）向保留组播地址 `01:80:C2:00:00:0E` 发广告，TTL＝4×interval（与 VPP txHold=4 同口径）；
   读视图沿用 `show lldp neighbors` / `GET /protocols/lldp/neighbors`（形状不变）。**真机验证待执行**
   （设计文档 §3.2e）。
5. ~~**memif 容器接入**~~——**已收口（决策 #441）**：内核侧对应物＝**veth + bridge**（宿主端由网络编排
   建、**bridge-domain 段**入交换机内核 bridge——接口先建、桥段 enslave；容器端在容器 start/restart
   成功后移入其 netns；veth 成对，停容器随 netns 整对消失、巡检按声明幂等补回；nfvisd 重启宿主端按名
   复用、绝不重建）。**真机已验证**（alpine 容器取到产品 DHCP 租约 + ping 网关 0% 丢包 + 生命周期六态；
   证据 `docs/evidence/v3-round6-d441-container-veth.txt`）。
6. ~~**MAC 学习上限**~~——**已收口（决策 #435）**：内核 bridge 无「学习条数上限」原语，产品实现为
   「fdb 计数 + 阈值告警」（`BRIDGE_FDB_LIMIT_REACHED`，不强制限制学习、不伪造「已限速」）。
7. ~~**抓包**~~——**已收口（决策 #436）**：抓包命令面去 vpp 化（`show capture` / `request capture …` /
   `/capture`，旧名保留为兼容别名），内核侧以宿主 `tcpdump` 实现（真机导出可解析）。
8. **VPP 专有口径**：`show vpp *`、`request vpp restart`、DPDK 接管、大页池的「数据面占用」

## 四、round3 后续（内核数据面自研族）登记

### R3-11【高·同族死锁】`aclByName` 在 apply 路径回落读活配置

- **现状**：`internal/orchestrator/netkernel/families.go` 的 `aclByName` 在**进程内登记未命中**时回落
  `p.config()`（读 committed 配置 → 取 `Engine` 锁）。它在 `ApplyL3Interface` 的**应用路径**上。
- **风险**：与决策 #438 真机抓到的那条**同型**——**提交期间发动机锁由这次提交自己持有**，此时回落读
  它即**自死锁**、整个管理面卡死。正常路径命中登记时不会走到，故 round1 真机未暴露；但「该 ACL 未登记」
  是可达场景（例如恢复重放时该 ACL 下发失败、登记未写入，同一提交内绑定它）。
- **修法（已定裁：修）**：回落改为读**非阻塞快照**（如 `p.cfg` / 新增 `configSnapshot()`），差异仅限
  「快照与登记都没有时如实报『绑定了未下发的 ACL』而不是读活配置」——比读活配置更安全且不死锁。
- **取证方式**：套用 #438 的守护样式（「读取即阻塞」的假配置源 + 源码级扫描）。

### R7-1【中·告警不随事实消解】内核数据面下 `ReconcileRecoveryAlarms` 为空操作（**已收口：决策 #443**）

- **现状**：`internal/orchestrator/netkernel/api_surface.go` 的 `ReconcileRecoveryAlarms` 直接
  `return nil`（注释按「VPP 侧登记型对账、内核无对应族」处理）；但内核侧**确实会落这一族告警**
  （`netkernel/recovery.go` 按 `network.AlarmIfaceMissing` / `AlarmUnconverged` 落）。
- **影响（真机实证）**：走数据面切换固定动作（切内核 + restart + 再交还两口）必落两条 error 级
  `RECOVERY_IFACE_MISSING`；端口交还、事实愈合后**跨约 21 个 15s 巡检周期仍不消解**，文案与事实相反
  （「仍绑定在 vfio-pci、内核里没有它」），直到下一次**全量重放**（nfvisd 重启/换数据面）末尾 `Sync`
  才清。VPP 侧同场景（同轮实测）在端口出现后当场消解——两侧口径不一致（#333/#367 的纪律只落到 VPP）。
- **已收口（决策 #443）**：判定逻辑抽为数据面中立的 `network.ReconcileRecoveryAlarmsCore`（两数据面
  共用），内核侧按同一纪律实现——声明集覆盖 `netkernel/recovery.go` 的全部可判定来源
  （acls/qos/bonds/virtual-switches（含叶）/interfaces/port-mirroring/vrfs/vxlan）、
  `container-functions/<owner>/interfaces/<iface>` 与恢复重放同一派生口径、
  `interfaces/<name>` 的存在性判据＝**内核实况**（`ip -d -j link show`）。同纪律：只复核、
  不触发重放、不 Raise。**真机复验**（2026-10-10，换装二进制）：口仍缺时跨 2+ 个 15s 巡检周期
  **不误清**；交还两口后**首个巡检周期内自动消解、全程无重启**；VPP 侧行为不退化。
  证据 `docs/evidence/v3-round8-d443-kernel-recovery-reconcile.txt`。
