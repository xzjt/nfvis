## 4. 本轮教训（入册，接手必读）

1. **内核侧 apply 路径绝不可回头读配置发动机** —— 这是本轮最重的一条。`Engine.Committed()` 在**提交期间由这次提交自己持锁**，
   apply/Sync 路径里读它就是**重入自死锁**，整个管理面卡死（CLI 全无响应，只能 SIGQUIT 恢复）。本轮**两处**：
   `#438` 的 `vsOfBD`（真机抓到）、`R3-11` 的 `aclByName`（审计抓到）。**守护样式已成型**：
   ①「**读取即阻塞**」的假配置源（`internal/orchestrator/netkernel/dhcpserver_test.go` 的 `blockingConfigSource` + `runNoBlock`）；
   ② **源码级扫描**（`TestKernelApplyPathSourceHasNoConfigRead`，现覆盖 `dhcpserver.go`/`dhcp_relay.go`/`families.go`——
   **新加 apply 路径文件时记得加进这个列表**）。交换机/对象事实一律**从调用点传入**，或读**进程内快照**
   （`Provider.configSnapshot()`，由 `SetConfig` 在装配与每次恢复收敛时刷新）。
2. **内核 tap 必须有持有者才有 carrier**：`ip tuntap add` 只建**持久化设备**；TUN/TAP 的 carrier 来自
   「是否有进程打开 `/dev/net/tun` 持有它」。无人持有 ⇒ `NO-CARRIER` ⇒ bridge 洪泛的帧到不了它、
   AF_PACKET 也读不到（**命令全成功、功能恒不生效**的静默失效）。VPP 模式能用是因为 VPP 自己持有那个 tap。
3. **AppArmor 会挡住 tcpdump 写产品的抓包目录**：`/var/lib/nfvis/captures` 不在 tcpdump 的 profile 放行列表里
   （实测 `Couldn't change ownership of savefile` / `Permission denied`），而 `/tmp` 放行——工作文件落 `/tmp` 再搬。
4. **iproute2 的 JSON 键会变**：`bridge -j fdb` 旧版 `dev`/`flags`、新版 `ifname`/`state`；只认旧键会让读数**恒空**
   （本轮真机：21 行→0 行）。**判据涉及底座字段名时，务必喂真机应答形状进守护测试**。
5. **AF_PACKET 直接在 bridge 上发帧不进 bridge 的 RX**（它走的是"出去"路径）⇒ 用自制客户端测 DHCP 这类
   二层交互时，**要用一根 veth 把它接成 bridge 成员**，帧才会经 bridge 洪泛到本地端口。
6. **VMnet8 上有 VMware 自带的 DHCP**：在内核数据面做 DHCP 实验时它会**抢答**（yiaddr `192.168.155.x`）——
   客户端/判定要按**自己的地址段**筛选或用 server-id 区分，否则会被环境噪声蒙混。
7. **内核数据面切换的固定动作**（本轮反复用，照抄即可）：
   ```bash
   # 切内核
   /root/ncc -c "configure
   set system dataplane kernel
   commit"
   systemctl restart nfvis; sleep 18
   /root/nc -c "request interfaces ens192 unbind-dpdk --yes"                                  # 可能要先解绑
   /root/nc -c "request interfaces 0000:0b:00.0 unbind-dpdk to-driver vmxnet3 --yes"         # 内核未自动探测原生驱动时补这条
   # 切回 vpp
   /root/ncc -c "configure
   set system dataplane vpp
   commit"
   systemctl restart nfvis; sleep 16
   /root/nc -c "request interfaces ens192 bind-dpdk --yes"
   /root/nc -c "request interfaces ens224 bind-dpdk --yes"
   /root/nc -c "request vpp restart"; sleep 12
   ```
   ⚠️ **`systemctl restart nfvis` 之后可能残留上一次的内核对象**（本轮见到过孤儿 tap、以及早前几轮留下的
   未声明 `vs-wan`/`vs-nat`/`vr-vs-lan`/`vr-vs-dmz`）——收尾要 `ip -d link show type tun`、`ip link show type vrf/bridge`
   对一遍；**删场景要在内核模式下做**（切回 vpp 后再删，内核侧 teardown 不会跑，会留孤儿 tap）。
8. **换装二进制的配方**（本轮每项都用）：
   ```bash
   cd /d/Images/Code/test && tar czf /tmp/src.tgz cmd internal go.mod go.sum && \
     scp -i ~/.ssh/id_ed25519_nfvis -q /tmp/src.tgz root@192.168.155.129:/root/
   ssh -i ~/.ssh/id_ed25519_nfvis root@192.168.155.129 'cd /root/src && tar xzf /root/src.tgz && \
     export GOPROXY=https://goproxy.cn,direct && \
     go build -o /tmp/nfvisd-new ./cmd/nfvisd && go build -o /tmp/nfvis-cli-new ./cmd/nfvis-cli && \
     install -m 0755 /tmp/nfvisd-new /usr/bin/nfvisd && install -m 0755 /tmp/nfvis-cli-new /usr/bin/nfvis-cli && \
     systemctl restart nfvis'
   ```
9. **子智能体的单测全绿挡不住真机**：本轮四条真机发现（自死锁、tap 无持有、AppArmor、fdb 键名）**全部是单测抓不到的**——
   假配置不会重入锁、假 tap 不会没有 carrier、假 Runner 不会遇到 AppArmor。**每项交付都要真机过一遍**，
   且真机发现要回灌成守护（本轮已补：阻塞配置源用例、TUNSETIFF 认领断言、fdb 新形状用例、源码级扫描）。
10. **子智能体交付后先看清 `git status` 再动 git**：本轮一次审查中差点误操作未提交的实现（同族教训见上一份交接）。
