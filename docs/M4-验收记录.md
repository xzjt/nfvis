## M4-2 资源池账本与分配

**关联**：FR-CMP-001~004、FR-SYS-010、FR-CFG-011①⑤⑨⑩⑪；任务 M4-2；决策 #39、#24。

**落地现状**：账本（`internal/model/resources.go` 的 `PoolLedger`）与四类校验在 M1/M2 已交付并由
`Engine` 默认校验链（`model.Validate` + `model.CheckResources`）执行；M4-2 本次补齐：

1. **账本语义修正**：`memory.backing=normal` 的 VM 用普通内存，**不占用大页池**（FR-CMP-019，决策 #39）。
   此前实现会为其扣减大页，导致无资源池时普通内存 VM 被误拒。
2. **契约回归**：`GET /resource-pools` 原返回 `cpu.{isolated,vpp_reserved,free,vm_allocated}`，
   与 OpenAPI `ResourcePool.cpu.{isolated_cores,numa,allocated[{vnf,cores}]}` 漂移，且缺运行态
   `free`/`vpp_reserved` 声明；按契约先行修正**契约 + 处理器**（契约见 OpenAPI，决策 #39）。
3. **健壮性**：未配置 `resource-pools` 时 GET 不再 nil panic，返回空视图。
4. 运行态视图抽为纯函数 `resourcePoolView(cfg)`，直接单测。

**单测**（本地，`make check` 全绿）：新增 normal backing 不占页/无池可建/混合 backing 三例；
`allocated` 按 VNF 名升序、`vpp_reserved`/`free`/`numa` 形状断言；覆盖率
`internal/model` 78.6%、`internal/api` 纳入全量测试。

**真机交叉核对**（nfvis-vm，新增 `test/integration/m4_pool_test.go`）：

```bash
cd /opt/nfvis/src/nfvis
go test -tags integration -count=1 -v -run TestResourceLedgerMatchesHostFacts ./test/integration/
--- PASS: TestResourceLedgerMatchesHostFacts
    真机 HugePages_Total=3 Free=1（VPP 等已占 2 页）
    真机：1G 大页 total=3 free=1；VPP 保留核=[4 5]；隔离核=6 个
```

断言：① 账本 1G 池总量 = 真机 `HugePages_Total`（3）；② 账本 `vpp_reserved` = 真机
`/etc/vpp/startup.conf` 的 `main-core 4` + `corelist-workers 5`（FR-SYS-010 先扣）；
③ 1 台 1G VM 账本占 1 页，且真机 `Free=1` 恰好可启动；④ 池缩减到存量之下 commit 报错
（FR-CMP-004）；⑤ `backing=normal` 在页池为 0 时仍通过（FR-CMP-019）。

**未验证项（如实标注）**：「`show resource-pools` 与实际 domain 一致」需真实 domain。**已于 M4-3 闭合**：
`TestVMLifecycleRealLibvirt` 以账本 `model.AllocationFor` 分配绑核（隔离核 [1,2,3]）→ 定义并启动真实
domain → `virsh dumpxml` 回读 `vcpupin cpuset` 与账本一致（日志「账本绑核 [1] 与真实 domain vcpupin 一致」）。

SR-IOV 无解析报错）、删除级联与幂等、stop 优雅与超时强杀、restart 运行中与关机态、状态映射、

链路：以 1G 大页 VM（无 vNIC，vhost-user 通流属 M4-4）+ cloud-init 定义 → autostart 运行 →

须可由 libvirt-qemu 穿越（libvirt 动态属主只改文件属主，不解决目录穿越）。

## M4-4 vNIC 接入：vhost-user / SR-IOV / VPP 联动

**关联**：FR-NET-020/021/023；任务 M4-4；决策 #41。

**交付**：

- `internal/orchestrator/vnf.go`：`VnfPort` 中立描述 + 确定性 `VnfSocketPath`/`VnfIfaceName`（compute 与
  network 同源，避免各写一份）；`NetworkProvider` 增 `ApplyVnfInterface`/`DeleteVnfInterface`。
- `internal/orchestrator/network/vhost_user.go`（逻辑，mock 单测）+ `vhost_user_govpp.go`（`_govpp.go`
  薄适配，覆盖率排除）：VPP 建 server socket 接口、改名 `vh-<vm>-<vnic>`、置 MAC/admin up、按名解析、
  链路状态查询、删除；`vnf_alarm.go`：`CheckVnfPorts` 断连告警（`VNF_PORT_DOWN`）。
- L2 端口解析改为支持 VNF vNIC（按接口名复用 access/trunk/default 挂接）；`L3Provider.SetVnfTable`
  支持 L3 交换机（VRF）入表；apply 计划新增「vNIC 接入」段（**先于 bridge-domain**，删除在 VM 之后）。
- `model.Validate` 增 FR-NET-021：VF 直通占用 PF 时禁止其 PF 进 bridge-domain。
- `network.NewSysfsVFResolver`（VF PCI 由 sysfs `virtfn<N>` 解析）注入 compute Provider；nfvisd 装配
  `SetVhostUser` + `WithVhostDir` + VM 动作后刷新 vNIC 告警（`vmController`）。

**真机问题定位与修复（如实记录）**：

1. **socket 权限**：VPP 创建的 socket 属主 root，QEMU 以 `libvirt-qemu` 运行需写权限 → 启 VM 报
   `Failed to connect ... Permission denied`；`Apply` 后 `chmod 0777`。
2. **队列**：QEMU 未声明 `<driver queues>`（1 对队列）时握手停在 protocol features；显式 **2 对队列**
   （`compute.DefaultVhostUserQueues`）后完成协商。
3. **链路 up 的真实条件**（关键）：vhost-user link up 需 **guest 加载 virtio-net 驱动并置 DRIVER_OK**，
   QEMU 此时才发 `SET_MEM_TABLE`，VPP `show vhost-user` 的 `Memory regions` 才非零。**空白盘无 driver，
   永不 up** —— 因此本任务真机验证改用可引导的 alpine cloud 镜像（`/var/lib/nfvis/images/alpine.qcow2`，
   经代理下载；镜像仓库属 M4-8）。
4. **假幂等**：VPP 侧按名存在但 socket 不匹配（陈旧残留）时删除重建。

**真机验证**（nfvis-vm；`test/integration/m4_vnic_test.go`，缺引导镜像时跳过 up/down 断言）：

```
--- PASS: TestVhostUserLifecycleRealVPP (11.43s)
    vppctl show interface 片段:
        vh-it-m4-4-vm-eth0                4      up          9000/0/0/0
    VM 启动后 link up
```

链路：VPP 建 socket 接口（`vppctl show interface` 可见 `vh-it-m4-4-vm-eth0`）→ `vppctl show vhost-user`
含 `Memory regions`（guest 引导完成握手）→ `LinkState` up → `StopVM` → link down 且
`/alarms` 出现 `VNF_PORT_DOWN`(warning) → `DeleteVM`+`DeleteVnfInterface` → VPP 接口与 socket 消失。

**单测**：`network` 覆盖率 76.3%（vhost-user 创建/幂等/陈旧重建/删除/链路状态/告警 raise+resolve）、
`model` 78.0%（FR-NET-021）、apply 增 vNIC 排序与删除顺序断言。

**未验证项（如实标注）**：① **VM 经 vhost-user 与 VPP 通流（ping 对端）未验证**——需 guest IP 配置
（M4-5 cloud-init）与对端地址，随 M4-11；② SR-IOV VF 直通无 PF/VF 硬件（vmxnet3），仅 hostdev XML +
单测 + 「无 VF 明确报错」，真机标注未验证；③ 事件驱动实时告警随 M5 `/events`，当前告警在收敛/动作后刷新。

## M4-5 cloud-init 与串口 console

**关联**：FR-CMP-014/016、FR-OPS-032；任务 M4-5；决策 #42。

**交付**：

- **cloud-init 组合语义修正**（`compute/cloudinit.go`）：`user-data` 与 SSH 公钥**同时注入**——
  仅 user_data 时原样用；仅 hostname/ssh_keys 时生成最小 `#cloud-config`；两者都有时输出 cloud-init
  支持的 **MIME multipart**（托管 #cloud-config + 用户 user_data，按前缀判定 part 类型），避免重复顶层键。
  （此前 user_data 存在时 SSH 公钥被丢弃，被本次真机测试暴露并修复。）
- **串口 console**（`compute/console.go` 纯解析 + `console_libvirt.go` 适配 + `api/vm_console.go`）：
  - `POST /virtual-machine-functions/{name}/console` → 一次性 ticket（24B 随机、TTL 60s、绑定 VM）+
    相对 `ws_url`/`expires_in`；`serial_console=false` → 409，VM 不存在 → 404。
  - `GET .../console/ws?ticket=...` → WebSocket 升级，与域串口双向透传；ticket 一次性消费（防重放）。
  - **串口接入方式**：不用 go-libvirt `DomainOpenConsoleBidirectional`（真机实测该流式 RPC 阻塞在
    内部 channel 发送，打开即挂起 5 分钟超时）；改为取 domain XML 串口 pty（`SerialPtyPath`）直接
    O_RDWR 打开（QEMU 持 master、客户端开 slave，语义等价；nfvisd 以 root 可开 libvirt-qemu 所属 pty）。
  - **审计（FR-OPS-032）**：打开/关闭各记一条 `vm.console`（失败记 failure + 原因）。

**单测**：ticket 一次性/绑定 VM/过期（注入时钟）；WebSocket 桥（问候读取、输入到达串口、重复 ticket 拒握手）；
未装配 503 / VM 不存在 404；`SerialPtyPath` 正常/无串口/无 pty/空 XML；`BuildUserData` multipart 组合。

**真机验证**（nfvis-vm，`test/integration/m4_console_test.go`，需可引导 alpine 镜像）：

```
--- PASS: TestCloudInitAndSerialConsoleRealLibvirt (17.99s)
    串口读回 cloud-init 标记 "NFVIS-CLOUD-INIT-OK"（guest 内 runcmd 已执行）
    串口 console 可进可退（打开/读取/关闭成功）
```

链路：`DefineVM` 生成 seed ISO（`user-data` 含 runcmd 标记与 SSH 公钥、`meta-data` 含
`local-hostname`/`instance-id`）→ guest 引导后 cloud-init 执行 runcmd → 经串口 console 读回标记
（同时证明 **FR-CMP-016 注入在 guest 内生效**与串口双向）→ 关闭 console。

**未验证项（如实标注）**：CLI `request virtual-machine-functions <name> console` 的终端原始模式
（Ctrl-] 退出）在 M4-12 接线；本次真机验证经服务端 WebSocket + 集成测试完成。

## M4-7 容器编排（Docker + memif）

**关联**：FR-CMP-020~022、FR-NET-022；任务 M4-7；决策 #44。

**交付**：

- `internal/orchestrator/container`：`docker.go`（业务逻辑，mock 单测）+ `docker_client_docker.go`
  （Docker Engine API 薄适配，`_docker.go` 覆盖率排除）。规格映射：`memory_mb→Memory`、`vcpu→NanoCpus`、

## M4-9 计算/容器恢复收敛

**关联**：FR-OPS-010/011/012；任务 M4-9；决策 #46。

**交付**：

- `ComputeProvider/ContainerProvider.EnsureConsistent`：按 committed 补建/重定义缺失 domain（autostart 启动）
  与容器，逐对象处理、单对象失败不阻塞；**不可收敛项转告警**。
- `orchestrator.AlarmSink`（`Raise/Resolve`，由 `network.AlarmStore` 实现，避免计算/容器包依赖网络包）：
  provider 经 `SetAlarms` 注入，失败 `Raise RECOVERY_UNCONVERGED`(warning)、成功 `Resolve`，
  作用域 `recovery-compute`/`recovery-container`，经 `GET /alarms` 暴露。
- **FR-OPS-011**：`orchestrator.VnfPortsOf(cfg)` 统一派生 VM vhost-user 与容器 memif 端口（路径/VRF 同源，
  事务 apply 与恢复收敛共用，替换 applier 内的重复实现）；`L2Network.EnsureConsistent` **在 BD 之前重放
  vNIC 接入**；domain XML 的 vhost-user chardev 增 `<reconnect enabled='yes' timeout='5'/>`，
  VPP 重启 socket 重建后 QEMU 自动重连。
- **FR-OPS-012**：`DefineVM` 同步 `DomainSetAutostart`；nfvisd `runRecovery` 顺序改为
  网络 → 计算 → 容器 → vNIC 断连检查。

**单测**：compute/container 收敛告警（raise/resolve 分离）、libvirt 自启标志设置与清除、
vhost-user reconnect XML。
