## 1. 本轮做了什么（关键结论）
1. **真机恢复**（交接文档 §2 的既定任务）：nfvis 卡 activating → systemd 90s 超时 → restart 循环。
2. **根因（只读诊断，三层证据：journal 90s 零输出 / SIGQUIT 全栈 / virsh 同挂）**：
   ① **环境级**——libvirtd 开机自启 sem-vm（产品 `"autostart":true` ⇒ 产品建 libvirt autostart 软链）时**假死**
   （socket 可连、对一切客户端零响应；virsh 同挂）；② **产品缺陷 R129-1（高）**——`compute.Connect` 调 go-libvirt
   **包级 `ConnectToURI`（不收 context）**，认证握手无限阻塞 ⇒ main.go 的 10s `libvirtCtx` 形同虚设 ⇒ nfvisd 到不了
   READY ⇒ 超时循环。**round128 的两个假设被更正**（详见 AGENTS round129 条目）：「恢复收敛超 90s」不成立；
   「#348 四次失败」全部是本环境故障所致、与其代码无关。
3. **决策 #349（PR #279，已合并）**：底座组件无响应时 nfvisd 启动**有界降级**——libvirt 连接**自持 conn 有界化**
   （中断 = 超时关 conn；go-libvirt 的 `Disconnect()` 内部先发 RPC、对假死进程同样挂死——**不可用作中断手段**，源码核实）
   + Docker 探测/AppArmor Ensure 有界 ctx + 降级告警 `COMPUTE_UNAVAILABLE`/`CONTAINER_UNAVAILABLE`。
   四步真机验证全过（证据 `docs/evidence/v2-round129-d349-bounded-startup.txt`）。⚠️ 实现要点：**不给共享
   http.Client 加整体超时**（镜像导入等长操作共用同一客户端）；`probeOnce` 现为硬超时 + 真实 binary API 连通判定（#348）。
4. **决策 #348（PR #278，重基于 #349 后合并）**：dev44 **重启测试达成**——`reboot` 后**单次启动即 active**（无循环）、
   **VPP 自动拉起**（journal「检测到 VPP 未运行，发起拉起（不等待）」→「已连接 VPP」→「恢复收敛完成」）、
   幂等路径「VPP 已在运行，无需拉起」同场验证；开机 libvirtd 假死未复现（偶发非必现）。
   证据 `docs/evidence/v2-round129-d348-reboot-verified.txt`。
5. **新登记 R129-2（中，未修）**：**开机竞态**——libvirtd「Started」后要先做完 sem-vm 的 libvirt autostart
   （1G 大页 prealloc）才服务客户端握手（实测 >10s）⇒ nfvisd 10s 有界等待内连不上 ⇒ 按 #349 降级且**不自动重连**
   ⇒ **每次开机后 VM 编排需人工 `systemctl restart nfvis`**（VNF 由 libvirt autostart 拉起、数据面由 #348 拉起，
   均不受影响；降级以 `COMPUTE_UNAVAILABLE` 如实呈现）。候选修法见 `docs/v2待做.md`（启动期有界重试数次 /
   周期巡检自动重连）。
