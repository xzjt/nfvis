NFViS v3 · round29（2026-10-12）：决策 #480 `/resource-pools` 大页段改为真实可分配
=============================================================
主题：`show resource-pools` 的「可分配」不扣数据面占用（1G 显示 3、2M 显示 768，而 VPP 实占
      1×1G + 533×2M）——用户裁定改为**真实可分配**（＝内核空闲）。本决策**修正 #403** 的
      「数字不变」前提（#403 当时把该表定为配置口径；但「可分配」不扣在用页就不是「可分配」）。
方式：契约先行（附录 A #480 + AGENTS 计数 381→382）→ 子智能体实现（红-绿）→ make check 七项
      → 交叉编译换装 `3.0.13~dev3` 真机复核。

────────────────────────────────────────────────────────
§0 结论
────────────────────────────────────────────────────────
真机（3.0.13~dev3）：
    show resource-pools（大页段）
      页大小   声明   总数（内核实际）   已分配（在用）   可分配（VNF）
      1G         3           3                1               2
      2M       768         768              533             235
    show system hugepages
      1G  声明3/内核实际3/在用1/空闲2（状态 一致）；2M 768/768/533/235（一致）
⇒ 「可分配」＝ 2（1G）/235（2M），VPP 的 1×1G、533×2M 计入「已分配（在用）」；两视图**同源一致**，
  不再互相矛盾。用户诉求（可分配应扣 VPP 占用）达成。

§1 契约（附录 A #480，决策计数 381→382）
────────────────────────────────────────────────────────
#480（v3 线第 77 条）：`GET /resource-pools` 的 `hugepages[]` 数字改为**与 `show system hugepages`
同一事实源**（`system.HugepagePoolViews`）：`count`＝声明（保留）、`total`＝内核实际、`allocated`＝
在用（含数据面固定占用与 VNF/其它持有）、`free`＝内核空闲（真实可分配）；取不到内核值如实（-1/口径），
不编造。CLI/Web 列名/说明同步；**修正 #403**（该表数字不再「不变」）。**不改** CPU 段、
`/system/hugepages` 端点、`reclaim`、告警。

────────────────────────────────────────────────────────

- `internal/api/ui/app.js` `renderPools`：首表列名同步；**删除 #403 的「两处口径不同、数字不必相等」**

§6 教训（入册）
────────────────────────────────────────────────────────
- **「口径」不能当作「数字不对」的挡箭牌**：上一轮（#479）我把「两视图数字不一致」解释成决策 #403
  的口径差异、只补了标注——但用户指出「可分配」**必须扣在用页**，否则就是错的。裁决口径时先问
  「这个标签在用户眼里意味着什么」，而不是「历史上它被定义成什么」。（#479 的列名/欠配档仍有效；
  #480 把数字也改对。）
- **单一事实源的边界值要一并处理**：接内核视图后必须覆盖「取不到内核值」分支（-1/说明），
  否则会把 -1 当数字渲染。
