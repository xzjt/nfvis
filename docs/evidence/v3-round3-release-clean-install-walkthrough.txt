§2 【重】风暴抑制（storm control）→ VPP 数据面崩溃循环 + 管理面整体卡死
================================================================================
2.1 现象（时间线，均为 2026-10-08 UTC）
    · 09:53:5x 在 ens192 上配「广播+组播」两类风暴抑制（rev 12），读视图即报
      「分类表未挂（接口 L2 槽上无本类分类表）」——但同刻 `vppctl` 里
      `show interface features ens192` 有 `POLICER_CLAS (l2-policer-classify)`、
      `show classify table interface ens192` 有绑定（表 0，链到表 1）。**读视图与实况矛盾。**
    · 09:53:59 起 VPP **SIGSEGV 崩溃循环**（systemd `Restart=`，restart counter 一路涨到 23）。
      崩溃栈每次都相同（worker 线程）：
        #0 vnet_classify_find_entry +0x1b            （faulting address 0x0 —— 空表指针）
        #1 policer_plugin.so
        #4 vlib_worker_thread_bootstrap_fn
      apport 落 core：`/var/crash/_usr_bin_vpp.0.crash`（11,322,987 B，Signal 6/ABRT）。
    · 09:56 nfvisd 侧同时出现：`风暴抑制巡检未收敛项: interfaces/ens192/storm-control:
      读取分类表 1 属性: VPPApiError: Classify table not found (-91)`（登记指向的表已不存在）。
    · 09:53~10:02 期间**所有 CLI 命令挂起**（含 `show version`）：SIGQUIT 全栈显示
      goroutine 阻塞在 `govpp/core.(*Channel).receiveReplyInternal`（
      `network.(*govppL2Client).SwInterfaceNames` ← `cli_iface_vpp_show.go` 的接口名 dump），
      持 `cliexec.go:312` 的**全局 CLI 互斥**；十余条后续请求全部排队在同一把锁上。
      —— VPP 崩溃窗口内的一条 `show interfaces … detail` 把**整个管理面**拖死。
2.2 受控复现（11:03 起，干净态、无端口安全历史）
    仅 `set ens192 storm-control broadcast 8000` + `multicast 20000`（rev 32）：
      · 读视图仍报「分类表未挂」（同上矛盾）。
      · VPP 以 ~30s 为周期崩溃（restarts 17→18→19→20→21）：每次 VPP 新起后 nfvisd 恢复收敛
        重建风暴对象，随后**背景包（ens192 rx ~0.5pps 即可）**命中悬空表 → 崩。
      · 采样显示表链在两种形态间摆动（0→1 与 1→0），登记坐标（表 1）与实况持续错位。
    止血：out-of-band `vppctl set interface state ens192 down`（掐断触发包）→
      `delete ens192 storm-control` commit（rev 33）→ 崩溃循环立即停止（NRestarts 冻结）。
2.3 根因分析（代码级）
    · `internal/orchestrator/network/storm.go` 设计上以 `AttachedL2Table`（
      `classify_table_by_interface`）为**绑定唯一事实源**，并明文承认「本方法不区分
      『本就没挂』与『查询被拒』」（返回 ok=false 两者动作相同）。
    · 实测该判定在本底座**与 vppctl 给出的实况不一致**（vppctl 看得到绑定，产品看不到），
      于是重建/巡检走「按登记解绑」分支；重建过程中表被删而接口 L2 槽仍指向旧表 ⇒
      policer-classify 节点解引用已释放的表 ⇒ worker 线程 SIGSEGV。
    · 连带面：崩溃窗口内的 VPP **dump 型**请求（接口名 dump）在 govpp 侧**无超时**，
      持 CLI 全局锁永久阻塞 ⇒ 管理面整体不可用（HTTP 层仍 200，但 `/cli/execute` 全挂）。
2.4 影响与边界（如实）
    · 影响：数据面崩溃循环（业务中断）；管理面被单条读命令拖死；重启 nfvisd 可恢复，
      但**只要风暴抑制还在配置里，重放后再次进入崩溃循环**（本机实测 2 轮，共 23 次崩溃）。
    · 建议优先级：**P0**。修法方向（供立项参考）：① 以可用的实况来源（如按
      `classify_table_by_interface` 的 vppctl 等价路径）核查绑定，或对「登记与实况不符」
      先解绑后删表；② VPP dump/多请求路径加**有界超时**（govpp 层面），失败即弃请求而非
      持锁等待；③ 提交期对「同一接口已有 L2 槽对象」做前置拒绝（端口安全↔风暴抑制的互斥
      已有提交期检查，但**换绑/重建路径**未覆盖）。
    · 现场证据（保留在 VM）：`/root/crash-evidence/`（apport core、vpp/nfvis journal、
      SIGQUIT 全栈）、本文件 §2.5 的原始命令输出文件。
2.5 一条同族正例（端口安全→风暴抑制单提交换绑）
    · 同一提交里 `delete ens192 port-security` + `set ens192 storm-control …` 会以
      「L2 分类槽被非本产品对象占用（表 23，掩码 00…ffffffffffffffff…）」**下发失败并回滚**
      ——拒绝本身正确（互斥），但拆成两次提交（先删端口安全，再加风暴）后仍进入 §2.1 的
      坏态 ⇒ 说明问题在风暴自身的重建路径，而非换绑顺序。

§3 【中】SPAN：同二层域分析口 → 自持镜像环（无检测/无告警）
================================================================================
3.1 拓扑：源 ens224（DPDK 口，该时刻无其他角色）、分析口 ens192（DPDK 口），
    二者与宿主 VMnet8 **同属一个二层域**（本机三口皆 nat 到 VMnet8）。
3.2 现象：从 VM 内核侧（ens160）发 5 个广播包后，ens224 **rx 287→84,212（2s）**、
    tx 5→84,637；删除会话前累计 rx 385,375 / 分析口 ens192 tx 385,531（≈1:1，即镜像副本）。
    机理：被镜像的广播帧从分析口出去 → 上游交换/VMnet8 泛洪 → 回到**源口** → 再次被镜像……
    自持循环（~42kpps 量级，随链路与端侧而定）。
3.3 正向面：同一会话也**证明了镜像本体可用**（分析口 tx ≈ 源口 rx 逐包对齐）。
3.4 边界/建议：与 #79 的 cross-connect 环路教训同族（当时触发 soft lockup）。建议：
    ① 手册 §8.7 明写红线「分析口不得与源口处于同一二层域（或上游须隔离）」；
    ② 产品侧可考虑对「源/分析口同属一个 BD 或同域」给提交期**警告**（不硬拒，因真实场景
    可能是有意的）；③ 与学习上限/风暴抑制一样，环路检测（LOOP_SUSPECTED）当下**不覆盖**
    镜像环（无 MAC 学习参与），建议纳入观察。

§4 其它发现（中等/低等 + 文档口径）
================================================================================
R3-1【中】`.run` 首装的「大页池 sysctl 单源接管」未生效，且 90 号文件自述失实
    · 现场：`dpkg-divert --list | grep sysctl` = 0；`/etc/sysctl.d/80-vpp.conf` 原样在场
      （`vm.nr_hugepages=1024`）；产品写的 `90-nfvis-hugepages.conf` 注释却写
      「vpp 包自带的 /etc/sysctl.d/80-vpp.conf **已由 dpkg-divert 挪到 .vpp-disabled**」。
    · 根因（证据链）：dpkg.log 显示 `configure nfvis` 在 09:32:38、`configure vpp` 在 09:32:40；
      而 `/etc/sysctl.d/80-vpp.conf` 的 **ctime=09:32:40.87**（连同 /etc/vpp/startup.conf 同时刻）
      ——**vpp 的 conffile 要到 vpp 自己 configure 时才落盘**，晚于 nfvis postinst（其 divert
      段只在那一刻尝试一次，判据 `[ -e 80-vpp.conf ]` 当时为假）⇒ 静默跳过（连「接管失败」的
      提示分支也不进）。这是 #182（AppArmor 同事务后配置）的同族结构缺陷：**同一次 apt 事务里
      的时点假设不成立**，单次 postinst 不是保证点。
    · 影响：未声明 2M 池时，80-vpp.conf 每次开机把 2M 池钉到 1024 页（7.4GB 机器上 2GB），
      产品如实显示「未声明（不托管）」；90 号文件的自述与实况不符（操作者会误判已接管）。
    · 建议：与 #182 同法——把该保证移到 nfvisd 运行期（启动/巡检时若发现 80-vpp.conf 仍在且
      未 divert 则接管），或 postinst 改为「定时重试/下次启动再由 nfvisd 收口」；同时修正
      90 号文件注释为「以实况为准」。
R3-2【中】`set system hostname|timezone|ntp server` **只存不落**（无任何应用路径）
    · 现场：`set system hostname nfvis-lab` 提交成功（rev 5），但 `hostnamectl hostname`=nfvis、
      `/etc/hostname`=nfvis；`set system timezone Asia/Shanghai` 后 `/etc/localtime`→Etc/UTC；
      `set system ntp server ntp.ubuntu.com prefer` 后 chrony 源仍是发行版默认（
      `/etc/chrony/sources.d/ubuntu-ntp-pools.sources`）。全仓无 `hostnamectl`/`timedatectl`/
      resolved/chrony 写入路径（`grep` 仅命中断言与读侧）。
    · 影响：控制台/`GET /system/status.hostname` 显示的是**配置值**（#197 的取向），与宿主
      实况不一致；NTP 声明对实际同步无作用（`request system ntp sync` 只跑 `chronyc makestep`，
      用 chrony 自己的源）。
    · 定裁点：这三项是「记录/展示」还是「应落到宿主」？若后者则为「命令成功、无实际效果」族，
      建议补应用路径（或在校验期如实拒绝并给出替代）。
R3-3【中】SPAN 的 VNF 源：文档说可用、实现是「下发期拒绝」，且**提交期不拦**
    · 《命令全表》该行标 ✅、《命令树设计》/手册 §8.7 均写「源也可为 vnf <vm> interface <vnic>」；
      实测 `set source vnf vnf-b interface eth0` 提交**通过**，下发时被
      `%% 底座下发失败（已补偿）: SPAN 源 vnf-b 为 VNF 接口，暂不支持`（provider 明确 stub）。
    · 与内核数据面口径不一致（内核侧是**提交期**拒绝并给替代）。建议：二选一——实现
      （模型已有 `vh-<vm>-<vnic>` 确定性口名，VPP span 可用 sw_if_index）或**提交期拒绝**+
      改文档；至少补一条与内核侧对称的前置校验。
R3-4【中】VPP→内核数据面运行期切换：VPP 不被停、网卡交还必须带外，且内核模式禁用了
     `request interfaces unbind-dpdk`
    · 实测切换序列：`set system dataplane kernel` + commit（正确警告）+ `systemctl restart nfvis`
      → `show vpp` 如实报 `dataplane: kernel … 未使用 VPP`；内核侧按配置建出
      bridge/VRF/vxlan（`ip -br link` 可见 vs-lan/vs-dmz/vs-wan/vs-nat/vr-*/vx-a）。
    · 但：① **VPP 仍在运行**（systemd active）并持有两块 vfio 网卡 → 手工 unbind 挂死；
      停 `vpp.service` 后网卡才交还内核（vmxnet3）——产品在切换路径不提示也不停 VPP
      （只有安装器的 kernel 分支有 stop_vpp_for_kernel）。② 内核模式下
      `request interfaces <n> unbind-dpdk` 回答「该能力不可用」⇒ 产品内**没有**交还路径。
      ③ 交还后还需 `request interfaces <n> enable`/重启 nfvis 才收敛，且本机 netplan
      `activation-mode: off` 会让内核口恒 down（**v3 round1 已记录的环境前置**，快照恢复即复现；
      本轮已改 manual 并留 `/root/netplan.bak`）。
    · 建议：切换时给出「VPP 仍在运行/网卡仍在 vfio」的**点名提示 + 照做步骤**（或由 nfvisd
      在 kernel 模式下自动停 VPP——与安装器同源）；把 unbind 的适用面从「数据面=当前实现」
      解耦为「驱动层面动作，内核模式下同样需要」。
R3-5【低】容器配置变更的生效语义未入手册；崩溃循环容器在读视图里是「running」
    · 实测：改 `args` 后 `request … restart` / `stop+start` 均**沿用旧容器规格**
      （`docker inspect .Config.Cmd` 不变），需 **delete+recreate** 才生效——该语义只写在
      `container/docker.go` 注释（「M4-7 语义」），手册/命令表未写；本机因此出现
      「配置已修好、容器仍按旧参数 crash loop」的现场。
    · `restarting → running` 的状态映射是规格 #44 既定（非缺陷），但**崩溃重启循环**既无
      告警（`CONTAINER_EXITED` 只覆盖 dead/exited）也不在读数里可见（无 RestartCount）。
      建议：读数给「重启次数」或对高频重启（如 5 分钟内 ≥N 次）出告警；手册补一句生效语义。
R3-6【低】`show interfaces <if> statistics` 输出原始结构体（无字段名）
    · 例：`interface ens192 statistics: {355512 417 469792537 34348 0 0 0 0}`——操作者无法
      判读（对照：`show virtual-machine-functions <n> statistics` 是有列名的表格）。
      建议给列名（rx/tx packets/bytes/errors/drops…）或与接口详情同源渲染。
R3-7【提示】`HUGEPAGE_POOL_ORPHAN`（2M 池 14 页）在**干净首装**后即出现且长期保持
    · 属 DPDK 预留未用页（消息自述准确、`reclaim` 明确不动它）；但一条 warning 从首装起常驻，
      建议评估是否对「预留来源=数据面自身」的情形改判 info/或与 `nfvis_system` 面板合并说明，
      避免运维噪声掩盖真告警。

§5 正向验证（逐项，独立事实源）
================================================================================
5.1 L2 + BVI 真实转发：vs-lan（ens192 端口 + BVI 192.168.99.1/24）→ 宿主加次地址
    192.168.99.10 → `ping 192.168.99.1` 5/5 0%；VPP：bvi0 带地址、ens192 在 bd-id 14615916。
5.2 L3 + 静态路由：vs-wan（type l3，`l3-interface ens224 ip address 192.168.98.1/24`）+
    `static-routes 10.99.0.0/24 next-hop 192.168.98.10` → 产品 `ping 10.99.0.1 source
    192.168.98.1` 4/4 0%（宿主持 10.99.0.1/24 次地址）。
5.3 ACL（唯一可用形态 L3 接口）：acl-icmp-deny 绑 ens224 acl-in → 产品 ping 10.99.0.1
    **0/3（失败并给平面归属提示）**；vppctl `acl-plugin-in-ip4-fa` checked 3 / deny 3；
    **ARP 不受影响**（宿主 `arp -d` 后仍能解析 192.168.98.1 ⇒ #341 伴随 macip 生效）；
    解绑（`delete l3-interface ens224 acl-in acl-icmp-deny`，rev 9）后 ping 3/3 ⇒ #361 撤销链生效。
    注：不写 ACL 名的 `delete … acl-in` 报「无匹配配置: l3-interface」（语法需带值；按 #361 口径）。
5.4 端口安全 / 学习上限 / 互斥：`set ens192 port-security mac 00:50:56:c0:00:08`（rev 10）→
    详情页「ACL 在场、接口已绑定」；宿主 ping 仍通；`set learn-limit 8192` 生效（BD 详情
    Learn-li 8192）。**互斥双向拒绝**：在已配端口安全的口上加风暴抑制 → 提交失败并给
    「两者留其一」的照做路径（文案逐条列出两侧）。
5.5 DHCP 服务器 v1 端到端（真 guest）：vs-dmz（L2 + BVI 192.168.100.1/24 +
    `dhcp-server pool .100-.200` + dns + domain）→ 新建 vnf-b（debian12 generic 云镜像，

8.5 #432 容器重启可见性（RestartCount 读视图 + 崩溃重启循环告警）——真机抓出并修掉两处实现缺陷
    · **缺陷一（字段位置）**：Docker 29.1.3 的 `RestartCount` 在 inspect 应答**顶层**，**不在** `State`
      （真机：`--format '{{.RestartCount}}'`=10 而 `{{.State.RestartCount}}` 报 `map has no entry for key`）。
      首版按 `State.RestartCount` 读 ⇒ 永远「取不到」：读视图省略该字段、告警也不触发（现场：容器
      `restarting`、累计 15，`show container-functions` 无 restart-count、`show alarms` 空）。修法：以顶层为准 +
      `State` 兼容回退；新增守护 `internal/orchestrator/container/docker_inspect_restartcount_test.go`
      （用**真机应答形状**钉死；红-绿：退回 State-only ⇒ `known=false count=0` 失败）。修复版复验：
      `restart-count 22` 与宿主 `docker inspect` 的 `RestartCount` 逐值一致。
    · **缺陷二（判据不可达）**：初稿判据「两次巡检间有增长且累计 ≥3」，而真机崩溃循环里 Docker 做**指数退避**
      （实测约 40~60s 才重启一次，巡检 15s 一轮）⇒ 「两轮都在涨」几乎不可达、告警永不触发。修法：判据改为
      「原始状态 `restarting` ＋ 累计 ≥3」（`restarting` 本身即「没在服务、Docker 反复拉起」；「重启过几次但
      此刻 running」不会误报）；**决策 #432 正文已按真机更正**并注明。测试同步（`NoGrowthStillReported`：
      不增长也报、低于门槛不报、重建后重新起算；活动告警按 `AlarmStore.Raise` 的幂等更新语义断言）。
    · 真机建/消：坏 args 造崩溃循环 → `show alarms active` 出现 **`CONTAINER_RESTART_LOOP`**（warning，
      source=容器名，message 含累计次数与两个排查入口）；`request container-functions ct-2 delete --yes` →
      对象消失即**自动消解**（计数 0）。
    · Web 复验：容器详情页新增 **`重启次数`** 行（ct-1 显示 0，与 docker 一致；字段缺失时显示「—」不显示 0）。
