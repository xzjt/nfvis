2.10 容器（rev 26~28）：ct-lab（image ct，memif eth0 挂 vs-lan，1 vCPU / 128MB）。
    **两条如实登记**：① `command sh` 会被当作**单元素 entrypoint**（`BuildCreateSpec`
    `Entrypoint = []string{TrimSpace(command)}`，参数走 `args`），故 `command "sh -c \"…\""`
    会被当成一个可执行文件名而报 `exec: "sh -c …": executable file not found`——
    按契约用 `command sleep` + `args 3600` 即正常（非缺陷，是**契约形态**）；
    ② 改规格后 `start` 沿用旧规格（契约明文），需删重建。
    start → docker `Up`、vppctl `mf-ct-lab-eth0` up、memif socket
    `/run/nfvis/memif/ct-lab-eth0.sock`、容器内挂到 `/run/memif/eth0.sock`（docker inspect 实证）。
    `exec "id -un; hostname"` 与宿主 `docker exec` **逐字一致**（root / 容器 ID），
    `exec "nonexistent-cmd"` 如实回 `退出码: 127` + `/bin/sh: nonexistent-cmd: not found`。
    **交互 shell**（真 pty）：进容器 `/ #`，`id -un`=root、`ls /run/memif` 见 `eth0.sock`。
    **VPP 侧 memif 在容器内不可见 eth0**——与既有 T0-3 登记同因（夹具镜像不带 memif 客户端），
    容器侧无产品缺陷。

    **两条如实登记**：① analyzer **不能是已有角色口**——先试 ens224（VRF vs-wan 的 L3 接口）
    与 ens192（vs-lan 成员口）都被提交期**角色冲突**正确拒绝（文案点名冲突方与「同一网口
    在 bond 成员/交换机端口/L3 接口/镜像源或分析口 中只能出现一次」）；删掉 vs-wan 后才建成。
    ② **环路红线再现**：analyzer 与源同处 VMnet8 同一广播域，镜像帧回灌 ⇒
    ens224 tx **+839,601 包/3s（≈280k pps）**；`delete port-mirroring pm-vnf`（rev 23）后
    **立刻归零**（+0/3s）——绑定与撤销都真实生效，属**拓扑红线**不是缺陷（手册 §8.11 已警告）。
2.12 **环路检测告警未触发——已核实不是缺陷**：把 ens192+ens224 **双双**入 vs-lan 制造「跨口环」
    后，两成员口 `tx` 各 +314,670/330,994 包/3s（≈105k/110k pps）、
    `show errors` 见 `l2-flood 8466337` 与 `BVI L3 mac mismatch 8432027`，但
    **两口的 `rx` 恒 +0**（VMware 虚拟交换机不会把同一 VM 两个口的帧互相回灌）⇒
    `LOOP_SUSPECTED` 判据③（「每成员口 rx 同时 ≥50000 pps 连续 2 轮」）**正确地不成立**
    （该判据由 round115 真机标定，需要 guest 内成环/双 vNIC 才产生真 rx）。等满 3 个 60s
    巡检周期确实无告警——**判据与事实一致**。清理后 ens192 tx 立即归零。

        （`show errors` 里 `…-tx tx packet drops (no available descriptor)`），
        `drops` 与 tx 同步增长——即「VPP 有帧要发、guest 侧一个描述符也没给」；
      - guest 内部（VGA 截图 + 串口）：**已进到 `deb13-a login:`**（系统正常起来），
        但网内无地址。
  · **根因（三方独立证据）**：
    ① 产品生成物：`internal/orchestrator/compute/cloudinit.go BuildNetworkConfig` 按
       **`eth%d`**（vNIC 声明顺序）写 `network-config`；本轮直接读刚建 VM 的 seed.iso，
       内容确为 `ethernets: eth0: dhcp4: true`（未改一字）。
    ② guest 事实：Debian 13 cloud image 的 GRUB 用 `console=tty0 console=ttyS0,…`（串口有输出），
       且 systemd 的 `80-net-setup-link.rules` 在位 ⇒ virtio 网卡被**可预测命名**成 `enp1s0`；
       guest kernel journal 逐字为
       `virtio_net virtio0 enp1s0: renamed from eth0`（两次开机都有）；
       cloud-init 的 `ci-info` 也只列 `enp1s0`。
    ③ 结果：cloud-init 把 netplan 渲染成 `ethernets: eth0: dhcp4: true` 落到
       `/etc/netplan/50-cloud-init.yaml`，而该名字**不存在** ⇒ 没有任何 DHCP 客户端发包。
       `cloud-init.log` 里 `net: all expected physical devices present` 是**误导性的**
       （cloud-init 的物理设备集合判定不覆盖 netplan 键名与实际内核名的匹配）。
  · **A/B 定因（唯一变量＝guest 的 netplan 键名）**：把该 guest 的
    `/etc/netplan/50-cloud-init.yaml` 改成 `enp1s0: dhcp4: true`（产品零改动、VPP 侧零改动）
    → 再次 start（75s 内）：
      - 租约表 `192.168.99.100  52:54:b9:b8:ef:bd  active  7139`；
      - vhost 口 `rx packets 49 / tx 809`（rx 从 0 变 49）；`show l2fib` 学到该 MAC；
      - **BVI ping 租约地址 4/4 0% 丢包**；VPP 邻居表 `192.168.99.100 … bvi0`。
    ⇒ 数据面、DHCP server、BD 成员、租约下发**全都正常**；唯一坏的是「seed 里的网卡名」。
  · **跨数据面复现（内核侧同因）**：内核数据面下再建一台**产品 seed 未打补丁**的 deb13-k →
    `vnet1` RX **恒 0 字节/20s**、租约表无其条目；其 seed 同为 `eth0`。
    ⇒ 与 `AttachedPortName`/vhost/tap 命名无关，是**镜像侧可预测命名 vs 产品假设**的问题。
  · 影响：**所有使用 systemd 可预测命名的现代 cloud 镜像**（Debian 12+/13、新版 Ubuntu/
    RHEL 系）在「靠产品 DHCP 拿地址」这条主路径上**拿不到租约**，而产品侧唯一的观测量
    （租约表空）**不会告警**：vNIC 是 up 的、VM 是 running 的 ⇒ 没有 `VNF_PORT_DOWN`，
    极易被当作「guest 自己没配网」而排查很久（本轮即是）。属「命令成功、事实不达」同族。
  · 修法方向（**未实施**，须先定裁）：
    ① **首选**：seed 的 `network-config` 不写死名字——用 cloud-init v2 的
       **`match: {name: "e*"}` / `set-name`** 或 `match: {driver: virtio_net}` 形态
       （v2 支持 `match.driver`/`match.macaddress`），或直接写 `eth0` + **`set-name: eth0`**
       （把网卡钉回 eth0，代价是改变 guest 内命名习惯）；
    ② 取 vNIC 的 MAC（libvirt 分配后可知）写 `match.macaddress`——最确定，但要求 seed
       **在 MAC 确定之后**生成（当前 `disk_libvirt.go` 的调用序需核实）；
    ③ 保守兜底：保留 `eth0` 的同时**追加**一条 `match: {driver: virtio_net}` 的条目，
       并把「租约表长时间为空 + vNIC up」提升为**可诊断提示**（本轮暴露的观测缺口）。
  · 边界（如实写清）：**不是所有镜像都有此问题**——Alpine 等不经可预测命名的镜像仍叫
    `eth0`（本产品历史夹具全是 Alpine，故历轮未暴露）。**本轮实测对照**：离线挂载
    `/var/lib/nfvis/images/alpine`，其根文件系统里**没有** `/lib/udev/rules.d/80-net-setup-link.rules`
    （也没有 udevd 从该路径装载的痕迹）⇒ 网卡保持内核缺省名 `eth0`，产品 seed 恰好对；
    Debian 13 **有**该规则文件（`/lib/udev/rules.d/80-net-setup-link.rules`）⇒ 改名成 `enp1s0`。
    两条镜像在同一份产品 seed 下一对一错，这就是本缺陷的判别线。
    契约侧 `BuildNetworkConfig` 的注释已**如实**写明「ethN 与 PCI 槽序一致是**经验事实**而非契约
    保证（guest 若有 udev 改名规则…序号可能不同）」，即**假设已知但未覆盖现代默认命名**。

**R47-2（中）接口 `rx_drops`/`tx_drops` 在所有出口恒为 0（VPP 侧真有丢弃）**
  · 构造现场（100% 丢弃可复现）：vs-lan（BVI 192.168.99.1/24、成员 ens192）+ 端口安全白名单
    只放 `00:50:56:c0:00:09`，宿主真实 MAC 是 `…:08` ⇒ 宿主 ping `8 发 1 收（87% 丢）`。
  · 同一时刻四处读数：
      · **独立事实源** `vppctl show interface ens192`：`rx packets 85 / drops 85`；
        `vpp_get_stats dump` 的 `/interfaces/ens192/drops` = **148 包**；
      · 产品 `show interfaces ens192 statistics`：`rx-drops 0 / tx-drops 0`；
      · 产品 `monitor interfaces ens192`：`rx-drops 0 / tx-drops 0`；
      · REST `GET /interfaces/ens192` → `statistics.rx_drops=0, tx_drops=0`；
      · `/metrics` → `nfvis_vpp_interface_rx_drops{interface="ens192"} 0`、
        `nfvis_vpp_interface_tx_drops{interface="ens192"} 0`。
  · **同一次取数里其它字段是对的**（反证接线遗漏）：`tx-errors` 如实给 **1**（VPP 侧
    `/interfaces/ens192/tx-error` = 1），`rx_packets/rx_bytes` 与 vppctl 同步递增。
  · 根因（代码层，逐行定位）：`internal/orchestrator/network/stats_linux.go
    InterfaceCounters` 只把 `c.Rx.Packets/Tx.Packets/Rx.Bytes/Tx.Bytes/c.RxErrors/c.TxErrors`
    映射进 `state.InterfaceCounters`；而 `state.InterfaceCounters` 声明了
    `RxDrops/TxDrops` 两个字段（`internal/state/state.go`）**但全仓没有任何填充者**
    （`grep -rn "RxDrops\s*:" --include=*.go .` 除声明外零命中；
    `func …InterfaceCounters` 的唯一实现就是 `stats_linux.go` 这一处，
    `stats_other.go` 是非 Linux 的 `return …, false` 桩）。
    govpp 的 `api.InterfaceCounters`（`go.fd.io/govpp@v0.13.0/api/stats.go`）里
    **有** `Drops uint64` 字段（对应 `/interfaces/<if>/drops`），只是没被读。
  · 影响：所有依赖 `rx_drops/tx_drops` 的判断都拿到恒 0——`CLI/REST/Web 接口页/metrics 看板`，
    以及**告警与对账**（例如「接口在丢包」类判据）；与 AGENTS.md 的
    「**凡含可分配/可用/空闲/剩余或丢弃类读数必须扣掉/如实反映在用者与实际事实**」红线同族：
    这里是把**有**报成**无**，属「假读数」。方向明确的一处：`CLI 接口列表` 甚至**没有**丢包列
    （列表只给 Rx/Tx 包），而 `statistics`/`monitor`/REST/metrics 给了数字却是 0——
    两种「看不见」叠加，操作者无从判断是否在丢。
    另：`docs/NFViS-openapi.yaml` 的 `Interface.statistics` 里 `rx_drops/tx_drops` **没有任何
    description**（同族的 `rx_errors/tx_errors` 也没有），契约读者无从知道这两个数的口径；
    而 VPP 底座的 `/interfaces/<if>/drops` **不区分方向**，所以「rx_drops/tx_drops」这个名字
    本身在 VPP 下就**无法被诚实填满**（填哪个都算编造方向）。
  · 修法方向（**未实施**，一行量级）：`stats_linux.go` 里补
    `RxDrops: c.Drops`（VPP 的 `/interfaces/<if>/drops` 是**单口总丢弃**，无 Rx/Tx 之分——
    是否把它拆成 rx/tx 或**新增一列 `drops`** 需先定裁：拆会**编造**方向，建议
    ①`RxDrops`/`TxDrops` 停用或明说「VPP 不区分方向」，②REST/CLI 增加 `drops` 并列展示，
    ③metrics 的 `nfvis_vpp_interface_{rx,tx}_drops` 改名/标注口径，避免继续误导）；
    另需在 `CLI 接口列表` 决定是否加丢包列（否则配置态看板仍看不出丢包）。

§8 观察项与既有登记复现（不单列缺陷）
--------------------------------------------------------------------------------
· **O-1（观察项）换证窗口的极窄不一致**：`internal/system/tls.go regenerate` 先
  `os.WriteFile(cert)` 再 `os.WriteFile(key)`（两次独立写），而
  `internal/api/server.go buildTLSConfig` 的 `GetCertificate` 每次握手读盘、
  失败时**回退启动时加载的旧证书**。理论窗口＝两次写之间：客户端按**文件**取 CA 时，
  可能拿到「新 cert」而服务端这一瞬返回「旧 fallback 证书」⇒ 本轮 fulltest S6 观测到
  **一次** `x509: certificate signed by unknown authority`。**未能稳定复现**
  （40 次串行 + 12×12 并发重签，0 失败）⇒ 登记为观察项并给修法方向
  （临时文件 + `os.Rename` 原子替换；client 侧对 `certificate signed by unknown authority`
  给「服务端可能正在换证，稍后重试」的提示）。**与产品功能无关**，但会打断脚本与套件。
· **R41-O1 复现**：同一轮「多口 unbind-dpdk」时，第一个口的收敛会对**尚未交还的第二个口**
  报 `Cannot find device "ens224"`；按序解完即「已按状态收敛」（文案给了原因）。
  两个数据面切换方向都遇到，未变差。
· **Web 删除对象后不停留在已删对象路由**（「读取失败：…不存在」）：数据已正确删除，
  只是未自动跳回列表（round41 §3.4 同一处，仍未改）。
· **VPP 侧容器 memif 在夹具内不可见 eth0**（T0-3 既有登记，夹具无 memif 客户端）；
  内核侧同一容器有 veth（本轮未再复验容器 ping，按既有登记）。
· **SPAN 环路红线**：analyzer 与源同广播域时镜像回灌（§2.11，839,601 包/3s）；
  删会话后计数立刻冻结。**不是缺陷**，是拓扑红线（手册 §8.11 已警告）。
· **`show vpp` 的 `threads: N` 是「主线程 + workers」**（本机 1+1=2，与
  `show vpp runtime` 的 `vpp_main` + `vpp_wk_0` 两行一致），不是 worker 数——读视图无需改，
  但容易被误读（本轮核对过，**非缺陷**）。
· **抓包文件是 VPP 固定单文件**（`/tmp/rxtx.pcap`）：上一次会话/别处手动 trace 的帧会混进下
  一次导出（§2.13）。产品 start 有单会话守卫，属我自己的操作噪声，登记为**观测陷阱**。
· **`systemd-resolved` 不在（`rc` 状态）时 DNS 声明如实跳过**（#424 口径），
  本现场即此形态；**NTP 的 UDP/123 在本环境被挡**（223.5.5.5 Reach=0），换可达源后正常。
· **LDAP/带外/温度传感器类**：本机无 IPMI/传感器（硬件健康页如实「（无）」+ 磁盘 SMART
  「未知」并给原因），与既有登记一致。
