====================================================================
日期：2026-10-03；环境：nfvis-vm（2.0.0~dev53 = 本分支构建，PR #285）。

§0 三.7 核实结论（先核实后立项）
- 遗留条目「`internal/metrics` 只采集宿主运行态；VPP/VNF/容器指标是否进 /metrics 未见证据」**是旧状态**：
  真机全量盘点（46 行）实含——主机（cpu/内存/磁盘/uptime/大页）、**VPP**（线程数、主堆三亚、buffer 池
  逐池可用/已用 + 可用性序列、逐接口 rx/tx 包·字节·错·丢）、配置计数（接口/交换机/VRF/VM/容器）、
  告警按级、VNF/容器**聚合**运行数与 vCPU。
- **真发现两处不足**（→ 决策 #355）：① 聚合 `nfvis_vnf_running` 在编排不可用时**静默计 0**（外部看板
  会把「读不到」误读成「全停」）；② 无逐对象序列（无法按单 VM/容器做告警与看板）。核实即收口（条目更新）。

§1 验证① —— 基线读数（dev53）
- `nfvis_vnf_up{kind="vm",name="sem-vm"} = 1`；`runtime_available` 双侧 = 1；
  sem-ct 当时因 `sleep 3600` 到点自然 exited（**up=0 如实**，非缺陷）——恰为验证②的起点。

§2 验证② —— 容器起/停双向
- `start sem-ct` ⇒ `up{container,sem-ct}=1` 且 `nfvis_vnf_running{container}` 0→**1**；
- `stop sem-ct` ⇒ `up=0` 且计数 1→**0**（sem-vm 侧不受影响）——up 与聚合计数同步、方向正确。

§3 验证③ —— libvirt 停/起（决定性对照，联动 #354）
- **停窗口**（40s 后采样）：`nfvis_vnf_runtime_available{kind="vm"} = **0**`、
  **vm 逐对象序列消失**（输出中只有 container 的 up，无 `nfvis_vnf_up{kind="vm",...}`）、聚合
  `nfvis_vnf_running{vm}=0`（既有行为不变）——对照修复前：同样 0 但**无任何提示**，看板会把
  「VM 可能仍在跑、只是读不到」误读成「全停」；现在可用性序列让外部可判定「计数不可信」。
- **起回**（45s 后采样，含 #354 自动复连）：`runtime_available{vm}=1`、`nfvis_vnf_up{kind="vm",name="sem-vm"}=1`
  恢复；journal 同窗见「libvirt 连接已恢复（自动复连成功）」——#354 状态机与 #355 指标联动一致。
