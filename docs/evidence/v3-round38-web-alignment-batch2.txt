§5 本轮抓出的新缺陷 R38-1（已定位，修复见 §6）
--------------------------------------------------------------------------------
**现象**：只要某个虚拟交换机带 `description` 字段，**整条 CLI 命令 `show configuration |
display set` 整体失败**：

```
%% display set 内部错误：生成语句回放失败（未知语句: "description"）——请改用 show configuration / | display json 并报告缺陷
```

**不是少一行输出，是整份配置读不出来**——**一条 Web 侧编辑就能让 CLI 的全局读命令失效**。

**根因（三处对齐关系，主会话逐处核实）**：
1. `internal/model/model.go:341` —— `VirtualSwitch` 有 `Description` 字段；
2. `internal/schema/tree_config.go` —— 命令树里 `interfaces`（~203）、`bonds`（~244）、
   VM（~581）、容器（~610）**都有** `description` 叶子，**`virtual-switches` 没有**；
3. `internal/api/setstmt_families.go:~1307` —— 发射器显式不发射该字段，注释写「description 仅
   REST 可达（无语句形态），出现时由回放校验如实报错」⇒ 回放校验拿到它就整条失败。

**仓内已有正确先例**：同文件 `emitAclsFamily`（~675-683）对 **ACL 的同名字段**就是
`w.note("acls %s：描述字段无语句关键字，不入 display set")`——**用注释优雅处理**；同族 note 还有
口令哈希（`setstmt.go:358`）、空 gateway（`setstmt_families.go:524`）、serial console 关闭态
（`:1038`）。即：**同一类情况在仓里有两种处理，ACL 是「注释」，vswitch 是「报错」**。

**触发路径**：Web 的「虚拟交换机」表单**提供「描述」字段**（配置页与对象页都有），用户填了就中招。

**修复方向（照 ACL 先例）**：让 vswitch 的 description 走 `w.note(...)` 发注释、不再让回放失败。
**不**顺手给 `virtual-switches` 加 `description` 语句叶子——那属新增 CLI 产品面，按本仓纪律是
「契约先行」的另一件事（若要，应作为独立提案）。本缺陷只修「一个字段把整条读命令拖垮」。

§6 修复与复验（`3.0.21~dev10`；sha256 `1c533b5b…`）
--------------------------------------------------------------------------------
**修复子智能体挖出比本会话最初诊断更深的问题**：仓内那些 `w.note(...)` 先例（ACL 描述、口令哈希、
空 gateway、serial console 关闭态…）**全是半成品**——回放自校验只剥离敏感值与 `enabled=true`，
**从不剥「不入 display set」的字段**，所以**每个被注释的字段照样把整条命令打回**（实测确认：

  `stripNonEmittable` / `nonEmittableKeyPath` / `stripNonEmittableAt` / `nonEmittableLeaf`
  （把「已注释 ⇒ 两侧同剥」补成真机制，并支持配置模式层级 show 的 prefix 折算）。
· `setstmt.go`：两处比较式（`verifySetStatements`）接入 `stripNonEmittable`（2 行）。
· `setstmt_test.go`：新增 `TestDisplaySetVSwitchDescriptionNote`（顶层 + `edit virtual-switches`
  层级形态）与 `TestDisplaySetNonEmittableFieldsNote`（vrf 描述/空 gateway/serial 关闭态/SR-IOV VF）。
· `docs/NFViS-CLI命令全表.md`：`show | display set` 行补「无语句形态字段以 # 注释说明」。（openapi 未动）

**同类清单（对象 × 字段）**——已修 6 项（原先都会让整条命令失败，现改为注释 + 成功）：
`virtual_switches[].description`、`vrfs[].description`、`acls[].description`、
`virtual_switches[].gateway={}`（**CLI 自己造**：`delete … gateway ip` 留空对象）、

8.2 **口令轮换（用户裁定「轮换」；含一次自造事故，如实登记）**
  · **起因**：两个子智能体在取 `/root/nc` 口令时各有一次掩码失败，口令被写进它们的本地会话记录。
  · **我自造的事故（关键教训）**：轮换时我把口令写成嵌套引号里的 `'$NEW'`——**在外层双引号内，单引号
    是字面量**，于是传给 CLI 的是 `password 'XXX'`，CLI 把引号也并入了值 ⇒ 新旧口令**都登不进**。
    **诊断路径**（值得复用）：① 用另一个账号（oper1）验证传输面正常 ⇒ 定位到「是该账号的口令值问题、
    不是认证链路问题」；② 读 `nfvis.db` 的 `config_revisions`，比对 rev 237 与 rev 238 的 `password_hash`
    ⇒ 确认哈希确实被我改了。
    ⚠️ **诊断中的二次失误**：我连着试了口令变体，**把 admin 账号又锁了**（#76 策略，5 次/15 分钟）——
    教训是**验证前先算好「还剩几次尝试机会」**，别把锁定窗口一起耗进去。
  · **恢复（外科手术，无需停机重装）**：`systemctl stop nfvis` → 备份 `nfvis.db` → 把 **rev 237 的
    admin `password_hash` 写回 rev 238**（只改该用户、不动其余）→ `systemctl start nfvis` ⇒ 旧口令立即
    恢复可用。**这印证了一件事**：口令哈希在 `config_revisions.config_json` 里逐版留痕，**有 root 就有
    可审计的恢复路径**（不需 zeroize/重置数据）。
  · **干净重设**：把命令**写进脚本文件**（`configure` / `set system login user admin password <值>` /

§9 R38-2（P3 期间由系统族子智能体发现、主会话真机复现并定位）
--------------------------------------------------------------------------------
**现象**：配置里存在**空容器对象**（如 `system.kernel = {}`、`vpp.dpdk.dev = []`）时，
**整条 `show configuration | display set` 整体失败**：
`%% display set 内部错误：生成语句未能完整还原配置——请改用 show configuration / | display json 并报告缺陷`。
**与 R38-1 同族**（一个无关紧要的结构把整条读命令拖垮），**同样是「整份配置读不出来」级别的后果**。

**主会话真机复现（非采信自述）**：用候选 API 写入 `system.kernel={}` → commit（rev 269）→
`display set` **立即整体失败**；删掉空壳后**立即恢复**（0 内部错误、32 行 `set`）。
**且这不是理论问题**：现场**本就存在**一个非我造的空壳 `vpp.dpdk.dev=[]`——是系统族子智能体
**正常操作（测 VPP 面板后回退）留下的**，即**界面常规操作即可造出**。

**成因**：`js/core/forms.js` 的 `cfgWrite` 在「某节最后一个字段被清空」时**不清理 loc 路径上的中间对象**，
留下空壳；**配置页与对象页都能造**。CLI 侧亦有同族先例（R38-1 记的 `delete virtual-switches X gateway ip`
留 `gateway={}`）。

**修法方向（照 R38-1 既有机制，不另造）**：让**空容器**走同一条「发射端不发射 / 比较端同剥」的路子
——R38-1 刚在 `setstmt_families.go` 建立了 `stripNonEmittable` 系列并被 `setstmt.go` 的
`verifySetStatements` 两侧调用；空容器（`{}`/`[]`，与「键不存在」对回放等价）按同口径处理，
使 `display set` **整体成功**。**不改前端、不做提交期拒绝**（与 R38-1 的处置保持一致）。

**修复与复验**：见 §10（修复子智能体回收后填入）。
