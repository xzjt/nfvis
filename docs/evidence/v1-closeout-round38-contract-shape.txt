------ 0. 根因（比 round37 记的更准） -----
round37 记的是"契约声明了、实现没回"。本轮逐条查清后发现是**两类**根因：

**① 契约自身重复定义**（此前没识别出来）。`components/schemas/VppStatus` 在
`docs/NFViS-openapi.yaml` 里被定义了**两次**：一处准确（version/connected/pending_restart/
threads/buffers/buffers_source/memory…）、一处过时（state/dpdk/buffers_per_numa/main_heap_size/
config_revision）。而 `check_openapi_json_sync.sh` 用 `yaml.safe_load` 生成内嵌 JSON，**静默保留
最后一个** ⇒ **发布出去的规范带的是过时形状**，照它开发的客户端必然取错字段。
**定位手法**：正则扫行会误报（契约里有 `{name}:start` 这类含冒号的路径、有内联 map、有列表项——
实测按行扫报 62 处"重复"，真重复只有 1 处）；改用**真正的解析器**（PyYAML 自定义 mapping 构造器逐层查重）
才得到唯一答案：`重复键 'VppStatus'（第 1757 行 与 第 1955 行）`。

**② 实现未落地契约声明的字段**。`GET /system/status` 契约声明 `cpu`/`memory`/`hugepages`/`storage`
而实现只回 `hostname`/`uptime_seconds`/`config_ready`（`config_ready` 还反过来没进契约）；
`GET /interfaces` 契约声明 `kind`/`driver`/`enabled`/`link`/`speed_mbps`/`mac`/`numa_node` 而实现只回**配置**对象。

**为什么长期没被发现**：`routes_contract_test.go` 只守护「路由 ⊆ 契约」（**路径**）——
既**不守护响应形状**，也**看不见 YAML 里的重复键**。

**另登记 R37-2**（同类、单独处置）：`GET /system/version` 是**桩**——7 个键都在、只有 `nfvis` 有值，
`ubuntu`/`vpp`/`dpdk`/`libvirt`/`qemu`/`docker` **全是空串**（CLI `show version` 同样只印 NFViS 版本）。
补齐要跨 libvirt/docker/qemu 三个 provider 与宿主事实探测，属独立一批。

------ 1. 处置（决策 #116） -----
| 项 | 处置 |
|---|---|
| 重复的过时 `VppStatus` | **删除**（保留与实现一致的那份）；内嵌 `openapi.json` 随之重生 |
| `/system/status` | **补实现** `cpu{total,isolated,usage_percent}`、`memory{total_mb,used_mb}`、`storage{total_bytes,free_bytes,used_ratio}`、`hugepages[]`；**数据源与 CLI 同源**：前三者取 `internal/metrics.HostMetrics()`（与 `show system cpu\|memory\|storage` 同一来源），`hugepages` 取 `resourcePoolView(cfg)`（与 `GET /resource-pools` 同一来源）。宿主指标是 Linux 采集：**取不到就不给该子对象**，不编造零值 |
| `/interfaces` | **补运行态** `kind`（=physical，与 `show interfaces physical` 同口径）、`enabled`/`link`/`speed_mbps`/`driver`；来源与 CLI **同源**（`VppStateRuntime.InterfaceStates()`，决策 #84 定的运行态事实来源）。取不到的（mac/numa_node）**不给** |
| `/vpp/status` | **补** `config_revision`（`Engine.CurrentRevision()`，供判断数据面是否落后于配置） |
| 契约形状修正 | `SystemStatus.storage` 改为实际可得的 `{total_bytes,free_bytes,used_ratio}`（原 `data_total_gb/data_used_gb/images_gb` **无数据源**）；`hugepages` 由单对象改**数组**（产品有 1G/2M 两个池，单对象表达不了）；`config_ready` 补进契约 |

**为什么不取"缩契约"**：契约是产品对第三方的承诺（FR-API-002 明说"Web 控制面据此开发"），
缩掉等于承认这些能力不做；而数据其实都在（CLI 早就读得到），只是 REST 侧没接。

------ 2. 新增两道守护（防同类再发生） -----
1. **契约 YAML 重复键查重**：`contrib/scripts/check_openapi_no_duplicate_keys.sh`，已纳入 `make docscheck`。
   用**真正的解析器**（PyYAML 自定义 mapping 构造器）逐层查重——按行正则必出假阳性（见 §0①）。
   **红-绿**：临时追加一个重复的 `SystemStatus` → 报 `重复键 'SystemStatus'：第 1717 行 与 第 2559 行`（退出码 1）；
   删掉即绿。
2. **响应形状核对**：`internal/api/shape_contract_test.go`，按**契约声明的 schema**逐字段核对实际响应
   （字段必须出现；**字符串字段还必须非空**——"声明了却恒回空串"与"没实现"是一回事，R37-2 就是这么现形的）。
   会合法缺席的字段进**显式白名单并写明理由**；`/vpp/status` 需要数据面 Provider（测试进程起不了），
   改用**静态核对**：契约声明的字段，响应结构体必须发得出来（json tag 覆盖）——这正是 VppStatus 漂移的形态。
   **红-绿两处**：① 把 `config_revision` 的 json tag 改名（能编译但不发出）→ 报"结构体发不出该字段"；
   ② 给契约的 `SystemStatus` 加一个实现不返回的字段 → 报"契约声明了 X，响应里没有"。还原后全绿。
   ⚠️ 过程中发现**白名单自己会变成空转**：我一度把已实现的 `config_revision` 也列进白名单，
   于是红-绿①**静默通过**——白名单只该收"会合法缺席"的字段，已实现字段列进去等于关掉断言（已修正并加注释）。
   守护还当场抓出一条既有事实：`/system/status.hostname` 在**未配置** `system.hostname` 时是空串
   （真机上已配置），按"字符串非空"规则它必须显式进白名单并写明理由，不能默默放过。
