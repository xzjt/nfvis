§2 ❌ #317 引入的回归（本轮抓到，**尚未修**）
- **cli-fulltest：195 通过 / 3 失败 / 11 预期报错**（此前 198/0/11）
- **cli-semantic-check：10 通过 / 1 失败 / 1 不可判定 / 1 登记**（此前 12/0/1）
- 失败签名一致：`%% candidate 会话锁被占用: 由 admin@ssh 持有`
- 复现与现状证据：CLI 调用结束后**锁仍在**（`sessions` 里可见
  `{holder:"admin@ssh", session_id:"50df88b7-…", dirty:false}` 无人释放）；
  随后任何一次新的 CLI 调用（新 token = 新会话键）**取不到锁**，于是 `configure` 失败
- 根因（定位结论）：旧模型把 CLI 会话按 `user@ssh` **归并**，下一次调用天然「接管」同一把锁；
  #317 按 token 拆开会话后，**前一次调用留下的锁不再被下一次接管**，而释放路径（调用结束时的登出/
  或空闲巡检）**没有在这些路径上及时生效**——于是 `dirty:false` 的**干净锁**也会挡住后续调用。
  除回归外，这也说明：**「干净锁」本就不该具有排他性**（没有未提交改动可保护）。
- 现场已用 `systemctl restart nfvis` 清掉遗留锁（装配期释放遗留锁），环境恢复可用

§4 下一步（新登记，优先于二组其余条目）
新增条目 **R98-1（#317 引入）**：CLI 一次性/脚本调用留下的**干净锁**挡住后续调用。
建议修法（择一，实现时在决策行写清口径与理由）：
  ① **干净锁不排他**——候选无未提交改动（`dirty=false`）时，同用户的新会话可直接接管该锁
     （保护语义只在「有脏候选」时成立，与 R79-1 的修复不冲突）；或
  ② **路径级释放**——让 CLI 调用结束（含 `-c`、脚本、`commit and-quit` 等所有路径）必定释放本会话锁，
     并让空闲巡检对 `dirty=false` 锁更激进。
必须同时加**回归测试**：连续多次 CLI `configure/commit` 调用不得因上一把干净锁而失败
（即本轮 fulltest 的 3 条失败场景）。
