    在 guest 的 mark 循环里 ping 192.168.98.10（域外地址）时，tcpdump 在 **ens160（管理口）**
    抓到 `192.168.100.100 > 192.168.98.10: ICMP echo request` 与
    `192.168.100.100.xxxxx > 139.199.214.202:123 NTPv4`（guest 的 NTP 客户端）——即
    **BVI 域（vr-vs-dmz）表内无匹配路由的流量，落在宿主 main 表默认路由（ens160）上带原私网源

    blackhole 兜底。对照：**VPP 数据面同流量为丢弃**（域内 FIB 无路即 drop）。影响：VNF 可绕过
    域内路由策略/ACL/NAT 直触管理网与上游（本轮为单向可见——回程无人路由 192.168.100.0/24；
    若上游有回程路由即双向可达）。设计文档（v3-数据面可切换-设计.md）未讨论该语义。
3.13 内核模式删对象（#4.7 教训遵守）：在内核模式下完成全部清场（vnf-a/ct-1/vs-*/vx-a/acl/qos/风暴/

§7 新缺陷登记（R8-1~R8-4；逐条独立事实源）
--------------------------------------------------------------------------------
R8-1【中低】oper 模式的 `exit` / `quit` **不退出 CLI**，而契约三处都写「退出 CLI」
    · 事实：真 pty 内连发 44 次 `exit` → 均静默回到 `nfvis>`（无输出、不退出）；`quit` 同；
      仅 Ctrl-D 退出。`internal/schema/tree_oper.go:419-420` 与《命令全表》§1.3 均为「退出 CLI」，
      `internal/cli/repl.go` 的 Run() 无 exit 分支、服务端 execOper 的 exit/quit 只做释放锁（#318 复用）。
    · 影响：用户按帮助/文档输入 exit 无法退出，Ctrl-D 是事实上的唯一出口，属「契约宣称的行为缺失」。
    · 建议：REPL 收到 oper 模式 exit/quit 后正常退出（保留释放语义），或把契约改写成「释放会话；
      退出请 Ctrl-D」。
R8-2【中】内核数据面下域内到未知目的地流量经**管理口**外泄（VPP 下为丢弃）
    · 事实：见 §3.12（ens160 抓到 guest 源地址的 ICMP/NTP 出包；`ip rule` 内核默认链；
      vr-vs-dmz 表无 default；main 表 default via ens160）。文档未声明该语义。
    · 影响：域隔离/路由策略被旁路（VNF 可触管理网/上游）；单向可得，双向取决于上游回程路由。
    · 建议：在域的 VRF 里加 blackhole/unreachable 兜底（或明确文档化「内核数据面使用宿主默认路由」
      并给出关闭方式）。
R8-3【中低】容器镜像的 docker 侧标签不对账：上传抢占 `<基名>:latest`、删除带走用户原 tag
    · 事实（docker events 铁证）：13:57 上传 alpine:3.20 时产品 `docker tag → alpine:latest`
      （decision #160 的注释是「按目录项名 <名>:latest」——含冒号目录项名下实际落成 `<基名>:latest`，
      且会**覆盖用户已有同名 tag**）；14:51 `request images delete` 时产品 `docker rmi alpine:3.20`
      （**删掉用户 docker 里的原 tag**）却留下自己打的 `alpine:latest` → 随后 fulltest 的
      `docker save alpine:3.20` 失败（2>/dev/null 掩盖）→ 14 连败（§6.1）。
    · 建议：派生引用改为不含歧义的合法引用（如 base+tag 分离或 hash 化），删除时对称清理派生 tag；
      上传/删除的 docker 副作用写进文档。
R8-4【中低】`delete interfaces <if> disable` 无法撤销禁用（与 set 同体写 enabled=false）
    · 事实：`internal/api/cliexec.go:1987-1994`——`!isSet` 与 `isSet` 两个分支**同体**
      （都 `cur["enabled"]=false`）；实测 `delete interfaces ens224 disable` 回「值未变化」、
      候选仍是 `enabled false`、ens224 持续 admin-down。套件 phase2 会留下该状态且无 delete 清理
      （脚本里本就没有对应 delete，因为 delete 是坏的）。
    · 建议：delete 分支改为删除 `enabled` 字段（缺省即启用），补红绿单测；套件补还原动作。
观察①【文档-实测偏差，低】vpp→kernel 后手册承诺「unbind 后 enable 即收敛」不成立，需再重启 nfvis
    一次（§3.3）；建议改手册或让 enable 触发交换机段收敛。
观察②【既有口径】LLDP 在 DPDK 物理口启不起来（底座 -7；M3 曾记录、现 #34 正文已无；产品透传
    原始错误并补偿）；内核侧自研代理正常（§2.14/§3.8）。建议写回契约 + 报错人话化。
观察③【既有口径】DNS 代理首次查询超时、其后全绿（R4-2 复现，§2.11）。
观察④【改进项】风暴计数在 stats segment **实际可读**（形状=组合计数+索引），实现按名字找路径恒不
    命中；可低成本落地真计数（§2.6）。
观察⑤【轻微】`set port-mirroring x source … analyzer …` 连写被拒（实现要求两条语句），但候选树

观察⑥【行为提示】`cloud-init user-data <文件路径>` 只比较路径值——内容改了但路径不变时
