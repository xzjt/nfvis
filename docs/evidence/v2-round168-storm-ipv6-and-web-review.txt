§2 storm control 的 IPv6 组播实测（#385 的如实边界补验）
- **现场**：`ens192` 临时加入 `sem-vs` 作第 4 端口（与 round167 同法；`show bridge-domain 314680 detail` 里
  bvi1 / ens192 / vh-sem-vm-nic0 三成员）；**rx 必须是被测接口 ens192**；观测点＝VPP `l2-flood` 计数增量（独立事实源，与 round167 同）。
- **帧**（64 字节整帧，Python 精确构造，写为 pcap 载荷）：目的 MAC `33:33:00:00:00:01`（IPv6 组播）、
  源 MAC `02:00:00:00:00:99`、以太类型 `0x86dd`、IPv6 头 `60 00 00 00 | 00 0a | 11 | 40 | 2001:db8::1 | ff02::1`、余 10 字节载荷。
- **注入通道（如实登记一处工具差异）**：本底座的 `packet-generator new { … data { hex … } }` 内联 hex **需要 `0x` 前缀**
  （`data { hex 0x… }` 可建流；无前缀报 `failed to parse packet data from …`、空格分隔亦不被接受；单参数与 stdin 多行、
  带 `node`/`interface` 各组合均复现——**round167 记录只写了 `data { hex … }`，本记录补齐前缀要求**）。本轮功能对照改用
  **pcap 载荷**：`packet-generator new { name <n> interface ens192 pcap /tmp/ipv6mcast.pcap limit 2000 }` + `enable <n>`；
  两种通道注入的是同一帧、观测同一计数，不影响结论。
- **四相位结果**（每相位 2000 帧；基线/增量逐相位记录）：

  | 相位 | storm 配置 | 注入帧 | l2-flood 增量 |
  |---|---|---|---|
  | 对照 | 无 | IPv6 组播 ×2000 | **+2000**（基线 54 → 2054） |
  | 实验 | `multicast 1` kbps | IPv6 组播 ×2000 | **+15**（2054 → 2069） |
  | 负对照 | `broadcast 1` kbps | IPv6 组播 ×2000 | **+2000**（2076 → 4076；广播表掩码 `ff…ff` 不覆盖 33:33） |
  | 链式 | `broadcast 1` + `multicast 1` | IPv6 组播 ×2000 | **+15**（4076 → 4091；广播表 miss → `NextTableIndex` → 组播表 hit） |
  | 链式·广播路径 | `broadcast 1` + `multicast 1` | 广播 `ff:ff:…` ×2000 | **+15**（4091 → 4106；两类各归其表） |

- **数据面形状对照**：`show classify tables` 掩码＝组播 `0100…` / 广播 `ffffffffffff…`；policer `nfvis-storm-ens192-multicast
  type 1r2c cir 1 kbps`（与 #385 round167 记录一致）。
- **结论**：**IPv6 组播 MAC（`33:33:`）确被组播类覆盖**（首字节 `0x33` 的 I/G 位=1 ⇒ 掩码命中），
  #385 声称的「按掩码 `0x01` 同覆盖」由此从推定变为**实测**（对照 2000 vs 实验 15）。
