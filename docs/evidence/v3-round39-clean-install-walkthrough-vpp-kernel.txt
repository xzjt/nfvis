§7 缺陷 / 观察登记
--------------------------------------------------------------------------------
【本轮抓到并已修复（决策 #488~#493，逐条真机复验）】

R39-A（#488，高）**同一台 L3 交换机内把地址从一个接口挪到另一个，一次提交必失败**
  现象：`delete … l3-interface vh-…-nic0` + `set … l3-interface vh-…-nic1 ip address 192.168.200.1/24`
    同提交 ⇒ `%% 底座下发失败（已补偿）: 下发失败 vrf[vs-nat]: … VPPApiError: Address in use (-105)`
    并整体回滚；只能拆两次提交。
  根因（两处叠加）：① `plan()` 里 `vrf[<名>]`（ApplyVRF 新）排在 `del-l3-if[<名>/<旧口>]` **之前**，
    而 ApplyVRF 只清**新声明里仍有**的接口地址 ⇒ 旧口前缀还在同表上；② 即便两口都仍在声明里，
    ApplyVRF 的逐接口「clear→置表→add」也会按声明序先给后处理的口 add。错误文案的 `vrf[vs-nat]`
    正是那个 op 的 desc，可据此定位（`del-l3-if` 根本没跑）。
  修法：① `del-l3-if` 上移到本 VRF 的 ApplyVRF **之前**（undo 仍 ApplyVRF(旧)，可回滚复原）；
    ② ApplyVRF 改**两趟**（先全清地址+置表，再统一配地址）。
  复验：一次提交迁移成功（rev 65）、vppctl 见新口持地址且旧口无地址、无告警。
  测试：`TestApplyPlanL3RevokeBeforeDeleteACL` 改为钉住新顺序。

R39-B（#489，高）**NAT 的 inside 不随 L3 拓扑变化重算（改完拓扑 NAT 静默失效）**
  现象：地址从 nic0 挪到 nic1 后，配置与 `show nat` 都正常，但 `vppctl show nat44 ei interfaces`
    仍是**旧口 in**；guest 的包进了 NAT（`nat44-ei-in2out` 计数在涨）却 **0 会话**，
    `out2in` 报 `no translation`——转发静默不通；手工重提一次 NAT 规则才恢复。
  根因：只在 `nat` 段本身变化时才排 `nat` 操作，而 inside/outside 是从「规则引用的 L3 交换机的
    l3-interface 集合 + 挂到该交换机的 vNIC + 出接口所属转发域」**推导**的；15s 巡检不管 NAT。
  修法：新增 `natDerivedInputs(cfg)`（被引用 VRF 的 l3-interface + 挂其上的 vNIC + 出接口所属 VRF，
    排序后比较），指纹变了就重放 ApplyNAT；只含被引用对象，无关 VRF 改动不白重放。
  复验：一次提交迁移后 `show nat44 ei interfaces` 直接是新口；guest 连续 ping 造出 **33 条动态会话**、
    `tcpdump` 见 `192.168.98.1 > 192.168.98.10`（源地址被改写）。
  测试：`TestApplyPlanReappliesNATWhenReferencedVrfChanges`（含三条负控）+
    `TestApplyPlanReappliesNATWhenVnfNicAttached`。

R39-C（#490/#491，中）**`l3-interface` 语句建出「半个对象」+ `delete … type l3` 留无 type 空壳**
  现象一：交换机未声明时执行 `set virtual-switches vs-z l3-interface ens192 ip address …` ⇒ 只建出
    同名 **VRF 条目**；`show virtual-switches` 不列它、`show virtual-switches vs-z` 报「在数据面中不存在」，
    而 `show vrfs` / display set / 数据面表都在；**CLI 再无语句能删它**（两种 delete 都报「无匹配配置」），
    现场只能整份 REST 候选文档改写。
  现象二：`delete virtual-switches vs-nat type l3` 只清 type 叶 + 删同名 VRF，交换机条目留着却无 type ⇒
    提交被「type 必须为 l2 或 l3」打回，只能改用裸 delete。
  修法：`l3VrfOf(create=true)` 一并建出同名交换机（type=l3；已存在时不动 type）；
    `aliasVSType` 的 delete 分支在「清 type 后只剩 name」时整条回收。
  复验：一条 set 后列表直接列出 vs-z2（l3（VRF））、详情给 VRF 视图；`delete … type l3` 一次删净
    （rev 67，`show vrfs` 与 `vppctl show ip table` 残留计数 0）。
  测试：`TestL3InterfaceAutoCreatesSwitch`、`TestL3InterfaceDoesNotRetagExistingL2`。

R39-D（#492，中）**同一次提交里「DHCP 服务器换中继」必撞 bind :67**
  现象：`delete … dhcp-server` + `set … dhcp-relay server …` 同提交 ⇒
    `绑定中继源地址（BVI 网关地址）192.168.99.1 的 UDP 67 … bind: address already in use`、整体回滚；
    拆两次提交才行。反向（relay→server）无此问题。
  根因：交换机段固定按「relay 在前、server 在后」下发，中继启动时 bind `<BVI 地址>:67`，而服务器的
    停用（注销 punt + 删内置 tap）排在后面。
  修法：仅「旧声明有可运行 server、新声明没有」时把 server 停用前置；其余情形保持既有顺序逐字不变。
  复验：一次提交成功（rev 70）、`dhcp-relay` 块在位、无告警；反向切回 server 亦一次成功（rev 71）。
  测试：`TestApplyPlanRelayAfterServerTeardown`。

R39-E（#493，中）**Web「历史趋势」图例色块空白（内联 style 被 CSP 拦）+ 容器 exec 超时框同族**
  现象：图例只有文字、色块是空白方块（`getComputedStyle` = `rgba(0,0,0,0)`），控制台报
    `Applying inline style violates … 'default-src 'self''`；容器 exec 的「超时」输入框
    `style="width:5em"` 同样被拦（宽度失效）。
  根因：色块用 `el('span', { style: 'background:…' })` 上色，而 CSP 无 `unsafe-inline`。
  修法：色块改**类名**（`MH_SWATCH_CLASSES` ↔ `.mh-sw-0…5`）、窄输入框改 `.w-5em` 工具类；
    **不加 unsafe-inline**（不削 XSS 纵深防御）。
  复验：色块 backgroundColor 实测四色、CSP 违规 **0**（改前每页 1 条）；截图入册。
  测试：三层守护（JS 无内联 style 键 / index.html 无内联 style / 图例类名↔CSS 配色成对），
    已做红-绿（注回内联写法即精确报红）。
