§3 决策 #311 VM 启动失败可诊断（✗ 未按设计验成，但暴露一条**真实待处理项**）
- 我的注入方式：`systemctl stop vpp` → 期望「约 3s 回 `%% … paused (starting up)` + 诊断」
- 实际：`start` 请求**卡到客户端 90s 超时**才返回（`context deadline exceeded (Client.Timeout exceeded while awaiting headers)`），
  **没有走到设计中的 3s 探测窗口**；`virsh domstate cli-vm` 独立印证为 `paused`；
  `systemctl start vpp` 后再 `start` 仍然 90s 超时、VM 仍 `paused`
- 恢复：`virsh destroy cli-vm` + `systemctl restart nfvis` 后服务与数据面正常（此后对象已清零）
- **登记为待处理项（本轮发现）**：VPP 不在运行时，`start` 的**请求本身**在到达 `StartVMChecked` 的探测窗口之前就阻塞
  （疑似 vhost-user/socket 准备阶段在等 VPP 连接），于是 #311 设计的「有界窗口 + 原因透出」在这条路径上**根本用不上**——
  需要一条**前置判定**（VPP 未运行/连接不可用 → 立刻失败并给 `request vpp restart` 指引），或把探测窗口提前到阻塞点之前。
  建议单独立项（可直接补进 v2 待做第二节），并把验收条件写清：VPP 停 → `start` 在数秒内返回原因，而非 90s 超时
- 也如实说明：本轮的注入方式（停 VPP）本身把数据面留在了坏状态，导致脚本后续的清场/套件阶段卡住、**四套件本轮未执行**；
  恢复后环境已回到基线（sw=0 / vmf=0 / VPP 2 口 / nfvis 与 vpp 均 active）
