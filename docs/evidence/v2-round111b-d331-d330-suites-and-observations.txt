§2 交接第 3 条：#330 `ping ipv6` 可达路径 + 候选正确探针（✓ 可达路径端到端成立）
- **重要更正（任务前提错、被真机纠正）**：配置树**没有** `interfaces <if> address`；
  BVI 的 v6 地址走 `set virtual-switches <vs> gateway ip <v6-prefix>`（值校验器 ip-prefix
  本就声明 IPv4/IPv6；govpp `SwInterfaceAddDelAddress` 用 ParseAddressWithPrefix，v4/v6 同源）。
  `set virtual-switches sem-vs gateway ip 2001:db8::1/64` 提交成功（rev 772），VPP bvi0 出现
  `L3 2001:db8::1/64 ip6 table-id 1445873`。
- guest v6：user-data 加 `ip -6 addr add 2001:db8::2/64` + restart 重放生效；
  `vppctl show ip6 neighbors` 出现 2001:db8::2（NDP 通）。
- **可达路径**：`ping ipv6 2001:db8::2 vrf vr-sem-vs count 2` → 76 bytes from 2001:db8::2、
  `2 sent, 1 received`（首包被 NDP 解析消耗）、**rc=0**。v4 回归 `ping 192.168.99.2 vrf …` 2/2 rc=0。
- 不可达两型复确认（rc=1 + 行首 %%）：无 vrf → `0 sent`；带 vrf → `2 sent, 0 received`。
- 候选两面同源确认：REST `GET /cli/candidates?tokens=ping` → `<host>,count,ipv6,source,vrf`；
  pty `ping ?` → 列出 ipv6（traceroute 同）。round110 的「执行当探针」做法正式废弃。
- **探针测试入仓**：`TestCLIDiagIPv6Candidates`（internal/api/cli_diag_test.go，PR #258 squash
  合入 v2 @ 9aac572，CI 双跑全绿）——断言 tokens [ping]/[traceroute] 的候选都含 ipv6。
- 经验备忘：非 VRF 表内目标 ping（v4/v6 同）默认查表 0 → `0 sent`；判不可达建议带 vrf 复核
  （round110 的「0 sent」型证据与「目标在别的表」不可区分）。REST 登录字段是 `username`。
- 清场：删 v6 网关地址（rev 773）+ fixture down（rev 774~776）。
- 原始输出：nfvis-vm:/tmp/ipv6-*.log。

§4 新登记 R111-1（中）：恢复收敛告警族不随事实变化重估（根因已定位，未修）
- 现象链（全在本会话实测）：`interfaces bvi0` 声明 + VPP 无此口 → 启动告警
  RECOVERY_IFACE_MISSING（error，raised 12:56:40）；① fixture 把 bvi0 带进 VPP 并通流 25 分钟以上
  → 告警不消；② 配置声明删除（rev 795）→ 告警仍不消；③ lifecycle 的 VPP 重启（OnConnect）后
  → 立即消解（「（无 active 告警）」）。
- 根因（代码定位）：`runRecovery`（内含 EnsureConsistent 末尾对 recovery 作用域的 `Sync` 全量覆盖）
  **只挂在 `vppMgr.OnConnect`**（cmd/nfvisd/main.go:698）；15s 巡检的残留对账
  `applyResidueAlarms`（internal/orchestrator/network/residue.go:172）**有意只动残渣码**
  （其注释：Sync 覆盖整个作用域会把不在本轮失败清单里的项当陈旧清掉，而 15s 路径不算全量失败集）。
  故恢复族告警的事实基础（声明已删/口已出现）变化后无人重估，直到下次 VPP 重连。
  与 #188/#321 的「随对象消失/状态恢复自动消解」口径不符。
- 修法方向（待立项决策）：恢复族告警的**廉价按事实复核**（按 source 查「声明是否已删/口是否已在 VPP」），
  不做周期性全量重放（重且会把暂时性错误刷成告警抖动）。
