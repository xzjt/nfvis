§1 根因（修复前确认）
- round110b 登记的 R110-1 **确认为真缺陷**：网络对象页（#/network）QoS 策略卡在策略有
  出向绑定（CLI/REST 读视图 ens224:out）时「类型/目标」两列显示「—」。
- **字段级根因**：该卡自决策 #128 起渲染 `q.type` / `q.target || q.interface`，而
  `/qos/policies` 响应里**从来没有**这些字段（#331 前是 {name,cir,cbs}；#331 后是
  {name,cir,cbs,bound_interfaces,bindings}）——「类型/目标」自始恒「—」，不是 #331 引入的回归。
  #331 的三面同源补了 CLI/REST 读视图、QoS 详情页（绑定（方向））与接口详情页（入向/出向限速策略），
  漏了这张列表卡。路径级覆盖守护（ui_coverage_test.go）只盯端点，挡不住「端点对、字段错」。
- 修复前复现（dev20 上）：建 `pol-web cir 8000 cbs 8000` + `set interfaces ens224 egress-policy pol-web`
  → CLI `show qos policies` 显示 `pol-web … ens224:out`；REST `GET /qos/policies` 返回
  `bindings:[{interface:"ens224",direction:"egress"}]` —— 两面都有数据，只有 Web 卡看不见。

§2 修复（PR #257，决策 #332）
- 卡列改为与 CLI `show qos policies` 同源：`名称 / CIR(bps) / 绑定（接口:in|out）`；
  绑定文本逐条 `接口:in|out`（无绑定时如实「—」）；CBS 只在详情页展示。
- 绑定文本抽 `qosBindingsText` 单源，列表卡与详情页共用（防两处再漂移）。
- **字段级守护** `internal/api/ui_qos_card_fields_test.go`：从 ui/app.js 提取 QoS 卡行与
  共用 formatter 消费的全部 `q.*`/`b.*` 属性，逐个对照 openapi QosPolicy schema（含
  bindings.items）；解析器带自校准（已知字段缺失即失败）。**负向验证**：往卡行注入 `q.type`
  守护即红（报「这就是 R110-1 的复刻」），还原后回绿。
- openapi 未改（bindings/bound_interfaces 已是 #331 契约）；规格书附录 A 追加决策 #332；
  AGENTS.md 决策条数 233→234。`make check` 全绿（app.js `node --check` 通过）。
