### §3.1 fulltest 首跑 265/35/23 的**全数判读（单一根因，非产品缺陷、非本分支引入）**

- 根因（`/tmp/cli-test/full.log` 完整输出实锤）：

  手工单条复现同样被拒。
- **现场变化的 rev 级证据**：配置库 `config_revisions` 中，紧随当日 12:01 基线轮之后，
  **rev 206→207 的唯一差异 = management 段新增 `address: "192.168.155.129/24"`（12:11:39 CST，
  当日 walk 会话的走查动作）**；12:01 基线轮跑在同一现场但**尚无此声明**（当时 management 只有

## §5 本轮教训（入册）

1. **「套件全绿」依赖现场前置，回归前先对前置**：同一代码 09:52/12:01 两轮 297/0，17 小时后
   同套件 35 红——变量不是代码而是**现场（管理地址声明）**。判读路径固定为：读完整输出落点
   （`/tmp/cli-test/full.log`，stdout 只有 head -8 截断）→ 先看 S2-pre 的 commit 结论。
2. **产品守卫会把「工具假设」照出来**：FR-CFG-011② 的重叠守卫在套件写死业务地址 + 现场管理
   同网段时**必然拒绝**；处置是撤声明（文档化前置）而非松动守卫——守卫语义正确。
3. **撤/恢复管理地址的正确形态**：`commit confirmed` 提交 + **配置模式内再 `commit` 确认**
   （裸 `commit` 在配置模式外会报「脚本在第 1 行停止」）；`delete system management ip address`
   带值（R152-1 形态）。
4. **底座硬约束要按事实校**：`corelist-workers/coremask` **必须同时给 main-core**（VPP 拒绝启动，
   实锤 `cpu_config: main-core must be specified…`）；且 main-core 必须在隔离核池内（产品校验）。
   恢复声明时两条约束都要过。
5. **状态展示含「管理态」与「链路态」两层**：VPP 里 ens 口 `State=down` 是管理员态
   （`vppctl set interface state … up` 即恢复），与链路速率为两回事——排障先分清。
