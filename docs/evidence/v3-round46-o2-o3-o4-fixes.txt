## O-2（数据面缺陷）vhost-user vNIC + `vlan access` 时主接口不在 BD ⇒ blackholed

### 结论：**已修好功能**（不是只做告警兜底）。VTR 路线经真机实证**不可用**，改走「父接口直接入 BD」。

### 一、VTR 路线不可用（真机实证 + VPP 头文件）

任务书建议先查证 VPP 的 `l2_interface_vlan_tag_rewrite` 语义再定。查证结果是**该路线在本底座不可用**：

```
# VPP 26.06-release，逐个接口类型试 pop1
$ vppctl set interface l2 tag-rewrite vh-vm1-nic0 pop 1
set interface l2 tag-rewrite: vlan tag rewrite is not compatible with interface
$ vppctl set interface l2 tag-rewrite tap0        pop 1   → 同上报错
$ vppctl set interface l2 tag-rewrite bvi0        pop 1   → 同上报错
$ vppctl set interface l2 tag-rewrite vxlan_tunnel0 pop 1 → 同上报错
```

机制（反汇编 + 头文件）：`libvnet.so.26.06` 的 `l2vtr_configure` 在 0x18b7da..0x18b7e9 处取接口的
hw_class 与 `ethernet_hw_interface_class` 比较，**不相等即返回 0xffffffb9（= -71 INVALID_INTERFACE，
见 /usr/include/vnet/error.h:55）**。vhost-user / tap / BVI / VXLAN 各自注册自己的 hw class，故
**全部虚拟口都不支持 L2 VTR**（只有物理 ethernet 口才可能支持）。

`l2_vtr_op_t` 取值已从头文件 `/usr/include/vnet/l2/l2_vtr.h:15-25` 核实（0=DISABLED,1=PUSH_1,
2=PUSH_2,3=POP_1,4=POP_2,5=TRANSLATE_1_1,…），与仓库里 `VlanTagRewriteReq.Op` 的注释一致。
**产品 production 代码里 VTR 至今零调用是对的**——这条路在本底座走不通。

### 二、采用的修法（`internal/orchestrator/network/l2.go`）

`desiredMembers` 的 `case vs.VlanAccess > 0` 拆成两支：

| 端口形态 | access 处理 | 理由 |
|---|---|---|
| **虚拟口**（`port.Vnf != ""` / `port.Container != ""`） | **父接口直接挂进 BD**（`SwInterfaceSetL2Bridge(portIdx, …)`） | 虚拟口对端（guest/容器）**侧上无 tag**；BD 内本就是无 tag 域，与物理口 access 子接口在 BD 内的形态一致 |
| **物理口**（`port.Interface`） | **保持原样：建 VLAN 子接口** | FR-NET-011 已真机验证的路径，动它会引入回归 |

语义等价性说明（写进代码注释）：「L2 交换机 = 一个 bridge-domain，BD 内流量一律无 tag；物理口的
access 子接口正是『入向 pop、出向 push』。虚拟口入向本来就无 tag，父接口直接入 BD 即『无 tag 进 BD』
——两种端口落在**同一份无 tag 域**，可互通。」
**如实边界（代码注释与文档都写明）**：若 guest 自己给帧打了 tag，该 tag 会原样进 BD（产品不做逐 tag
收敛）；guest 侧要带 tag 请用 `trunk <vlans>`。

新增两个助手：
- `isVirtualPort(port)`：判据用**端口来源字段**（`Vnf`/`Container`），不用接口名前缀（前缀只是命名约定）。
- `dropLegacyAccessSubif(...)` + `forgetSubif(...)`：清掉**升级前留下的**虚拟口 access 子接口
  （`<父口>.<vlan>`，按确定性名字查，查到才摘 BD + 删接口，失败不阻断提交）。不清理的话 BD 里会长期
  留一个无人管理的 `vh-….100`（FR-NET-016 同族问题）。

#### blackholed 计数的正确解读（重要，避免误判）

修复后 `show errors` 里 `null-node / blackholed packets` **仍会缓慢增长**，但**与 VLAN 无关**。
用 `vppctl trace add vhost-user-input` 逐包追踪（修复后）：

```
$ vppctl show trace
 Packet 1: vhost-user-input → ethernet-input → l2-input → l2-learn
           → l2-fwd  sw_if_index 1 … bd_index 1 result [0x700000003, 3]     ← 已进入 BD 1
           → ip4-input → ip4-lookup → ip4-drop  (fib:1 adj:0)
           → error-drop → null-node: blackholed packets
   包内容: IP4 10.10.10.100 -> 169.254.169.254 TCP:41048 -> 80
```
即：帧**正常经 l2-fwd 在 BD 内转发**，随后因目标是 `169.254.169.254:80`（cloud-init 的 metadata
服务）而**在 IP 层**被丢——那是 **O-4 的另一半**（guest 在找 metadata），不是 L2 黑洞。
修复前则是帧**根本进不了 l2-fwd**（父接口不在任何 BD，rx 全计 drops）。

| `contrib/scripts/cli-fulltest-phase4.sh` | 非破坏性段加两条（无锁时如实回「无持锁会话」，幂等可反复跑） |

**引擎侧零改动**：只用既有导出方法 `Engine.Sessions()` / `Engine.Discard()`。强制释放「别人的」锁走的是
**以该持锁会话的身份调用 `Discard`**——引擎按匹配键（holder + 稳定会话 ID）判定，因此精确落到那把锁上，
且复用引擎唯一的「释放锁 + 清编辑态」路径（不另造第二份释放逻辑，避免与 sweep/接管语义漂移）。
**`internal/config/engine.go` 未改。**

**为什么执行器落在 `cli_config_unlock.go` 而不是 `requestSystem`**：`requestSystem` 在
`cli_compute_oper.go`（另一个会话在改的文件）；且它语义上是「编排动作分发器」，而本命令只动配置引擎的
编辑锁、与底座编排无关。故在 `execOper` 的 `case "request"` 处**先拦一次**，命中即返回。

### 真机证据（nfvis-vm）

**① 无锁时如实说（两种形态都不谎报）**
```
$ nfvis-cli … -c "request system configuration unlock"
（无持锁会话，无需释放）
$ nfvis-cli … -c "request system configuration unlock force"
（无持锁会话，无需释放）
```

**② 脏锁现场：非 force 从「别人的会话」执行 → 正确拒绝并指向 force，且不动那把锁**
（用 REST `PUT /configuration/candidate` 造一个 `admin@api` 的脏锁）
```

Holder       Session                              User   Acquired          Last-Activity     Dirty

提示：本会话持锁用 discard 释放；如锁由其它会话持有，可用
  request system configuration unlock force
强制释放全部编辑锁（**会丢弃持锁会话未提交的 candidate**）。      ← 读视图给出照做路径（O-3 原文诉求）

$ request system configuration unlock
```

```
$ show configuration sessions
（无持锁会话）

$ configure / set system hostname qa-desc / commit      ← 新会话立刻取锁并提交成功
```
