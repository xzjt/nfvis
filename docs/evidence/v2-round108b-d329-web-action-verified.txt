§1 复验设计（针对 round108 失败原因）
round108 未验成的原因：造占用后**60s 巡检先把池自动收敛**，点击效果无法归因。
本轮先尝试「用持有者把多余页钉住使其无法自动收敛」，但 `echo 800` 抬高 2M 池**未生效**（nr 仍 768），
持有者只是吃掉了池内既有空闲页（在用 533→565、空闲 235→203）⇒ 没有「多余页」可钉，该路径不成立（如实登记）。
改用**确定性可归因**的**空操作路径**：池已与声明一致时点击，服务端的如实回文只可能由这次点击产生。

§2 实机操作与结果（Browser Use）
- 打开 `#/system/pools`（admin，super-user）：大页池卡显示 `1G 2 2 1 1 0 一致` / `2M 768 768 533 235 0 一致`，
  与 CLI/REST/sysfs 一致；「回收空闲的多余页」按钮可见
- **点击该按钮 → 中危确认弹窗**（内容与设计口径逐条相符）：
  「只回收「内核实际高于声明、且**空闲**」的多余大页；**在用页一律不动**（不会抽走 VPP/VNF 正在用的大页）／
   收敛目标 = 已声明值；本动作**不改变**声明值／写后会**回读内核实际值确认**；未收敛（被在用页挡住）会**如实报出谁在占用**／
   可回退：把声明值调回去并重启…／**对应命令（只读回显）：`request system hugepages reclaim`**」+ 取消/确定
- **点「确定」→ 对话框关闭，界面呈现服务端如实回文**：结果 JSON 可见
  `"reasons": ["实际 2 不高于声明 2，无需回收"]`（1G）与 2M 对应条目 ⇒ **空操作如实报告** ✓
- 结论：**Web 端动作链路（按钮 → 中危确认 → 服务端 → 界面呈现）端到端成立**，round108 的待补项关闭。

§3 如实登记（仍未取得的一项，附带原因）
**「有真实多余页时、在浏览器里点回收并观察成功收敛」**仍未取得可归因证据——原因是
① 60s 巡检会先把空闲多余页收敛掉（竞态）；
② 本轮用来钉住页的持有者方案因「抬高未生效」而不成立（抬高失败的原因未深究，可能与宿主可用连续内存/产品侧钉值相关）。
该项的**功能等价路径**已由 CLI + REST + sysfs 独立事实源端到端验证（见 round108 §1③⑤）；
Web 侧的**状态呈现**（四方数字/状态/口径说明）与**动作链路**（本轮）均已验。
如需补齐「Web 成功回收」这一格，建议办法：先用持有者把**全部空闲页**吃满再抬高（即 free=0 而实际>声明），
此时巡检无法收敛、状态稳定，再在浏览器里释放一个持有者后立刻点回收。
