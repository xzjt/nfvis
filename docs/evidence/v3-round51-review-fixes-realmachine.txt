### 2.4 安装包 Version（在任何文件操作前拒绝）

dpkg 自身对 `Version` 有语法约束（不以数字开头、含 `/` 或引号者连包都打不出来），
故用 dpkg **接受**的形态 `1.0..2` 构造：

```
$ dpkg-deb -f /tmp/badpkg.deb Version   → 1.0..2   （dpkg 接受）
$ request system software add /tmp/badpkg.deb --yes
%% 软件包 badpkg.deb 的 Version 字段不可用（版本号含非法字符: "1.0..2"）：拒绝安装
   （该值会被拼进归档路径与以 root 执行的安装脚本）
```

副作用核对：`/var/lib/nfvis/software/` 目录清单**前后逐字相同**（未归档、未安装），
仓库外无 `*escaped*` 文件；`dpkg -l nfvis` 仍为 `3.0.33~r51`。

> 如实登记：`1:../../../r51-escaped` 这类"能折叠出路径"的形态**被 dpkg 自己拒绝**
> （`version number does not start with digit`），即真实安装路径上不可达；本项防护的价值在于
> 自定义/手工投递的包以及 dpkg 未来放宽语法的情形——校验仍在**任何文件操作之前**执行。

## 3. #525 L3 VLAN 子接口（本轮真机抓到 3 条本轮引入的缺陷并修掉）

### 3.1 缺陷 A：组合语句形态无别名（文档推荐写法不可用）

首验时按命令树枚举出的规范序提交：

```
set virtual-switches vs-l3v l3-interface ens224 vlan 100 ip address 10.99.0.1/24
→ %% 配置中不存在字段 "l3_interface"（多为关键字位置有误或语句不完整…）
```

根因：别名表按 token 数**精确匹配**，而模型把 l3-interface 落在 `l3_interfaces`（复数数组），
组合形态（9 token）无规则命中 ⇒ 落到通用树遍历必然报"字段不存在"。
分步写法（`… vlan 100` 一条、`… ip address …` 一条）当时是通的——即"文档推荐写法不可用"。

修法：新增 `aliasL3InterfaceVlanThen`，把组合形态裁成"先 vlan、再交给既有叶子别名"两步，
与分步写法**逐字等价**（用例 `TestFixR51CLIL3InterfaceVlanCombinedForms` 直接比较两棵候选树
`reflect.DeepEqual`）。红-绿已验：撤掉该别名后用例红的报错就是真机那句
`配置中不存在字段 "l3_interface"`。

### 3.2 缺陷 B：子接口创建漏 `ExactMatch`（永远配不上地址）

第二次真机提交：

```
%% 底座下发失败（已补偿）: 下发失败 vrf[vs-l3v]: 接口 ens224 配地址 10.99.0.1/24:
   VPPApiError: Unsupported (-126)
```

**底座语义实证**（绕过产品直接 vppctl）：

```
$ vppctl set interface ip address ens224.100 10.99.0.1/24
set interface ip address: sub-interface without exact-match doesn't support IP addressing
$ vppctl create sub-interfaces ens224 200 dot1q 200 exact-match     → 成功
$ vppctl set interface ip address ens224.200 10.97.0.1/24           → 成功
$ vppctl show interface address ens224.200 → L3 10.97.0.1/24
```

即 VPP 26.06 **只允许 exact-match 子接口配地址**；L2 的 trunk 端口早就带着该标志
（`l2.go desiredMembers`），L3 侧此前漏了 ⇒ 该特性自诞生即不可用。
修法：L3 创建带 `ExactMatch: true`（用例 `TestFixR51N8L3SubifRequiresExactMatch`）。

### 3.3 缺陷 C：按名复用不验标志（复用历史坏壳）

第三次真机提交**仍然** -126。现场核对：

```
$ vppctl show interface | grep ens224        → ens224.100 存在
$ vppctl set interface ip address ens224.100 10.92.0.1/24
  → sub-interface without exact-match doesn't support IP addressing
```

原因是 VPP 里那个 `ens224.100` 是**早先版本（v3.0.33）建的、没带 exact-match 的壳**，
产品按确定性名查到它就复用了 —— 只把创建改成带标志**不够**，复用路径同样要验。
修法：`L3Client.SubifExactMatch`（读 `interface_dump` 的 `sub_if_flags`，
是运行态事实、跨重启成立）；不是 exact-match 就删掉重建，问不出来则不复用也不删。
用例 `TestFixR51N9StaleNonExactMatchSubifRebuilt` / `TestFixR51N9HealthySubifStillReused`。

### 3.4 修好后的真机证据（重装 deb 后）

## 7. 一次 VPP SIGSEGV 的归因（如实登记，未完全定裁）

过程中出现**一次** VPP 崩溃（`vpp[192193] received signal SIGSEGV`，栈顶为
`mfib_entry_get_fib_index` ← `mfib_table_entry_delete_index` ← `ip6_mfib_table_destroy` ←
`mfib_table_bind` ← `ip_table_bind` ← API 消息处理），随后 nfvisd 侧 `sw_interface_set_table_reply`
超时、VPP 重连（`NRestarts=1`），并导致一次 90s 登录超时（管理面被 VPP 断连卡住）。

- **触发时点**：正是"先装了**未含 ExactMatch 修复**的 r51 首版，提交 vlan 子接口 → 地址下发
  `-126` → 补偿删表"的那一轮（04:52）。该路径的特征是"子接口建成但配不上地址，随后补偿删表"。
- **A/B 尝试**：在 **v3.0.33 发布件**上重复同一链路（REST 写 `vlan` 字段 → 提交 → `-126` → 补偿）
  6 轮、以及在修复版上做 10 轮 vlan 子接口建/删（含 IPv6 地址）、用 vppctl 直接构造
  "非 exact-match 子接口 + v6 表 + FIB 项 + 表切换/删除"等 10 余种形态，**均未再复现**。
- **结论（如实）**：崩溃**未能稳定复现，因而无法把责任钉到某一行**；已确认的是：
  ① 触发它的那条业务路径（非 exact-match 子接口 → 配地址失败 → 补偿删表）在修复版上
  **已不存在**（创建带标志、复用验标志、坏壳重建），实测 0 次崩溃；
  ② 崩溃栈全部落在 VPP 26.06 的 `ip_table_bind`/mfib 销毁路径上，属**底座**代码，
  我方只发了一条 `set interface table` 类请求；
  ③ 这是一条**应该继续观察**的项：若后续在"删表/切表与接口归属变更交错"的现场再见到，
  应先抓 `vppctl show ip6 table` + 崩溃栈再判定。
