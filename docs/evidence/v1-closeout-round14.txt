报告来源  用户提问：「`set interfaces` 时 Tab 应该显示已被 DPDK 接管的网卡吧？」

问题（真机实测，1.1.3）
--------------------------------------------------------------------------------
`<ifname>` 的动态候选一律取自 committed 配置的 `interfaces[].name`，与真实端口无关：

  · 空配置时 kind=ifnames → []，`set interfaces ?` 只剩占位符 <ifname>；
  · 把 ens224 写进配置并 commit 之后，候选才变成 ["ens224"]。

宿主实况：内核网卡只有 docker0/ens160/lo/virbr0（**ens192/ens224 已绑 DPDK，内核中已无
netdev**），VPP 中有 ens192/ens224/local0。于是候选**既漏真又含假**：漏掉唯一可用的那批
（VPP 里的口），却会列出根本不存在的名字——`set interfaces no-such-nic9` 在 set 阶段返回
[ok]、commit 才失败「接口在 VPP 中不存在」。

而**有效取值域本就是 VPP 接口清单**（这点由实测反证）：`set interfaces ens224`（已接管）
commit 成功，`set interfaces ens160`（内核有、未接管）commit 失败。语句树自身的注释
（`set vpp dpdk dev <ifname>` 标注「须为 DPDK 物理口，FR-CFG-011⑧」）与契约
（`show interfaces physical` = 「DPDK 物理口」）也都指向同一结论。

修复（附录 A #83）
--------------------------------------------------------------------------------
① 新增运行态端口清单 `network.L2Network.VPPIfnames()/KernelIfnames()`：
   VPP 侧 `sw_interface_dump`（剔除 VPP 内置 local0、排序去重）；
   内核侧取 `/sys/class/net/<n>/device` 存在的物理口（据此排除 lo/docker0/virbr0；
   已接管的口本就不在内核）。经 `api.PortInventory` 接口注入、`cmd/nfvisd` 装配。
② 候选按语义拆三个 kind：`vpp-ifnames` / `kernel-ifnames` / `ifnames`（并集），
   13 处 `<ifname>` 各自声明正确来源（对照表见契约 §5.3）。
③ 清单不可用时退化为「仅关键字」，**不退回「已配置接口名」**。
④ `show interfaces physical` 空态改为列出运行态端口。

判读方法
--------------------------------------------------------------------------------
§1 用 kind 模式（`GET /cli/candidates?kind=…`）与 `-c` 命令；§2 用 CLI 自身的 `?` 候选
（非 TTY 路径，与交互式同一套补全引擎）。两侧都只给「新二进制」的结果——修复前的结果
即上文「问题」段所列（已单独实测记录）。

§3 结果判读（逐条）
================================================================================
① 用户报告的那处（`set interfaces <TAB>`）：空配置下即列出 `ens192 ens224`
   —— 正是已被 DPDK 接管、内核里已不存在的两个口。修复前此处**零候选**。
② 语义分侧正确：
   · `set system management interface` → `ens160`（内核网卡；管理口不得是数据面口）
   · `set vpp dpdk dev` → `ens192 ens224`（数据面口）+ 全局默认关键字
   · `set protocols lldp interface` → `ens192 ens224`
   · `show interfaces physical` → `ens192 ens224`
   · `request sriov create-vfs` → `ens160`（PF 在内核侧，sysfs 路径 `/sys/class/net/<pf>/device/sriov_numvfs`）
   · `request interfaces`（enable/disable 与 bind-dpdk/unbind-dpdk 动作混合）→ 并集 `ens160 ens192 ens224`
③ 不再「自产自销」：把运行态不存在的 `ghost9` 写进配置并 commit 之后，
   vpp-ifnames 仍只有 `["ens192","ens224"]`——已配置名不再是候选来源（负例）。
④ show 空态现在给出口清单与下一步，用户不必再靠 `vppctl` 带外发现端口名。

§5 已知影响与未做
================================================================================
1. **行为变化**：`<ifname>` 的候选不再来自配置，而来自运行态。
   - 好处：空配置即可发现端口名；不再列出根本不存在的名字。
   - 代价：**VPP 未接入时接口名将没有任何动态候选**（退化为仅关键字，符合契约 §5.3）。
     这是有意的——回退到「已配置名」正是本决策要修的错误来源。
   - `set system management interface <ifname>` 由「无候选」变为「内核网卡候选」（此前完全无补全）。
2. 未做（如实登记）：
   - **接口名的取值仍未在 set/commit check 阶段校验**：`set interfaces ghost9 …` 仍会返回 [ok]，
     直到 commit 下发时才失败「接口在 VPP 中不存在」（有补偿回滚，报错明确）。是否把校验前移到
     `commit check` 需单独决策——「先声明端口、绑定后再提交」是被支持的流程（决策 #72：绑定属安装期动作），
     直接拒绝声明会挡住该流程。
   - `request interfaces <ifname>` 同层动作语义不同（enable/disable 作用于 VPP 口，
     bind-dpdk/unbind-dpdk 作用于内核口/PCI 地址），当前取并集；要按动作区分需改语句树结构
     （参数位置在动作之前），未在本轮范围内。
   - `vpp-ifnames` 只剔除 VPP 内置 `local0`（按名字）；子接口（如 `ens192.100`）、
     vhost-user/memif/tap 等虚拟接口仍会作为候选出现——它们确实在 VPP 中且可被 `show`/`clear`，
     但对 `set interfaces` 无意义。按接口类型过滤需给 `SwIfInfo` 补 `IfType`（govpp dump 有该字段），
     涉及告警路径共用的结构体，留待后续。
   - SR-IOV 相关候选未真机验证（本环境无 PF/VF，与既有登记一致）。
