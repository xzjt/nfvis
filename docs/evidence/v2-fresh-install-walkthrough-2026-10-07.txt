§7 本轮发现（**新登记，均未修**）
------------------------------------------------------------------
【发现 1（中）】`pending_restart` 重启后假阳性
  现象：**每次整机重启后**，`show vpp` / `GET /vpp/status` / Web 总览「待重启生效」均报 **是**，
        而 VPP 实际正按 committed 配置运行。三次复现（向导后重启、改 1G 后重启、本轮专测重启）。
  独立事实源：同一时刻 `grep main-core /etc/vpp/startup.conf` = 5、`corelist-workers 4`；
        `show vpp threads` = vpp_main core 5 / vpp_wk_0 core 4；`vppctl show memory` 主堆 2M。
        即配置**已生效**，只有手动 `request vpp restart` 才把它清成 no。
  根因（代码级）：`internal/orchestrator/network/vpp.go` 的 `Manager.appliedHash` 是**进程内**字段；
        `PendingRestart` 在 `appliedHash==""` 时把「有 vpp 配置」一律判为待重启。
        启动路径 `cmd/nfvisd/main.go` 只 `vppMgr.EnsureRunning`（拉起已存在的 startup.conf），
        **不调用 `SetApplied`** ⇒ 重启后 appliedHash 恒空 ⇒ 恒报待重启。
  影响：误导操作者做无谓的 `request vpp restart`（数据面中断）；CLI 与 Web 两面可见。
  建议方向：启动/接入成功后，若磁盘 startup.conf 与 committed vpp 段一致则 `SetApplied`（或持久化 applied 哈希）。

【发现 2（中）】storm-control 与 port-security 同接口冲突未检测（L2 分类槽争用）
  现象：同一接口（ens192，已是某 L2 交换机成员）同时配 `storm-control broadcast` 与
        `port-security mac` —— **提交被接受**（rev 11），读视图 `show interfaces ens192 detail`
        两者都显示「在数据面」（storm 报「分类表 #6」、portsec 报「ACL 在场且已绑定」）；
        但接口 L2 入向分类槽**实际只挂着 portsec 的 macip 表**（掩码 `000000000000ffffffffffffffff…`）。
  暴露路径：随后删 `storm-control` 提交报
        `%% 底座下发失败（已补偿）: 接口 ens192 的 L2 分类槽被非本产品对象占用（表 24，掩码 …）：
          风暴抑制无法收敛，请先清除该占用（例如 VPP 侧的其它分类表绑定）` —— 占用者其实是**产品自己**
        port-security 的 macip 表。**先删 port-security 再删 storm-control，则两者都干净删除**（rev 16/17）。
  根因（代码级）：`internal/model/validate.go` 的 `checkPortSecurity` 只校验「与 L3 接口 ACL 的 macip 槽互斥」，
        **不校验与 storm-control 的 L2 分类槽争用**；两者在 VPP 侧都绑接口 L2 入向分类槽
        （storm 走 classify，portsec 走 macip，单槽互斥）。`internal/orchestrator/network/storm.go` 的
        `Dataplane` 读视图按**进程内登记** `e.tableIdx` 报表，不核对该表是否真的挂在槽上 ⇒ 读视图失真。
  影响：限速（安全相关）静默不生效；删除时给出去向错误的报错文案。
  建议方向：提交期**双向拒绝**（同接口 storm-control 与 port-security 不能并存，照 #340/#389 的互斥先例），
        或按 VPP 能力改为表链共存；读视图按实况（AttachedL2Table）而非登记报表。

【发现 3（低）】Web 诊断页 ping 缺 `vrf` 参数（与 CLI/REST 不对称）
  现象：Web「诊断」页 ping 表单只有 目标/次数/源地址/IPv6，**没有 vrf**；
        对 VRF 内目标（如 guest 192.168.99.100）执行即 `Failed: no egress interface`（0 发包）。
  对照：同一目标 `POST /diagnostics/ping {"host":"192.168.99.100","vrf":"vr-vs-lan"}` **3/3 通**；
        CLI `ping … vrf vr-vs-lan` 亦通。即 REST 与 CLI 都支持 vrf，**只有 Web 表单未暴露**。
  影响：Web 用户无法 ping 任何 VRF 内对象（VNF/交换机域——最常见场景），且错误文案未提示 vrf 选项。
  建议方向：诊断页表单加 vrf 输入（REST 契约已具备，纯前端接线）。

【发现 4（低）】`set system dns proxy server` 触发「vpp 变更需 request vpp restart」与 pending_restart
  现象：仅改数据面 DNS 代理（`set system dns proxy server <ip>`，DNSProxyServers 属 `cfg.Vpp`）
        即报 `警告: vpp 变更需 request vpp restart` 并置 pending_restart=yes。
  对照：生成器输出的 startup.conf **恒含** `punt { socket /run/vpp/punt.sock }`（决策 #345），
        全新安装首启即在场 ⇒ 启用/停用代理**并不需要**重启 VPP。
  影响：误导性重启提示（同发现 1 的观感面）。决策 #345 的用意是升级首启提示，但在新装实例上是假阳性。

【观察 5（低）】资源池页两个「空闲」数字语义不同、同名并列
  现象：Web「资源池」页首表 `页大小/总数/已分配/空闲` 显示 2M `768/0/768`，而同页「大页池」段
        （与 `show system hugepages` 同源）显示 2M `空闲 235`（VPP 缓冲占用 533）。
        两处「空闲」含义不同（前者=未分配给 VNF 的声明量，后者=内核空闲页），易误读。
