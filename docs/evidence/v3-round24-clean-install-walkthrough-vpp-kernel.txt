§1 首装与基线（真人路径）
--------------------------------------------------------------------------------
1.1 sh /root/nfvis-v3.0.11.run -y → 载荷校验 → **自检 18/0/0**，退出码 0；一次性口令
    **dtsP1GXPNqIX-9gk@Aa1**（nfvisd 首启行；后续全部命令用它）。安装期提示 2M 池已由 vpp 包
    一次性 sysctl 形态给出 1024 页（既定口径，重启后按基线）。
1.2 重启（安装期基线 default_hugepagesz=2M hugepagesz=1G hugepages=1）→ nfvis/vpp active。
1.3 真 pty 向导（/root/wizard-3.0.11.log；在 REPL 内注入 wizard，问答一次通过）：
    vpp / 隔离核 2-5 / VPP 主 5 工 4 / **1G=3 / 2M=768** / 低延迟 false → 计划含
    `set vpp memory hugepage-preference 2M`（2M 池在场自动取 2M）→ commit **rev 3**；
    `request system kernel apply` 写入 GRUB 片段 + fstab。⚠️ 本轮为**双池标准布局**
    （承接 R12-1 用户裁定：目标部署同时用 1G+2M 双池），非 3×1G-only。
1.4 重启。cmdline：`default_hugepagesz=2M hugepagesz=2M hugepages=768 hugepagesz=1G hugepages=3
    isolcpus=2-5 nohz_full=2-5 rcu_nocbs=2-5 irqaffinity=0-1 intel_iommu=on intel_pstate=disable
    iommu=pt`。**两个 hugetlbfs 挂载点均在位**（/dev/hugepages 1G + /dev/hugepages-2M 2M，
    [#459 回归]）；1G 池 nr=3。
1.5 管理口首次声明 + 系统基线（一次脚本）：**无 guard 直接 commit 被正确拒绝**
    （「%% 管理口地址/网关变更必须以 commit confirmed 提交」，RC=1）→ `commit confirmed 2` +
    同会话 `commit` 确认 → **rev 4**。宿主四处实读（[#424 回归]）：hostnamectl=nfvis-lab /
    timedatectl=Asia/Shanghai CST / /etc/chrony/sources.d/nfvis.sources=pool ntp.aliyun.com /
    resolved drop-in DNS=223.5.5.5 114.114.114.114。
    ⚠️【观察 R24-O4，§7】声明后 nfvisd 仍监听 `*:443`——`ResolveListenAddr` 只在**启动装配期**
    调用，管理口地址收敛到下一次 nfvisd 启动才生效（journal 的「已收敛为管理口地址」行在其后出现）。
1.6 业务口：`request interfaces ens192 bind-dpdk`（不带 --yes）被正确拒绝（提示补 --yes）→
    `--yes` ×2（ens192=0000:0b:00.0、ens224=0000:13:00.0 → vfio-pci）→ `set interfaces <口>
    description` + `set vpp dpdk dev <口> rx-queues 1` → **rev 5** → `request vpp restart` →
    vppctl 见 ens192/ens224 均 up（startup.conf 重生成含 dpdk 双 dev 段）。
1.7 夹具入库：`request images upload` alpine（vm-image 178.1 MiB）+ ct.tar（container-image；
    **[#447 回归]** 回显「内嵌 tag 为 alpine:3.20；Docker 侧引用为 ct.tar:latest（与内嵌 tag
    不一致时已自动重打）」，docker images 里用户 tag alpine:3.20 完好 + ct.tar:latest 新增）。

      dev='vnet0'/> <model type='virtio'/>`、vnet0 入 vs-lan 桥（[#455] freshness 生效）。

§7 缺陷/观察登记（R24-A~E + 观察；逐条独立事实源）
--------------------------------------------------------------------------------
R24-A【低-中低·读数面三面不一致】CLI `show virtual-switches`（列表与 `<名称>` 详情）只覆盖
  BD（L2 运行态）：① 列表不显示 L3 交换机（REST GET /virtual-switches 与 Web 页均显示全部
  含 L3；命令全表 §87 声称「全部虚拟交换机摘要」）；② 对已配置且 VPP 中存在的 L3 交换机名
  报「% 虚拟交换机 vs-wan 在 VPP 中不存在（show virtual-switches 看运行态列表）」——文案与
  事实相悖（它在 config 里、也在 vppctl `show ip table` 里，只是没有 BD）。建议：L3 名指向
  `show vrfs <n>`；列表补 L3 条目或注明「仅 L2（BD）」。
  （现场：§2.4；佐证：REST JSON 两台 vs-lan/vs-wan、Web 三台。）
R24-B【低·事件 payload 拼写】`vnf-state-changed` 事件的 state 在 stop 时为 **"stoping"**
  （`action+"ing"` 对 stop 拼错；start→"starting"、restart→"restarting" 正常）。SSE 帧现场：
  `{"name":"ct-1","resource":"container-functions","state":"stoping"}`（§2.22）。消费方若按
  该值匹配将被固定拼写绑定，建议更正为 "stopping"（或改为与其它事件一致的过去式/枚举）。
R24-C【中低·内核侧校验缺口（R13-C 同族）】VPP-only 形态「**vNIC 作 L3 接口**」
  （`set virtual-switches <n> l3-interface vh-<vm>-<nic> …`，#172 文档化 NAT-inside 形态）
  在**数据面切换**提交期被放行；内核侧对该名字无解析 ⇒ 恢复收敛如实报 3 条告警
  （`RECOVERY_IFACE_MISSING vrfs/vs-nat` + `RECOVERY_UNCONVERGED vnf-a`（域组装失败：
  「vNIC nic1 缺少接入的虚拟交换机」）+ `RECOVERY_UNCONVERGED dns-proxy`），且该 VM 在内核侧
  **start 必失败**。R13-C 已把「vNIC 接 type=l3 交换机」提交期硬拒——本形态（l3-interface
  引用 vNIC）漏网。建议：数据面切换/内核态提交期对「l3-interface 指向 vPNIC 派生名」前置
  拒绝或给照做路径（删除该 l3-interface 并改用可内核化的形态）。如实边界：产品**不静默**
  （3 条告警齐全），缺的是提交期可发现性。
R24-D【中低·运行中负载形态变更的可发现性】两态同根（域/设备形态变更须 stop+start，而
  `restart` 的 ACPI 语义不重定义是**文档化**的、`start` 对已运行负载是**幂等空操作**）：
  ① 给运行中 VNF **新增 vNIC**（rev 17）→ commit 成功（VPP 侧端口已建、持久域已更新）但
  运行中 guest 拿不到设备；`restart` 也不生效；唯一线索 `VNF_PORT_DOWN`（其括号解释
  「VM 未启动或已关机」与事实相反——VM 正在运行）。
  ② 数据面**切换**后仍在运行的 VM 保持旧形态域（vhostuser；VPP 已停 ⇒ guest NIC 实际断连），
  对其 `start` 为幂等空操作；唯一出路 stop+start（本轮实测：stop+start 后域重建为 bridge/
  vhostuser 各一次，均正常）。
  建议：提交期检测「声明 vNIC 集合 ≠ 运行域 vNIC 集合」与「运行域的接入形态 ≠ 当前数据面」
  并给提示（如「运行中，需 stop+start 生效」）；顺带把 VNF_PORT_DOWN 的括号文案改准确。
R24-E【低·监听地址运行期不收敛】管理口**首次声明**（live commit）后 nfvisd 仍监听 `*:443`
  ——`ResolveListenAddr` 仅启动装配期调用（main.go 装配段），「管理面仅监听管理网卡」
  延迟到下一次 nfvisd 启动生效（journal 的收敛行在其后出现；round13 记录即重启后场景）。
  建议：管理口地址变更提交成功后触发一次监听重解析（或至少在提交输出/读视图注明
  「监听地址将于服务重启后收敛」）。

观察（如实登记，非缺陷或口径）
R24-O1【口径】`request capture stop` 之后的中断切换：**租约不跨数据面切换**（teardown 按

R24-O2【口径】RECOVERY_UNCONVERGED（非 IFACE_MISSING 类）在事实修复后**保留到下一次整体
  重放**才消解（#333 明示「保守保留不猜」）——本轮实测：nic1 修好后该警在 vpp restart

R24-O3【低】内核数据面下**未绑定的 ACL** 也在 nft netdev 表里建链（未挂载、不影响流量；
  绑定后另建 `bind_<口>` 挂载链）。建链/挂载两段语义未见文档说明，如实登记。
R24-O4【文档账目】命令全表 `set port-mirroring <n> source vnf …` 行与 §490 汇总仍标

R24-O5【口径】改 user-data **文件**后重跑 `set` 报「值未变化」（模型存路径文本），但

R24-O6【lab artifact 复现】guest DHCP 广播经 BD 泛洪与 VMnet8 外置 DHCP 竞速：本轮两次
