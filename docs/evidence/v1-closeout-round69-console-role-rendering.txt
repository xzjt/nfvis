===== V1 收尾第六十九轮：控制台按角色渲染（实现设计 §8，决策 #145）=====
日期：2026-09-24；分支 `feat/console-role-rendering`（main `d029800` 之上）；契约未改（前端呈现层 + 路由表加一个标记字段）

----- 1. 起因 -----
决策 #141 的设计文档 §8 写明「导航与按钮按 class 渲染：`read-only` 只见只读页（总览/列表/详情/审计/告警/诊断的
只读部分），写按钮**隐藏**（不是禁用）」，骨架计划的验收清单里也有「只读账号看不到写入口」——但 round57~64
的十四刀只做了功能接线，**这条一直没实现**。round66 的浏览器实测把它登记为未裁项：read-only 账号登入后
**21 个导航项与各页写按钮全部可见**（含「恢复出厂」「重启主机」「安装升级包」）。

----- 2. 处置（三件套：标记 → 隐藏 → 导航/说明）-----
**① 标记**：写/运维入口一律带 `data-write`。
- 静态入口在 `index.html` 打标 **74 处**（接口详情 DPDK/SR-IOV、内核基线、用户与口令、证书、配置事务、
  VM 快照与串口、镜像导入三模式、QoS/SPAN 删除、运维动作、诊断 ping/traceroute/清零、抓包）；
- 动态生成的入口经新增的 `wbtn()` 助手生成 **15 处**（用户行内改/删、配置表单增删清空、历史回滚、
  VM/容器行内与详情动作、快照回滚删除、镜像删除、**归档下载 ×2**）。
- **判据**：会改状态的动作 + CLI 里声明为 O/S 的动作（因此 `ping`/`traceroute`/抓包/串口/快照/镜像导入/
  `清除已恢复告警`/**归档下载**（决策 #143 起为 super-user 级）都算写入口；刷新/查看/详情/看差异/
  `列出 core dump` 等纯读控件**不**打标）。

**② 隐藏**：`app.js` 的 `applyRole()` 按登录响应的 `user.class` 切 `<body>` 的 `role-readonly` 类；
`style.css` 一条规则整类隐藏：`body.role-readonly [data-write] { display: none !important; }`。
用 CSS 而不是逐个 JS 隐藏——页面是**每次重渲染**的（轮询/SSE/切页/详情页 Tab），CSS 规则不会漏掉后生成的元素。

**③ 导航与说明**：`routes.json` 给 6 条"写页"加 `write: true`（`#/config`、`#/system/users`、`#/system/tls`、
`#/system/kernel`、`#/ops/actions`、`#/ops/capture`），`router.js` 对只读角色**不列**这些导航项；
深链/收藏落到写页时由 `#role-notice` 说明「本页的动作入口已隐藏、需要什么账号」（**只读页上不出现**这条——
首版实现漏了这一点：说明元素在每个页面都显示（内容为空），验收时发现并改成 `body.role-readonly.role-notice-on`）。

----- 3. 边界（有意）-----
- **隐藏不是安全边界**：服务端按 class 判定（决策 #141 前提⑥）；界面只是不把"点下去必被拒"的入口摆出来。
- `class` 取不到时按**全量**渲染（fail-open）——界面是呈现层，服务端才是边界；也避免登录响应缺字段
  把 super-user 自己的入口藏掉。

----- 4. 守护 -----
`TestUIConsoleRoleGating`（`internal/api/ui_routes_test.go`）查形状与存在性：
① 写页标记必须与**期望集合逐条一致**（多标/漏标都报错，且每条写明"为什么这页是写页"）；
② 三件套每个环节在源码里真的存在：`data-write` 数量下限 60、`#role-notice`、CSS 隐藏规则、`applyRole`、
`wbtn`、导航过滤（`r.write && isReadOnlyRole()`）、`renderRoleNotice`。
`make check` 全绿；两个前端自校准（分级确认 / 配置口令）仍全绿（它们以"无角色类"运行 = 全量渲染）。

----- 5. 浏览器验收（决策 #141 口径：每个功能都要在浏览器里真的操作一遍）-----
环境：本分支构建的明文实例（`/tmp/nfvisd-ia`）+ 生产库副本；宿主经 SSH 隧道用内置浏览器黑盒操作。

**只读账号 `ro-role`（18 条路由逐页巡检）**：
| 断言 | 结果 |
|---|---|
| 导航项数 | **15**（21 项里滤掉 6 条写页）✓ |
| 每页**可见写入口**（`[data-write]` 且可见） | **全部为 0**（其中 VM 页 6 个、VM 详情 10 个、镜像 9 个、接口详情 6 个、历史 50 个、诊断 7 个、运维 32 个等都被隐藏）✓ |
| 写页（6 条） | 显示说明条「当前账号是 read-only：本页（X）的动作入口已隐藏…」✓ |
| 只读页 | **不**显示说明条 ✓ |
| 归档「下载」按钮 | 不可见（决策 #143 起下载是 super-user 级）✓ |
| JS 错误 | 0 ✓ |

**super-user 正向对照**：导航 **21** 项；写入口可见（VM 6/6、运维 32/32、配置 48/51（3 个是本来 `hidden`
的提交态按钮）、用户 11/11、内核 2/2、抓包 5/5）；归档「下载」15 个可见；说明条全隐藏；`<body>` 无 `role-readonly` 类 ✓。

**验收抓到并当场修掉的两处漏标**（正是"浏览器里真的走一遍"才看得见的那类）：
1. `清除已恢复告警`（`request alarms clear` = **O** 级写动作）当时未打标 → 只读账号仍能点（点下去被服务端拒）；
2. **归档「下载」**（`GET /system/backup/{file}`，决策 #143 起 = **super-user** 级）当时未打标 →
   只读账号仍能看到下载入口（点下去 403）。

----- 6. 未做/登记 -----
**operator 级粒度**：本决策只区分"只读 vs 有写权限"，**operator 仍会看到声明为 super-user 的入口**
（如「恢复出厂」「重启主机」「安装升级包」「归档下载」），点下去被服务端如实拒绝。
要做 operator 级隐藏需要每个动作的**权威 class**，而这份权威在服务端（REST 端点注册时的 class / 命令树的
`RequiredClass()`）——界面自己维护第二份权限表**必然漂移**（本仓库对"两处同源"的教训很多）。
建议下一步：由服务端提供一个"当前账号可做哪些动作"的读物（例如把各动作的 `min_class` 随 `/system/permissions`
一类端点下发），界面据此渲染——**需契约先行**。
