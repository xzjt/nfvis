四条修复（附录 A #82）
--------------------------------------------------------------------------------
① 实例名位置的解析优先级（根因）：`applyTokens` 状态机里「身份取值数组」（pendingIdentity）
   在关键字匹配**之前**消费身份，而「实例参数」（pendingArrKey：`login user`、
   `virtual-switches`…）却在**之后**（原「2b」分支）。于是容器关键字之后的第一个 token
   若与子关键字同名，就被短路成关键字，而 `cur` 仍停在祖先容器上 → 取值写到祖先层级。
   修复前 dump 出的错树（临时测试）：
     user password Admin@123 → {"system":{"login":{"password":"Admin@123","user":[]}}}
     user class super-user    → {"login":{"class":"super-user","user":[]}}
   → 模型收到不存在的键，报 `json: unknown field "password"`。
   修：把实例参数的身份消费提到关键字匹配之前（与 pendingIdentity 同构）。
② 报错口径（NFR-005）：`fromJSONTree`/`validateTreeJSON` 直接 `%v` 了 Go 的 json 报错。
   修：`describeTreeErr` 译为中文并给出下一步。
③ `system login user` 静默建号：4 token 的 `user <n>` 把子关键字当用户名。
   修：别名层子关键字同名守卫（保留名取自 schema 树；仅 set）+ 5 token 形态的缺名提示。
④ 交互 REPL 退出不收尾：EOF 直接返回、超时只吊销 token，都不释放配置模式/候选锁。
   修：`Session.Teardown()`（discard → exit → Logout），EOF 与超时两条路径都调用。

§4 已知影响与未做
================================================================================
1. **行为变化（可能影响已有配置/脚本）**：
   - `system login user` 的实例名**不得再与子关键字同名**（`password`/`class`）——这原本会
     静默建出一个无口令账号，现改为拒绝并提示正确写法（仅 `set`；`delete` 不受限，
     以便清理历史上误建的账号）。若确需以此类名字建号，只能经 REST 或 `load`。
   - 从配置模式退出（Ctrl-D / 空闲超时 / 管道结束）时现在会**自动丢弃未提交 candidate**
     并打印一行 `candidate 已丢弃，会话锁已释放`。此前是「静默什么都不做」——把候选锁
     留给下一次登录（决策 #82④ 的根因）；现在改为显式收尾，代价是已提交后退出也会看到该行
     （服务端 discard 不区分有无变更，此处选择了「宁可多提示，不可静默丢变更」）。
   - 语句报错文案由「语句未映射到模型（键名不匹配或类型不符）: <Go json 原文>」改为中文口径；
     依赖该原文做匹配的脚本需同步调整。
2. 未做（如实登记）：
   - 实例名优先消费只修了「同名 token 落在实例名位置」的情形；**通用的**「实例名与子关键字
     同名的歧义」仍只在 `system login user` 一处显式拒绝，其余 subtree（如
     `virtual-switches ports`）按「名字优先」解释（树正确、语义明确，但不会提示用户
     可能想输入关键字）。是否推广为全局守卫（并因此禁止一切与子关键字同名的实例名）
     留待后续决策。
   - `?`/Tab 候选列表在实例名位置仍把 `<name>` 与子关键字并列展示，未标注「须先给名字」；
     本次只改了报错，未改补全展示（补全展示改动面更大，建议单独一轮）。
   - NFR-005 仅覆盖「树 → 模型」解码报错；其它路径（如校验错误、govpp/libvirt 底层报错）
     的中文化未在本轮范围内。
