# v3 round17 证据：`unbind-dpdk` 不带 `to-driver` 不自动重探——**行为已确认（非缺陷，口径收口）**

日期：2026-10-11　　分支：`v3`　　VM：nfvis-lab（`3.0.10~dev7`）

## 0. 一句话

round12/13 登记的「`unbind-dpdk --yes`（不带 `to-driver`）报『内核未自动重新探测原生驱动』，
而 round10 同操作自动交还 vmxnet3——**环境时序 vs 代码变化待确认**」，本轮**在真机上确定性地确认**：
**本平台内核就是不会自动重探**。产品的行为（**先试** unbind → 清 `driver_override` → `rescan`，
失败则**如实报错并给可照做提示**）**是正确的**；round10 的「自动交还」在本平台**不可复现**。
该项按**口径**收口（**非产品缺陷、无代码改动**，决策计数不变）。

## 1. 实验（把「内核行为」与「产品行为」分开量）

前提：先 `systemctl stop vpp`（**否则 sysfs 写会阻塞**——见 §3 的教训），确保没有进程持有该设备。
设备：ens224 = `0000:13:00.0`（VMware vmxnet3，`0x15ad:0x07b0`，当前绑 `vfio-pci`）。

```
# ① 从 vfio-pci 解绑
$ echo 0000:13:00.0 > /sys/bus/pci/drivers/vfio-pci/unbind        # 成功
$ basename $(readlink /sys/bus/pci/devices/0000:13:00.0/driver)   # → (无驱动)

# ② 清掉 driver_override（这是产品解绑路径里做的同一步）
$ printf '\n' > /sys/bus/pci/devices/0000:13:00.0/driver_override # 返回 0
$ cat /sys/bus/pci/devices/0000:13:00.0/driver_override           # → (null)  ← 确认已清

# ③ 触发 PCI 重新探测（产品解绑路径里的同一步）
$ echo 1 > /sys/bus/pci/rescan                                    # 成功

# ④ 观察 3s（每 250ms 采样一次）
3s 内仍无驱动（内核未自动探测）
```

⇒ **内核侧不会自动把该设备交还 vmxnet3**。因此产品在解绑后回读不到驱动、进而报出
「已解绑 …，但内核未自动重新探测原生驱动；请显式指定：`request interfaces <pci> unbind-dpdk
to-driver <驱动名>`」——**这是对事实的如实陈述**，不是产品缺陷。

补充事实（同一现场）：`modinfo vmxnet3` 的 alias 与设备 modalias 在**语义上**是匹配的
（`pci:v000015ADd000007B0sv*sd*bc*sc*i*` ↔ `pci:v000015ADd000007B0sv000015ADsd000007B0bc02sc00i00`），
即**模块在位、alias 也对**，内核在 `rescan` 后仍未 probe 该设备——把结论限定为「内核行为」而非
「模块/alias 缺失」，避免把平台行为误判成产品问题。

## 2. 产品的既有实现（读代码核对，与上面对得上）

`internal/orchestrator/network/dpdkbind.go` 的 `Unbind`：
`从当前驱动 unbind` → `清 driver_override` → `Rescan()`（**产品侧确实调了**，构造函数里
`b.Rescan = 写 /sys/bus/pci/rescan`）→ **按 PCI 回读驱动**；仍为空才返回可照做的错误。
另：`cmd/nfvisd/dataplane.go` 的 `readbackDPDKDriver` 在解绑后**轮询最多 3s** 等驱动出现——
即产品对「内核探测有延迟」也留了余地，本实验把这点排除掉了（3s 内确实没有）。

## 3. 顺带确认的一条守卫必要性（教训入册）

第一次实验我**没先停 VPP**，直接对仍被数据面持有的设备写 sysfs：`driver_override` 的写**阻塞**
（ssh 会话挂住、`override` 值保持 `vfio-pci` 不变），实验因此作废。
这正是产品那条守卫存在的理由——`request interfaces ens224 unbind-dpdk` 在口仍属数据面时**拒绝**：

```
%% 接口仍被数据面占用：ens224 当前仍在数据面中。请先在配置里删除它的 DPDK 声明与接口声明，
   执行 request vpp restart 并确认它已不在数据面，然后再解绑——直接解绑会让该口悬空，
   并可能阻塞后续命令
```

⇒ 守卫的文案（「可能阻塞后续命令」）与实测一致，**不是危言耸听**。

## 4. 现场还原（已核对）

`request interfaces ens224 bind-dpdk --yes` → `已绑定到 DPDK 驱动，当前驱动 vfio-pci`；
`request vpp restart` → `已按 committed 配置重启 VPP`。终态：nfvis/vpp **active**、
ens192/ens224 在 VPP 中 **up**、1G 池 **3**、hugetlbfs 挂载点 **2**、无业务对象、
告警仅既有 `HUGEPAGE_POOL_ORPHAN`。

## 5. 未做（如实登记，非本项范围）

**可用性改进（候选，未立项）**：产品在**绑定那一刻**是知道原生驱动的（`Bind` 里的 `cur`，例如
`vmxnet3`），却在切到 vfio-pci 后把它丢了，于是解绑时只能靠操作者报出驱动名。把 `cur` 记进
**本机运行态**（与决策 #100 的 `dpdk-bindings.json` 同类），解绑时按「显式 `to-driver` >
绑定时记录 > rescan 试探」取值，就能让 `unbind-dpdk` 无需操作者报驱动名。
**本轮不做**的原因：① 本次确认的结论是「产品现有行为正确」，改动属**增强**而非修缺陷；
② 需要新增一份持久状态（**牵动 `format-data` 受管清单与备份/恢复语义**）或做 modalias 匹配
（优先级规则脆弱）——两案都值得单独定裁。已登记进 `docs/v3待做.md` §七末。
