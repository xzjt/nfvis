# v3 round23 证据：抓包会话跨 nfvisd 重启收敛（决策 #466）

日期：2026-10-12　　分支：`v3`　　VM：nfvis-lab（Ubuntu 26.04.1 / 内核 7.0.0-34 / 6 核 7 GB）
装的是**交叉编译换装二进制** `3.0.10~dev12`（原件备份 `/root/bin-dev11/` 与 `/root/bin-orig-r13/`）。

## 0. 一句话

round22 §5 登记的边界（「会话登记只在进程内：冻结数据在盘上却无登记、在抓 trace 静默残存」）
本条收口：会话落**持久记录**（`/var/lib/nfvis/capture-sessions.json`，start/冻结/取走三处同步）、
**冻结即暂存**（工作文件搬进导出目录隐藏位，不依赖 /tmp）、**启动收敛**（重启前冻结/在抓的会话
经 VPP 补 `pcap trace off` / 内核孤儿判定后重建为「已停止待导出」，读视图标 `recovered=true`），
无记录残件归档为可见 pcap。真机 A/B（VPP + 内核两数据面）逐条实锤，改前改后同场景对照。

## 1. 改前复现（`dev11` 未修版，同一台机器）

**A：冻结 → nfvisd 重启（数据失联 + 下一次 start 静默删除）**

```
$ /root/nc -c 'request capture start interface ens192 count 500'
已开始抓包（接口 ens192，count 500（环形缓冲深度，超出丢最旧））。
# ← 宿主发 4 类广播 ICMP（VMnet8 共享 L2，ens192 上真的有帧）
$ /root/nc -c 'request capture stop'
已停止抓包（数据已保留，待导出）。
$ ls -l /tmp/rxtx.pcap
-rw-r--r-- 1 root vpp 384 Oct 12 02:05 /tmp/rxtx.pcap        ← 冻结数据在盘上

$ systemctl restart nfvis
$ /root/nc -c 'show capture'
capturing: none                                              ← 改前：登记没了（读视图全盲）
$ /root/nc -c 'request capture export'; echo EXPORT_RC=$?
%% 当前无抓包会话（提示：当前既无进行中的抓包、也无待导出的数据；请先 request capture start）
EXPORT_RC=1                                                  ← 改前：数据取不回（仍在盘上）
$ ls -l /tmp/rxtx.pcap
-rw-r--r-- 1 root vpp 384 Oct 12 02:05 /tmp/rxtx.pcap

$ /root/nc -c 'request capture start interface ens192 count 50'   # 再开新会话——成功
$ ls -l /tmp/rxtx.pcap
ls: cannot access '/tmp/rxtx.pcap': No such file or directory     ← 改前：旧冻结数据被静默删除
```

**B：在抓 → nfvisd 重启（trace 静默残存，产品读视图全盲）**

```
$ /root/nc -c 'request capture start interface ens192 count 50'   # 不 stop
# ← 宿主发广播 ICMP
$ systemctl restart nfvis
$ /root/nc -c 'show capture' | head -2
capturing: none                                                   ← 改前：产品不知道还有会话
$ vppctl pcap trace off
Write 4 packets to /tmp/rxtx.pcap, and stop capture...            ← 铁证：trace 一直在 VPP 里缓冲
$ ls -l /tmp/rxtx.pcap
-rw-r--r-- 1 root vpp 384 Oct 12 02:06 /tmp/rxtx.pcap
```

另一条同轮的底层实验（`vppctl` 直测，设计前核实能力前提）：`pcap trace off` 在未启用时回
`dispatch trace already disabled...` RC=0（无害、可幂等补打）；**对已启用的 trace 再次 start
只回 `dispatch trace already enabled...` RC=0（静默 no-op）**——即若不收敛，「产品登记了新会话
而 VPP 还在按旧 config 抓」会是**假成功**（这正是必须收敛的另一半理由）。

## 3. 改后验证（`dev12`，内核数据面，同一台机器）

切换（手册 §7.0 口径，**只重启服务、不整机重启**）：

```
printf 'configure\nset system dataplane kernel\ncommit\nexit\n' | nfvis-cli -f -   # revision 268
systemctl restart nfvis      # nfvisd 自动停 vpp.service（systemctl is-active vpp → inactive）
/root/nc -c 'request interfaces ens224 unbind-dpdk --yes'                     # 按 #464 记录自动交还 vmxnet3
/root/nc -c 'request interfaces ens192 unbind-dpdk to-driver vmxnet3 --yes'   # 无记录：显式 to-driver
ip -br link show → ens192/ens224 UP（vmxnet3）
```

**B3a：内核冻结 → 重启 → 恢复 → export**

- start 后 `pgrep -a tcpdump` 可见 `tcpdump -i ens192 -w /tmp/.nfvis-cap-…part -c 50`；记录带 `pid`。
- stop 后：**tcpdump 已终止**（pgrep 空）、/tmp 工作文件搬走、暂存位
  `.nfvis-cap-…part` = **2704 B**、记录 `stopped=true`。
- 重启后 journal「已恢复重启前的抓包会话（接口 ens192…）」；`show capture` 标「重启前会话已恢复」；
  export 取到 **2.6 KiB** pcap；记录清除、无 tcpdump 残留。

**B3b：内核在抓 → 重启（孤儿 tcpdump 态）**

- start（不 stop）→ `pgrep -a tcpdump` = 孤儿 pid 6892；宿主发广播 ICMP。
- `systemctl restart nfvis` 后：**pgrep 空**；journal「已恢复重启前的抓包会话（接口 ens192，
  数据待导出 nfvis-cap-ens192-20261011T181116Z.pcap）」；export 取到 **9.5 KiB** pcap（tcpdump
  在 SIGTERM 时刷写了它捕获的全部帧）；记录清除、/tmp 无残留。
- **如实更正一处口径**：本机 unit 是默认 `KillMode=control-group` ⇒ `systemctl restart` 的
  停单元阶段会把 nfvisd 的整个 cgroup（含它 exec 出来的 tcpdump）一起 SIGTERM，
  **孤儿进程往往活不到新进程收敛**；新进程实际走的是「进程已死 → 直接重建」路径。
  「按记录 pid + 命令行核对身份后终止」的终止分支为**防御性**覆盖（nfvisd 脱离 systemd 手工运行、
  或将来改 KillMode 时才可达），由单测钉住；旧注释里「孤儿会继续写」的前提在本部署下不成立
  （systemd 已代收），但**旧代码确实没有恢复登记**这一点不变。

**B3c：无记录残件 → 归档为可见 pcap**

```
$ printf 12345678 > /tmp/.nfvis-cap-ens192-20261012T001500Z.pcap.part
$ systemctl restart nfvis
{"msg":"抓包重启收敛","结果":"无记录残件已归档为 nfvis-cap-ens192-20261012T001500Z.pcap
 （源 /tmp/.nfvis-cap-ens192-20261012T001500Z.pcap.part）"}
$ ls -l /var/lib/nfvis/captures/nfvis-cap-ens192-20261012T001500Z.pcap → 8 B（源名归档）；/tmp 已清
```

切回（同一口径，只重启服务）：

```
set system dataplane vpp + commit → systemctl restart nfvis
request interfaces ens192/ens224 bind-dpdk --yes → request vpp restart
show vpp → dataplane: vpp / connected；show interfaces physical → 两口 dpdk up
```

## 8. 教益（入册）

1. **能力前提必须在真机上量**：`pcap trace` 对已启用 trace 的重复 start 是**静默 no-op（RC=0）**——
   只读代码/文档都看不出，是设计启动收敛（而不是「放任 + 让 start 兜底」）的决定性证据。
2. **systemd 的 cgroup 会替我们收尸**：`KillMode=control-group` 下 `systemctl restart` 会顺带
   SIGTERM 掉 nfvisd exec 的子进程——「孤儿 tcpdump 继续写」的前提在本部署下不成立；
   登记恢复才是真缺口（如实更正旧注释的口径）。
3. **测试隔离要连「扫描范围」一起隔离**：新增的启动收敛会扫描工作位（/tmp 与导出目录）——
   单测夹具若不注入工作目录，会把共享系统临时目录里**其它测试**留下的 `.part` 搬进本用例
   导出目录（首跑即踩到，`SetWorkDir`/`SetSessionsFile` 注入后干净）。
