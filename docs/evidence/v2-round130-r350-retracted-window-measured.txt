NFViS v2 真机测量记录 round130 —— R129-2 的开机忙窗口测量；决策 #350 撤回依据
====================================================================
日期：2026-10-03；环境：nfvis-vm（2.0.0~dev45 = PR #280 分支构建，未合并）。

§0 结论
**决策 #350（启动期 libvirt 连接 3 次有界重试）被真机测量否决，按「不留假功能」整体不合并（撤回，
决策号保留）**。立项前提「开机 libvirt 不可服务窗口 < 32s」不成立：三次开机实测窗口 ≈ **65s / >32s /
~90s**——固定启动期重试预算被 systemd TimeoutStartSec（90s）顶死、无法覆盖真实窗口，加预算会把
「启动超时 → 重启循环」风险重新引入（round129 根治过的问题不得回归）。R129-2 保持未收口，
根治路线（启动后异步接入 + Provider 动态换装）另行立项（#351），取舍留契约审查。

§1 实现（PR #280 分支，未合并）与验证 ② —— 机制本身成立
- `boundedRetry` 纯函数（次数/退避/回调语义，6 个单测全绿，make check 全绿，决策条数 252）；
- 真机降级路径回归（验证②）：libvirtd 全停 + 假死监听（nc -lU 收一连接即退）→ restart nfvis ⇒
  journal 三次尝试如实留痕（attempt 1 吃满 10s；attempt 2/3 拨号即拒——监听已消失）⇒ 12s 后
  仍降级 + `COMPUTE_UNAVAILABLE`、服务 active 无超时循环。**重试机制按规格工作**。

§2 决定性测量（验证①，重启测试）—— 窗口远超重试预算
三次开机（同一机器、同一配置：sem-vm 声明 autostart=true ⇒ libvirt autostart ⇒ 1G 大页 prealloc）：
| boot | nfvisd 起跑 | 放弃时刻 | libvirt 可服务时刻（virsh 首次 OK） | 窗口 |
|---|---|---|---|---|
| dev44（单次尝试，20:15 版） | 19:27:21 | 19:27:31（1×10s） | ≤19:28:30（首测即通，精确值未取） | ≥65s |
| dev45（boot2） | 20:15:55 | 20:16:27（3×10s+2s） | ≤20:18:0x（复查时通） | >32s |
| dev45（boot3，探针测量） | 20:19:28 | 20:20:02（3 次全败） | **20:20:56**（探针 t=41s，探针起点 ≈ boot+50s） | **≈86~91s** |
- 探针：`timeout 3 virsh -c qemu:///system list` 每 5s 一次；boot3 时间线：libvirtd Started 20:19:25 →
  sem-vm scope 20:19:30 → nfvisd 起跑 20:19:28、20:20:02 放弃 → virsh 首通 20:20:56。
- 期间 nfvisd 行为全部符合 #349/#350 规格：尝试留痕、最终降级、`COMPUTE_UNAVAILABLE`、
  VPP 由 #348 自动拉起（「发起拉起（不等待）」）、单次启动无循环。**R129-2 的痛点原样保留**：
  开机后 `show virtual-machine-functions` State「-」、VM 动作拒绝，需人工 `systemctl restart nfvis`。
- 附：窗口期间 virsh 3s 探针也可能「可服务但慢于 3s」——对客户端（10s 上界）同样不可用，
  不影响结论（nfvisd 的 10s×3 全部失败是直接事实）。

§3 预算算术（为何不能加次数）
启动序列同步等待项最坏合计：libvirt 重试 + Docker 探测 10s + 启动期 AppArmor 15s + DB/引擎等数秒。
3 次尝试（32s）时合计 ~60s（余量 30s）；若 5 次尝试（54s）则 ~84s——余量 <6s，慢盘/慢启动即触发
90s 超时循环（round129 根治过的故障模式）。⇒ **在「启动序列同步等待」的框架内无解**，
必须改架构：READY 不再被 libvirt 阻塞（异步接入）。

§4 根治路线（待立项 #351，两案取舍留契约审查）
- **路线 a：启动后异步接入**——启动序列对 libvirt 只做单次短界尝试（或零等待直接降级），READY 快速
  达成；后台有界重试（预算不再受 TimeoutStartSec 约束），连接成功后**动态换装 Provider**
  （`vmAPI`/applier/15s 巡检等消费方须经并发安全的持有层转发），`COMPUTE_UNAVAILABLE` 随接入成功消解。
- **路线 b：运行期巡检自动重连**——15s 巡检发现降级即尝试重连（同一换装问题；节奏受巡检周期限制）。
- 两案共同点：都需要 Provider 动态换装的并发安全设计（这正是 v2待做 R129-2 预先标记的风险点）；
  Docker 是否同治留审查。
