§2 真机抓到的两条缺陷（均已修 + 复验）

BUG-1（Critical，真机才暴露）—— boot-order 映射为 libvirt 非法设备值
  真机错误：`XML error: Invalid value for attribute 'dev' in element 'boot': 'cd'.`
  libvirt 合法 `<boot dev>` 值为 `fd|hd|cdrom|network`（无 `cd`；「dc」也不能用单个值表达——
  顺序由多个 `<boot>` 元素表达）。**既有 ISO 路径同样用了 `cd`（latent bug）**，且单元测试把
  错误值也钉死了（自洽但错）。修复 ea6bf36：hd→`hd`、cd→`cdrom`、dc→[`cdrom`,`hd`]（顺序即优先级）、
  iso 默认→`cdrom`；枚举保持 hd|cd|dc 不变。复验：场景 3/4 的 dumpxml `<boot dev='cdrom'/>`。

BUG-2（Critical，真机+真浏览器才暴露）—— WS↔VNC 代理用 TEXT 帧，noVNC 收不到
  `golang.org/x/net/websocket` 的 `Handler` 默认以 `TextFrame` 发送；noVNC 设 `binaryType=arraybuffer`
  且 `new Uint8Array(e.data)`，TEXT 帧给出的是 JS 字符串 ⇒ 长度 0（浏览器亦会以 1007 关闭非 UTF-8 文本帧）
  ⇒ 握手永不完成、黑屏。单元测试被 x/net 客户端「不看 opcode」掩盖。修复 36dd440：VNC 处理器设
  `ws.PayloadType = websocket.BinaryFrame`，并加**帧 opcode 红-绿测试**（修前 0x1、修后 0x2）。
  复验：场景 6 浏览器实测帧缓冲 1280×800（若仍 TEXT 不可能到这一步）。
