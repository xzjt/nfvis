§2 真机四维验证（**逐条，独立事实源**）
--------------------------------------------------------------------------------
【#400】pending_restart（构建 2.0.0~dev176）
  ① 建立已应用态：`request vpp restart` → 落点 `/var/lib/nfvis/vpp-applied.hash` 生成
     （`4fa54788…`）、`show vpp` → `pending_restart: no`。
  ② **整机重启后**（关键项）：`show vpp` → `pending_restart: **no**`；
     **独立事实源** `show vpp threads` → `vpp_main core 4 / vpp_wk_0 core 3`，与 committed
     （`set vpp cpu main-core 4` / `corelist-workers 3`）**逐项一致** ⇒ VPP 确在跑 committed 配置。
     （修复前：同一现场恒报 `yes`，三次复现。）
  ③ 仅改 DNS 代理：`set system dns proxy server 223.5.5.5` + commit → **无**「vpp 变更需 request vpp
     restart」警告、`pending_restart` 保持 **no**（对照修复前会误报）。
  ④ 真实 vpp 段变更：`set vpp cpu main-core 4 / corelist-workers 3` + commit → 提交输出**有**警告、
     `pending_restart: **yes**`；`request vpp restart` 后 → **no**（方向正确，未变成恒 no）。
  ⑤ 单元：`TestPendingRestartFalseAfterReboot` / `…IgnoresDNSProxyOnlyChange` /
     `…OnRealVppSectionChange` / `…OnGeneratorShapeChange`（保 #345）+ `TestAppliedStoreRoundTrip` +
     `TestEngineCommitNoVppRestartWarningForDNSProxyOnly`；红-绿（暂回旧实现逐项按预期失败）。

【#401】storm × portsec 互斥与读视图
  ① 前置：`set virtual-switches vs-t type l2` + `ports 1 interface ens192`（rev 101）。
  ② **同一提交**同时配 storm + portsec ⇒ 提交期拒绝，**两条**错误同时给出（storm 侧 + portsec 侧），
     文案含两者、机理与照做路径。
  ③ storm 单独提交 ⇒ 成功（rev 102）；随后**再加** portsec ⇒ 第二次提交被拒（rev 未推进）。
  ④ 删 storm ⇒ **一次提交成功（rev 103）**——对照修复前必撞「L2 分类槽被非本产品对象占用（表 24…）」
     （占用者是产品自己的 portsec macip 表）而整批失败。
  ⑤ portsec 单独提交 ⇒ 成功（rev 104）。
  ⑥ 单元：`TestValidateStormControlPortSecMutex` / `TestValidatePortSecurityStormMutex` /
     `TestStormDataplaneSlotHeldByForeignTable` / `TestCLIStormControlReadViewNotAttached`；红-绿逐项。

【#402】Web 诊断页 ping 带 vrf（Browser Use）
  ① 前置：`vs-lan`（l2 + BVI 192.168.99.1/24 + port ens224）+ VNF `vnf-b`（vhost-user 挂 vs-lan，
     user-data 置静态 192.168.99.5）→ 邻居表出现 `192.168.99.5`、CLI `ping 192.168.99.5 vrf vr-vs-lan`
     **3/3 通**。
  ② Web 诊断页出现 `VRF（可选，目标在 VRF 内时必填其名，如 vr-vs-lan）` 输入框（`diag-vrf`）。
  ③ 填 目标 `192.168.99.5` + VRF `vr-vs-lan` + 次数 3 → 执行 ping →
     **`3 sent, 3 received, 0% packet loss`**（回显 `116 bytes from 192.168.99.5 … ttl=64`）。
     对照修复前：同一目标在 Web 上只能报 `Failed: no egress interface`（0 发包）。
  ④ `traceroute` 仍不传 vrf（REST 明文拒绝、不静默降级）。

【#403】资源池页「空闲」语义
  Browser Use 打开 `#/system/pools`：首表列头 = **`页大小 / 总数（声明） / 已分配（VNF） / 可分配（VNF）`**，
  表下出现口径说明行「本表是配置口径：「可分配（VNF）」= 声明总数 − 已分配给 VNF 的页数；与下方「大页池」段
  的「空闲」（内核空闲页…）口径不同，两处数字不必相等」——与下方「大页池」段的 sysfs 口径不再同名混淆。

§4 如实边界 / 未覆盖
--------------------------------------------------------------------------------
- **不做表链共存**（#401）：VPP classify 与 macip 单槽，链式共存风险高，另立项才做；本轮取「提交期双向拒绝」。
- **#400 的形状哨兵是人工约定**：将来生成器新增/删除 startup.conf 段时须同步改 `startupShapeSentinel`
  （注释已写明；若忘记，升级后不会提示首次重启）。
- **#402 的 guest 前置插曲（非本轮缺陷）**：运行中的 VNF 改 `cloud-init user-data` 后**不重定义 domain**
  （seed ISO 未挂），须 **stop → start** 才生效；本轮据此调整操作顺序后 guest 正常。此为既有行为，
  未在本轮登记为新缺陷，**如实记录**供后续评估。
- 四套件**未在本轮 dev176 构建上复跑**（本轮为定向修复 + 逐条真机四维；发布前四套件基线沿用 round176 走查的
  2.0.0 结果：fulltest 273/0/20、语义 26/0/3、lifecycle 21/0/3、pty 10/10）。
