§4 数据面切换 vpp → kernel（带对象切换）
--------------------------------------------------------------------------------
4.1 `set system dataplane kernel` 首次 commit **被两条校验正确拒绝**（逐条给照做路径）：
    ① `vrfs[vs-nat].l3_interfaces[vh-vnf-a-nic1]`：内核侧不存在该 vNIC 派生设备名（[#469]）；
    ② `virtual_machine_functions[vnf-a].interfaces[nic1].virtual_switch`：VNF 虚拟网卡不能接入
    `type=l3` 交换机（内核侧 L3 交换机不建桥）。按指引删 nic1 + vs-nat（**一次提交**）→ **rev 33**。
4.2 `set system dataplane kernel` → **rev 34**（提交输出如实提示需重启服务、运行中负载需
    stop+start/restart、vpp 段配置不生效）→ `systemctl restart nfvis` → **VPP 被自动停掉**
    （inactive），`show vpp` 如实报 `dataplane: kernel / connected: no / last_error: 未使用 VPP`。
4.3 DPDK 交还（[#464 保持]）：`unbind-dpdk --yes` ×2（不带 to-driver）→ 均按

§7 缺陷登记（本轮新增）
--------------------------------------------------------------------------------
R40-1（低）**内核数据面下诊断 `vrf` 参数的错误消息自相矛盾 + Web 占位提示写错写法**
  现象：内核数据面下 `ping <host> vrf <名>` 只接受**交换机名**（`vs-lan`）/ VRFs 条目名 /
  L3 交换机名；传内核设备名 `vr-vs-lan` 时报
  `%% ping … 未通: 未知的 VRF/交换机 "vr-vs-lan"；本机已知的内核 VRF 设备: vr-vs-lan、vs-wan`
  ——**同一句里既说「未知」又把 `vr-vs-lan` 列为已知设备**。REST `/diagnostics/ping` 同文案。
  Web 诊断页的 `#diag-vrf` 占位提示也写「如 vr-vs-lan」，照提示填必然 502。
  影响：操作者按错误消息/占位提示照做**一定失败**，且错误消息把人往更错的方向引。
  根因（代码级）：`internal/orchestrator/netkernel/diag.go` 的 `KernelVRFDeviceName` 只按
  **配置对象名**（交换机名 / VRF 条目名）解析，不认内核设备名；而 `knownKernelVRFDevices`
  返回的是**设备名**列表（`vr-<交换机名>`、`<vrf 名>`），两者口径不同源。
  **功能本身正确**（用交换机名 `vs-lan` 可通，CLI 与 REST 均 3/3），属**口径/文案缺陷**。
  **修法候选**（择一，待定裁）：
  ① 错误消息改列**可接受的写法**（交换机名 / VRF 名）而不是内核设备名，并把 `vr-…` 明确标为
    「内核设备名，不接受」；② 同时接受 `vr-<交换机名>` 形态（解析时若首段为 `vr-` 则回退到
    同名交换机）——更贴操作者直觉，但需定义 `vr-` 前缀与交换机名重名的歧义；
  ③ 仅修 Web 占位提示为「如 vs-lan」（最小改动，但错误消息仍误导）。
  **同轮核实**：CLI 命令全表对 `vrf` 参数的描述为「`vrf` 经 VPP 路径」，未点明内核侧写法；
  `docs/NFViS-用户手册.md` 只写「缺省归入专属 VRF `vr-<交换机名>`」（描述数据面设备名，正确）。
  证据：`/root/walk/`（VM 侧）、本文件 §3.6 / §4.16。
