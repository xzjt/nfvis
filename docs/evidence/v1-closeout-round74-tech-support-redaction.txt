----- 1. 先查证：归档里到底有什么、哪些成员含秘密 -----

生成实现 `internal/system/techsupport.go:Generate`（tar.gz，逐节写入），数据来源在
`cmd/nfvisd/main.go` 的装配处注入。逐成员判定（**裁决的依据**）：

| 成员 | 内容（来源） | 含秘密？ |
|---|---|---|
| `version.json` | nfvis 版本、hostname、VPP 版本/连接态、内核 release | 无 |
| `config.json` | `engine.Committed()` —— **完整 committed 配置** | **有：`system.login.users[].password_hash`（PBKDF2 原文）**；另有 cloud-init 的 `user_data`（自由文本）与 `ssh_keys`（公钥，非秘密）；`system.api.tls.cert_file/key_file` 是**路径**不是密钥正文 |

| `README.txt` | 生成时间/版本/分节清单 | 无 |

**落盘权限（改前现状）**：`os.Create(path)` → 0666&~umask ⇒ **0644**；目录 `MkdirAll(t.Dir, 0o755)`
⇒ `/var/lib/nfvis/tech-support` 0755 ⇒ **同机任意用户可读到口令哈希**（与决策 #70/#77 的「导出件 0600」
口径不一致；配置备份归档是 0600、其目录 0755）。

----- 2. 裁决：脱敏 + 保持 read-only（不提到 super-user）-----

两条路的取舍（判据按交接文档给的规则）：
- 含秘密的成员**只有「顺带放进去的配置快照」这一类**（`config.json`；日志那一处是产品自己打印的
  一次性口令，可定点剥掉）；
- **脱敏不破坏诊断用途**：复现问题要的是配置结构与运行态，不是哈希；真要**可恢复**的完整配置，
  本就有配置备份导出（决策 #143：super-user、**有意**不脱敏）；
- 提到 super-user 会挡掉「operator 生成诊断包（`request system tech-support generate` 声明 **O**）
  → 自己下载送支持」的现场流程，且**并不减少**暴露面——支持人员手里的包同样不该有哈希。

⇒ **在归档里脱敏，下载保持 ClassReadOnly**；生成端 class 不变（仍 O）。需要完整配置的现场口径写进
契约与手册：诊断包里的配置是**脱敏视图**，不能用于恢复。

| 文件 | 改了什么 |
|---|---|
| `internal/model/redact.go`（新） | `RedactSensitive`/`RedactTree`：脱敏实现从 `internal/api` **下移**到 model（规则仍是唯一的 `model.IsSensitiveKey`）。理由：`internal/system` 是 `internal/api` 的**下游**（反向 import 成环），而两条路径（配置视图回显、诊断归档）必须共用同一份实现 |
| `internal/model/diff.go` | `redactedPlaceholder` → 导出 `RedactedPlaceholder`（归档的日志分节用同一个占位，免得同一件事两个写法） |

| `internal/api/redact_test.go` | 直测改调 `model.RedactSensitive` |
| `internal/api/resources.go` | 注释指向新实现位置（口径不变） |
| `internal/system/techsupport.go` | ① `config.json` 走新的 `sectionRedacted`；② 新增 `scrubBootstrapCredential`（只把带 `bootstrapCredentialMarker` 的那一行值换成 `«已隐藏»`，行保留）；③ 落盘 `os.OpenFile(…, 0o600)`（**不再 `os.Create`**）、目录 `MkdirAll(0o700)` + **显式 `Chmod(0o700)`**（`MkdirAll` 不改已存在目录）；④ `README.txt` 写明「配置是脱敏视图、不能用于恢复」 |
| `internal/api/server.go` | 该路由**class 不动**（仍 read-only），只补注释说明口径 |
| `internal/system/diag_test.go`、`internal/model/redact_test.go`、`internal/api/diag_ops_test.go` | 用例（见 §3） |
| `docs/NFViS-openapi.yaml` + `internal/api/openapi.json` | 下载端 summary/description（脱敏视图、保持 read-only、要恢复用配置备份）+ 生成端 summary；`--write` 重新生成内嵌件 |
| `docs/NFViS-CLI命令树完整设计.md`、`docs/NFViS-CLI命令全表.md`、`docs/NFViS-用户手册.md`（§10.8/§12.1） | 操作者读物三处补口径 |

| `docs/V1-收尾待办.md` | §2.3 那条改为 ✅ 已完成（round74，决策 #149） |

**如实登记的残留**：① `user_data` 是自由文本，与配置视图**同口径不脱敏**（操作者若把私钥/口令写进
cloud-init，它会随配置快照出去）；② 日志分节除引导口令外**不脱敏**（日志是原文才有诊断价值；
产品自己往日志里写凭据才是缺陷）；③ 自定义 class 的路径 ACL 仍按 `show system tech-support` 路径放行
（与决策 #143 登记的同一口径，未动）。

② 落盘改回 `os.Create(path)`：

```
    diag_test.go:296: 跳过：Windows 无 POSIX 权限位

--- FAIL: TestTechSupportArchiveModeIsExplicit0600 (0.00s)
FAIL	github.com/xzjt/nfvis/internal/system	0.085s
```

> **为什么权限要两条用例**（本机实测，不是推断）：Windows 上 POSIX 权限位不存在，
> `os.OpenFile(…,0o600)` 与 `os.Create` 的 `Stat().Mode().Perm()` **都是 0666**（探针实测：
> `OpenFile 0600 -> perm=0666` / `os.Create -> perm=0666`；目录 0700 读回 0777）⇒ 只留 POSIX 断言的话，
> 「把 0600 改回 0644」在本机**无人报错**。故补一条**跨平台**守护核对开档语句本身（不得 `os.Create`、
> 必须显式 `0o600`），真实权限行为那一层仍由 `TestTechSupportArchivePermissions` 在类 Unix 上验
> （沿用决策 #77 的既有口径）。

----- 5. 真机复验（**由主会话执行**：nfvis-vm 上的开发态实例 + 生产库副本）-----
环境：本分支构建的实例 + 生产库副本；操作者分别用 **super-user（admin）** 与 **read-only（viewer 类账号）**。
要点：**不要**动管理路径（`ens160`）与 `make integration` 之外的东西；归档目录先记下改前的权限。

| 步骤 | 命令（真机） | 期望 | 独立事实源 |
|---|---|---|---|
| ① 生成并看权限 | `request system tech-support generate` → `ls -l /var/lib/nfvis/tech-support/`；`stat -c '%a %U' /var/lib/nfvis/tech-support` | 归档 `-rw-------`（0600）、目录 `700`（**旧安装上若为 755，生成一次后应变 700**） | `stat -c '%a'` 直接读，不经管道量退出码 |
| ② 解包看成员 | 复制一份到 /root 下解开：`tar tzf` 列成员（7 个），`grep -c 'password_hash\|pbkdf2\$' config.json` | `0`（**脱敏视图**）；`grep -n hostname config.json` 仍能看到非敏感配置 | 与 `GET /api/v1/configuration` 的脱敏视图对照（同口径）；与配置库 `sqlite3 nfvis.db` 里的 committed 对照——库里**有**哈希、归档里**没有** |
| ③ 日志分节 | `grep -n '一次性口令' logs.txt`（解开后） | 该行**在**，值已是 `«已隐藏»`；同文件其余行与 `journalctl -u nfvisd -n 500` 一致 | `journalctl -u nfvisd \| grep 一次性口令` 看原始行（root）；两边行数/其余行一致 |
| ④ read-only 仍能下载 | 用 read-only 账号 `curl -H "Authorization: Bearer <token>" -o /tmp/ts.tar.gz https://<host>:443/api/v1/system/tech-support/<file>`；`echo $?`（**不经管道**） | HTTP 200；本地文件与源归档 sha256 一致 | `sha256sum` 两端对照 + `curl -w '%{http_code}'` 单独量 |
| ⑤ 反面（可选，验证没被过度收紧） | 同一 read-only 账号下载**配置备份**归档 | **403**（决策 #143 的口径未受影响） | `curl -w '%{http_code}'` |

收尾：真机上产生的临时解包目录与复制的归档删掉；确认配置库指纹（`cfgsha`）与动作前一致
（本轮只读操作，不该变）。

----- 6. 存疑 / 未做 -----
- **`user_data` 不脱敏**（自由文本，与配置视图同口径）：操作者若把私钥/口令写进 cloud-init，
  它会随诊断包出去。已写进决策 #149 的残留项，建议在 V2 评估「user_data 是否该整体打码」。
- 日志分节除引导口令外**不脱敏**（有意）：日志原文才有诊断价值。
- 自定义 class 的路径 ACL 未动（与决策 #143 登记的同一口径）。
- POSIX 权限行为（0600/0700）在本机（Windows）**无法实测**，只有跨平台的语句守护；
  真实权限位请按 §5 步骤 ① 在真机核一遍。
