日期：2026-10-02；环境：nfvis-vm，2.0.0~dev32；VPP v26.06-release；分支 v2 @ 76f1b98。
缘起：决策 #338（VPP dns 插件）真机实证「只在默认表解析上游」而整体撤回；本轮立项前按 #338 的教训
**先核实能力前提**再写契约——被核实的对象是「VPP punt socket 能否把域内（VRF 表内）的 UDP/53 查询交给
宿主用户态程序，且用户态回注的应答能否按该域的表路由回域内客户端」。

§1 底座语义（源码 + 真机实测双向确认）
- `punt { socket <path> }` 必须在 **startup.conf** 里配置（VPP `punt_config` 是 VLIB_CONFIG_FUNCTION），
  否则 `vnet_punt_socket_add` 直接以 `"socket is not configured"` 拒绝注册——**运行期无 API 可补**。
- `punt socket register ipv4 udp <port> socket <client-path>` 的实现是 `udp_register_dst_port(...)`：
  只对「**目的地址是 VPP 本机地址**」的 UDP/<port> 包生效（转发中的 UDP 包不进 udp4-lookup，不受影响）。
- 上行包格式 = `punt_packetdesc_t{u32 sw_if_index; enum punt_action_e action}`（8 字节，packed）+ 包体；
  上行 action 恒 0，`sw_if_index` = `vnet_buffer(b)->sw_if_index[VLIB_RX]`，即**包进入 IP 栈的那个接口**。
- 回注格式同 8 字节 desc；`action = 1 (PUNT_IP4_ROUTED)` 时 VPP 执行
  `sw_if_index[VLIB_RX] = desc.sw_if_index` 后送 **ip4-lookup**（即**按该接口所属的 FIB 表**查路由），
  `action = 0 (PUNT_L2)` 则送 interface-output（按 L2 直接发）。送 ip4-lookup 的是**裸 IP 包**（无以太头），
  VPP 自己重写 L2 头。

§2 实测（两段，均为真机）
2a 最小通道（loopback 在**非默认表**，证「按接口的表解析」而非只看表 0）
- `punt { socket /run/vpp/punt.sock }` 写入 /etc/vpp/startup.conf → `systemctl restart vpp`（产品现场自动恢复：
  bond0/ens192/ens224 回到 VPP、nfvisd active）。
- `ip table add 100` + `set interface ip table loop0 100` + `loop0 10.99.99.1/24` + 静态邻居 10.99.99.2。
- 用户态（python，unix datagram）注入伪查询 10.99.99.2:34567 → 10.99.99.1:53（action=1, RX=loop0）：
  **收到了 punt**（`desc: sw_if_index=6 action=0`，len=78；VPP 侧 `ip4-udp-punt-socket Socket TX` 计数 +1）。
- 同轮回注应答（action=1, RX=loop0，dst=10.99.99.2）：`show interface loop0` 由无计数变为
  `tx packets 2 / tx bytes 140`——**回注的包确实按 loop0 所在的表 100 路由并发出**。
2b 生死点（真实域：BVI 在 VRF 表 + 真实 vhost 口 + 真实 guest）
- 现场：`cli-semantic-fixture.sh up` → sem-vs（L2 + BVI 192.168.99.1/24，VPP 表 `vr-sem-vs` table-id 1445873）
  + sem-vm（guest 192.168.99.2，vhost 口 `vh-sem-vm-nic0`，同 BD 314680，邻居已解析 52:54:42:e6:31:0d）。
- **关键实测（一条判据就分清了对错）**：注入伪查询时
  · `RX = vhost 成员口（idx 4）` → **收不到 punt**（L2 成员口不在任何 VRF 表里，包落在表 0 而丢失）；
  · `RX = bvi0（idx 5）` → **收到 punt**（`desc: sw_if_index=5`）。
  ⇒ 真实场景中包是**经 BVI 进到 IP 栈**的，上行 desc 的 sw_if_index 就是 **BVI**；回注用同一索引即对称。
- 回注应答（action=1, RX=bvi0，192.168.99.1:53 → 192.168.99.2:34567）后，抓 **vhost 口出向** pcap
  （`pcap trace tx intfc vh-sem-vm-nic0`，注意 CLI 是 `intfc`、且 `file` 只认相对名、VPP cwd=/tmp）：
  `08:06:14.641170 IP 192.168.99.1.53 > 192.168.99.2.34567: [udp sum ok] 8738+ A? probe.test. (28)`
  ⇒ **应答以 BVI 地址为源、经 vhost 口送到域内客户端**（独立事实源，非产品自述）。

§3 结论（路线 c 的能力前提成立）
1. 域内客户端 → 域网关地址:53 →（VPP 本机地址）→ punt socket → nfvisd：**成立**。
2. nfvisd 用宿主网络栈向上游解析：普通用户态 UDP 查询，无底座前提（本次未实测上游，风险低）。
3. nfvisd 回注应答（desc.action=1 + sw_if_index=该 BVI）→ 按该域的 VRF 表路由 → 经 vhost 口到客户端：**成立**。
4. 不需要「默认表寻址」（路线 a 的前提）、不需要 VPP dns 插件（#338 的死因）——**#338 的阻塞点被绕开**。

§4 实测暴露的实现要点（必须写进契约/实现口径）
- startup.conf 必须有 `punt { socket … }`（产品生成器 `startup.go` 要加），且**这会改变 vpp 段哈希** ⇒ 升级后
  首次需要 `request vpp restart` 才生效（pending-restart 语义已有）。
- 注册是**运行期**动作、VPP 重启即丢 ⇒ 必须并入恢复重放；nfvisd 重启也要重注册。
- **代价（如实告知）**：注册存在期间，指向 VPP 本机地址的 UDP/53 由 nfvisd 独占处理；注册在而 nfvisd 不在
  （崩溃/被停）时包会被 punt 节点**丢弃**（该节点 flags=IS_DROP）⇒ 域内 DNS 中断，直到 nfvisd 回来或注销。
  故：关闭代理必须注销（恢复 VPP 默认处理），启用是显式动作。
- 上行包体的前 14 字节（以太头位置）在「注入方未带 L2 头」时可能是**残留垃圾**（实测两次内容不同）⇒
  读侧不要依赖它；产品自己构造应答时应按 desc 决定从哪张表回注，而不是照抄 L2 头。
- punt 注册是**全局单点**（udp 端口级，不分表/接口）：多域共用同一注册，靠上行 desc.sw_if_index 区分来源。

§6 真机验证（2.0.0~dev33；四维覆盖：配置 → 数据面 → 读视图三面 → 边界）
6.1 前置与升级路径
- `dpkg -i` dev33 → `show vpp` 报 **`pending_restart: yes`**（vpp 段哈希混入 punt 路径所致，如实提示）；
  `request vpp restart` 后 `pending_restart: no`，且 punt 注册由**恢复重放**自动回来
  （`punt ip4 UDP port 53 to socket /run/vpp/nfvis-dns.sock` 重新在场）；startup.conf 由**产品生成器**重建并含
  `punt { socket /run/vpp/punt.sock }`。⇒ 「升级后首次需 restart 让 punt 段生效」这条路径真机成立。
6.2 现场（可用产品能力自造）
- `dns-vs`（L2 + BVI 192.168.77.1/24）+ `dns-vm`（debian-12 cloud image；guest 每 3s 向网关 :53 发
  `A? probe.test`）+ 宿主侧最小 DNS 应答器（127.0.0.1:53 → 10.9.9.9、127.0.0.2:53 → 10.8.8.8，各自打印
  收到的查询＝独立事实源）。

6.4 数据面（独立事实源）
- 注册：`vppctl show punt socket registrations l4` → `punt ip4 UDP port 53 to socket /run/vpp/nfvis-dns.sock`；
  nfvisd 的 client socket 文件在场。
- 端到端（**真实 guest 流量**，非伪造包）：宿主 `tcpdump -i lo udp port 53` 每 3s 看到
  `127.0.0.1.x > 127.0.0.1.53: A? probe.test.` 及其应答；vhost 口出向 pcap 每 3s 看到
  `192.168.77.1.53 > 192.168.77.2.y: 1/0/0 A 10.9.9.9 (44)`——**以网关地址为源、经 vhost 口把真实应答送到
  域内客户端**（即「域内 VNF 把 resolver 指向网关即可解析」）；`ip4-udp-punt-socket Socket TX` 同步增长。
- 排除性证据：直接把伪造上行包投到 nfvisd 的 client socket → 3 次上游查询被转发、收到应答 ⇒ 转发器处理
  路径（解析 → 选上游 → 转发）本身成立，问题若在必在投递侧。
6.5 语义矩阵
- **按域优先**：全局=127.0.0.1、dns-vs 按域=127.0.0.2 时，guest 收到的是 **10.8.8.8**（按域上游），而非
  全局的 10.9.9.9。
- **皆空 ⇒ SERVFAIL**（该域无按域上游且全局为空；代理因另一交换机非空仍启用）：guest 收到
  `192.168.77.1.53 > …: ServFail- q: A? probe.test.`，且 **[udp sum ok]**（回注包 UDP 校验和为真值）。
- **撤销 ⇒ 注销 ⇒ 回落**：全部清空后 `show punt socket registrations l4` 为空、读视图「未配置」，guest 随后
  收到 `ICMP 192.168.77.1 udp port 53 unreachable`（VPP 默认处理）——**实证了「无上游时回 SERVFAIL 而非
  静默」的必要性**：静默超时比这个默认行为更差。
6.6 四套件（dev33）
- `cli-fulltest` **228 / 0 / 13**（让出 1G 页、无第二个 VM 争用时的干净基线）。同一现场若 sem-vm 在跑，
  stage 4 会有 4 项失败，全部是 `cli-vm` 因 **1G 池无空闲页**而起不来（`Cannot allocate memory`）；
  与 #345 无关（修套件用例后 stage 2 由 71/3 转 **80/0**）。
  ⚠️ **更正（用户指正后复核）**：那页 1G 页**不是 VPP 占的**——`vppctl show memory` 显示 VPP 的 main heap
  是 **2M 页**（`page-size 2M, total 512` = 1G），`show physmem` 的 `default-page-size 2M`、arena
  `subpage-size 2M`；VPP maps 里那条 1024MB 是 **vhost-user 对 sem-vm guest RAM 的共享映射**（与 qemu
  同 inode），VPP 不额外占 1G 页。1G 池的真实账（单 NUMA node）：声明 2 / 内核 2 / `free 0` / `Rsvd 0` /
  `Surp 0`，而**唯一持有者只有 sem-vm 的 guest RAM 1 页** ⇒ **另有 1 页是无主占用**。
  ⇒ 结论改为：环境里有 1 页 1G **无主占用**（分配了但无活进程持有），产品当前口径
  （可回收 = 内核实际 − 声明）既**看不见**也**回收不了**它（已登记进 `docs/v2待做.md`）。
- `cli-semantic-check` **26 / 0 / 3**（新增 **S13**：读视图 ↔ CLI ↔ `vppctl show punt socket registrations l4`

- `cli-lifecycle-check` **19 / 0 / 4**（首跑 18/1/4：失败项系 sem-vm 刚启动尚未就绪的时序波动，复跑归零，

§7 本轮发现与修复（真机验证的价值）
1. **套件用例缺陷（本轮修）**：`cli-fulltest-phase2.sh` 的 DNS 代理段把「**带地址的 delete**」放在
   「独立会话、不 commit」的解析段里——该形态候选不保留，`delete … <ip>` 必然报「无匹配配置」⇒ 3 项假失败
   （对照：同段 `learn-limit` 用无值 delete 才通过）。修法：该段 delete 一律用无值形态，并照登录横幅的样板
   新增「真落库 → 回读 → 按地址删除」的提交往返（`run`×6 + `expect_out`×2，提交后立即清除，不改长期现场）。
2. **审查中修的三处实现问题**（已随 PR #272 合并）：回注包按 IPv4 伪头计算 UDP 校验和（真机 pcap 显示
   `[udp sum ok]`）；`extractIP` 改三级判据（ethertype → 首字节 nibble → 14 偏移 nibble，兼容带/不带 L2）；
   回注失败计入 `SendFailCount`。
3. **覆盖边界如实化**：punt 注册按地址族，故 v1 覆盖 **IPv4/UDP/53**；IPv6 的注册与回注路径未做真机验证，
   不先做成假能力（契约/读视图/手册三处已写明）。
4. **对「1G 池被占」的更正**（用户指正后复核）：VPP 用 **2M** 页（`show memory`/`show physmem` 两项实证），
   `/proc/<pid>/maps` 里那条 1024MB 是 vhost-user 对 guest RAM 的**共享映射**，不能按路径过滤判占用者；
   1G 池 2 页 = sem-vm guest RAM 1 页 + **无主占用 1 页**（`Rsvd`/`Surp` 皆 0、单 NUMA、仅一个 inode 被映射）。
   新登记的缺口（可见性 + 回收）见 `docs/v2待做.md`；§6.6 与 §7.4 的措辞已同步更正。
