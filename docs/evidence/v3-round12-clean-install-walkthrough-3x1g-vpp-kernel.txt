§2.0 【R12-1（高）】用户目标布局（3×1G、无 2M 池）下 VNF 容量=0，且提交校验放行
--------------------------------------------------------------------------------
事实链（/root/walk/r12-1-1g-only-vnf-failure.log）：
  a) `request vpp restart`（产品生成的 startup.conf 生效）后：1G 池 nr=3/**free=0**。
     vppctl show memory：main heap 1×1G 页；smaps：vpp 进程持有**三块 1G memfd 映射**
     （seg_0-0 / seg_2-0 / buffers-numa-0）——缓冲池（430184×2496B≈1.07GB）在
     default-hugepage-size=1G 下按整 1G 页分配，吃掉另外 2 页。
  b) 读视图如实：「1G：数据面占用 3、空闲 0——VNF 可起页数 = 空闲页数（当前 0）」。
  c) **但提交校验放行**：`set virtual-machine-functions vnf-a memory size-mb 1024` + commit
     成功（rev 6）——提交侧的池账本 Free=声明值−VNF 声明（model/resources.go 初始化口径），
     **不扣数据面占用**，与读视图两套事实源互相矛盾。
  d) `request … start` 才失败：`internal error: QEMU unexpectedly closed the monitor …
     unable to map backing store for guest RAM: Cannot allocate memory`（裸 libvirt 文案，
     无「大页池空闲不足」的照做指引）。
  e) 契约面：向导提示「可起 VNF 数 ≈ N−1」（N=3 ⇒ 承诺 2）、#347 明示边界「1G 池声明 N ⇒
     VNF 可用 N−1」——**两者只在 2M 池存在（缓冲落 2M）时成立**；2M=0 时实际容量=0。
  影响：用户按规划布局（3×1G、VPP 占 1、VNF 用 2）部署会得到「VNF 全部起不来」的整机。
  处置（走查内）：补 `set resource-pools hugepages page-size 2M count 768` +
  `set vpp memory hugepage-preference 2M` + kernel apply + 重启 + request vpp restart 后：
  1G 池 dp=1/free=2（用户意图达成；主堆落 2M 段 512 页、缓冲落 2M）。
  修复方向建议：① 向导/手册的 N−1 承诺按「2M 池是否存在」分叉；② 提交校验引入 sysfs
  空闲对账（或至少预测式警告）；③ startup.conf 对 2M=0 布局给 default-hugepage-size 的
  更保守取值（避免缓冲吃 1G 页）或文档明示「2M 池是 VNF 容量的前提」。

4.10 **#446 复核（round11 修复，round10 R8-2 的收口）**：域内成员（容器 192.168.99.77，带
    默认路由经网关）ping 域外（192.168.98.10 / 8.8.8.8）→ **100% 丢**（包到网关被

§5 数据面切回 vpp（往返）——【R12-7（中高）/ R12-8（高）】
--------------------------------------------------------------------------------
5.1 对象保留（vs-lan/vs-dmz/vs-wan/vnf-a/vnf-b/ct-1/qos/storm/vxlan 均未删）直接
    set system dataplane vpp + commit → systemctl restart nfvis → VPP 自动拉起、connected。
5.2 **【R12-7】内核侧不清理、双活数据面**（/root/walk/06-r12-7-residue.log）：
    切回后 ip -br link 仍有 vs-lan/vs-dmz/vr-vs-lan/vr-vs-dmz/vs-wan/nfvisct…/nfvisdh… 7 类
    设备，**ens192/ens224 仍是内核桥/VRF 成员（forwarding）**、vnet0/vnet1（两台 VM）仍挂在
    内核桥上、nft inet nfvis-forward + netdev nfvis-acl 两表在位——内核数据面整体**活跃**，
    而产品读视图只反映 VPP。交接教训 #7 只覆盖「切回后再删不跑内核 teardown」，未覆盖
    「带对象切换时旧数据面不 teardown」。设计文档未声明该语义。内核 DHCP tap 残留至收尾
    手工 rtnetlink 删除。
5.3 **【R12-8】VPP 侧静默不收敛、修复路径全部失效、唯一出路整机重启**：
    · 症状：`request vpp restart`/`systemctl restart nfvis` 多次后——VPP 无 BD/BVI/vhost/
      vxlan/policer、物理口 admin-down、VNF_PORT_DOWN×2 告警挂着；**全程零 UNCONVERGED 告警、
      零错误 surfaced**（静默）。
    · API 层：nfvisd↔VPP 连接反复死亡（write: broken pipe，健康探针 15s 才发现→重连）、
      vpp 进程 100% CPU 空转（Consumed 2m17s CPU / 2m14s wall）、EAL「236 hugepages of 2M
      reserved, but no mounted hugetlbfs found for that size」。
    · 配置路径全断：`request interfaces ens192 enable`（#449 整段重放）→
      「下发失败 interface[ens192]: 绑定接口 ens192 入向策略 pol-lab: VPPApiError: No such
      entry (-6)」已补偿失败；连带 **QoS 解绑也失败**（单向解绑触发另一向重放 → 同 -6）——
      用户经 CLI 无法修复。
    · 机理（代码级定位）：apply 计划是**配置差分引擎**（apply.go：configEqual(old,new) 才
      跳过创建）——往返后配置零变化 ⇒ **零创建计划**（policer/BD/BVI/vhost 全不建），而
      绑定/enable 路径照跑 ⇒ -6；EnsureConsistent 名义全量重放但同样无效果（无 UNCONVERGED
      落表），恢复路径对「数据面被整体替换」这一事实不感知。启动期 sw_interface_dump multi
      写 broken pipe 中止收敛（journal 实录）亦无重试/上报。
    · 对照实验：**整机重启后一切自愈**（BD/BVI×2/vhost×2/vxlan/policer 全量重建、端口 up、
      池/告警正常）——楔死纯属运行态。
    · round10 的「往返零残留」结论成立的前提是**切换前删净对象**（其 §3.13 即如此）；round1
      的带对象切回未核对 VPP 侧对象收敛，本缺口自 round1 起未被观察到。
5.4 修复方向建议：① 数据面切换时清空/失效 VPP 侧 applied 状态与登记（或让
    EnsureConsistent 对「数据面代际变化」强制全量重建）；② 恢复收敛的未收敛项必须落
    UNCONVERGED 告警（本轮静默违反 #192/#333 的「事后可见」口径）；③ 内核侧 teardown
    纳入切换编排（或手册明示「带对象切换」的后果与手工清理步骤）。

§7 新缺陷登记（R12-1~R12-8；逐条独立事实源）
--------------------------------------------------------------------------------
R12-1【高】3×1G-only（无 2M 池）布局：VPP 吃满 1G 池 ⇒ VNF 容量=0；提交校验与读视图两套
    账本矛盾（校验放行、启动裸 QEMU 报错）
    · 事实：§2.0 全链（startup.conf 的 default-hugepage-size=1G 使缓冲池按整 1G 页分配；
      smaps 三块 1G memfd；读视图空闲 0 如实但 commit rev 6 放行；start 报
      "Cannot allocate memory"）。
    · 契约面：向导「可起 VNF 数 ≈ N−1」与 #347 边界在 2M=0 时全部失真；无任何提前警告。
    · 建议：见 §2.0 修复方向。用户规划的布局需产品明确表态（支持则改内存编排，不支持则
      向导/校验挡下）。
R12-2【中】LLDP 语句族多处破坏（两数据面合计四种症状）
    · a) per-interface `enable true` 有时不落地：「语句未产生配置变更（值未变化或尚未映射
      到模型）」no-op（VPP 模式、protocols 段缺席时实测）；**同形态在内核模式/段存在时又
      能落地**——行为不一致，判据未定位。
    · b) 落地后 VPP 模式 apply 也不动作：配置有 ens192 enable true，重启收敛后 vppctl
      show lldp 无任何本地口、无 -7 报错、无告警——round11「-7 人话化」修复路径不可达。
    · c) 叶子级 delete 失败：`delete protocols lldp interface <if> enable` → 「无匹配配置:
      interface」（set 能写 enabled false、delete 找不到——键位/路径家族，#158 同族）；
      整条删除可用。
    · d) 同一候选里第三个 delete 报「无匹配配置: virtual-switches」（前两个 delete 成功后）。
    · 净效果：产品 CLI 在两数据面上都无法可靠启用 LLDP。
R12-3【中低】已存在容器改 command/args 后不重建：restart 与 stop+start 均继续跑旧命令
    （docker Command 仍 "/bin/sh"、Exit(0)），配置与运行态静默分叉；唯一出路 delete+create。
    （VM 有 DefineVM 重定义语义，容器侧无对应物；Docker 不支持原地改 command——产品应在
    spec 变更时重建容器并如实提示。）
R12-4【中】`show configuration | display set` 回放自校验失败（内部错误）的两个触发形态：
    · a) 空 L3 交换机（`set virtual-switches vs-test type l3` 无任何内容）——创建即坏、删除即好
      （三段 A/B 复现）。
    · b) **vhost 派生名作 L3 接口**（`set virtual-switches vs-nat l3-interface vh-vnf-a-nic1 …`
      ——#172 文档化的 NAT-inside 形态）——配置在即坏；意味着标准 NAT 用法让 display set
      不可用。display json 不受影响（错误文案如实指引）。
R12-5【中】内核数据面 LLDP 代理零发帧：配置收下（display set 在）、AF_PACKET socket 在位
    （ss -0 见 LLDP:ens192）、advertisement-interval 3s 下多窗口 tcpdump（含 -i any）零帧、
    无邻居、REST /protocols/lldp 只回配置无运行态错误暴露——与 round5 证据（3s 间隔真帧、
    TLV 解码、TTL 过期）矛盾，回归点待查。
R12-6【中】内核模式 `ping <ip> vrf <交换机>` 恒失败：`ip vrf exec vs-dmz ping …: Invalid VRF
    name`——CLI 传交换机名，内核 VRF 设备名实为 vr-vs-dmz（且命名不统一：vs-wan 的 VRF
    设备就叫 vs-wan，网关域才有 vr- 前缀）——诊断面在内核模式不可用。
R12-7【中高】数据面 vpp→kernel→vpp 往返（对象保留）：内核侧不 teardown——桥/VRF/tap/veth/
    nft 表全在位且**活跃转发**（物理口/VM tap 仍是成员），与 VPP 形成双活数据面；产品读视图
    只反映 VPP；内核 DHCP tap 残留需手工 rtnetlink 删除。教训 #7 只覆盖「切回后再删」。
R12-8【高】上述往返后 VPP 侧静默不收敛（详见 §5.3）：恢复收敛零效果、零 UNCONVERGED 告警、
    VPP API 连接反复死亡 + 100% CPU 空转、端口 admin-down、QoS 绑定/解绑全部 -6 补偿失败
    ——enable/#449 重放/request vpp restart/nfvisd 重启均无效，**唯一出路整机重启**。
    根因面：apply=配置差分引擎，对「数据面被整体替换」不感知；恢复路径静默。

观察项（如实登记，非缺陷）：
  观察①【低】Web VM 详情「资源」块绑核/内存后端/大页/NUMA 恒「—」而运行态有事实

  观察④【低】`unbind-dpdk --yes`（不带 to-driver）本次报「内核未自动重新探测原生驱动」；
    round10 同操作自动交还 vmxnet3——行为差异待确认（环境时序 vs 代码变化）。
  观察⑤【低】抓包口径：`request capture stop`＝「停止且不导出」，先 stop 后 export 得到

    无法做 vNIC 源 SPAN」——round10 证据中 analyzer=ens192 与该校验并存的路径已不可复现，
    记录口径差异。
