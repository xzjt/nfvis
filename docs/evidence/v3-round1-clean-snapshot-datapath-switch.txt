§7 环境发现（不是产品缺陷，但会挡住内核数据面）
--------------------------------------------------------------------------------
干净快照的 netplan 配置把两张业务网卡设为**永久 down**：
    /etc/netplan/00-installer-config.yaml
        ens192: { dhcp4: false, dhcp6: false, activation-mode: off }
        ens224: { dhcp4: false, dhcp6: false, activation-mode: off }
    ⇒ /run/systemd/network/10-netplan-ens224.network: [Link] ActivationPolicy=always-down
    ⇒ journal: `systemd-networkd: ens224: Activation policy is "always-down", forcing link down.`
后果：内核数据面要把声明口置 up 时会被 networkd 立即压回 down（`ip link set up` 返回 0 但无效）。
处置（本轮验证用的环境改动，已留备份与自动回滚安全网）：
    activation-mode: off → manual（netplan 只接受 manual|off），`netplan apply`；
    改后 ens192/ens224 均 UP,LOWER_UP，管理口 ens160 地址/默认路由不变。
说明：VPP 数据面下这两张口交 DPDK（内核里已无 netdev），networkd 的策略自然失效，故此前各轮未暴露。
      内核数据面下口留在内核，该策略就会与产品冲突——**产品侧已按 V3-7 如实报出根因**，
      环境侧需放开（或改用 `Unmanaged=yes`）。

9.3 ACL 强制（真实对端，A/B 对照）
    实验组：`set acls acl-icmp-deny rule 10 … protocol icmp action deny` + 绑到
            `l3-interface ens224 acl-in acl-icmp-deny`，commit (revision 12)
        nft 事实：chain bind_ens224 { type filter hook ingress device "ens224" …;
                                      meta protocol != { ip, ip6 } accept;
                                      jump acl_acl_icmp_deny_be78 comment "acl-icmp-deny" }
        $ ping -n 4 192.168.98.1 → **已接收 0，丢失 4（100% 丢失）**
    对照组：`delete … l3-interface ens224 acl-in acl-icmp-deny`，commit (revision 13)
        $ ping -n 4 192.168.98.1 → 已接收 4，丢失 0（0% 丢失）
    ⇒ 唯一变量是绑定状态；且 ARP 仍通（非 IP 放行生效）。

9.4 QoS 限速（真实流量，A/B 对照）
    实验组：`set qos policies pol-8k cir 8000 cbs 1000` + `set interfaces ens224 ingress-policy pol-8k`
        tc 事实：`police 0x1 rate 8Kbit burst 1000b action drop`
        $ ping -n 10 -l 20000 192.168.98.1 → **100% 丢失**
        $ tc -s filter show dev ens224 ingress
            Sent 203258 bytes 147 pkt (**dropped 130, overlimits 130** requeues 0)
    对照组：`delete interfaces ens224 ingress-policy pol-8k`
        $ ping -n 10 -l 20000 192.168.98.1 → 已接收 10，丢失 0（0% 丢失）
        tc 事实：filter 里 police 计数 0
    ⇒ 限速在真实流量上生效，且**计数与丢包一一对应**。

9.5 端口安全（真实对端，A/B 对照）
    实验组：`set interfaces ens192 port-security mac aa:bb:cc:dd:ee:ff`（白名单不含宿主 MAC）
        nft 事实：chain ps_ens192 { type filter hook ingress device "ens192" …;
                                    ether saddr != aa:bb:cc:dd:ee:ff drop }
        $ ping -n 4 192.168.99.1 → **100% 丢失**（宿主 MAC 00:50:56:c0:00:08 被丢）
    对照组：白名单加入宿主 MAC
        nft 事实：ether saddr != { 00:50:56:c0:00:08, aa:bb:cc:dd:ee:ff } drop
        $ ping -n 4 192.168.99.1 → 已接收 4，丢失 0（0% 丢失）
    ⇒ 白名单**按源 MAC 真的在拦**，且桥口学习关闭不阻断白名单内主机。

9.6 风暴抑制（真实广播洪水，A/B 对照）
    实验组：`set interfaces ens192 storm-control broadcast 8`（8 kbit/s）
        tc 事实：flower dst_mac ff:ff:ff:ff:ff:ff + `police rate 8Kbit burst 8000b action drop`
        宿主发 20×60KB 广播（`ping -n 20 -l 60000 192.168.99.255`）
        $ tc -s filter show dev ens192 ingress
            Sent 1216560 bytes 820 pkt (**dropped 796, overlimits 796** requeues 0)
    对照组：`delete interfaces ens192 storm-control broadcast 8`
        $ tc -s filter show dev ens192 ingress → 无 police filter、无丢包记录
    说明：广播 ping 本身**不会被应答**（100% 丢失是正常现象），故这里的独立事实源是
          **tc 的丢包计数**（796/820），不是 ping 的回包率。
    另记一次**无效实验**（如实登记）：首版用 `storm-control broadcast 8000`（8 Mbit/s），
          实测 offered 远低于门限 ⇒ `dropped 0`——**这是正确行为**，是实验设计错了
          （门限要低于 offered 才有对照意义）。

      `TestBuildDomainXML_KernelDataPlaneUsesBridgeAndVhostNet` 断言
      `<interface type="bridge">` + `<source bridge="vs-lan">` + `<driver name="vhost" queues="2">`
      + `<vlan><tag id="100">`，且**不出现** `vhostuser` / `mode="shared"` / `.sock`；
      另一条断言缺虚拟交换机时如实报错。**真机连通性仍未验。**

10.2 内核数据面下的 VNF（普通内存 + 不绑核 ⇒ 无需资源池、无需重启）
    ⚠️ **本轮修掉的一处产品缺陷**：`vhost-user` 型 vNIC 曾被**无条件**要求
    `memory backing=hugepage`（FR-CFG-011①）。该约束的由来是 VPP 的 vhost-user 是
    **共享内存**形态；而**内核数据面下同名类型落成 virtio + 宿主 tap + vhost-net，
    没有共享内存对端**，普通内存即可。原判据会让内核数据面下建 VNF 被迫声明资源池 + 重启。
    修法：判据加数据面条件（`c.DataPlaneMode() != DataPlaneKernel`），并补单测
    `TestKernelDataPlaneAllowsNormalMemoryWithVhostUserNic`（内核放行 / VPP 仍拒，红-绿双向）。

§11 追加：NAT 真实转发验证（宿主作对端）——顺带修掉三条「转发前置条件」缺陷
================================================================================
11.1 结论先说
    实验组（NAT 规则在场）：内网主机 ping 宿主，**ens224 上抓到的包源地址是 192.168.99.1**
    对照组（删掉规则）    ：同样流量，**源地址是 10.99.0.3**（未改写）
    ⇒ nftables masquerade 在真实转发路径上确实生效。

11.2 拓扑（全部由产品声明，两侧都是产品设备）
    vs-all（L3 交换机）
      ├─ l3-interface ens192  ip 10.99.0.1/24     ← 内网侧
      └─ l3-interface ens224  ip 192.168.99.1/24  ← 外网侧（朝宿主）
    nat rules 10 match source 10.99.0.0/24 virtual-switch vs-all action interface ens224
    内网主机 = 测试夹具（netns `ns-in` + veth `vin` 挂在 vs-all 里，10.99.0.2；ns 内 10.99.0.3）
    宿主：VMnet8 次地址 192.168.99.10/24

11.3 取证（唯一可信的做法：在**转发方向**上抓包）
    $ timeout 12 tcpdump -ni ens224 -c 6 icmp &   # 规则在场
    $ ip netns exec ns-in ping -c 3 192.168.99.10
      15:38:02.282726 IP **192.168.99.1** > 192.168.99.10: ICMP echo request, id 57236, seq 1
      15:38:02.282970 IP 192.168.99.10 > **192.168.99.1**: ICMP echo reply
      …（3 组，源恒为 192.168.99.1）
    $ delete nat rules 10（对照组）
      15:38:36.254641 IP **10.99.0.3** > 192.168.99.10: ICMP echo request, id 57372, seq 1
      …（源保持 10.99.0.3）
    ⇒ 唯一变量是 NAT 规则是否存在。

11.4 本轮先走的两次弯路（如实登记，都是"实验设计错"而不是产品错）
    ① **对 reply 方向期望 SNAT**：先试「宿主 ping 内网地址 10.99.0.1，看回复源是否被改写」——
       不行。那条流的**原始方向是 INPUT**（目的地址是本机），conntrack 的 NAT 映射只在**原始
       方向**建立；reply 方向沿用既有映射，不会新建。读数是「回复源仍是 10.99.0.1」。
    ② **单二层下"宿主 ping 内网地址"也不是 forwarded 流**：VM 的三块网卡与宿主同二层，
       宿主能直接 ARP 到任何地址，构造不出需要转发的流量（§9.8 已登记）。
       正解是把内网侧放进 **netns + veth**，让"内网主机"真的在 VM 后面。
    教训与 §9.6 同源：**先想清楚"这条流在数据面上走的是哪条路径"**（INPUT / OUTPUT /
    FORWARD / conntrack 的哪个方向），再设计对照组——否则量到的是别的东西。

11.5 顺带抓出并修掉的三条**转发前置条件**缺陷（都是"命令成功、包全丢"型）
    编号  现象（真机现场）                                        修复

          `Chain FORWARD (policy DROP)`）。VPP 数据面**完全绕开内核     （比 filter 的 0 更早），
