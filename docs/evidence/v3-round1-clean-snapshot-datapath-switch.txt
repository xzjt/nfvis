§4 内核数据面：经**产品**下发（不是直接调 Provider）
--------------------------------------------------------------------------------
4.1 配置（CLI 脚本，一次提交）
    configure
    set system management interface ens160
    set interfaces ens192 description l2-port
    set interfaces ens224 description l3-port
    set virtual-switches vs-lan type l2
    set virtual-switches vs-lan vlan access 100
    set virtual-switches vs-lan gateway ip 192.168.99.1/24
    set virtual-switches vs-lan ports 1 interface ens192
    set virtual-switches vs-l3 type l3
    set virtual-switches vs-l3 l3-interface ens224 ip address 10.99.0.1/24
    set virtual-switches vs-l3 static-routes 10.99.99.0/24 next-hop 10.99.0.2
    set acls acl-test rule 10 source any destination any protocol icmp action deny
    set acls acl-test rule 20 source any destination any action permit
    set virtual-switches vs-l3 l3-interface ens224 acl-in acl-test
    commit / exit
    → commit 成功 (revision 4)

4.2 内核事实（逐条独立核对）
    $ ip -o link show vs-lan                  → <BROADCAST,MULTICAST,UP,LOWER_UP>，master vr-vs-lan
    $ bridge vlan show dev ens192             → ens192  100 PVID Egress Untagged
    $ ip -o -4 addr show dev vs-lan           → 192.168.99.1/24
    $ ip -o link show vr-vs-lan               → <NOARP,MASTER,UP,LOWER_UP>
    $ ip -d link show vs-l3                   → vrf table 625570517
    $ ip -o -4 addr show dev ens224           → 10.99.0.1/24
    $ ip route show table all | grep 10.99.99 → 10.99.99.0/24 via 10.99.0.2 dev ens224 table 625570517
    $ nft list table netdev nfvis-acl
        chain acl_acl_test_d18a { ip protocol icmp drop; accept; drop }
        chain bind_ens224 { type filter hook ingress device "ens224" priority filter; policy accept;
                            meta protocol != { ip, ip6 } accept
                            jump acl_acl_test_d18a comment "acl-test" }
    ⇒ L2 交换机=内核 bridge（含 VLAN 与网关 VRF）、L3 交换机=内核 VRF、静态路由进 VRF 表、

编号  现象/根因（真机现场）                                       修复

V3-1  安装器 `apply_dataplane` 用 `;` 分隔语句 → `无效命令`，     改用 `-f <临时脚本>`（CLI 脚本模式按
      数据面配置**根本没写进库**（首装时静默）                    **换行**切句，见 cliparse.SplitStatements）

      报**失败**，把「读不到」误报成「配错了」
V3-3  `show vpp` 缺 `dataplane:` 行（内核数据面下看不出在用哪套） 补上（并让 vpp 侧也恒报 Mode，两侧对称）

      stats segment 未启用」——把操作者引向 VPP 排查              无 VPP 运行态读数」
V3-5  未实现族（DHCP 中继/服务器、DNS 代理、LLDP）在**未声明**时  只在确有声明时报不支持；未声明即空操作
      也报不支持——而提交编排把它们当 bridge-domain 的伴随操作
      调用 ⇒ **任何一次普通提交都被挡住**
V3-6  同一次提交里「建 ACL → 绑到三层接口」报「绑定了未下发的     ACL 规则体改从**本次已下发的登记**解析
      ACL」——绑定从 `p.config()`（上一次收敛的快照）解析         （与 QoS 策略同法），快照仅作回落
V3-7  `ip link set dev <口> up` 返回 0 却**不生效**（宿主 netplan  置 up 后**回读确认** + 有限重试；
      `activation-mode: off` → networkd `ActivationPolicy=         仍不生效则**如实报出**并点名常见原因
      always-down` 把它压回去）⇒ 后续路由报 `Nexthop has         （不再让根因埋在下游）
      invalid gateway`，根因被埋在下游
V3-8  端口安全把**VRF 从属口**当成 bridge 成员（判据只看           判据改 `linkinfo.info_slave_kind == "bridge"`
      `master != ""`）⇒ `bridge link set … learning on` 报
      `Operation not supported`，把整个提交打挂
V3-9  `show virtual-switches` 的 Learn/Flood 两列在内核数据面下    内核 bridge 默认学习并洪泛 ⇒ 如实填 true
      显示 **down**（VPP 概念取零值）——看起来像交换机坏了          （并注明端口安全关的是单端口学习）
V3-10 路由读视图的「Distance 未下发：VPP 路由 API 不接收该参数」   该注记只在 VPP 数据面下打印
      在内核数据面下**是错的**（内核侧 distance = ip route metric，
      真的下发了）
V3-11 `delete virtual-switches` 回收了 bridge，却把它创建的网关     删除时一并回收**派生的** `vr-<交换机名>`
      VRF `vr-vs-lan` **留成残留**（真机实测残留）                （显式声明的 gateway vrf 不动）

§7 环境发现（不是产品缺陷，但会挡住内核数据面）
--------------------------------------------------------------------------------
干净快照的 netplan 配置把两张业务网卡设为**永久 down**：
    /etc/netplan/00-installer-config.yaml
        ens192: { dhcp4: false, dhcp6: false, activation-mode: off }
        ens224: { dhcp4: false, dhcp6: false, activation-mode: off }
    ⇒ /run/systemd/network/10-netplan-ens224.network: [Link] ActivationPolicy=always-down
    ⇒ journal: `systemd-networkd: ens224: Activation policy is "always-down", forcing link down.`
后果：内核数据面要把声明口置 up 时会被 networkd 立即压回 down（`ip link set up` 返回 0 但无效）。
处置（本轮验证用的环境改动，已留备份与自动回滚安全网）：
    activation-mode: off → manual（netplan 只接受 manual|off），`netplan apply`；
    改后 ens192/ens224 均 UP,LOWER_UP，管理口 ens160 地址/默认路由不变。
说明：VPP 数据面下这两张口交 DPDK（内核里已无 netdev），networkd 的策略自然失效，故此前各轮未暴露。
      内核数据面下口留在内核，该策略就会与产品冲突——**产品侧已按 V3-7 如实报出根因**，
      环境侧需放开（或改用 `Unmanaged=yes`）。

§8 结果与边界
--------------------------------------------------------------------------------
通过：
  · 干净快照从零重建 → 内核数据面 9 条真机集成用例全绿（另一内核构建上复现同样结论）
  · `--dataplane kernel` 整机安装：**通过 17 / 失败 0 / 不可判定 2**；VPP 按 #406 照样装上
  · 内核数据面经**产品**下发：bridge/VLAN/网关 VRF/VRF/静态路由/ACL 全部落到位（独立事实源逐条核对）
  · 切回 vpp：**一次提交 + 一次重启，无二次安装** → VPP 拉起、connected: yes、版本 26.06-release

未验证（如实登记）：
  · VM 侧 virtio + vhost-net 接入的连通性（域定义已按 `<interface type='bridge'>` + `<driver name='vhost'/>`
    生成，但本轮未真起一台 VM）
  · 未实现族的真机逐族提交期拒绝（仅单测覆盖；本轮只实测了「未声明时不再误挡提交」）
  · `.run` 自解压包的**完整闭环**：本轮用的是等价载荷目录（install.sh + debs + Packages + SHA256SUMS，
    与 .run 解包后的结构一致），未跑 `build-offline-run.sh` 的打包与自解压路径
  · 内核数据面的**真实转发**（域内 ping 通、NAT 出网）——需要第二台机器或宿主侧配合，本轮未做
