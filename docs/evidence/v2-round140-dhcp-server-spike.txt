NFViS v2 真机验证记录 round140 —— 三.1 DHCP server 本体：能力前提核实（spike，先于契约与实现）
====================================================================
日期：2026-10-04；环境：nfvis-vm，2.0.0~dev68；VPP 26.06-release；分支 v2 @ d8edb42。
缘起：按 #338/#357 的纪律，DHCP server（租约池/状态机）立项前**先核实能力前提**再写契约——
被核实的对象是「域内（BVI 网关域）客户端 DHCP 广播能否交给宿主用户态程序、且用户态应答能否回到客户端」
（与 #338 的教训同型：能力前提必须落到**本产品的网络模型**上核实，不能停在「FIB 内可达」这类抽象说法）。

§1 现场与工具（全部 spike 用、不入库；真机 /root/spike-dhcp/）
- 交换机 `sem-vs`（L2，BVI `bvi1`=192.168.99.1/24，域表 table-id 1445873，BD 314680）+ sem-vm（debian-12 cloud image）。
- 观测/注入三件套：
  ① **VPP tap**：`vppctl create tap host-if-name dhcp-spike` → VPP 侧接口名 `tap0`、内核侧 `dhcp-spike`
     （两者名字**不同**，产品必须同时持有）；宿主用 AF_PACKET 读/写（双向 L2）。
  ② **punt socket**：`vppctl punt socket register ipv4 udp 67 socket /run/vpp/spike-dhcp.sock` + 用户态 unixgram 收包；
     回注用 8 字节 desc（action=0 送 interface-output / action=1 送 ip4-lookup）+ 包体（同 #345 口径）。
  ③ **真实客户端**：临时改 guest user-data 跑一个 raw-socket 最小 DHCP 客户端（DISCOVER→OFFER→REQUEST→ACK→续租），
     并把过程日志以 **L2 广播（ethertype 0x88b5）** 发出——宿主从 tap 侧即可读 guest 状态（无需进 guest/串口）。
- 注入的合成帧（pcap/计数器逐字核对过）：真实 DHCP 报文格式（含 IP/UDP 校验和），
  `0.0.0.0:68→255.255.255.255:67` DISCOVER / `99.55:68→99.1:67` REQUEST 等形态。

§2 机制实测（每行一个独立事实源）
2a 结论性成功路径
- **T1 单播到 BVI:67 能进 punt**：注入「eth 单播到 BVI MAC、IP `192.168.99.55→192.168.99.1:67`」DHCPREQUEST
  → 用户态收到 `PUNT {sw_if_index: 5(=bvi1), src: 192.168.99.55, sport: 68, dport: 67, msgtype: REQUEST, ...}`，
  `ip4-udp-punt-socket · Socket TX` 同增。⇒ **续租/释放（客户端已获地址后的单播）路径成立**。
- **T7 punt 回注 L2 帧能到客户端**：`action=0, sw_if_index=5` + 完整以太帧（dst=guest MAC, IP 99.1→99.2, ICMP echo）
  → vhost 口 pcap 出现该 echo request，**guest 回了 echo reply（id 4660 与注入一致）**。
  ⇒ 回注帧以 BVI 为出口**进入 BD、按目的 MAC 交换到成员口**（不需要预先的邻居/ARP）。
- **T9 tap 架构全链路 + 真实客户端完整 DORA（决定性）**：
  · tap 加入 BD（`set interface l2 bridge tap0 314680`）后，**guest 真实广播 DISCOVER 经 BD 洪泛到达 tap**
    （tap 侧 sniffer：`DHCP DISCOVER 0.0.0.0:68->255.255.255.255:67`，同帧的 guest 日志广播也在）；
  · 用户态从 tap 回 OFFER（eth 单播到 chaddr MAC）→ guest `RX OFFER` → 广播 REQUEST → 回 ACK
    → **guest 侧 `LEASED 192.168.99.55 server 192.168.99.1`**（完整 DORA，四路一致：tap sniffer / 用户态服务器 /
    guest 日志广播 / guest 实际使用）。
  · 反向核对：`tap→BD→成员口` 用 ICMP 也单独实证（写入 tap0 的 echo request 被交换到 vhost 口、
    guest 回 reply——见 §2c T7'）。

2b 失败路线（如实登记，避免重走）
- **广播直投 punt 不成立**：`0.0.0.0:68→255.255.255.255:67` 的 DISCOVER 到 BVI 后**不进 UDP 本地注册**——
  bvi1 rx +1、`null-node · blackholed packets` +1（255.255.255.255 在本产品模型里没有本地归属）。
- **relay 指向自身/BVI 不成立（两变体）**：
  · src 用 BVI 地址（产品 relay 的既有形态）→ 转发包（`192.168.99.1:68→192.168.99.1:67`）被 **ip4-local
    以 `ip4 spoofed local-address packet drop` 丢弃**（VPP 对源=本机地址的入向包做反欺骗）；
  · src 改用**非本机**地址（binapi 直发 `DHCPSrcAddress=99.254`）→ 转发包被 proxy 再次捕获 ⇒ **回环**
    （一次注入触发 `dhcp-proxy-to-server · DHCP packets relayed` ×124，直到 `too big` 守卫才止），
    用户态一个包都收不到。⇒ 「用内置 relay 把广播送进来」这条路整体不可行。
- **src=0.0.0.0 直投本机地址不成立**：`0.0.0.0:68→192.168.99.1:67` 被 `ip4-local · ip4 source lookup miss` 丢弃
  （VPP 对源地址做查表；客户端 DISCOVER 的 0.0.0.0 源恰好踩中）。

2c 补充对照
- **T5 源=本机地址**（`192.168.99.1→192.168.99.1:67`）同样命中 `ip4 spoofed local-address packet drop`（机理与 2b 第一变体一致）。
- **T7'**（tap 回程方向单证）：写入 tap0 的 ICMP echo（dst=guest MAC）→ vhost 口 pcap 出现、guest 回 reply（与 T7 互证双向）。
- punt 注册与 tap 都是**运行态**：`request vpp restart` 后两者都消失（tap 接口本身随 VPP 进程消失）；
  产品必须有恢复重放（本 spike 中重建 tap + 重注册 punt 各一次实证）。

§3 结论：能力前提成立，可行架构已定形
**用户态 DHCP 服务器 + 每交换机一条 L2 tap（BD 成员口）+ UDP/67 punt 注册（收单播）**：
1. 入向广播（DISCOVER / SELECTING 的 REQUEST / REBINDING）：BD 洪泛 → tap → 用户态（真实客户端实证）；
2. 入向单播（RENEW/RELEASE，eth 单播到 BVI MAC）：ip4-local → udp/67 → punt → 用户态（实证）；
3. 回程（OFFER/ACK）：用户态写以太帧到 tap → BD 按目的 MAC 交换（或洪泛）→ 客户端（实证，完整 DORA）；
4. **不需要** VPP dhcp 插件/proxy、**不需要**默认表寻址、**不需要**宿主 IP/路由配置（tap 不配任何 IP）；
   与 #338 的「插件只在默认表」死因、relay 的 src 反欺骗问题**全部无关**。

§4 实现硬口径（给契约/实现，均由本轮实测定）
- tap 生命周期：`create tap`（VPP 侧默认 `tapN`、内核侧由 `host-if-name` 指定）→ **必须** `set interface l2 bridge <tap> <bd>`
  与 `set interface state up`；**内核侧接口也要 up**（AF_PACKET 才能收）。VPP 重启两项全失 ⇒ 恢复重放必须重建。
- 消息面：`govpp/binapi/tapv2` 有 `TapCreateV3`（含 HostIfName/Tag 等字段）与 `TapDeleteV2`；
  Tag 可作为「这是产品的 DHCP tap」的查找依据（VPP 重启后按 tag 搜存量）。
- **tap 会成为 BD 成员口**：产品的交换机读视图（#326 派生端口）会把它当端口列出（本轮实测：`show virtual-switches sem-vs`
  的 ports 里出现 `port tap0`）⇒ 必须按内置口**过滤/标注**，且不得被用户当成员口删除。
- 与 relay **互斥**：relay 的 proxy 会夺走 UDP/67 的处理权（见 §5 R140-1 同机理），同一交换机同时配二者必然互相踩；
  v1 校验期直接拒绝并存。
- 真实客户端从「广播」到「单播续租」的切换点是拿到 ACK 之后（server-id=BVI，客户端 ARP 网关后单播）——
  服务器必须在两条入径上都可达（本架构天然满足）。

§5 新登记缺陷（真机复现，走产品路径）
- **R140-1（中）relay 撤销后 UDP/67 的 proxy 处理残留，域内 DHCP 包被静默吞掉**：
  产品路径 `set virtual-switches sem-vs dhcp-relay server 192.168.99.10`（rev 1478）→ 注入 UDP/67 包
  被 proxy 正常中继（`dhcp-proxy-to-server · DHCP packets relayed` +1）；
  再 `delete virtual-switches sem-vs dhcp-relay`（rev 1479，`vppctl show dhcp proxy` 已空）→ **同一包不再到 punt**，
  而是被 proxy 节点按 `dhcp-proxy-to-server · no dhcp server configured` 丢弃（计数 +2、punt 无收包）。
  **可恢复**：同端口重新注册 punt（deregister+register）即夺回（实测后 punt 恢复收包）。
  ⇒ 影响：relay 用过又删掉的域，客户端 DHCP 实际被吞（若此时启用 DHCP server，其 punt 也必须重注册才有效）；
  修法方向：DHCP server 的 punt 注册不能只在「启用↔停用」边沿做，须在 relay 变化后重申（或按巡检自愈）。
- 现场观察（非缺陷，登记备查）：`vppctl packet-generator new` 建流会**顺带创建 pg-N 接口**（删流不删接口；
  VPP 重启后消失）。本轮据此解释了接口清单里出现过的 `pg-1`。
