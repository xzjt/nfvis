----- §1 修复前复现（v1.1.48，同一脚本三条都成立）-----------------------------------

R86-10：同一 candidate 内「改 NAT 出接口 + 删旧 L3 交换机」必然失败
  拓扑：vs-in（inside，池落它的表）/ vs-old（ens192 10.10.10.1/24，旧出接口所在）/
        vs-keep（ens224 192.168.155.20/24，新出接口所在）；`nat rules 10` 出接口 = ens192。
  独立事实源（`vppctl show ip fib summary`，提交前）：vs-old 的表带 `nat44-ei-hi:1`
        （NAT44 把该表当 outside 后 VPP 留的引用；inside 表另有 `nat44-ei-low:6`）。
  一条提交：
        set nat rules 10 … virtual-switch vs-in action interface ens224 source-pool p1
        delete virtual-switches vs-old
        commit
      ⇒ `%% 底座下发失败（已补偿）: 下发失败 del-vrf[vs-old]: VRF 对应的 IP 表删除后仍存在于
        VPP（未收敛）: IP table 12675530（IPv4）在删除后仍存在于 VPP，vs-old 的数据面未收敛
        （表可能仍被数据面插件引用：NAT44 用过这张表后 VPP 不释放该引用，执行 request vpp
        restart 后重试删除）`
  提交后事实：`show alarms active` = **（无 active 告警）**；被回滚的配置仍指向旧出接口
        （`vppctl show nat44 ei interfaces` = `ens192 out`）；vs-old 的表仍在，且 **interface 锁
        已消失**（ens192 已被失败的删表操作解绑）——即数据面已偏离配置而无人知道。

R86-9：补偿也失败时，残渣只出现在当次提交输出里
  构造（一条提交）：新建 `vs-lock`（L3）→ NAT 规则改引用它 → 声明一台 `vm-r87`，其
        `cloud-init user-data /root/does-not-exist-r87.sh`（apply 阶段读文件必失败）。
  下发顺序（vrf → nat → vm）⇒ vm 失败 → 逆序补偿：先撤 NAT，再撤 `vrf[vs-lock]`
        （`DeleteVRF` 读回发现表仍在 = 上面那把锁）⇒ 补偿失败。
  提交输出（1.1.48）：`%% 底座下发失败（已补偿）: 下发失败 vm[vm-r87]: 生成 VM vm-r87
        cloud-init seed: 读取 user-data 文件 …: no such file or directory;
        补偿失败 vrf[vs-lock]: VRF 对应的 IP 表删除后仍存在于 VPP（未收敛）: IP table 9292598
        （IPv4）在删除后仍存在于 VPP …`
  提交后：`show alarms active` = **（无 active 告警）**——残渣（多出来的 9292598 表）
        事后完全不可见，而配置里已没有 vs-lock。

R87-1（本轮新发现）：接口换表后旧表登记残留，删旧表会把接口踢回默认表
  一条提交：`set virtual-switches vs-keep l3-interface ens192 ip address 10.10.10.1/24`
        （改挂）+ `delete virtual-switches vs-old` ⇒ **commit 成功（rev 250）**，但
  `vppctl show interface address`：
        ens192 (up):            ← 既无地址
        ens224 (dn): L3 192.168.155.20/24 ip4 table-id 9767356
  即：配置说 ens192 是 vs-keep 的 L3 接口且带 10.10.10.1/24，数据面却在默认表且无地址，
  全程零报错（旧表成员清单里还留着它，删旧表时"照章"清地址 + 解绑）。

----- §2 R86-10 复验（1.1.49~dev3，同一拓扑与脚本）-----------------------------------
  前置（rev 252 提交后）：`vppctl show ip fib summary` 三张表，vs-old 带 `nat44-ei-hi:1`；
        `show nat44 ei interfaces` = `ens192 out`。
  同一条提交（改出接口 + 删旧交换机）：
        [ok] nat rules 10 … action interface ens224 source-pool p1
        已删除 virtual-switches vs-old（未提交）
        commit 成功 (revision 253)
        警告: L3 交换机 vs-old 的表被 NAT 使用过：VPP 不释放该引用，表要到 request vpp restart
              后才从数据面移除（在此之前该表仍留在数据面，已记告警）
  提交后：
    - `show alarms active`：
        warning  COMMIT_VRF_DELETE_DEFERRED  vs-old  2026-09-29 05:50:58
        L3 交换机 vs-old 的表在数据面仍存在（NAT 用过该表后 VPP 不释放引用，只有重启数据面
        才会移除）：配置已删除，执行 request vpp restart 后自动清理；在此之前该表仍留在数据面
    - `vppctl show ip fib summary`：`vs-old, … locks:[nat44-ei-hi:1]`（表确实还在——提交成功
      不等于表已消失，这句话在提交输出与告警里都写明了）；
      `show nat44 ei interfaces` = `ens224 out`（出接口已改到新交换机）；
      `show interface address`：ens192 已解绑、无地址（它不再属于任何交换机，符合新配置）。
  自动清理与消警：`request vpp restart --yes` → 恢复收敛后
    - `vppctl show ip fib summary`：只剩 vs-keep / vs-in（**vs-old 的表已消失**）；
    - `show alarms active` = （无 active 告警），`show alarms resolved` 留该条记录（可追溯）；
    - journal：`恢复收敛完成`；（同族的「删表延后项已清理」日志见 §3 的补偿场景）。
  跨进程复核（R86-9 的「事后不可见」）：重启 nfvisd（不重启 VPP）后，残留在**新进程**里
    仍然可见——恢复收敛按「配置声明集 ⇄ VPP 实况」对账：
        warning  VRF_TABLE_LEFTOVER  ip-table/9292598  2026-09-29 06:05:44
        数据面存在配置未声明的 IP 表 9292598：多来自「删表延后」或提交补偿失败留下的残渣
        （不会被任何配置引用），执行 request vpp restart 后自动清理；若该表是手工 vppctl
        创建的，请自行核对
        （journal 同时有一条「网络恢复收敛未收敛项 ip-table/9292598: …」）
    随后 `request vpp restart` ⇒ 表消失、该告警自动消解（active 空、resolved 留痕）。

----- §8 本轮登记未修 / 已知限制 ------------------------------------------------------
  - `COMMIT_COMPENSATION_FAILED` 的**通用**消解路径只有两条：同一对象的计划操作下次成功执行；
    或该对象是 VRF 表类残渣且网络侧确认表已清理（§3 的路径）。其它对象类型的残渣（例如某个
    NAT 特性没被恢复）在**不动配置**的前提下不会被自动消解——告警文案已写明复原方式
    （重试同一提交 / 先 request vpp restart 再提交）。V1 的告警表本身是进程内的，
    nfvisd 重启会丢掉历史；**表类残渣**不受此限（§2 的跨进程复核）。
  - `VRF_TABLE_LEFTOVER` 的判据是「VPP 里的 IP 表 ∉ 配置声明集」，因此**手工 `vppctl` 建的表**
    同样会报（文案里已写明这一可能）——这是有意的：配置与数据面不一致就该有人看见。
  - 策略上仍不自动重启数据面：产品只把「需要重启」这件事说清楚（提交警告 + 告警 + 手册 §8.8），
    重启仍由操作者决定（`request vpp restart` 是一次明确的数据面中断）。
