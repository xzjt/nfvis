----- 0. 测试方法 -----
分 6 阶段，脚本化（逐条独立 CLI 会话，避免一条失败掩盖其它条）：
  阶段 1 show 只读；阶段 2 配置语句（先提交前置对象，再逐条独立会话）；阶段 3 前置对象（镜像/VM/容器）；
  阶段 4 request 运维动作；阶段 5 操作命令与管道；阶段 6 事务语义。
判定：输出含行首 % / %% 或「校验失败」即失败；**预期报错**（环境受限 / 防呆守卫正确拒绝）单列。
失败分三类并分别标注：(a) 真缺陷（§2、§2b）；(b) 环境受限（SR-IOV 无 PF/VF）；
(c) 用例本身问题（重复设置默认值触发「语句未产生配置变更」、未带引号的多词取值、
VRF 名写错、trace export 隐含 stop 后重复 stop、脚本模式手写 discard 与自动收尾重复）。
**不把 (b)(c) 混入缺陷数**。

脚本已整理为**可复用、可反复运行**的工具：`contrib/scripts/cli-fulltest.sh`
（`bash contrib/scripts/cli-fulltest.sh [阶段号...]`；前置见脚本头部）。

----- 2. 发现并修复的 5 处真缺陷（§2b 另加 2 处，共 7 处；全部「契约已声明但经 CLI 不可用」）-----

【缺陷 1】set vpp dpdk dev <全局默认> 完全不可用（契约 §2.9）
$ nfvis-cli -c "configure\nset vpp dpdk dev rx-queues 2"
  %% 取值类型不符: json: cannot unmarshal array into Go struct field
     VppDPDK.vpp.dpdk.dev of type model.VppDevDefault
根因：`dev` 关键字下有 `<ifname>` 参数子节点 → 通用遍历把它当**数组容器**写 JSON 数组，
      而模型 `vpp.dpdk.dev` 是**对象**（VppDevDefault；per-NIC 覆盖在兄弟字段 `per_dev` 数组）。
      4 个参数（rx-queues/tx-queues/rx-descriptors/tx-descriptors）全部如此。
修复后：
  rx-queues      -> [ok] vpp dpdk dev rx-queues 8
  tx-queues      -> [ok] vpp dpdk dev tx-queues 8
  rx-descriptors -> [ok] vpp dpdk dev rx-descriptors 8
  tx-descriptors -> [ok] vpp dpdk dev tx-descriptors 8
落库（commit 后 show configuration）：
            rx-queues 8;

【缺陷 2】set system ntp server <ip|host> [prefer] 不可用（契约 §2.2）
$ nfvis-cli -c "configure\nset system ntp server 192.168.155.1"
  %% 配置不完整，缺少取值: system ntp server 192.168.155.1
$ nfvis-cli -c "configure\nset system ntp server 192.168.155.1 prefer"
  %% 未知语句: "prefer"
根因：模型为对象数组 `system.ntp[{server,prefer}]`，CLI 多一层 `server` 关键字，且 `prefer`
      是无值 flag；通用遍历既落不到 `ntp` 键（末位实例参数不终止语句 → 报「缺少取值」），
      也无法以 flag 结尾。
修复后：
  [ok] system ntp server 192.168.155.1
  [ok] system ntp server 192.168.155.2 prefer
落库：server 192.168.155.1;  prefer true;

【缺陷 3】VM stop 成功却报「连接 nfvisd 失败」（FR-CMP-011）
现象（客户端超时 30s，服务端 ACPI 等待上限也是 30s）：
  $ time nfvis-cli -c "request virtual-machine-functions cli-vm stop"
  %% 连接 nfvisd 失败: Post "http://127.0.0.1:18443/api/v1/cli/execute":
     context deadline exceeded (Client.Timeout exceeded while awaiting headers)
  stop 用时: 30s
  stop 后状态: state shutoff;      ← 实际已停成功
根因：`pkg/cliclient` HTTP 超时 30s **等于** 服务端 `compute.StopTimeout`（默认 30s）。
      凡走「guest 不响应 ACPI → 超时强杀」路径的 stop **必定**先触发客户端超时。
      空白盘/无 guest agent 的 VM 100% 复现（集成测试亦记「空白盘走强杀路径」）。
修复：RequestTimeout 提至 90s，且超时与真正连不上**分开报**。
修复后（**空白盘**，确定性走 30s 强杀路径）：
  $ nfvis-cli -c "request virtual-machine-functions blank-vm stop"
  停止 VNF blank-vm 已受理
  用时 31s
  结果状态: state shutoff;

【缺陷 4】show vrfs <不存在> routes 静默为空（FR-NET-013）
$ nfvis-cli -c "show vrfs ghost-vrf"          → % VRF ghost-vrf 不存在
$ nfvis-cli -c "show vrfs ghost-vrf routes"   → （FIB 无路由）      ← 误导：其实是 VRF 不存在
根因：showVrfRoutes 未校验 VRF 是否在 committed 配置中；VPP 对不存在的 VRF 返回空表。
修复后：show vrfs ghost-vrf routes → % VRF ghost-vrf 不存在
        （存在者不受影响：show vrfs vs-l3 routes → ::/0 与 fe80::/10 正常渲染）

【缺陷 5】annotate 只认绝对路径（FR-CFG-007）
$ nfvis-cli -c "configure\nedit system\nannotate hostname \"注释A\""
  %% 未知命令: "hostname"
$ nfvis-cli -c "configure\nannotate system hostname \"注释B\""     → [ok]（仅绝对路径可用）
根因：annotate 不走 session 层级解析（canonicalize 对 annotate 原样返回 token），
      与同级 set/delete/show 行为不一致。
修复后：
  $ nfvis-cli -c "configure\nedit system\nannotate hostname \"相对路径注释\"\ntop\ncommit"
  [ok] system hostname 注释已更新
  commit 成功 (revision 3)
  $ show configuration → /* system hostname: 相对路径注释 */
绝对路径写法保留可用（向后兼容）。

【缺陷 6】set system dns server <ip> secondary <ip> 不可用（契约 §2.2）
$ nfvis-cli -c "configure\nset system dns server 8.8.8.8"                    → [ok]
$ nfvis-cli -c "configure\nset system dns server 8.8.8.8 secondary 8.8.4.4"
  %% 未知语句: "secondary"
根因：通用遍历在消费完第一个 IP 后会**下潜到参数节点**（为支持「参数的子关键字」如 vnf 下的
      interface），导致该参数的同级关键字 `secondary` 不再可见。
修复后：$ ... server 8.8.8.8 secondary 8.8.4.4  → [ok] system dns server 8.8.8.8 secondary 8.8.4.4
落库：dns-servers [ 8.8.8.8 8.8.4.4 ];

【缺陷 7】set resource-pools cpu numa node <n> cores <list> 不可用（契约 §2.6）
$ nfvis-cli -c "configure\nset resource-pools cpu numa node 0 cores 1-4"
  %% 取值类型不符: json: cannot unmarshal object into Go struct field
     CPUSetup.resource_pools.cpu.numa of type []model.NumaNode
根因：模型是对象数组 cpu.numa[{node,cores}]，CLI 多一层 `node` 关键字，通用遍历把 numa 写成
      **对象**（`identityFields` 虽已含 numa→node，但遍历未走到实例数组分支）。
修复后（真机）：
  [ok] resource-pools cpu numa node 0 cores 1-4
  commit 成功（先配 isolated-cores 1-4，否则校验会正确拒绝「核不在隔离核池内」）
落库：numa 0 { cores [ 1 2 3 4 ]; node 0; }
