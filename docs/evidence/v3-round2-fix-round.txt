§0 摘要
--------------------------------------------------------------------------------
· 五轮**能力 spike** 在真机上钉死了两处此前只有推理的语义：① 同一 clsact hook 低 pref 的 filter
  判决 ≥0 会**短路**后续 filter（police 默认 0 / mirred 默认 pipe），`conform-exceed drop/continue`

  别处 drop（含宿主 `-P FORWARD DROP`）——#410 F2 的修法被证伪并更正为「检测 + 告警 + 照做指引」。

§2 能力 spike（真机；五轮，全部只碰 dummy/veth/netns，跑完清理核对残留=0）
--------------------------------------------------------------------------------
2.1 tc 判决矩阵（veth 夹具；收包侧 clsact，pref10 被测、pref30 探针）
    · `police ... drop`（无 continue）：pref10 `Sent 305`、pref30 `Sent 0` ⇒ **短路成立**。
    · `police ... drop continue` / `police ... continue` / `conform-exceed continue/drop`：
      **探针仍 0**（前两者只改「超限动作」，后者语义相反：超限继续、未超限被丢）。
    · `police ... conform-exceed drop/continue`：1kbit/burst 1000 下 pref10
      `Sent 301 (dropped 285, overlimits 285)`、pref30 探针 `Sent 16`（=未超限的那些）；
      10gbit 下 pref10 `dropped 0`、探针 `Sent 300` ⇒ **超限丢、未超限继续遍历**（正是 QoS 所需）。
    · `mirred egress mirror dev X continue`：语法被接受、**镜像仍发生**（对端 veth rx 增量 293，
      对照组默认 pipe 303）、后续 filter 可收到包（探针 300）⇒ 镜像族用它解除短路。
2.2 nft 转发四态（两 netns + 两条 veth；该机 `iptables -S FORWARD` 首行即 `-P FORWARD DROP`）
    · 策略 ACCEPT ⇒ 转发 **通**；策略恢复 DROP ⇒ **不通**；
    · 策略 DROP + 产品式 `-10` accept 链（`iifname/oifname` 集合）在场 ⇒ 仍**不通**；
    · 策略 DROP + 只加**单向** accept 规则 ⇒ 仍不通（回程方向被丢）。
    ⇒ 结论：`-10` accept **不能**豁免同 hook 其余链的策略 drop；要真放行必须写进**真正生效**的链
      （且双向）——产品按「不碰宿主规则」口径改为检测 + 告警 + 照做指引。
2.3 `ip -j link show` 的 `linkinfo`（bridge/vrf/vlan/bond/veth 五类逐条）
    · **不带 `-d` 时 `linkinfo` 键不存在**（info_kind=None）⇒ 修复前 `DevType` 恒 `physical`；
    · 带 `-d` 时 info_kind 正确（bridge/vrf/vlan/bond/veth）⇒ `state.go` 补 `-d` 的依据。
2.4 `bridge -j link show master <br>` 与 `/sys/class/net/<tap>/statistics` 语义、宿主与 VM 同二层
    拓扑（前几轮已证）沿用。

§7 本轮新发现（体检报告未列；已处理或登记）
--------------------------------------------------------------------------------
1. **`cross-connect` 的 CLI 叶子与模型不一致**：命令树把 `virtual-switches <n> cross-connect`
   声明为两个位置参数（`<port-a> <port-b>`），而模型字段是 `bool` ⇒ CLI 语句**不可用**
   （`set virtual-switches vs-empty cross-connect ens192 ens224` 会报
   `cannot unmarshal array into Go struct field … cross_connect of type bool`）；只有 REST 可达。
   本轮的内核拒绝因此经 REST 验证（§3.4）。建议：定裁 cross-connect 的 CLI 形态（bool 还是两端口对）
   并修树/模型之一 + 补覆盖守护。已登记 `docs/v3待做.md`。
2. **删除交换机端口的叶子后留「空壳端口」**：`delete virtual-switches <n> ports 2 interface ens224`
   只清叶子，ports[2] 仍在且违反「端口必须且只能指定 interface/vnf/container 之一」，
   后续提交被这条打断；应整条删 `delete virtual-switches <n> ports 2`（或让叶子删除回收空壳，
   与 `pruneEmptySingleton` 同口径）。已登记。
3. **R2-3 的读视图计数口径**（内核 tc 的 dropped/overlimits 与 conform/exceed/violate 不对应）：
   如实不映射并在 detail 里说明（见 §3.3）；若要给三档计数需重做语义，登记待定裁。
4. **风暴两档并存的边界**：广播档（pref 30）保持裸 `drop` 终止遍历，广播帧只落广播档；
   只配组播档时广播帧按 I/G 位落入组播档（与 VPP 无广播档时一致）。已写进代码注释与手册。
5. **清场后仍留一张空 `inet nfvis-forward` 表**（R2-16 幂等重建的副产物）：与 #410 F3 判为缺陷的
   「`delete nat` 留空表」同类。已回修为「无数据面设备时回收整表、有设备时 flush + 重写」，
   并补红-绿单测；真机复核见 §6.1。
6. **内核数据面 bond 成员 enslave 失败（真机 dev4 抓到，P1 级）**：声明 `interfaces ens192` +
   `bonds b0 members 1 ens192` 后提交，底座补偿报
   `ip link set dev ens192 master b0: … Error: Device can not be enslaved while up.`
   ——内核 bonding **要求成员先 down**（VPP 数据面无此约束，故此前各轮未暴露）。
   修法：`ApplyBond` 对每个成员 **先 down → enslave**，全部 enslave 完、bond `up` 之后**成员再 up**
   （回读确认）；属性重建路径同受益。已回修（红-绿单测断言命令序列），真机复核见 §3.9。
