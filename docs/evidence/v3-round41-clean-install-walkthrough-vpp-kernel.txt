    提交期**逐条拒绝**并给照做路径：① `vrfs[vs-inside].l3_interfaces[vh-vnf-a-nic0]`
    「vNIC 的派生名在内核侧不存在该设备，请改用物理口/bond，或切回 VPP」；

§7 新登记缺陷（两条，均为口径/契约）
--------------------------------------------------------------------------------
**R41-1（中）交换机「成员端口」同一事实三个数，契约未说明**
  · 现场（最小复现，rev 187~189）：仅配 `set virtual-switches cal-test type l2`（无 ports）
    → 再 `set virtual-switches cal-test gateway ip 192.168.77.1/24`（产品据此建 BVI）。
  · 读到：
      - `GET /virtual-switches` 的该对象 `ports` = **null / 0 条**（= 配置库原始 `ports` 字段）
      - `GET /virtual-switches/cal-test/ports` = **1 条**（bvi1，source=runtime）
      - CLI `show virtual-switches` 的 Ports 列 = **1**
      - CLI `show virtual-switches cal-test ports` = **1 条**（bvi1）
  · 对照（更早的现场）：vs-lan 有 1 静态口 + 2 VNF 派生 + 1 容器派生 + 2 运行态口时，
    出现 **CLI 列表 3 / REST 列表 1 / ports 端点 6** 三个数并存（CLI 列表过滤了内置 tap
    与部分派生项，REST 列表只给配置静态项）。
  · 根因：`handleGetVSwitches`（internal/api/resources.go:346）直接序列化
    `model.VirtualSwitch`，其 `ports` 是**配置原始端口**；而 `/ports` 端点与 CLI 走
    `switchPortViews`（`model.DerivedSwitchPorts` ∪ 运行态，且剔除内置 DHCP tap）。
    `docs/NFViS-openapi.yaml` 的 `VirtualSwitch.ports` **没有任何 description**，
    openapi 读者无法分辨两者口径不同。
  · 影响：按名单取 `ports` 做「这个交换机有几个口/这个口在不在」的判断会漏掉
    VNF/容器派生与运行时口（bvi0/bvi1、vxlan、VNF vhost、容器 veth），
    与 AGENTS.md「同一事实两个视图必须并排读、口径须同一」的红线相违。
  · 建议修法（未实施）：① 契约补 description（列表 `ports` = **配置声明**，
    成员读视图见 `/ports`）；② 或在列表视图里改名/加 `ports_declared_count` +
    `ports_runtime_count`，避免与成员读视图同名不同义。**须先定裁口径再改实现**。
  · **补充追查（用户追问「是不是内核/VPP 不同导致」后的实测与代码核实）**：
    **主因与数据面无关**，但**确有一层与数据面有关**，须拆成三层看：
    ① **REST 列表**＝纯配置（`handleGetVSwitches` 只序列化 `cfg.VirtualSwitches`，不碰数据面）；
    ② **`/ports` 与 CLI `… ports`**＝配置派生 ∪ 运行态（`switchPortViews`）；
       —— ①② 的差是「运行态有多少成员」，**两个数据面都会有这个差**，不是切换造成的。
       本场实测（VPP，vs-lan 静态口只有 ens192）：
         REST 列表 `1 条（ens192）`｜`/ports` `2 条（ens192, bvi0）`｜
         CLI 列表 **2**｜`vppctl show bridge-domain 14615916 detail` 真实成员 `bvi0/ens192/tap0`。
    ③ **CLI 列表的 `Ports` 列取的是运行态 BD 成员数**（`len(bd.Ports)`，已剔内置 tap），
       **不是** `/ports` 那套派生并集 ⇒ **CLI 列表与 CLI `… ports` 本身也不同口径**
       （前者看不到「配置里声明了、数据面还没建」的 VNF vNIC）。这是本缺陷最容易被忽略的一层。
    ⇒ 三数并存的**主因是「配置 / 配置∪运行态 / 运行态」三种取数**，与数据面无关；
    数据面的影响只在「运行态成员有多少、派生名怎么叫」（见 R41-3）。
  · **与数据面有关的那一层（新登记 R41-3）**：派生条目**取名**两数据面不对称——
    `internal/model/switchports.go:197 AttachedPortName` 只有容器分支读 `DataPlaneMode()`
    （内核→veth 宿主端 `nfvisct…`，#442 修 R5-1）；**VNF 分支（:223）不看数据面**，
    内核下仍返回 VPP 逻辑名 `vh-<vm>-<nic>`，而内核侧真实设备是 libvirt 的 `vnetN`
    （§4.4 实测 `interface type='bridge'`，宿主侧 `vnet0` 在 bridge 里 forwarding；
    `netkernel/api_surface.go:161` 已如实写明「产品侧没有可靠的 tap 名映射」）。
    后果：内核现场端口表出现「`vh-…` 派生 + `vnet0` 运行态」**两条并列**、数字偏大，
    且按 `vh-…` 去 `ip link` 找不到设备——R5-1 同类问题在 **VNF 侧**的残留。

**R41-3（中，2026-10-21 追查新增）内核数据面下 VNF 派生端口名仍是 VPP 逻辑名**
  · 根因如上（`AttachedPortName` 的 VNF 分支不看 `DataPlaneMode()`）。
  · **真机复验（同日，switch 到 kernel + 新建 VNF `r41v`，rev 191）**：
      宿主 `bridge link show master vs-lan` 真实成员 = `ens192` / `vnet0` / `nfvisdh…(内置 tap)`；
      CLI `show virtual-switches vs-lan ports`：
        `ens192  config`｜`vh-r41v-nic0  vnf`｜`vnet0  runtime`  ← **同一 vNIC 两条并列**
      `GET …/ports` 同为 **3 条**（含 `vh-r41v-nic0` source=vnf）；CLI 列表 Ports 列 = **2**
      （纯运行态，故不含 `vh-`）。
      按派生名核对：`ip link show vh-r41v-nic0` → **`Device "vh-r41v-nic0" does not exist.`**
      而 `ip -br link show vnet0` → 存在且 UP。⇒ 「表里有、设备没有」**实测成立**。
  · 影响：① 端口表两条并列、数字偏大；② 按名核对找不到设备（`vh-…` 在内核不存在）；
    ③ 反查 vNIC 归属被引到不存在的名字。
  · 修法方向（**待定裁**）：① 内核侧 VNF 派生名**留空**、退回 `<vm>/<nic>` 语义名
    （`AttachedPortName` 注释已有「无法确定时返回 ""，不编造不存在的接口名」的既有约定）——
    小且与既有口径一致；② 编排层在 DefineVM 时把 libvirt 分配的 tap 名记进运行态簿记
    （与容器 veth 同路数）——完整但需新增簿记与生命周期维护。**倾向 ①**。
  · 连带：`CheckVnfPorts` 在核下恒 no-op（`VNF_PORT_DOWN` 在核下不判，有意避免误报）——
    若走 ② 可顺带转成可判；若走 ① 则该告警族在核下继续「如实不报」，须在手册写明。


**R41-2（中）内核数据面下 `show nat` 整条命令失败（与同族降级口径不一致）**
  · 现场：`set system dataplane kernel` + 已配 NAT 规则与池（rev 40 同域 NAT），
    VPP 侧同配置下 `show nat` 正常（rc=0）。
  · 读到：`show nat` 先打印配置段（池/规则），随后
      `%% 该能力在 Linux 内核网络数据面下不受支持：NAT 会话表`
    → **整条命令判失败**（CLI 退出码 **1**）；`show nat sessions` 同。
  · 对照同族：`show vxlan tunnels` 在内核下**行内降级**（`运行态不可用（…不受支持…）`，
    配置字段仍给出），**退出码 0**；`show virtual-machine-functions … interfaces` 等亦行内说明。
    REST 侧 `GET /nat` = 200（配置齐全）、`GET /nat/sessions` = **501 NOT_IMPLEMENTED**
    （**这条是对的**，监控能区分「不支持」与「故障」）。
  · 根因：`execShowNat`（internal/api/cli_net_runtime_show.go:404）把
    `x.natRT.Sessions()` 的错误**原样带 `%%` 前缀返回**，于是被 CLI 脚本模式判成
    「命令执行失败」；而同族「能力不支持」的读视图（vxlan）在渲染层做了行内降级。
  · 影响：内核数据面下**任何** `show nat` 脚本/巡检都会判失败并中止后续行
    （`-f`/`-c` 脚本在第 1 行停止），把「该能力在此数据面不存在」误报为「命令坏了」；
    与 `rest_501_test.go` 里已确立的「能力不受支持 ≠ 服务异常」口径不一致。
  · 建议修法（未实施）：把 `netkernel.ErrUnsupported` 一类**能力哨兵**在 CLI 渲染层
    转成**行内降级**（照 `show vxlan tunnels` 的既有做法，配置段照常给 + 末行说明
    「运行态不可用：该能力在内核数据面不受支持，切回 VPP 后可用」），退出码 0；
    真实执行故障仍保留 `%%`。

· **R41-O1** 同一轮「多口 unbind-dpdk」时，第一个口的收敛会对**尚未交还的第二个口**

10.6 **⚠️ 本轮踩到并根治的一个坑：整文件 CRLF 污染让三条契约守护同时「假报排版坏了」**
  · 现象：`make check` 的 `test` 里三条字段级守护同时失败，报的都是
    「契约里找不到 QosPolicy / PortMirroring / SwitchPortView schema（排版变了？）」。
  · 真因：子智能体在 Windows 上改 `docs/NFViS-openapi.yaml` 时把**整个文件**的行尾写成了 CRLF。
    `.gitattributes` 有 `* text=auto eol=lf`，提交时会被归一化 ⇒ **`git diff` 只显示真实的 30 行改动，
    污染在 git 层面完全看不见**；而这三条守护是「按 `
` 切行 + 精确字符串比较」
    （`if l == "    SwitchPortView:"`）⇒ 每行尾部多一个 ``，精确匹配永不命中。
    更隐蔽的是：CI 在 Linux 检出为 LF 会**全绿**，只有 Windows 工作区才红。
  · 处置：把 4 个文件（openapi.yaml + AGENTS.md + 本证据 + round39 证据 + round-d485 证据）的行尾
    转回 LF；新增守护 `contrib/scripts/check_line_endings.sh`（`git ls-files --eol` 判 `w/crlf`，
    未跟踪文件退化为查 CR），带 `--selftest` 自校准（已知 LF → 通过 / 已知 CRLF → 报违规），
    已接进 `make toolcheck`（`make check` 的一环）。
  · **教训**：Windows 上用整文件重写的方式改仓库文件时，**必须先确认行尾**；
    「git diff 干净」不能证明文件没被污染——`eol=lf` 会在提交时把污染藏起来。
