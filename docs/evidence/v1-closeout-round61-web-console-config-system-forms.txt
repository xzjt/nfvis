**口令处理（本段的关键设计）**：模型只有 `password_hash`，故明文在**浏览器内**就地派生成与命令行同格式的
PBKDF2-SHA256/60 万轮哈希（盐 16B、密钥 32B、无填充 base64），派生后清空控件；口令策略在派生**之前**按服务端
同一判据本地判；**非安全上下文（明文 HTTP 打开控制台）没有 Web Crypto → 拒绝并说明，绝不退化成明文**。

**顺带修掉 2 个真缺陷**：① `vpp.dpdk.per_dev` 的定位器漏一层 `dpdk`（新增行会写进模型里不存在的
`vpp.per_dev`，静默丢数据）；② 系统段 DNS/NTP 原「两槽位 + 整表替换」会**静默丢掉第 3 条**（NTP 改子表、DNS 改多值）。

**未覆盖（如实登记）**：证书/镜像上传与 `request` 族运维动作（属刀 4 的中危确认范围）、
`interfaces … sriov vf-count`（无硬件，沿用界面暂不提供）、`delete vpp cpu|memory|dpdk` 整组（逐字段清空等价）。

----- 4. 追记（round61 补验，2026-09-24）：口令字段那条**仍未判定**，登记为待查项 -----
按第 2 节的补验方法在明文 HTTP 开发态实例上复跑：定位到口令控件（`#cfg-df-36`，type=password），
填入明文 `Xx9!zzzz` → 点「保存到 candidate」→ **界面报「已保存到 candidate（有未提交变更）」**，
且**口令控件里明文仍在**（与页面自称"派生后清空控件""明文不留在页面上"不符）。

代码侧确认**有**这条防线（`app.js`：`if (!c.subtle || !c.getRandomValues) throw new Error('本页面不能派生口令哈希
（浏览器只在 HTTPS 或 localhost 下提供该能力）…')`），故两种可能都还没排除：
(a) 派生确实抛错、口令**没写进候选**（安全），但界面**谎报成功**且没清控件（假绿 + 文案不实）；
(b) 明文被写进了候选（严重）。
**本次没能判定**：我第一次探测候选时，候选已被同一步骤里的「丢弃」删掉（探针顺序错了）。
**复现与判定步骤（下一刀开头做，别再漏）**：
1. 明文 HTTP 起开发态实例 → `#/config` → 开始编辑 → 在「登录与口令策略」节的口令控件填明文；
2. 点「保存到 candidate」→ **先别丢弃**，用独立事实源看候选：`GET /api/v1/configuration/candidate`
   → `system.login.users[*].password_hash` 是 `pbkdf2$…`（写了哈希）、是明文（严重缺陷）、还是**该用户条目不存在**（没写）；
3. 再看界面消息与控件内容是否与事实一致（不一致就是假绿/文案不实，要修）；
4. 结论落进证据文件与待办，再决定修法。

----- 5. 判定（2026-09-24 复跑，按 §4 的步骤；**结论：假绿，非明文泄露**）-----
复跑：明文 HTTP 开发态实例 → `#/config` → 开始编辑 → 在「登录与口令策略」节的口令控件（`#cfg-df-36`）填明文
`Verdict123!x` → 点「保存到 candidate」→ **先不丢弃** → 用独立事实源读候选：

    GET /configuration/candidate → keys: ['candidate','dirty']；system.login.users = 1 条（admin）
      admin | password_hash: **None**        ← 既不是 pbkdf2$…，也不是明文

**判定**：
1. **没有明文泄露**（候选里不是明文）——安全侧没问题；
2. **口令改动被静默丢掉**：候选里该用户的 `password_hash` 为空，而界面报「已保存到 candidate（有未提交变更）」
   ——**假绿**：操作者以为改了口令，实际什么也没改（若真的提交，R44-1 的引擎兜底会拦住"无口令用户"，
   不会锁死账号，但"没改成功却报成功"本身就是缺陷）；
3. **为什么子代理的验证没抓到**：它的 DOM 桩跑在 **Node** 里（`crypto.subtle` 存在、等价于"安全上下文"），
   而目标环境是**明文 HTTP 的浏览器**（没有 `crypto.subtle`）——**验证环境比目标环境更强**，
   于是这条路径根本没被走到。**教训：桩式验证要显式覆盖"能力更弱"的环境**（这里就是删掉/屏蔽 `crypto.subtle` 再跑一遍）。

**修法（下一刀做，判定已定，可以动了）**：
- 口令派生失败时**不要**"存一个没有哈希的用户条目然后报成功"，而要让这次保存**明确失败**并把原因说清
  （页面已在文案里承诺"明文不进配置"；现在需要的是**失败要显式**，而不是静默降级）；
- 保存失败时**保留**口令控件内容（便于切到 HTTPS 后重试）并在消息里写明"请用 HTTPS 打开控制台后重试"；
- 加一条**桩式自校准**：在 DOM 桩里屏蔽 `crypto.subtle` 跑同一路径，断言"保存被拒 + 消息含 HTTPS 提示"
  （这样 CI 能挡住回归；真机/浏览器验收仍是最终判据）。

----- 6. 修复与复验（2026-09-24；**并更正 §5 的判据错误**）-----
**⚠️ 更正 §5**：§5 用「候选里 `password_hash` 为 None」当判据，**这条判据不成立**——`GET /configuration/candidate`
会**脱敏**（`redactConfigView`），该键本来就不返回，修前修后都一样。**假绿本身是真的**（子代理用 DOM 桩对
**修复前的实现**做了红-绿复现：`saved=true`、消息「已保存到 candidate」、只发了一次 PUT 而候选里没有哈希）。
可用的判据是「候选/差异与操作前逐字节一致」与「客户端候选文本里的 `pbkdf2$…`」。

**修复**（提交 `fcd12b0`）：把闸门放在 `cfgSave()` 入口（保存/预校验/提交三条路共同前置）——口令派生失败
（非安全上下文或不合策略）时**整次保存显式失败**、不写 candidate、消息写明原因与"请用 HTTPS（或 localhost）
打开控制台后重试"，并**保留控件内容**便于重试。**顺带修掉同一条路径上第二个真缺陷**：派生是异步的而
`input` 每键一次，原「派生成功即清空控件」在**真人打字**时会把半截口令清掉 → 写进候选的是某个**后缀**的哈希
（对修复前实现实测：控件里只剩 `23!x`）；现改为输入过程不清空、离开控件或点保存时才清空。
**桩式自校准进 CI**：`contrib/scripts/web-console-config-selftest.sh`（+ `.js`，已接进 `make check` 的 toolcheck）——
① 屏蔽 `crypto.subtle` → 保存被拒 + 消息含 HTTPS + 未发写请求 + 控件保留明文；② 提供 `crypto.subtle` → 出现
`pbkdf2$` 前缀 + 控件清空 + **哈希可用 Node `pbkdf2Sync` 独立复算**；③ 不合策略同样显式失败；④ 逐键输入后
只写**整段**口令的哈希。**红-绿**：拆掉闸门 / 换回修复前的 `app.js` → ①③④ 报 ✗。
