NFViS v3 · round27（2026-10-12）：决策 #478 管理面额外监听回环地址
=============================================================
主题：管理口声明后 `nfvisd` 只在管理网卡地址监听，而 `nfvis-cli` 缺省连 `https://127.0.0.1:443`
      ⇒ 本机裸跑 `nfvis-cli` 连接被拒。修法＝主监听之外**额外监听回环 `127.0.0.1:<port>`**。
方式：契约先行（附录 A #478 + AGENTS 计数 379→380）→ 子智能体实现（红-绿）→ make check 七项
      → 交叉编译换装 `3.0.13~dev1` 真机逐条复核。

────────────────────────────────────────────────────────
真机复现并修复：管理口声明后 `ss` 仅见 `192.168.155.129:443`、`127.0.0.1` refused；修复后

#478（v3 线第 75 条）：主监听（管理网卡地址）之外**额外监听回环 `127.0.0.1:<port>`**；
主监听为**通配/回环**本身时**不再重复绑回环**（通配已覆盖回环、且会 EADDRINUSE）；

§2 实现（子智能体）
────────────────────────────────────────────────────────
【设计】`internal/api/server.go`：
- **决策函数**（纯函数）`loopbackListenAddr(mainAddr)`——主监听为通配（host `""`/`0.0.0.0`/`::`）
  或回环（`IsLoopback`/`IsUnspecified`）⇒ 不绑；具体非回环 IP 字面 ⇒ `127.0.0.1:<主监听端口>`；
  主机名（无法判定）保守**不绑**（不猜、避免 EADDRINUSE）。
- **生命周期** `reconcileLoopbackLocked()`（受 `listenMu`）——主监听建立后（`ListenAndServe`）与
  **换绑成功后**（`Rebind` 成功/回退两路径）各协调一次：需要则幂等复用/新建、不需要则关旧。
  回环走**独立 goroutine**，其退出只记日志、**不走 `serveErr` 代际通道**（该通道仅主监听）。
  `Shutdown` 先关回环。
- **换绑顺序**：新主监听若本身覆盖回环（通配/回环），**先放掉回环再绑新主监听**——否则同端口
  具体→通配切换会撞自己占着的 `127.0.0.1:<port>`（EADDRINUSE）被误判失败。回环失败**不影响**
  `Rebind` 返回值/回退。
- TLS：两条监听共用同一 `*http.Server`，`TLSConfig` 抽 `buildTLSConfig` 并由 `tlsOnce` 只设一次
  （避免两 serve goroutine 并发写）；`GetCertificate` 仍每握手读盘，换证即时生效语义不变。
【不改】`nfvis-cli` 缺省、`ResolveListenAddr` 口径、TLS/SAN、`Rebind` 既有对外语义。
【测试可注入】新增 `Server.listenFn`（默认 `net.Listen`）——Windows 上真绑具体非回环地址不可行时，
  用「上报另一个 Addr 的包装监听」模拟、用工厂注入绑定失败。

§3 红-绿测试（internal/api/loopback_test.go）
────────────────────────────────────────────────────────
`TestLoopbackListenAddrDecision`（通配/回环→不绑、具体 v4/v6→`127.0.0.1:<port>`、非法→不绑）、
`TestListenAndServeBindsLoopbackForConcreteMain`（具体主监听 ⇒ 多出 `127.0.0.1:port` 且 200）、
`TestListenAndServeNoLoopbackForWildcardMain`/`…ForLoopbackMain`（工厂仅被请求一次＝不重复绑）、
`TestLoopbackBindFailureDoesNotAffectMain`（注入回环 bind 失败 ⇒ 主监听仍 200、`ListenAndServe` 不返回）、
`TestRebindReconcilesLoopback`（具体↔通配切换协调）、`TestRebindConcreteToWildcardSamePort`
（同端口具体→通配，工厂里探测回环端口模拟真实 OS 的 EADDRINUSE）、
`TestConcreteMainAndLoopbackServeTLS`（两条监听同证书 HTTPS 均 200）。
**红验证**：关掉 `ListenAndServe` 里的协调 ⇒ `BindsLoopback`/`RebindReconcilesLoopback` 失败；
移除 `Rebind` 的「先放回环」⇒ `RebindConcreteToWildcardSamePort` 失败（报「换绑前未释放」）。
`GOFLAGS=-p=1 go test ./internal/api/ ./internal/system/` 全绿（api 513.8s）。

§6 教训（入册）
────────────────────────────────────────────────────────
- **「缺省值」与「实际监听」要成对看**：CLI 缺省 `127.0.0.1` 早已写死、自签 SAN 也早已含回环
  （`ServerCertSANs` 的 `LocalIPs`）——唯独**监听**没绑回环，于是三处里两处就绪、一处缺口，
  裸跑 CLI 才失败。修前先把「谁以为会通」的三处（CLI 缺省 / 证书 SAN / 监听）对齐排查。
- **换绑与「额外监听」的顺序**：具体地址→通配是 EADDRINUSE 的经典陷阱（通配会覆盖自己占的回环端口），
  必须先释放回环再绑新主监听；单测用「探测端口」把 Windows 弱绑会掩蔽的冲突显式造出来。
- **两条监听共用一个 http.Server 时的并发写**：`TLSConfig` 只设一次（`sync.Once`），避免两个 serve
  goroutine 竞争写。
