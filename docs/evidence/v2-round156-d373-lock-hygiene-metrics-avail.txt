§2 实现（c892bf6）
1. **C11**（`internal/orchestrator/network/dhcpserver.go`）：池耗尽告警**决策与应用分离**——`poolAlarmState`（纯决策：池是否耗尽 + 文案）
   与 `applyPoolAlarm`（Raise/Resolve，**不得持 p.mu**）；三个调用点（收包路径 `handleMessage`、15s 巡检 `Reconcile`、`refreshPoolAlarm` 助手）
   改为「锁内取决策、解锁后应用」。告警码/严重度/文案/消解条件**逐字不变**（行为等价，仅持锁范围收窄）。
2. **A10**（`internal/api/metrics.go`）：`vnfMetrics` 在 `engine` 缺失或 `Committed()` 读失败时不再 `return nil`，
   仍发出两 kind 的 `nfvis_vnf_runtime_available`（=0）与聚合计数（=0），与「编排不可用时不计入 running」口径一致。

§3 实现期真回归与修正（教训入册）
- **现象**：既有用例 `TestDHCPServerProviderReconcile`（③「到期回收并落盘」）失败——租约文件里仍留到期条目。
- **定位**（诊断打印对照旧/新实现）：改造前的 `refreshPoolAlarmLocked` 在 `p.alarms == nil` 时**先早退**，
  **从不调用** `rt.leases.free()`；我抽出的 `poolAlarmState` 无条件调 `free()`（内部 `sweep()`），
  于是在 `Reconcile` 的 `Sync` 阶段就**提前删除**了到期条目 ⇒ 其后循环里的 `sweep()` 返回 false ⇒ **不落盘**。
- **修法**：`poolAlarmState` 改方法并返回 `ok`——`alarms == nil` 时 `ok=false`、**不取决策**（不触碰租约表），
  调用点据此跳过应用；既保持改造前行为，又保留「告警已接入时锁外应用」的收益。
- **教益**：抽纯函数时要把**副作用边界**（此处 `free()` 内含 `sweep()`）一起搬过去——「纯」的假设不成立时，
  既有用例就是最好的告警器（本次靠它拦住）。

§4 测试与红-绿
- **C11**（真并发）：`TestPoolAlarmIODoesNotHoldProviderLock`——注入**慢通知器**（前两次通知放行、第 3 次起阻塞），
  占满池→释放→再占回（触发阻塞中的 Raise）；断言**告警 I/O 进行中 provider 锁空闲**（并发 `Leases` 立即返回，500ms 界）、
  释放后收包路径正常返回、告警确在册。**红-绿**：还原「持锁应用」⇒ 用例失败。
  （首版测试自身有缺陷：同步占满池时第 3 条 REQUEST 即触发告警、慢通知器卡死主 goroutine——已改为前两次放行 + 触发放 goroutine。）
- **A10**：`TestVNFMetricsAvailabilityAlwaysEmitted`——engine 缺失与 committed 读失败（关库）两路均**发出**可用性 0 与聚合 0。
  **红-绿**：还原 `return nil` ⇒ 用例失败。
