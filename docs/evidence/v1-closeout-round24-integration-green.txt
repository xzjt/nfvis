----- 1. 根因（两条，都有硬证据）-----

【RC1】产品把 NoCloud seed 挂成 **SATA 光盘**，而 guest 内核缺 `ahci` → seed 不可见 →
       cloud-init **静默禁用自己**，user-data 被丢弃（不是超时，是压根没跑）

链路：`DefaultMachine = "q35"`（internal/orchestrator/compute/domain_xml.go:32）→ seed 挂
`<target dev='sda' bus='sata'/>` → q35 的 SATA 控制器是 ich9-ahci，guest 侧驱动是 `ahci`。

四条独立证据（同一台 VM，宿主侧一切正常）：
① **宿主侧 seed 是挂上的**：`virsh domblklist it-m4-5-vm` → `sda  /root/diagvm/seed.iso`
② **guest 侧没有这个设备**：`lsblk` 只有 `vda/vda1/vda14/vda15`；`ls /dev/sr0 /dev/sda`
   均 "No such file or directory"；`blkid` 无 cidata 卷标
③ **guest 内核压根没加载 libata/ahci**：串口内核日志只有
   `virtio_blk virtio0: [vda] 6291456 512-byte logical blocks`，`grep -ci 'ahci|libata'` = **0**
④ **cloud-init 自己的判定**（`/run/cloud-init/`，经串口登录 guest 读出）：

       # cloud-init-generator.log
       checking for datasource
       ds-identify rc=1
       cloud-init is enabled but no datasource found, disabling

       # ds-identify.log
       FS_LABELS=
       ISO9660_DEVS=
       No ds found [mode=search, notfound=disabled]. Disabled cloud-init [1]

   即 Debian 12 的 cloud-init 22.4.2 策略是 `notfound=disabled`：找不到数据源就**不启动**，
   不报错、不回落。`/var/lib/cloud` 与 `/var/log/cloud-init*` 在 guest 里**完全不存在**。

镜像侧对照（`/lib/modules/<kver>/modules.dep` 实测）：
    debian-12-genericcloud-amd64.qcow2（6.1.0-53-cloud-amd64）：
        ata_piix.ko ✓  ata_generic.ko ✓  **ahci 无（modules.dep / modules.builtin 均无）**
        isofs.ko ✓  sr_mod.ko ✓  vfat.ko ✓
    → 有文件系统驱动但**没有控制器驱动**，设备根本不出现，所以与 iso9660 无关。
    alpine.qcow2（6.6.31-0-virt）：无 iso9660、亦无 ahci。

【RC2】测试的 `runcmd` 把 guest 网卡写死成 `eth0`，而 guest 里的实际网卡名是 **`enp1s0`**

证据（换镜像后主链路用例的 guest 串口，`NFVIS_SERIAL_DUMP` 落盘）：

    [  130.823564] cloud-init[421]: Cloud-init v. 22.4.2 running 'init' ... Up 130.80 seconds.
    [  130.904514] cloud-init[421]: ci-info: | enp1s0 | True | fe80::5054:aaff:fe4f:f605/64 | ...
    [  134.467645] cloud-init[514]: Cannot find device "eth0"
    [  134.479590] cloud-init[514]: Cannot find device "eth0"
    [  134.484455] cloud-init[514]: cc_scripts_user.py[WARNING]: Failed to run module scripts-user
    [  134.686823] cloud-init[514]: Cloud-init v. 22.4.2 finished ... Datasource DataSourceNoCloud [seed=/dev/sr0][dsmode=net].  Up 134.68 seconds
    [FAILED] Failed to start cloud-final.service - Execute cloud user/final scripts.

`Datasource DataSourceNoCloud [seed=/dev/sr0]` 证明 **RC1 已修好**（seed 生效、hostname 变成
`it-m4-11`）；`Cannot find device "eth0"` 说明剩下的失败是测试侧写死了接口名。
产品模型里的 `eth0` 是**逻辑名**（VPP 侧 socket 名 `vh-<vm>-eth0`），与 guest 内核名是两回事。

【时间基线】guest 的地址由 cloud-init 的 **final 阶段**（runcmd）配置，而该阶段
`After=network-online.target`（`/usr/lib/systemd/system/cloud-final.service` 实测）；本用例的
BD 上没有 DHCP，`systemd-networkd-wait-online` 要等约 120s 才失败放行 → guest 到
**uptime ~135s** 才有地址。上一轮按 alpine 的启动速度定的 60s/150s 窗口因此必然误判。

----- 4. 需要更正上一轮记录的一处结论 -----
`docs/V1-收尾待办.md` §2.13 #17 与证据 round23 §2 记的是「**换 Debian genericcloud 后同一条用例通过 ✓**」。
本轮实测**genericcloud 不可能通过**：它的内核缺 `ahci`（见 RC1 证据），seed 根本不可见，
cloud-init 必然自我禁用。round23 §4 记有一次「seed 改 vfat + 以 virtio 磁盘挂载」的实验（后被回退），
该次「通过」很可能发生在实验代码还在树里时（vfat + virtio 绕开了 SATA/ahci 依赖）。
故 #17 的结论应改为：**可用镜像是「完整内核」的 debian-12-generic-amd64，不是 genericcloud**。

----- 5. 本轮登记的发现（未改产品，需决策）-----
- **#22（中）seed 以 SATA 光盘交付，缺 `ahci` 的 guest 内核看不到，且 cloud-init 静默自我禁用**。
  影响面：Debian 的 cloud 内核（genericcloud）、Alpine 的 virt 内核都属此类；这两类恰是 NFV 场景
  常用的精简镜像。操作者可见的后果是「VM 起来了，但我注入的 user-data 没生效」，且**没有任何报错**——
  属项目最在意的「静默无效」类。产品侧可选修法（择一，需决策）：改用 virtio 交付 seed、
  或按机器类型选 guest 普遍支持的控制器、或在 start 后探测 seed 是否被消费并告警。
  本轮**未改产品**（改 seed 交付方式属已发布行为，round23 试过并回退过）。
- **#23（低）产品模型的接口逻辑名与 guest 内核网卡名不一致**：模型/CLI 里是 `eth0`（VPP 侧 socket
  名 `vh-<vm>-eth0`），而 guest 内是 `enp1s0`（systemd 可预测网名）。操作者写 user-data 时若按
  `eth0` 配网卡会得到 `Cannot find device "eth0"`。建议手册在 VM/cloud-init 一节加一句说明
  （本轮未改手册，避免与 §0 的文档轮次混在一起）。
- **#24（低）`test/integration` 里 5 处硬编码核池**已随本轮修掉（原 #18 关闭）。
