§3 本轮真机新发现（如实登记，未改代码）
-----------------------------------------
**R7-1（中）内核数据面下恢复收敛告警不随事实消解（`ReconcileRecoveryAlarms` 为空操作）**
- 时间线（证据 = journal + CLI `show alarms active` + Web 总览告警卡截图
  `docs/images/round7-web-overview-stale-recovery-alarms.png`，全程未改判定条件）：
  - `09:14:40` 按固定动作切内核并 restart（此刻两口仍绑 vfio-pci，内核里没有它们）；
  - `09:14:41` 内核侧恢复重放对 `interfaces/ens192|ens224` 失败 → 落 **error 级
    `RECOVERY_IFACE_MISSING`×2**（journal「网络恢复收敛未收敛项」同刻在场；**此刻告警是对的**）；
  - `09:14:5x` 两口交还内核（unbind → vmxnet3）→ 设备出现、ens192 入桥 UP——**事实已愈合**；
  - 此后多次取样（CLI + Web）两条 error 告警**一直在**，文案仍说「该口当前仍绑定在 vfio-pci 驱动上
    （PCI 0000:0b:00.0）、内核里没有它」——与同刻 `ip -br link`（ens192 UP / ens224 DOWN 按配置）相反；
  - `09:19:59` restart nfvis → `09:20:04`「恢复收敛完成」（本次重放成功）→ 告警被 `alarms.Sync`
    **清掉**（随后「无 active 告警」）。跨度 5 分 18 秒 ≈ **21 个 15s 巡检周期**不消解。
    现场重启后完整自愈（bridge 成员/DNS socket 新 pid/容器 running 均复核对过）。
- 根因（代码）：`internal/orchestrator/netkernel/api_surface.go:47`
  `func (p *Provider) ReconcileRecoveryAlarms(context.Context, model.Config) []error { return nil }`
  ——注释把它归入「VPP 侧登记型对账，内核无对应族」。但内核侧**确实会落这一族告警**
  （`netkernel/recovery.go:42` 按 `network.AlarmIfaceMissing`/`AlarmUnconverged` 落），而内核侧没有任何
  按来源的廉价复核路径：15s 巡检不消解，只有下一次**全量重放**（nfvisd 重启/换数据面）末尾的 `Sync`
  才会重估。与 VPP 侧口径（决策 #333/#367：口已出现即消解、来源对象已删即消解）不一致。
- **VPP 侧对照（同轮实测）**：`09:20:50` 切回 vpp 的重启窗口落同类告警
  （`接口在 VPP 中不存在: ens192`）→ `bind-dpdk`×2 + `request vpp restart`（`09:21:08`「恢复收敛完成」）
  后告警**当场消解**（随后「无 active 告警」）——VPP 侧有恢复路径，内核侧没有。
- 影响：走数据面切换**固定动作**必然产生两条过期 error 告警；不重启则永远看到「端口缺失/还在 vfio」
  的假象（`show alarms`/Web/诊断包一致可见）。属「告警不随事实消解」族（#188/#321/#333/#367 同一纪律）。
- 修法方向（待立项、契约先行）：给内核侧实现按来源廉价复核——「来源对象已不在 committed 声明 → 消解」
  部分与 VPP 侧配置驱动逻辑同源可共享；`interfaces/<name>` 的存在性判据换成内核实况（设备存在）。
  同纪律：只复核、不触发重放、不 Raise。

**R7-2（低）内核数据面下 Web 交换机详情页「容器派生端口」的运行态列为「—」（CLI 同行有 up/up）**
- 现象（同一现场、同一时刻的对照）：
  - CLI `show virtual-switches ct-vs ports` → `nfvisct7246f7c0  container  up  up  -  -`；
  - Web 详情页同一行 → 管理状态/链路/Rx/Tx 全「—」（截图同 §2）。
- 根因（口径差）：
  - Web 的运行态列取 REST `GET /virtual-switches/{name}` 的 `statistics.ports`（`api/resources.go`
    的 `vswitchStatistics`）；该列表内核侧来自 `BridgeDomains()`，其中**产品自持的容器宿主端 veth 按
    决策 #441 有意隐藏**（`netkernel/api_surface.go:242` 的 `isProductContainerVethPort` 过滤）⇒
    派生条目拿不到运行态。实测该 REST 原文：`"statistics":{"bd_id":0,"ports":[{"admin":true,
    "link":true,"port":"ens192","sw_if_index":0}]}`（只有 ens192，无 `nfvisct…`）。
  - CLI 同一读视图按**端口名**合并接口运行态（`api/cli_vswitch_ports.go` 的 `ifaceStates()`）⇒ 能取到。
  - VPP 数据面下该差异**预期不存在**（VPP 侧 statistics 不隐藏 memif 派生口）——**未复核，如实标为推断**。
- 影响：内核数据面下 Web 看不出容器 vNIC 成员口的 up/down（三面同源原则下的一处信息缺失，不影响功能）。
- 修法方向（待定裁）：不动「宿主端不进用户端口视图」前提，把派生条目的运行态按名补进 Web 所用读物
  （REST 补 state 字段或 Web 换读法），保持三面同源。
