§1 修复前逐条复现（全部在 3.0.24 发布件上，修复前）
================================================================================
BUG-02  IOMMU 矛盾：`set system kernel iommu off` + apply 后 GRUB 片段
         `… iommu=off intel_iommu=on intel_pstate=disable`（两参数并存）。
BUG-03  画像 CPU：`set vm-image-profiles newprof.qcow2 cpu mode host-passthrough`
         → `%% 无匹配配置: newprof.qcow2`；同族 `accel kvm` 能建壳。
BUG-04  ping 非法目标：`ping not-a-host!!` → usage 文案 + **rc=0**；`vppctl ping` 自身 rc=0。
BUG-05  直通占用：commit 成功（仅「下次启动生效」警告），start 才报
         `Could not open '/dev/vfio/8': Device or resource busy`。
BUG-06  分步 trunk：`… ports 5 interface ens192` 后 `… ports 5 interface trunk vlans 300`
         → `json: cannot unmarshal object into … trunk of type []int`。
BUG-07  Distance 列：每条路由单元格恒 `未下发`（真实在 FIB 的 `10.88.0.0/24` 也一样）。
BUG-08  SMART：`/dev/sda  unknown  -  -`，无原因；`smartctl` 未安装。
BUG-09  无显卡：Debian 13 genericcloud + 默认 `console serial`，串口 60s 内
         `Booting 'Debian GNU/Linux'` **39 次**、无 login，`virsh domstate` 恒 running；
         域 XML `<video><model type='none'/></video>`。对照组：同一镜像
         **手工改 vga 后立刻到 `localhost login:`**；Debian 12 同路径**不受影响**
         （其 grub.cfg 是 `terminal_output console serial`，D13 是 `gfxterm serial`）。
BUG-10  software add：`%% 安装失败…: signal: terminated` → `dpkg -l` = **iF**，
         `dpkg --audit` 报 half-configured；`dpkg --configure nfvis` 后回 `ii`。
BUG-11  ping vrf：`ping … vrf vs-lan` → `Failed: no FIB table for lookup`（0 发出）；
         `vrf vr-vs-lan` 能发出（1 sent）。
BUG-12  向导空 vNIC：REST 写 `interfaces:[{name:"",…}]` → **201**；
         预校验报 `container-functions[wizct3].interfaces[]：vNIC名称缺失`。
BUG-13  步骤按钮：`#dep-steps` 的 `<button data-step="N">` **无任何 click 处理器**；
         走查 App 层 `eval` 读 `input.value` 仍为空串（仅 placeholder 有值）。
BUG-14  空 VRF 壳：L2 交换机删最后一个 `l3-interface` 后 `display set`
         → `%% display set 内部错误…`；树里残留 `vrfs vs-lan { name vs-lan; }`。
BUG-01  坏 per-dev：造出「配置声明 `vpp dpdk dev ens224`、绑定记录无、内核无 netdev」
         ⇒ `request vpp restart` → `%% 解析 "ens224" 的 PCI 地址失败: 读取
         /sys/class/net/ens224/device/uevent: no such file or directory`，
         startup.conf 整份不生成、其余口一起起不来。
         ⚠️ 更正：同一设备**先删 per-dev 声明**时 restart 成功（连测两次），
         故报告「绑定记录被遗忘」与「永久失败、只能手工救场」两点均不成立。

§4 本轮自己引入并修掉的缺陷（教训入册）
================================================================================
**R42-F1（P0，自死锁，已修）**：BUG-05 的第一版把「数据面占用」写成**每次检查都回读**
`engine.Committed()`。而 `checkPCIDevices` 在 commit 的 apply 阶段被调用，
`Engine.Commit` 全程持写锁、`Committed()` 也要同一把锁 ⇒ **自死锁**。
真机现象：`request virtual-machine-functions db13 start` 卡住，随后连 `POST /login` 都
1m30s 超时；goroutine dump 栈为
  `compute.(*Provider).checkPCIDevices → config.(*Engine).Committed → sync.Mutex.Lock`
叠在 `config.(*Engine).Commit` 上。
**修法**：占用集改**进程内快照**（`dataplaneClaimSet`），启动与每次提交后
（`OnCommitted` 的 goroutine 内，事务已结束）刷新；`Claim` 只读快照、绝不回调引擎。
**守护**：`TestDataplaneClaimSetClaimNeverBlocks`（模拟配置来源被持锁卡死，要求 Claim 立即返回；
注回「回读」写法即红）。
**教训**：给「提交期会跑到的路径」注入依赖时，先确认该依赖**会不会去拿提交自己持有的锁**；
快照 + 提交后刷新是这类读的安全形态。

另两处**接线缺口**由子智能体如实上报、主会话补齐（否则修了不生效）：
  · `cmd/nfvisd/dataplane.go`：VPP 侧诊断未注入 `SetVRFTableResolver` ⇒ BUG-11 在生产不生效；
  · `cmd/nfvisd/dynamic_provider.go`：`computeFacade` 未转发占用检查 ⇒ 后台接入后检查静默消失。
