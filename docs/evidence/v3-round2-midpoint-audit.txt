§0 结论摘要（先说要点）
--------------------------------------------------------------------------------
内核数据面主链路（接口/bond/L2/L3/路由/NAT44/VXLAN/VNF vNIC/诊断 + 第二批五族）在
**单独配置**时成立且大多有真机证据；问题集中在四处：**重放/重启路径**、**同接口多族共存**、
**四类「未实现且未拒绝」的静默分叉**、**给用户看的读数/文案**。

最重的六条（P0/P1）：
  1. 【P0】内核数据面下**任何一次交换机重放都会把运行中 VM 的 libvirt tap（vnetN）从 bridge 上
     摘掉**（`nomaster`）——服务重启、升级、甚至「给同一台交换机再加一个端口」的提交都会触发；
     VM 仍在跑、产品零报错零告警，L2 静默断流（R2-1）。
  2. 【P1】#410 声称修好的「宿主 FORWARD 策略 DROP 吃掉数据面流量」**并未真修**——
     `inet nfvis-forward`（forward priority -10）里的 accept 在 nftables 语义上不能豁免别处
     （filter 链 priority 0 / 宿主 iptables）的 drop；本仓库 #388 已用真机 A/B 证过同一件事。
     在真正 FORWARD DROP 的机器上，内核数据面转发仍会全丢且零提示（R2-2）。
  3. 【P1】同一接口上多族 tc 过滤器**互相屏蔽**：QoS(10)/镜像(20)/风暴(30,40) 共享 clsact，
     内核在首个判决 ≥0 的 filter 处停止评估（police 判决 0、mirred 判决 3）——于是
     「限速 + 风暴抑制」同口配置时**风暴抑制静默失效**（R2-3）。
  4. 【P1】内核 ACL 的 `any/any` 规则落成「不限家族」，**同时匹配 v4+v6**——与手册
     「两侧都是 any 按 v4 处理」和 VPP 侧行为（v6 走隐式拒绝）相反；`permit any/any` + `deny v6`
     时 v6 安全策略被整体绕过（R2-4）。
  5. 【P1】内核恢复重放**段序错了**：`interfaces`（含端口安全）排在 `virtual-switches` 之前 ⇒
     主机重启后端口安全必然失败、白名单静默不下发；`port-mirroring` 在 `bonds` 之前 ⇒
     bond 源镜像不恢复（R2-5）。且内核侧**没有告警落点**（`netRuntime` 无 SetAlarms），
     未收敛项与 `INTERFACE_LINK_DOWN` 在内核数据面下全部只进 journal（R2-6）。
  6. 【P1】VPP（缺省）数据面**回归**：`main.go` 把 `SetSRIOV(nil)` 用在赋值之前 ⇒
     声明式 `interfaces … sriov vf-count` 从「可下发」变成硬失败（R2-7）。

另有 P1×3：向导 2/5 隔离核答案被拿去做数据面取值校验（输默认值必报错，R2-8）；
安装器内核分支的最后一条 `CLI show vpp` 未按数据面分叉（真·首装必自检失败、退出码 1，R2-9）；
内核侧 IPv6 转发开关从不设置（v6 三层配得进、转不出，R2-10）与 NAT 跨 VRF 形态无实现未拒绝
（规则在场、一个包不通，R2-11）。

账目侧（§3）：**AGENTS.md 缺 #409/#410 整段**；设计 §6.2 与 v3待做仍写「vhost-net 接入未验证 /
整机安装未验证」（#409/#407 已验）；openapi/命令树/AGENTS.md 三处仍把 ACL/QoS/镜像/风暴/端口安全
写成「内核未实现、提交期拒绝」（#405 已实现）；本轮新发现的四类静默分叉**一条都没登记**；
v2→v3 的三条移交（STP/shaper/v6 业务面）在 v3 侧无落点。

R2-1【P0】内核数据面：交换机重放把 libvirt tap（与 vxlan 口）从 bridge 摘掉
────────────────────────────────────────────────────────────────────────
位置：`internal/orchestrator/netkernel/l2.go:34-61`（成员收敛）、`util.go:22-38`
      （`bridgeMembers` 读内核实况）、`provider.go:293-296`（ApplyVnfInterface 空操作）
触发：`internal/orchestrator/netkernel/recovery.go:46-48`（每台交换机重放，nfvisd 每次启动都会走：
      `cmd/nfvisd/main.go:996` `go runRecovery()`）+ `internal/orchestrator/orchestrator/apply.go:353/355`
      （任何**声明有变化**的交换机提交都全量重放该交换机）
现象：`declared` 只装「配置里写了接口名的物理口/bond」（vNIC 端口被 `continue` 跳过，
      理由写在 l2.go:39-41：tap 由 libvirt 自建）；释放循环却按**内核实况**摘除所有不在
      `declared` 里的成员——libvirt 建的 `vnetN`（证据 §10.3 实测 `master vs-lan`）与
      ApplyVxlan 挂进来的隧道口都会被 `ip link set dev <x> nomaster` 摘掉。
后果：运行中的 VM 继续跑、guest 侧 link 仍 up、产品零报错（`ipBest` 把成功/不存在都当已达成），
      但宿主到 guest 的二层静默断开；vxlan 侧同样（恢复重放序里 vxlan 在交换机之后会自愈，
      **提交路径不会**）。`CheckVnfPorts` 在内核侧恒 nil（`api_surface.go:45-47`）⇒ 无告警。
对照：VPP 侧只摘**自己登记过**的成员（`internal/orchestrator/network/l2.go:417-434` 的
      `takeStale(bdID, desired)` 取自 `p.attached`），从不按数据面实况全量摘除——是 v3 新实现
      独有的结构性差异。
状态：**静态确定**（代码路径 + `bridge -j link show master` 语义 + 证据 §10.3 三方一致）；
      影响面需真机复现（§5-1）。
修法方向：释放循环只摘「本产品曾 enslave/声明过」的成员；或把 vNIC/vxlan 端口显式纳入保留集
      （判据改为「非本产品成员一律不碰」，与 VPP 侧登记语义对齐）。

R2-2【P1】「宿主 FORWARD DROP」的转发放行是无效层（#410/F2 的修复不成立）
────────────────────────────────────────────────────────────────────────
位置：`internal/orchestrator/netkernel/forward.go:64-89`（自建 `inet nfvis-forward`，`hook forward
      priority -10`，注释声称「比 filter 的 0 更早执行，因此宿主 FORWARD 策略 DROP 不会把我们的
      流量吃掉」）；证据 `docs/evidence/v3-round1-…txt` §11.5 F2 同款归因。
反证一：nftables/netfilter 语义——同一 hook 的多个 base chain 是相互独立的 hook 项，**accept
      只是让包继续走下一个 hook 项**，后续链（filter/priority 0 或 iptables 的 FORWARD）的
      `policy drop` 仍然生效。
反证二：**本仓库自己**已用真机 A/B 证过：`internal/system/firewall.go:10`（注释：「同 hook 的
      base chain 相互独立、drop 全局生效（高优先 accept 不能豁免别处 drop）」）与
      `docs/evidence/v2-round169-d388-host-firewall.txt`（另一张表 `-10` accept tcp/22，
      本表 drop-all 仍把 SSH 拦死）。
对证据的重新解释：§11.3 的 NAT A/B 能通过，只能说明当时该机**没有生效的 FORWARD DROP**
      （§11.6 的清理项「手工 FORWARD 放行规则 **0**」提示实验期层有过手工放行规则）；
      「唯一变量是 NAT 规则」的对照没有把「FORWARD 策略」作为变量隔离。
后果：在 libvirt/Docker 真的把 FORWARD 置为 DROP 的机器上（#410 观察到过），内核数据面
      「接口起来了、路由也下了、ping 全丢」的现场**仍在**，而产品自认为已修。
状态：语义层面确定（两条独立事实源 + 内核 hook 语义）；「现场仍丢」需真机 A/B 定案（§5-2）。
修法方向：① 把放行写进**真正生效**的那条链（如 `iptables -I FORWARD`，规则打产品标记、按
      设备集合放行），并在收敛时核对；② 至少 `EnsureForwarding` 要**读宿主 FORWARD 策略**，
      为 DROP 且自身放行链不可能生效时如实告警并给照做路径（当前零检测）；③ 修正
      forward.go 注释与 §11.5 的错误归因。

────────────────────────────────────────────────────────────────────────
R2-3【P1】同接口多族 tc 过滤器「低 pref 吃全部」：风暴抑制/镜像被 QoS 静默屏蔽
────────────────────────────────────────────────────────────────────────
位置：`internal/orchestrator/netkernel/tc.go:23-28`（pref 单一真源：QoS 10 / 镜像 20 /
      风暴广播 30 / 风暴组播 40）、`qos_kernel.go`（matchall + police，ingress/egress 各一条）、
      `span_kernel.go:56-59`（matchall + mirred）、`storm_kernel.go:144`（flower，ingress，protocol all）
内核语义（本轮现取源码核实）：`__tcf_classify` 对同一 chain 按 prio 升序遍历，
      **首个返回 ≥0 的 classifier 立即 return，后续 filter 不再评估**；police 在未写
      TCA_POLICE_RESULT 时对合规包返回 `TC_ACT_OK(0)`（iproute2 只有 `continue`/slash 形式才写
      该属性），mirred（mirror）返回配置判决（默认 `pipe=3`）——两者都 ≥0。
门槛：提交期只互斥「端口安全×风暴」「端口安全×L3 ACL」（`internal/model/validate.go:800-812`），
      **没有**禁止 QoS×风暴 / QoS×镜像源 / 风暴×镜像源的组合；`interfaces[]` 下它们就是同一节点
      的叶子，完全可同时声明。
后果：`set interfaces ens224 ingress-policy pol-8k` + `set interfaces ens224 storm-control
      broadcast 8` 同时在场时——两条命令、`tc filter show` 都在位、计数可读，但风暴抑制的
      police **恒 0 丢包**（被 pref 10 的 matchall 短路）；镜像源同口时镜像同样不发生。
      #405 修的是「撤除误删他族」（删除方向彻底），这是它的遗留同族（**执行方向**）。
状态：内核语义确定（源码 + man）、产品侧可达性确定（校验缺口已核）；需真机 A/B（§5-3）。
修法方向（三选一）：① 把同 hook 上本产品的族合并进**一个 filter 的 action 链**；
      ② 给「需要继续遍历」的族用能继续的判决（police 加 `continue`；mirred 需要单测确认）；
      ③ 组合在提交期硬拒并写入文档（最保守，但与 VPP 侧能力不等价）。

────────────────────────────────────────────────────────────────────────
R2-4【P1】内核 ACL：两侧 any 的规则同时匹配 v4+v6（与手册/VPP 语义相反，安全面）
────────────────────────────────────────────────────────────────────────
位置：`internal/orchestrator/netkernel/acl_kernel.go:376-418`（`if !aclIsAnyAddr(...)` 才写
      `ip`/`ip6` 限定；`protocol tcp`/`any` 分支不带家族）——两侧都是 any 时规则体里**没有任何
      家族限定**（`accept` / `meta l4proto tcp`），nft 会同时命中 v4 与 v6。
契约：`docs/NFViS-用户手册.md:1295-1298`——「`any` **跟随对侧家族**……**两侧都是 any 按 v4
      处理**。要同时过滤 v4 与 v6，写两条规则」。
对照：VPP 侧 `internal/orchestrator/network/acl.go` 的 `prefixOrAny` 把 any/any 落成
      `0.0.0.0/0`（v4 单族，`acl_test.go` 有断言）；v6 由「本族无规则 ⇒ 隐式拒绝」兜底
      （`docs/evidence/v2-round133-d352-acl6-enforcement.txt` 真机实证）。
后果：手册示例写法 `rule 10 … protocol tcp destination-port 443 permit` 在内核侧**同时对 v6:443
      放行**；更尖锐形态 `rule 10 permit any/any` + `rule 20 deny <v6 前缀>` ⇒ seq 10 先命中，
      rule 20 永不可达，**v6 完全绕过 ACL**（VPP 下同一配置 v6 被拒）。
状态：静态确定（代码 + 手册 + VPP 侧三方一致），机制无需真机。
修法方向：两侧皆 any 时显式下 `ip`（v4）限定；或提交期拒绝 any/any 并提示写两条。

────────────────────────────────────────────────────────────────────────
R2-5【P1】内核恢复重放段序：端口安全与 bond 源镜像在重启后必然不收敛
────────────────────────────────────────────────────────────────────────
位置：`internal/orchestrator/netkernel/recovery.go:31-54`，段序为
      forwarding → acls → **port-mirroring** → qos → **interfaces** → **bonds** →
      **virtual-switches** → vrfs → vxlan → nat。
  ① 端口安全：`ApplyInterface` 末端调 `applyInterfacePortSec`（`families.go:269-275`），
     而它要求该口**已是 bridge 成员**（`portsec_kernel.go:58-63` 如实报「需先挂到交换机上」）；
     主机重启后内核对象全失，重放到 interfaces 段时 bridge 还没建 ⇒ 必然失败 ⇒
     白名单不下发（安全特性静默失效），交换机段随后才把口挂上。
  ② 镜像：`ApplySpan` 先对源口 `tc qdisc add … clsact`（`span_kernel.go:42`），
     bond 在 bonds 段才创建 ⇒ 源为 bond 的镜像（模型允许，`validate.go:1382-1384`）报
     `Cannot find device` 不收敛。
对照：VPP 侧段序把接口层放最后（`internal/orchestrator/network/recovery.go:157-252`），
      span 在 bonds 之后；且 VPP 侧失败会进告警（见 R2-6）。提交路径无此问题
      （plan 段序正确），所以症状是「重启后没了、再提交一次又好了」的非确定性。
状态：静态确定（段序 + 前置判据），影响面建议真机确认（§5-4）。
修法方向：段序改为依赖序（bonds → switches → interfaces → …），或对「前置未就绪」的族做
      收敛后复跑（与 VPP 侧 recovery 的做法对齐）。

R2-7【P1】VPP 数据面回归：声明式 SR-IOV vf-count 被装配成「未接入」
────────────────────────────────────────────────────────────────────────
位置：`cmd/nfvisd/main.go:213`（声明）、`:270`（`l2net.SetSRIOV(sriovProvider)`，此时仍为 nil）、
      `:289`（`sriovProvider = network.NewSRIOVProvider()`，在 if/else 之后）；
      判定点 `internal/orchestrator/network/provider.go:210-211`（直接赋值）、`:411-414`
      （`n.sriov == nil` ⇒ 报「SR-IOV 未接入（编排器未装配）」）。

§5 建议的真机复核清单（只读/低扰动优先，逐条可判）
--------------------------------------------------------------------------------
1) R2-1（最优先）：kernel 数据面起一台带 vNIC 的 VNF（alpine.qcow2 已在镜像仓库）→
   `bridge -j link show master vs-lan | grep vnet` 有 → `systemctl restart nfvis` →
   再查 ⇒ 预期 tap 从成员列表消失、宿主 `ping <guest>` 丢；对照修复方向的可判定性：
   同一现象在「只改交换机 description 的一次提交」后也会出现。
2) R2-2：`iptables -S FORWARD | head -1`（看 policy）→ 若为 DROP：开/关
   `inet nfvis-forward` 各跑一次「netns 内网 → 宿主」的 ping（§11.2 的夹具），
   预期**两次都丢**（证明 -10 accept 无效）；若为 ACCEPT：把策略置 DROP 再跑对照。
3) R2-3：`set interfaces ens224 ingress-policy pol-8k` + `set interfaces ens224 storm-control
   broadcast 8` 同口 → 宿主发广播洪水 → `tc -s filter show dev ens224 ingress` 看
   pref 30 的 police 计数是否恒 0（预期复现）。
4) R2-5：kernel 数据面配好 `port-security`（口在交换机上）→ `reboot` →
   `nft list table netdev nfvis-portsec`（预期空）与 `show interfaces <口> detail`（预期读视图
   说已配置）对照；再单跑一次提交（触发重放）看是否转好（预期好转 ⇒ 确认是段序）。
5) R2-9 / R2-19②：干净快照 `./install.sh --payload <dir> -y --dataplane kernel
   --admin-password '<pwd>'` → 看 `CLI show vpp` 一项与退出码；随后
   `systemctl is-active vpp`（预期 inactive 才与文案一致——若 active 即证实 ②）。
6) R2-11：照 §11 的 netns+veth 夹具，把 inside 交换机（含 veth）与 outside 出接口分到
   **两个不同 VRF/交换机**，规则在场跑 `ping` + `tcpdump`（预期零通、nft 计数零）。
7) R2-14：一次提交完成「ens224 从 l3-interface 改为 vs-lan 端口」→
   `bridge -j link show master vs-lan`（预期不含 ens224 ⇒ 复现）。
