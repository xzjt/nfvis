§1 根因（报告指出 2 处 + 本轮自查 1 处）
================================================================================
① 收敛等待只在报错时执行（报告指出）
   installAndVerify: `if at.err != nil && looksInterrupted(at.err) { awaitTerminalStatus() }`
   首次升级 dpkg 以 0 退出 ⇒ 轮询没跑 ⇒ 直接读到配置中途的**瞬时 installed**。

   测试方 0.5s 采样时间线（本轮采信，未重复采样）：
     08:04:30–36  install ok installed        ← 12 次：postinst 执行中的瞬时态
     08:04:37–56  （dpkg 数据库短暂不可读）
     08:04:57–59  install ok half-configured  ← 44 次：终态

② 落盘状态是硬编码（报告指出）
   `res.Status = pkgStatusInstalled`——复核到的真实状态只进了返回文本 out，没回填到 res。
   故结论文件的 status 是字面量，不是事实。

③ 脱离 shell 也采一次就写（**本轮自查**，报告未提）
   installScriptWithResult 在 `dpkg -i` 退出后立刻读 /var/lib/dpkg/status 写结论——
   同一个瞬时态隐患，在第二个地方。只修 ①② 仍会在此处复现。

§2 修法
================================================================================
① 收敛判定**无条件**执行，判据＝「同一状态行连续 N 次采样一致」
   installSettleSamples=6 × installConvergeInterval=2s ⇒ 最小跨度 10s
   （由两常量单一推出 settleMinSpan()，不另立时间常量——否则两者迟早矛盾）。
   **为什么不是报告建议的「3 次」**：其时间线显示瞬时态持续约 7s，3×2s=4s 落在其中，
   改了等于没改。10s > 7s 才有判别力。
   超时未稳定 ⇒ 如实报「无法判定」（既不说成功也不说失败），且**跳过 dpkg --configure 补救**
   （dpkg 可能仍在跑，并发事务只会更糟）。
   永久不可读的通道与暂时不可读分开处理（后者不进入 60s 等待）⇒ 既有适配器桩不回归成长等待。

② 删掉两处硬编码：落盘状态取实测值（仅 stable 时写真值；未观测到就留空 + ok:false）。
   新增 Reason 字段承载「为什么没成/判不出」，与 Status（只放观测事实）分开。

③ 脱离 shell 改为**先写 pending、再写终判**：
   pending 让「升级进行中就来读」的 CLI 得到诚实的「未定」（而不是上一次的成功或空的「无记录」）；
   终判由 shell 侧同样按「连续 N 次一致」循环后写出（临时文件 + mv，读不到半截 JSON）。

④ 读口交叉核对：show system software result 实时读 dpkg 状态并与记录比对
   —— 一致则明说「与记录一致」；**不一致以当前事实为准**并给处理路径；读不到如实说「无法核对」。
   pending 单独渲染为「未定」而非「失败」。这正面回答了报告 §3.5「错误结论跨重启不自愈」：
   **不改写历史记录，但绝不让过期记录冒充现状。**

§6 追加：修 BUG-17 途中又挖出五个「工具层」坑（全是真机才现形，全部已修）
================================================================================
修这条缺陷的过程比缺陷本身更值得记录：每一层修好后，下一层才暴露。

① **`fmt.Sprintf` 改写 shell 脚本**
   `launchShell` 用 `fmt.Sprintf("%s >>%s 2>&1", command, …)` 拼命令，而脚本里含
   `${pair%%|*}` 与 `printf '…%s…'`：Sprintf 把 `%%` 折成 `%`、把 `%s` 当格式动词。
   真机现象：`st=${pair%%|*}` 变成 `st=`，采样恒空、结论永远 pending。
   → 改字符串拼接；守护 `TestLaunchShellDoesNotFormatScript`。

② **`systemd-run` 把 `${x%%|*}` 当环境变量赋值**
   即便脚本正确，`systemd-run … /bin/sh -c "<script>"` 仍会扫描参数里的 `NAME=value`：
   它报 `Invalid environment variable name evaluates to an empty string: pair%%|*` 并吞掉那段。
   → 脚本落成文件、用 `sh <file>` 执行；守护 `TestLaunchShellUsesScriptFileNotDashC`。

③ **拼进脚本的路径是 Windows 反斜杠**
   `filepath.Join` 在 Windows 宿主上产出 `\var\lib\…`，而脚本由 Linux 的 sh 执行——
   反斜杠被当转义，结论写不出去。单测跑在 Windows 上正好能抓，前提是有断言。
   → 改 `posixpath.Join`；守护 `TestInstallScriptUsesPosixPaths`。

④ **`--scope` 让脚本活在调用方 cgroup 里**
   nfvisd 被 postinst 重启时整组被 systemd 收走，脚本后半段（稳定采样 + 自救）没机会跑。
   真机现象：install.log 全空、结论 status=""。
   → 改 transient service（`systemd-run` 不带 `--scope`）；真机对照：
   `--scope` ⇒ 结论空/pending；transient service ⇒ ok:true + audit 干净。

⑤ **读 `/var/lib/dpkg/status` 文件会读到谎言（本轮最关键的一条）**
   真机同一时刻两个视图互相矛盾：
     awk 读 /var/lib/dpkg/status        → "install ok installed"   ← 陈旧字段
     dpkg-query -W -f='${Status}' nfvis → "install ok half-configured" ← 数据库真实视图
   早先为绕开「postinst 期间拿不到锁」而改读文件，那个取舍读到了谎言：半配置被判成功。
   实测 dpkg-query 此刻只花 16ms、不阻塞（读的是数据库快照）——原担忧不成立。
   → 采样改走 `dpkg-query`，读不到才回退文件。

**并因此得出 BUG-17 的真正判据**：仅看状态行不够（它可能写着 installed 而实际半配置），
必须**同时**要求 `dpkg --audit` 不列出该包。实测该「状态行假装 installed」的窗口持续
**16 秒以上**（12:05:52–12:06:08 逐秒采样：status=installed 而 audit=1）。
`installSettled` 增 audit 参数；脱离脚本同判据；且 audit 脏时脚本**自己**跑一次
`dpkg --configure nfvis` 自救（脚本是 CLI 唯一能读到结论的地方，不救就只能是「未定」）。

**真机闭环（脚本直跑，transient service）**：
  结论 {"action":"add","version":"3.0.28","status":"install ok installed","ok":true}
  dpkg --audit 空
三者一致——修复前同路径会落 ok:true 而实际 iF（报告 3/3 复现）。

**如实登记（仍未闭环的一环）**：CLI 侧读到终判需要等「服务端自救 + 稳定判定」全过程
（实测数十秒），CLI 的等待窗已放宽到 240s 且 pending/空状态都继续等；但由于每次
`dpkg -i` 都会把我换装的 `nfvis-cli` 覆盖回发布版二进制，**CLI 侧的端到端时延只能在
正式发布件上验**——本轮以服务端结论与读口交叉核对为准，CLI 侧由单测（3 条）覆盖。
