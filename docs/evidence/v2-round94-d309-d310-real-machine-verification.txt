§1 决策 #309 CLI 批处理 `-f <file>`（真机确认）
- `-f /tmp/n1.txt`（configure/set hostname/commit/exit）→ exit=0，配置库生效（`set system hostname fw-m94` 可见）
- **CRLF 文件**同样执行成功（配置生效 fw-m94crlf）→ 行尾归一兑现（Windows 编写的脚本可用）
- 缺文件 → exit=1 且文案含路径；空 stdin → exit=1 且明确提示；`-c` 与 `-f` 同时给 → exit=1 且文案说清二选一
- `-f -`（stdin）→ exit=0 且正常执行
- **行为一致性对照（关键）**：同一段含未知命令的文本分别走 `-f` 与既有 `-c`，**退出码与「是否继续执行」逐项相同**（都 exit=0、都不中止）——证明 #309 的「与 -c 同语义、同一执行入口」口径成立，未引入新语义
- 如实登记（**观察项，非本批引入**）：既有 `-c`（及随之的 `-f`）对**未知命令**不中止、不置非零退出码——脚本里写错命令会静默继续。属既有脚本模式语义（登记待核查，建议单独立项决定「未知命令是否应中止/非零退出」）

§2 决策 #310 console 断开后阻塞在 Read（真机确认，收口决策 #70⑤）
- 现场：建 vs-con + cli-vm(1G, vhost vNIC) 并启动；以 pty 起交互 CLI 并输入 console 命令接管串口（进程存活 = 已接管）
- **不按任何键**，从另一侧 `systemctl restart nfvis` 造成服务端断开 → 会话日志出现「串口已断开」= CLI 已退出 console 并回到提示符
- 结论：旧版「断开后需按键才退出」的阻塞已消除；`Ctrl-]` 与数据转发语义未变（单测 + pty 套件 10/10 兜底）
- 修法要点（已入决策 #310）：根因是客户端主循环「先检查 done 再阻塞在 stdin Read」，服务端断开置位的 done 再也看不到；改为输入协程 + select
