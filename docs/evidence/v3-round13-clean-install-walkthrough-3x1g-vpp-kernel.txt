§2.0 【R12-1 完整复现】用户目标布局（3×1G、无 2M 池）下 VNF 容量=0，且提交校验放行
--------------------------------------------------------------------------------
事实链：
  a) `request vpp restart`（产品生成的 startup.conf 生效）后：1G 池 nr=3/**free=0**。
     vppctl show memory：main heap 1×1G；vppctl show buffers：default-numa-0 2496B 430184 个
     （≈1.07GB）；/proc/<vpp>/smaps 三块 1G 映射：`seg_0-0`（主堆）、`buffers-numa-0`（缓冲池）、
     `seg_2-0`——即**缓冲池在 default-hugepage-size=1G 下按整 1G 页分配**，吃掉另外 2 页。
  b) 读视图如实：「1G：声明 3/内核实际 3/在用 3/数据面占用 3/空闲 0——VNF 可起页数 = 空闲页数
     （当前 0）」。
  c) **但提交校验放行**：`set virtual-machine-functions vnf-a image alpine` + `vcpu count 1` +
     `memory size-mb 1024` + commit **成功（rev 7）**——提交侧池账本不扣数据面占用，与读视图矛盾。
  d) `request … start` 才失败：`internal error: QEMU unexpectedly closed the monitor … unable to
     map backing store for guest RAM: Cannot allocate memory`（裸 libvirt 文案，无照做指引）。
  e) 契约面：向导「可起 VNF 数 ≈ N−1」与 #347 边界「1G 池声明 N ⇒ VNF 可用 N−1」只在 2M 池
     存在时成立；2M=0 时实际容量=0。
  影响：用户按规划布局（3×1G、VPP 占 1、VNF 用 2）部署会得到「VNF 全部起不来」的整机。
  处置（走查内，与 round12 同法）：补 `set resource-pools hugepages page-size 2M count 768` +
    `set vpp memory hugepage-preference 2M` + kernel apply + 重启 + `request vpp restart` 后：
    **1G 池 dp=1/free=2（用户意图达成；主堆与缓冲落 2M）**，全部功能验证在该布局完成。
  修复方向建议：① 向导/手册的 N−1 承诺按「2M 池是否存在」分叉；② 提交校验引入 sysfs 空闲
  对账（或至少预测式警告）；③ startup.conf 对 2M=0 布局给 default-hugepage-size 更保守取值，
  或文档明示「2M 池是 VNF 容量的前提」。

4.8 内核 ACL（#405）：绑 acl-lab 到 vs-wan l3-interface ens224 → nft netdev nfvis-acl 链
    `ip protocol icmp drop` 绑 ens224 ingress → **宿主 ping 3/3 全丢** → 解绑复通。
4.9 内核抓包（#436）：request capture start interface vs-lan count 20 → export → pcap 2.2 KiB。

§5 数据面切回 vpp（往返）
--------------------------------------------------------------------------------
5.1 对象保留（vs-lan/vs-wan/vnf-a/ct-1/vxlan/qos/lldp 等）直接 set system dataplane vpp + commit
    （rev 35 前）→ systemctl restart nfvis → VPP 自动拉起、connected。
5.2 **【R12-7 复现】内核侧不 teardown**：切回后 ip -br link 仍有 vs-lan/vs-wan/vr-vs-lan/vx-a/
    nfvisdh…/vnet0/nfvisct… 且 nft 两表在位——内核数据面整体**活跃**，产品读视图只反映 VPP。
    设计文档未声明该语义。
5.3 **补充实证 R12-7 的级联后果**：内核残留的 DHCP tap 名（nfvisdhf341ae1a）占用 ⇒ 切回 vpp 后
    **VPP 侧内置 tap 创建失败**（`RECOVERY_UNCONVERGED … VPPApiError: System call error #3 (-13)`），
    DHCP server 在 VPP 侧不可用；**手工 `ip link del nfvisdhf341ae1a`（清内核残留）+ 重启 nfvis
    后，VPP tap0「nfvisdhf341ae1a」重建、告警自动消解**——两数据面同名设备冲突，根治方向＝切换
    编排纳入内核侧 teardown。
5.4 **【R12-8 未复现】** round12 记「切回 vpp 后 VPP 侧静默不收敛、唯一出路整机重启」；本轮：
    · 切回后 VPP 侧对象（mf-ct-1-nic0/vh-vnf-a-nic0/vxlan_tunnel0/BD 14615916）**已按配置建立**；
    · 缺的是物理口（ens192/ens224 仍是内核 netdev）⇒ **恢复收敛如实上表** RECOVERY_IFACE_MISSING×N
      + RECOVERY_UNCONVERGED（DHCP tap）+ VNF_PORT_DOWN——**非静默**；
    · `bind-dpdk ×2 + request vpp restart` 后**全量收敛**（bvi0/ens192/ens224/BD/vxlan 齐备），
      无需整机重启。
    差异成因分析（如实）：round12 记录「物理口 admin-down」意味着其端口在 VPP 内；本轮端口被
    `unbind-dpdk` 交还内核（§4.2）故不在 VPP。两者现场不同；**本轮证据不足以判定 R12-8 已修复**，
    仅记「在端口交还内核的路径上，恢复收敛有告警且 bind+restart 可收敛」。

§7 缺陷/观察登记（R13-A~D + 观察；逐条独立事实源）
--------------------------------------------------------------------------------
R13-A【高】**出向 QoS 策略绑到 L2 交换机成员口 ⇒ BVI 路由回的 punt 注入包被丢弃（数据面 DNS 代理
     失效）**（本轮新发现，round12 未覆盖）
     · 现象：vs-lan（L2，成员 ens192）配 `set interfaces ens192 egress-policy pol-lab`（cir 8Mbps）
       + 数据面 DNS 代理启用后，**域内客户端（宿主）查 192.168.99.1 超时**；nslookup 与自写 raw UDP
       两工具均无应答。
     · 定位链：① 排除 nfvisd 侧——把产品 DNS 关掉，用**裸 Python socket 注册 punt**（`vppctl punt
       socket register ipv4 udp 53 socket <path>`）**能收到** punt 包（93/79 B）⇒ VPP→client 投递正常；
       ② 复开产品代理，**bvi0 pcap 显示应答被正确构造并送出**（`b0:b0:00:00:00:00 > 宿主MAC,
       192.168.99.1.53 > 192.168.99.10:59606, A 172.66.147.243 …`），但 **ens192 pcap 无该应答出向**；
       ③ 受控 A/B：**只绑 ingress-policy ⇒ DNS 正常；只绑 egress-policy ⇒ DNS 失败**；④ `vppctl show
       interface features ens192` 的 **l2-output 弧出现 `POLICER (l2-policer-output)`**；⑤ 解绑出向后
       l2-output 恢复仅 `OUTPUT (interface-output)`，**DNS 立即恢复**（同一 raw UDP 得到应答）。
     · 佐证计数：`vppctl show errors` 见 `l2-flood BVI L3 mac mismatch` 与 `l2-policer-classify`
       相关错误；`show policer` conform 计数正常递增（策略本身在放行）——**丢弃发生在 l2-output
       路径上、非策略判定**。
     · 边界：同口**入向**策略、以及 ICMP 到 BVI（宿主 ping 192.168.99.1 3/3）**均不受影响**——
       受影响的是「经 BVI 路由后由 BD 交换出该口」的 punt 注入流。
     · 影响：用户对 L2 成员口配出向限速后，**域内 DNS（数据面代理）静默失效**；亦可能影响其它
       经 BVI 注入的路径（DHCP server 的 punt 回注同类，未单独验证）。
     · 建议：修 l2-policer-output 对 punt 注入包的处理，或在提交期对「L2 成员口出向 QoS」给出
       警告/限制；至少应有人话告警而非静默丢包。
R13-B【中低】**内核数据面下改 vNIC 的 virtual-switch 后首次 start 用陈旧域定义 → paused，需
     destroy 重试**（本轮新发现）
     · 现象：kernel 模式下先给 vnf-a 的 nic0 补 `… interfaces nic0 virtual-switch vs-lan`（原 VPP 形态
       用交换机 ports 语句接入），commit 成功；随后 `request … start` 落在**仍是 vhostuser 的旧域**上
       → 域进入 paused、报「vhost-user vNIC 需要 VPP 先建立 socket」；`virsh destroy` 后重试 → 域变
       `<interface type='bridge' source bridge='vs-lan'/>`，正常启动。
     · 交叉数据面口径：**VPP 形态（`set virtual-switches <n> ports <seq> vnf …`）接入的 vNIC 不带
       VnfInterface.VirtualSwitch 字段**，内核数据面域生成需要它（`domain_xml.go:227`），故切内核后
       域生成失败（`vNIC nic0 缺少接入的虚拟交换机`）——即「同一份配置在 vpp 下可用、切 kernel 下不可用」，
       而数据面切换的提交期**未拦下**该不兼容。
     · 建议：数据面切换时对「内核侧域生成不可满足」的 vNIC 提交期拒绝/给照做路径；start 用陈旧域
       定义时应重建域而非直接启动。
R13-C【中低】内核数据面下 **VNF vNIC 不能接入 type=l3 的交换机**（提交期硬拒，文案含替代指引）——
     与 round1/#409「内核 VM 走 virtio+宿主 tap」一致，属**既有设计边界**；本轮如实复核（vs-nat
     L3 形态切内核被拒）。记作口径确认，非新缺陷。
R13-D【观察/口径更正】**内核 LLDP「零发帧」（round12 R12-5）的真因＝只配了全局 `set protocols lldp
     enable true`、未配 per-interface**。补 `set protocols lldp interface ens192 enable true` 后
     nfvisd 立即持 AF_PACKET socket 且真实发帧（3s 一帧、tcpdump 实证）。建议手册/读视图在「全局
     enable 但无 per-interface」时给出「尚未在任何口启用」的如实提示。
观察②【低】`unbind-dpdk --yes`（不带 to-driver）不自动重新探测原生驱动（round12 观察④同形）；
    显式 `to-driver vmxnet3` 即可。
观察③【口径】实验室拓扑伪影：vs-lan 的 BD 含物理口 ens192（接 VMnet8），guest 的 DHCP 广播经 BD
     泛洪被 VMware NAT DHCP 抢先应答（guest 取 192.168.155.138 而非产品租约）——真实部署无此同 L2
     外置 DHCP；产品侧租约如实记录。
观察④【低】Web VM 详情「资源」块 vCPU 绑定/绑定核/内存后端/大页大小/NUMA 恒「—」而运行态有事实
     （virsh cpuset/1G 后端）——字段级显示同族（#332/#353 方向）。
