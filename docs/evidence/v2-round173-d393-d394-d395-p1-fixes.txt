3.4 **#395② 防火墙内容比对（真机通过；含一处当场修复的真机缺陷）**：
  - **真机缺陷（当场抓出并修复）**：dev115 下正常配置（`rule 1 accept 192.0.2.0/24`，`nft list` 显示保留项齐全）
    读视图却报 `未收敛（保留项与配置不符：ct state 数据面 ""、期望 "established,related"）` 且计数显示 `-`。
    根因：真实 `nft -j` 的 **`ct state` 右值是普通 JSON 数组** `["established","related"]`（`{"match":{"op":"in","left":{"ct":{"key":"state"}},"right":[…]}}`），
    而 icmp/icmpv6 才是 `{"set":[…]}`——解析器只认后者 ⇒ `CTState` 抽成空串 ⇒ 假未收敛。修复 `3d5377b`：
    `nftMatchLeft` 识别 `match.left.ct.key=="state"`、新增 `nftRightValues` 兼容四种 `right` 形状（字符串/普通数组/`{"set":…}`/`{"match":"a,b"}`），
    ct 比较与 type 集合共用顺序无关规范化；并补**真机形状**回归用例（红-绿失败信息与现场报错**逐字一致**）。
  - **dev116 复验**：正常配置 ⇒ `下发状态: 已收敛` + 计数 `0 / 0`（计数可见）；
    - 条数不符（带外删保留项）⇒ `未收敛（规则集合与配置不一致：数据面保留项 3 条、期望 4 条（表可能已被手工修改））` + 计数 `-`；
    - **内容不符（条数不变、`iifname` 改 ens999）⇒ `未收敛（作用面与配置不符：数据面按管理口 "ens999" 过滤、配置为 "ens160"（管理口变更可能未下发成功））` + 计数 `-`**。
3.5 **#395① 被拒 commit 不隐式确认（真机通过）**：会话 A `commit confirmed 2`（防火墙无害 accept 规则，rev1176，到期 16:31:21）→
  会话 B 以 ssh 来源发被守卫拒的 plain commit（`set firewall rule 2 …` + `commit` ⇒ 拒绝）→ 规则当时在册 →
  **等 confirmed 窗口过期后配置自动回滚**（`show system firewall` = 未配置）。对照修复前：被拒 commit 会背书在途 confirmed（危险变更转永久）。
