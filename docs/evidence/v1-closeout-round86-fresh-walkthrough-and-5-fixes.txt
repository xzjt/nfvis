----- §2 五条缺陷（决策 #183~#187）-----------------------------------------------

R86-1（P1，假失败/与手册相反）**从零首次声明物理口：VPP 未运行时整体失败并回滚**
  现象（本机可稳定复现）：整机重启后（VPP 停止态）按手册 §7.3 顺序首次声明业务口并提交：
    `set interfaces ens192|ens224` + `set vpp dpdk dev …` → 四条都 `[ok]`，随后
    `%% 底座下发失败（已补偿）: 下发失败 interface[ens192]: VPP 未连接，L2 客户端不可用`
    → 配置整体回滚（`display set` 里没有 interfaces/dpdk；`request vpp restart` 生成的
    startup.conf 也没有 dpdk 段）——而手册该处明写「commit 会成功……执行 request vpp restart
    后自动收敛」。VPP 起来后重做同一提交即成功（revision 4 + 「vpp 变更需 restart」警告）。
  根因：`internal/orchestrator/apply.go` 的 `ifaceApply` 只把 `ErrIfaceUnavailable`（口不在数据面）
    当可延后，未覆盖 `ErrL2Unavailable`（VPP 未连接）。**决策 #186**。
  修：`ErrL2Unavailable` 定义下沉到 `internal/orchestrator`（network 包别名复用同一实例，依赖方向不变），
    `ifaceApply` 在 DPDK 端口上同时延后这两类失败并告警；未声明为 DPDK 的口照旧硬失败。
  单测：`internal/orchestrator/apply_dpdk_test.go` 两例（正例延后 + 告警含下一步；反例仍硬失败并保留原文）。
  真机复验（1.1.48~dev2）：停 VPP（`systemctl stop vpp`、`vppctl` 连接被拒）后重做同一提交
    → `commit 成功 (revision 25)`；守护进程日志两行 WARN：
    「接口 ens192 的数据面尚未就绪（VPP 未运行）：本次提交不阻断，执行 request vpp restart 后自动收敛」
    （ens224 同）→ `request vpp restart` 后 `vppctl show interface` 两口 up、CLI 同刻一致。

R86-2（P2，答非所问/诊断缺料）**show log system 与诊断包 logs.txt 恒空（已装 systemd 部署）**
  现象：`show log system last 20` → `-- No entries --`（同一时刻 `journalctl -u nfvis` 有 500+ 行）；
    诊断包 logs.txt 同样只有这一行（M5-4 诊断包核心内容为空，#149 的一次性口令打码因此空转）。
  根因：`cmd/nfvisd/main.go` `nfvisdLogTail` ① 查单元名 `nfvisd`，而安装的单元是 `nfvis.service`；
    ② journalctl 无条目时把提示行 `-- No entries --` 打到 stdout（rc=0、长度>0），
    代码用 `len(out) > 0` 判「拿到日志」→ 回退分支永不触发。**决策 #184**。
  修：按 `nfvis` → `nfvisd` 逐个单元名尝试 + `journalctlHasNoEntries` 识别提示行后再回退。
  真机复验：`show log system last 5` 返回真实日志行（本文件第 §3 现场即引用它）；诊断包 logs.txt 同样有内容。

R86-3（P2，功能缺口 + 误导文案）**URL 拉取镜像被「客户端整体超时」截断**
  现象：`request images download name alpine.qcow2 …`（URL 给的 alpine 云镜像，Content-Length
    187,695,104）两次尝试都在 ~10 分钟处失败：第一次停在 39,615,168 字节，last-error=
    「拉取中断（已下载 39615168 字节，可重试续传）：等待服务端数据超时（HTTP 客户端整体超时触发）」。
  独立事实源：同一 URL 经宿主代理 `curl` 取回 **187,695,104 字节，sha256
    900c91ed360beac704158ee99f45bab49e97858f8cb37469d0cc30e8e8e2ca60**（与产品登记的期望、
    与手册 §9.1 记的哈希逐字一致）→ URL 与文件本身没问题；实测 CDN 速率 ~26~78KB/s。
  根因：`defaultDownloadTimeout = 10*time.Minute` 是 `http.Client.Timeout`（**整体**上限：连接+读 body）；
    按实测速率，10 分钟只够 ~40MB，任何大镜像在常见链路上都走不完；文案还把责任写成「服务端停发」。
    **决策 #185**。
  修：缺省客户端 = 「连接+响应头 60s」+「**空闲**上限 5 分钟」（`idleTimeoutReader` 每次读到字节重置），
    不设整体上限；两种超时分开表述（空闲判据 = 服务端停发；注入客户端的整体超时 = 客户端侧上限）。
  单测：`internal/images/images_test.go` 两例（慢而持续 10 chunk × 30ms、空闲上限 200ms → 必须成功；
    chunk 间隙超空闲上限 → 必须报「服务端停发」且文案含续传指引）。
  真机复验：13:06:31 重跑同一条下载（从 52,734,717 字节断点续传）→ 13:13:30 63.8MB、13:18:22 69.9MB，
    **import-state 一直 downloading**——已跨过旧实现 13:16:31 的 10 分钟死线（旧版必失败）；
    续传本身也再次验证（52.7MB → 69.9MB 未重下）。

R86-4（P1，跨对象删除 + 补偿残渣）**NAT 用过的表让所属 L3 交换机永远删不掉（除 VPP 重启）**
  现象（本机稳定复现，纯产品路径）：`delete virtual-switches <用过 NAT 的 L3 交换机>` 报
    `%% 底座下发失败（已补偿）: 下发失败 del-vrf[vs-exp]: VRF 对应的 IP 表删除后仍存在于 VPP（未收敛）:
     IP table 1804284（IPv4）在删除后仍存在于 VPP`；重试永远失败。
  定位（VPP 事实源）：NAT44-EI 一旦把某张表当作 inside/outside，该表就带 `locks:[nat44-ei-hi:1]`
    （`vppctl show ip fib summary`）；此后**删 NAT 规则（特性已摘）、
    `nat44_ei_plugin_enable_disable(false)`、手工 `vppctl nat44 ei plugin disable` 都不释放该锁**，
    `ip_table_add_del(del)` 返回 0 却不真删（#179 的读回校验正确报了未收敛）；只有 `request vpp restart`
    回到干净状态后，同一删除**立即成功**（rev 23）。
  修（决策 #187，只改可诊断性，不改 VPP 行为）：读回失败的错误里直接带可照做指引
    「（表可能仍被数据面插件引用：NAT44 用过这张表后 VPP 不释放该引用，执行 request vpp restart 后重试删除）」；
    手册 §8.8 同步写明「NAT 用过的表，其所属交换机删除前先重启数据面；改 NAT 出接口 + 删旧 L3 交换机
    不要放在同一次提交里」。
  单测：`internal/orchestrator/network/l3_test.go`（文案必须含 `request vpp restart` 与 `NAT`）。
  真机复验（1.1.48~dev2）：同一删除命令返回上述带指引的文案。
  **同批登记未修**：① 提交失败后的补偿若也失败，残渣（新建 VRF 表滞留、NAT inside 特性被摘而配置仍声明它）
    只出现在当次提交输出，**不进告警**，事后不可见；② 同一 candidate 内「改 NAT 出接口 + 删旧交换机」必然失败。

R86-5（P0，服务中断）**console 用过之后停那台 VM，会让 nfvisd 退出（SIGHUP）**
  现象：`request virtual-machine-functions <vm> console` 用过之后，`… <vm> stop` 的调用方收到
    `Post "https://127.0.0.1:443/api/v1/cli/execute": EOF`；`systemctl` 侧看到
    `Deactivated successfully` + `ExecMainCode=0/ExecMainStatus=0` + `NRestarts` +1（systemd 按
    Restart=always 拉起）——**看起来像"服务自己重启了"**，从现象推不到根因；同一台机器上
    「没用过 console 就停 VM」不会复现（故单测/冒烟测不到）。
  定位过程：给调试构建装 `signal.Notify(ch)`（一次性接管全部可捕获信号）后复现，日志立刻现形：
    `DEBUG-R86 收到信号 sig="hangup"`（还有一次 `sig="broken pipe"`）；进程被接管才活下来。
  根因：`internal/orchestrator/compute/console_libvirt.go` 用 `os.OpenFile(pty, os.O_RDWR, 0)` 打开
    libvirt 给域串口分配的 pty——nfvisd 由 systemd 拉起时是「无控制终端的会话首进程」，
    **不带 O_NOCTTY 打开 tty 会让它夺取控制终端**；此后该 pty 的 master（QEMU）一关闭
    （VM 被 stop/destroy），内核就向会话前台进程组发 SIGHUP，默认动作是终止进程。
  修（决策 #183）：① `os.OpenFile(pty, os.O_RDWR|syscall.O_NOCTTY, 0)`（根因）；
    ② 纵深防御 `internal/systemd.WatchHangup`（linux 实现 + 非 linux 空操作）——接管 SIGHUP 记 WARN 后继续；
    ③ `deploy/nfvis.service` 删掉 `ExecReload=/bin/kill -HUP $MAINPID`（本进程无重载语义，
      旧行为下 `systemctl reload nfvis` 实为"杀掉再拉起"）。
  测试：`internal/systemd/hangup_linux_test.go`（真发两次 SIGHUP：回调被调用且进程仍存活）；
    `internal/archtest/console_pty_test.go`（源码守护：串口 pty 打开点必须带 O_NOCTTY）。
  真机复验（1.1.48~dev2，4 个循环）：每轮 start → 真 pty 打开 console（日志里能看到 guest 的
    `cloud-init`/`login:` 行，即**真的在用**）→ stop；结果 `ps -o tty` 全程 `?`（未夺取控制终端）、
    守护进程 PID 不变、`NRestarts` 0 → 0、四轮全部干净。

----- §5 工具假红（与产品缺陷分开记）：生命周期检查器把产品命名的 bond 当成了自由物理口
  现象：`cli-lifecycle-check.sh` 的 L1-2（删 bond 后无残留）恒报
    `✗ L1-2 建立 bond 失败或未落数据面`，细节是 `bonds[rc84t-b0].members: 成员口 "bond0" 不是物理口`。
  根因（工具侧）：`vpp_phys_ports()` 只按 `^BondEthernet` 前缀排除，而**产品会给 bond 起自己的名字**
    （如 `bond0`）——`vppctl show interface` 里显示的是产品名，`show bond details` 里才是 BondEthernet0；
    于是自由口枚举把 `bond0` 当成了可自由分配的物理口，L1-2 拿另一个 bond 当成员口 → 被产品校验正确拒绝
    → 看起来像「产品建不起 bond」。
  修：自由口枚举改为「物理口 = VPP 口 − `^BondEthernet/^bvi/^vh-/^tap/^memif` − **产品 `show bonds`
    列出的 bond 名**」；修后同一现场：枚举正确排除 `bond0`（无自由口时如实**跳过**而不是假红），
    有自由口时 L1-2 转绿（建立侧正向控制 `VPP bond 集合 →BondEthernet0`、删除后无 BondEthernet 残留、
    成员口回到普通口、配置逐字节一致）。
  与「工具假绿」同一条原则：**判据本身错了要先修判据**——本轮先确认产品校验的理由（角色互斥）成立，
    再改工具。

----- §8 本轮新登记（未修，如实记录）------------------------------------------------
- **R86-6（P2，告警生命周期）对象删除后告警不自消，且「主动停容器」被报成 critical「异常退出」**：
  `show alarms active`（配置里**已无** VNF/容器）仍长期挂着
  `VNF_PORT_DOWN vnf-a/eth0`、`VNF_PORT_DOWN vnf-b/eth0`、`critical CONTAINER_EXITED walk-ct
  容器 walk-ct 异常退出（状态 exited）`；其中 walk-ct 是**操作者主动 `request … stop`** 的
  （并非异常），措辞与严重度都指向"故障"。控制台总览页同样列出这三条（仪表盘长期挂着不存在的对象）。
  与 R84-17（删 VNF 后 VNF_PORT_DOWN 不自消）同族、本轮在「对象已删除」的条件下再次复现。
- **R86-7（P3，读视图缺字段）接口读视图不含 MTU**：`show interfaces <口> detail` 与 REST 都不给 MTU，
  故控制台接口列表的 MTU 列恒为「—」；而同刻 `vppctl show interface ens192` 明确有 `9000/0/0/0`
  （配置侧也能 `set interfaces <n> mtu`）——与 R84-3（列表端点不返回计数）同族，属"取不到就不给"的
  保守口径，登记待补。
- **R86-8（P3，脚本模式可用性）`-c` 脚本里「值未变化」的空操作会中止整段脚本**：套件与本轮多次踩到
  （`set interfaces ens192 description cli-pre` 已是该值 → `%% 语句未产生配置变更` → 后续行全部不执行、候选被丢弃）。
  这是套件头部写明的口径，也是"任一行出错即停"的必然结果；登记**建议**（非缺陷）：给套件加一个"前置复位"
  步骤，或让 CLI 支持 `--keep-going` 之类的脚本选项（交互模式下无此问题）。
