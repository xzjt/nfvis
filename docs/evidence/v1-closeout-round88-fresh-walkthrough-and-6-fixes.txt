----- §3 六条缺陷（R88-1~R88-6）：现象 / 定位 / 修法 / 单测 / 真机复验 -------------------

R88-1（P3，环境交互 + 读视图长期不一致）**VPP 包自带 sysctl 把 1G 大页池撑过内核基线声明值**
  现象（1.1.49，干净快照首装后即出现）：cmdline 声明 `hugepages=1`（1G），而
    `show system kernel` 显示「大页 1G：内核基线 1 / 运行实际 4」——池比声明多 3 页。
    此前被记作「1G 池无主占用（未做回收）」，机制未定位。
  定位（本轮查清）：VPP 的 deb 装了 `/etc/sysctl.d/80-vpp.conf`，其中 `vm.nr_hugepages=1024`
    （文件注释写明是给 **2M** 池留的）；而 **`vm.nr_hugepages` 只作用于「默认尺寸」池**。
    产品内核基线设了 `default_hugepagesz=1G`（1G 池 > 0 时必设）→ 该 sysctl 落到 **1G** 池上，
    systemd-sysctl 在开机早期按**可用内存尽量分配**（`journalctl -b` 可见 `systemd-sysctl.service`
    的执行记录）⇒ 1G 池被撑到内存允许的上限。
  修：产品写内核基线时**同时**维护 `/etc/sysctl.d/90-nfvis-hugepages.conf`，把 `vm.nr_hugepages`
    钉为**默认尺寸池的声明值**（判据与 `GenerateBaseline` 同源：1G>0 ⇒ 默认尺寸 1G，写 1G 页数；
    否则写 2M 页数）。文件名序 90 > 80 ⇒ systemd-sysctl 后执行者生效，多余空闲页随之释放；
    回退基线时该文件一并撤除。生成器单源：`internal/system.GenerateHugepageSysctl` +
    `nfvisd --print-hugepage-sysctl`（安装器脚本与运行期共用），运行期另有启动补写
    `EnsureHugepageSysctlFromCmdline`（覆盖「安装期直接写片段、没走 Apply」的首装路径，同 #182 口径）。
  单测：`kernel_apply_test.go` 两例（双池钉 1G 值且**不得**把 2M 数写给默认尺寸池 / 单 2M 钉 2M /
  都不托管则不产出；从 cmdline 补写的幂等与撤除）。
  真机复验（1.1.50~dev1，**对照实验**）：把 1G 声明改为 1 →
    ① **对照组**（删掉 90 号文件后重启）：cmdline `hugepages=1`，实际 **nr=3**（缺陷复现）+
       nfvisd 启动时自动重建了钉值文件（本 boot 的 sysctl 已执行完，故本 boot 不生效）；
    ② **实验组**（有钉值文件时重启）：cmdline `hugepages=1`，实际 **nr=1（free 1）**，
       `show system kernel` 三方对照「大页 1G：基线 1 / 实际 1」**一致**。
    随后恢复 1G=4 并复跑，池 = 4（声明值）。

R88-2（P1，功能不可用 + 假绿）**VRF 内静态路由的下一跳解析在默认表，路由恒 drop 而读视图全绿**
  现象（1.1.49 干净现场，纯产品路径）：`set virtual-switches vs-wan static-routes 10.0.0.0/8
    next-hop 192.168.155.2` → `commit 成功`；`show vrfs vs-wan routes` 也读得到这一条。
    但 VPP 侧该路由 **DPO 恒为 `dpo-drop`**、不转发：
      `vppctl show ip fib index 2 10.0.0.0/8` → `path: recursive: via 192.168.155.2 **in fib:0**`
    而同一张表（fib 2）里 `192.168.155.2/32` 在 ARP 解析后是 resolved adjacency（fib 0 里始终 drop）。
  定位：`internal/orchestrator/network/l3_govpp.go` 的 `IPRouteAddDel` 构造 `FibPath` 时**没填
    `TableID`**（binapi 的 `fib_types.FibPath.TableID` 存在）——递归下一跳在**哪张表**里解析由该
    字段决定，缺省 0 = 默认表。控制面（`IPRouteDump`）回读正常，所以「命令成功、读视图正常、
    数据面全丢」，属典型「答非所问」。
  修：把路径构造抽成纯函数 `recursiveNextHopPaths(tableID, nextHop)` 并填 `TableID: tableID`。
  单测：`l3_route_table_test.go` 三例（表号必须落到 FibPath、IPv6 分支、非法地址报错）。
  真机复验（1.1.50~dev1）：同一条命令后 FIB 里 DPO 变为已解析的
    `ipv4 via 192.168.155.2 ens192: mtu:9000 next:3`（**不再是 dpo-drop**）。

R88-3（P1，改配置的顺序敏感 + 整体回滚 + 数据面残留）**L2 access/trunk 子接口重建不幂等**
  现象（可稳定复现）：先建好 vs-l2（`type l2` + `vlan access 100` + 端口 ens224）→ commit 成功；
    之后**再给同一台交换机加一个端口**（本例是 VNF 的 vNIC）→ commit 报
      `%% 底座下发失败（已补偿）: 下发失败 bridge-domain[vs-l2]: 创建 access 子接口 ens224 vlan 100:
       VPPApiError: VLAN subif already exists (-56)` → **整次提交失败并回滚**。
    第二个面：删掉该交换机后，VPP 里长期残留 `ens224.100`（`show interfaces physical` 标「未声明」，
    产品当时**没有**清理它的路径；`delete interfaces ens224.100` 也报「无匹配配置」）。
  定位：BD 自身有存在性判断（`ApplyBridgeDomain` 的 `BridgeDomainExists`），但**成员子接口**
    在 `desiredMembers` 里无条件 `create_subif`——而「按声明全量重放」在交换机定义有任何变化时都会
    重跑一遍。残留面则是 `DeleteBridgeDomain` 只摘成员、不删子接口。
  修：① `ensureSubif` 幂等——建之前按真实命名规则 `<父口名>.<vlan>`（`l2ParentIfaceName` +
    `subifName`，与 L3 侧同规则）查一次，存在即复用，并登记进「本交换机建的子接口」集合；
    ② 删 BD 后回收该集合（`DeleteSubif`，已不存在按已达成容错），回退/恢复收敛的 `reset`
    一并清登记。
  单测：`l2_test.go` 三例（幂等重放：给已建交换机新增端口必须成功且旧端口子接口只建一次 /
    删交换机回收子接口 / 原有「access vlan 建子接口」仍绿）；假客户端复刻 `-56` 语义与
    `delete_subif` 的 `-2`。
  真机复验（1.1.50~dev1）：① 建 vs-l2a（access 200、端口 ens224）后**追加端口 ens192** →
    `commit 成功 (revision 67)`，VPP 里 `ens224.200`（复用）与 `ens192.200`（新建）并存；
    ② `delete virtual-switches vs-l2a` → `commit 成功 (revision 68)`，两子接口**都从 VPP 消失**，
    `show interfaces physical` 只剩两个物理口。

R88-4（P3，读视图缺字段/答非所问）**`/system/status.hostname` 只取配置值，全新安装恒为空**
  现象（1.1.49 干净安装）：控制台总览「系统 → 主机名」显示 **「—」**，而机器实际主机名是 `nfvis`
    （`hostname`、`/etc/hostname` 一致）；`GET /api/v1/system/status` 里 `"hostname": ""`。
  定位：`internal/api/resources_w5.go` 只取 `cfg.System.Hostname`；全新安装没人设过
    `set system hostname` ⇒ 恒空。形状守护的白名单里当时写着「有意不退回内核 hostname」，
    但附录 A 并无对应决策（属实现口径未与「面板承诺了该字段」对齐）。
  修：配置显式值优先，未声明时回退 `os.Hostname()`，两者都取不到才为空串（不编造）——
    与 #189 接口 MTU 的「配置优先、否则运行态」同一口径。白名单说明与 OpenAPI 字段描述同步。
  单测：`system_status_hostname_test.go` 两例（未声明 ⇒ 等于 `os.Hostname()`；**显式声明优先**，
    不能被内核主机名盖掉）。
  真机复验（1.1.50~dev1）：配置里有套件留下的 hostname ⇒ 返回该配置值（配置优先）；
    `delete system hostname` 后 ⇒ 返回 **`nfvis`**（= 主机名事实）。

R88-5（P2，界面渲染错误）**控制台网络对象页 VRF 的「路由数」列把对象数组直接渲染成 `[object Object]`**
  现象（Browser Use 黑盒）：网络对象页 VRF 表里 vs-wan（两条静态路由）的「路由数」列显示
    **`[object Object],[object Object]`**；而同一页的 ACL「规则数」与 VRF 详情页的「静态路由」
    计数都是正常数字（同一数据在 detail 用的是 `.length`）。
  定位：`internal/api/ui/app.js` 的 `NET_OBJECT_VIEWS` 里 VRF 行取值为 `v.routes != null ? v.routes : …`
    （直接把路由对象数组塞进单元格）。
  修：取 `v.routes.length`（列名即「路由数」，与详情页口径一致）；加源码守护
    `TestNetworkObjectsVrfRouteCountRendersNumber`（禁止旧写法回归）。
  真机复验（1.1.50~dev1，浏览器刷新后）：该列显示 **2**。
  ⚠️ 附带发现（观察项，非缺陷）：SPA 的 hash 导航不重载页面，升级后**已打开**的旧页面会继续跑旧
    `app.js`（界面上版本号会随轮询变新，渲染逻辑还是旧的）；手动刷新即恢复。静态资源响应头是
    `cache-control: no-cache`（策略正确），故这里只是「升级后需刷新」的体验提示。

R88-6（P1，一次清干净做不到 + 依赖容错）**同一提交里删 VNF 与「把它 vNIC 当 L3 接口的交换机」必然失败**
  现象（清出走查对象时撞上，可稳定复现）：一次提交里
      `delete virtual-machine-functions vnf-b` + `delete virtual-switches vs-nat`
    （vs-nat 的 l3-interface 是 `vh-vnf-b-eth0`）→ 报
      `%% 底座下发失败（已补偿）: 下发失败 del-vrf[vs-nat]: 清理接口 7 地址:
       VPPApiError: Invalid sw_if_index (-2)`；补偿也失败（本轮 **#191 的机制如实报出**
      `补偿失败 del-vrf[…]`/`补偿失败 del-bridge-domain[…]` 与原因）。
    拆开也走不通：先删 VNF ⇒ 校验正确拒绝（悬空引用）；先删交换机 ⇒ 需在别的提交里。
    用户只能按「先删交换机、再删 VNF、再删其余」三次提交绕行（本轮即如此清场）。
  定位（两层）：① `internal/orchestrator/apply.go` 的删除段把 `del-vnf-if` 排在 `del-vrf` **之前**，
    于是被引用的 vNIC 先消失，`DeleteVRF` 清理地址时接口已不在；② `DeleteVRF` 对
    「接口已不存在」不容错，直接中断整次删除。
  修：① 删除顺序按**依赖倒序**——`del-vnf-if` 移到 `del-vrf`/`del-bond` **之后**
    （先解引用、后删被引用）；② `DeleteVRF` 的清地址与 `unbindTableIfaces` 对
    `isMissingIfaceErr`（`Invalid sw_if_index`/`-2`）按**已达成**容错（接口都没了，地址与表归属
    自然不存在，属第二道保险）。
  单测：`apply_test.go` 新增 `TestApplyVnicDeleteAfterVrfThatReferencesIt`（断言
    `del-vrf:vs-nat` 下标 < `del-vnf-if:vnf-a/eth0` 下标）。
  真机复验（1.1.50~dev1）：重建同样拓扑（vnf-x + vs-nat2 以其 vNIC 作 l3-interface）→
    **一次提交**同时删两者 → `commit 成功 (revision 70)`，现场干净（无交换机/无 VNF），
    `show alarms active` = **（无 active 告警）**（修复前必有补偿失败残渣）。

----- §4 观察项（如实登记，不占缺陷号）--------------------------------------------------
O-1（P3，可用性）**systemd 看门狗在负载尖峰下会杀服务**：本轮套件跑到阶段 3 的
  `request images upload`（179MB）时，nfvisd 的登录请求超时（1m30s）→
  `nfvis.service: Watchdog timeout (limit 30s)!` → systemd 按 Restart=always 杀掉并以 SIGABRT
  终结（同刻 systemd-resolved/networkd/udevd 等单元也被 SIGABRT，load average 达 8.68）。
  不是代码崩溃（journal 无 panic/goroutine dump），也**不是本轮修复引入**（该次跑的阶段 2
  59 条全绿，含本轮改动涉及的交换机/子接口路径）。同一套件在系统 idle 时跑则全绿（见 §5）。
  建议：`WatchdogSec=30`（interval 15s）在 6 vCPU 小机上遇到「大文件上传 + 并发配置」这类
  尖峰时偏紧，可评估放宽或用独立于请求路径的喂狗。
O-2（P3，展示）**`show version` 的 DPDK 恒为「（未探测到）」**：CLI 注释写明「DPDK 无可靠来源」
  （决策 #118 收口，如实呈现不编造），VPP 26.06 的 `show version verbose` 里也确实没有 DPDK 版本行；

§7 round88 追加（同轮）：`show vpp runtime` 落地 + 大页 sysctl 单一事实源
（用户点名两问：「runtime 能修吗」「大页声明能否全由 nfvis 控制」；两条都是设计级改动，
  先查数据源再动手 —— 决策 #200 / #201，修复版 1.1.50~dev2/~dev5 真机复验）
================================================================================

① `show vpp runtime`（此前是「%% VPP runtime 统计未接入」占位，cli-fulltest 长期**唯一一条 ✗**）

   数据源实测（VPP 26.06-release，nfvis-vm）：
   · **按节点**明细（`show runtime` 主体那张 Calls/Vectors/Suspends/Packet-Clocks 表）**没有结构化来源**：
       - `vpp_get_stats dump machine "/*"` 全量 **18090 条**里没有任何 `/sys/node/*` 或 runtime 类路径；
       - govpp v0.13.0 的 module cache 里**没有 runtime 的 binapi 包**（无二进制 API 可用）；
       - 本机 `vpp_plugins/` 里也没有 `runtime_plugin.so`——`show runtime` 是 vlib 内核数据、由 vppctl 直读。
   · **线程级**运行态在 stats segment 里有，且与 `show runtime` 每线程汇总行同源：
       `/sys/vector_rate`、`/sys/vector_rate_per_worker`、`/sys/loops_per_worker`（后两条是**组合计数**，
       按线程索引一条，索引 0 = 主线程、1..N = 工作线程）、`/sys/num_worker_threads`、`/sys/boottime`。
       实测对照（同一时刻附近采样）：产品读到主线程 loops 420873 / 工作线程 7671480，
       `vppctl show runtime` 给 290325.85 / 7536236.03 —— 同量级同步调。

   实现：`state.RuntimeStats` + `network.ParseStatsPerThread` / `RuntimeStatsFromDump`（纯函数）+
     `show vpp runtime [thread <id>]` 渲染；数据源走既有的同版本工具 `vpp_get_stats`（决策 #68 的通道，
     组合计数正是 statsclient 在 26.06 上解不出的那类值类型）。**不解析 vppctl 文本**，按节点明细在输出里
     如实说明需 `vppctl show runtime`，不假装有。

   真机复验（1.1.50~dev2）：
   · 有流量（300 个 ICMP 穿过 VPP）→ `vector rate: 2.00`、两线程 `VectorRate 1.00`；
   · 空载 → `vector rate: 0.00`；`uptime` 随 /sys/boottime 变化（3164s）；
   · `show vpp runtime thread 0` 只列主线程；`show vpp runtime thread 9` →
     `% 无线程 9 的运行态（可用线程：0,1）`（不静默给空表）。
   测试：`runtime_stats_test.go` 4 例（用**真机 dump 原文**：值在第 4 段、简单计数不得混入组合表、
     无运行态计数时宁缺勿错、boottime 缺失/未来时刻不给负数）、`cli_vpp_runtime_test.go` 3 例
     （有数据时不得出现行首 `%`、过滤与不存在的线程、不可用时 `%%` + 原因）；
     该命令补进 `cli_contract_coverage_test.go` 的契约命令清单。
   套件效果：`cli-fulltest` 从 **194/1/12 → 195/0/12**（round80 以来那条唯一 ✗ 归零）。
     附注：CLI 命令全表里这条的「⚠️ 未接入」登记与手册三处「未接入」说明已同步更新，
     已知缺口计数 3 → 2。

② 大页池 sysctl 的单一事实源（接管 vpp 包的 conffile；承接 #199）

   事实：`/etc/sysctl.d/80-vpp.conf` 是 **vpp 包的 conffile**（dpkg 记录了 md5），其**生效内容只有两行**
     —— `vm.nr_hugepages=1024`（本轮问题源）与 `vm.hugetlb_shm_group=0`（root 组可访问大页），
     其余（`vm.max_map_count`、`kernel.shmmax`）全是注释。`dpkg-divert` 是 dpkg 官方机制且本机已在用
     （libreadline8t64）。
   实现：postinst `dpkg-divert --package nfvis --add --rename --divert …80-vpp.conf.vpp-disabled …80-vpp.conf`
     （**幂等**；失败只提示不阻断安装，因为 90 号钉值仍在），prerm 的 `remove|deconfigure` 分支
     `--remove --rename` 还原，postrm 的 `purge` 分支删掉产品自己的 90 号文件；90 号文件同时**接管**
     `vm.hugetlb_shm_group = 0`。
   ⚠️ 过程中真机抓到一处自伤：第一版幂等守卫写成 `[ -e /etc/sysctl.d/80-vpp.conf ]`——接管之后该路径
     本就不存在，于是「已接管」这条日志永远不会出现（行为正确、可观测性错）。判据改为 **diversion 记录**
     （`dpkg-divert --list <path>`）后才正确。

   真机复验（1.1.50~dev2~dev5，**装/幂等/卸/重装/重启**全链路）：
   · 首装（从已卸载态）：`已接管 /etc/sysctl.d/80-vpp.conf（挪到 .vpp-disabled；大页池由 NFViS 单源声明）`，
     `/etc/sysctl.d/` 里只剩 `80-vpp.conf.vpp-disabled` + 我们的 90 号文件；
   · 覆盖安装：`大页池 sysctl 已由 NFViS 接管（…vpp-disabled）`（幂等分支，diversion 仍只一条）；
   · `dpkg -r nfvis`：`已还原 /etc/sysctl.d/80-vpp.conf（vpp 包自带的 sysctl 恢复原位）`，
     diversion 清零、`80-vpp.conf` 回到原路径；
   · **接管后的对照实验（决定性问题）**：把产品自己的 90 号文件移走、cmdline 声明 `hugepages=1` →
     池 **nr=1**；而接管前同一条件是 **nr=3**（被 vpp 的 1024 撑大）⇒ 撑大机制**彻底消失**，
     不只是"被压回"；重启后 nfvisd 又按 cmdline 补写了 90 号文件（启动单源补写仍生效）；
   · 恢复声明 4 + 重启：`1G nr=4`、`vm.nr_hugepages=4`、`vm.hugetlb_shm_group=0`，服务 active；
     `/etc/sysctl.d/` 只剩被接管的 vpp 件与 90 号文件 ⇒ 开机期不再有"先撑大再回缩"的抖动。
   测试：`kernel_apply_test.go` 断言 90 号内容含 `vm.nr_hugepages = <默认尺寸池声明值>` 与
     `vm.hugetlb_shm_group = 0`；`check_maint_scripts.sh`（顶层 exit 后可执行语句守护）在改动后仍通过。
