§1 真机复现确认（4 项，均独立事实源）
1a【高】**L3 接口 ACL 解绑无路径（配置删了、数据面还在拦）**
   - 复现：`set acls r142-acl rule 10 source 192.168.99.200/32 destination any protocol tcp action deny`（rev 1554）
     → `set virtual-switches sem-vs l3-interface ens224 ip address 192.168.111.1/24` + `… acl-in r142-acl`（rev 1555）
     → VPP 绑定生效：`show acl-plugin interface` = `sw_if_index 2: input acl(s): 0`、
     `show acl-plugin macip interface` = `sw_if_index 2: 0`（#341 的伴随 macip 也在）。
   - **只清绑定**：`delete virtual-switches sem-vs l3-interface ens224 acl-in r142-acl`（rev 1556）→
     配置读视图已无 `acl_in`，**VPP 仍 `input acl(s): 0`**（deny 规则继续拦）。
   - **整条删 l3-interface**（rev 1557）→ 同上仍拦；且 **ens224 仍留在表 314680 且带 `192.168.111.1/24`**
     （接口未被回收）。
   - 代码根因：`acl.go:243-268` 的「空绑定=解绑」分支**没有任何生产调用者**；`l3.go:197-205` 对
     `AclIn==""` 直接 `continue`；`apply.go` 无 L3 接口/绑定的差分撤销计划。删除被引用 ACL 被校验拒绝，
     所以「先清绑定、再删 ACL」是操作者撤销 ACL 的**主路径**，正好落在缺口上。
   - 影响：撤销 ACL 后旧规则（含 deny）继续生效 —— 与 #340/#341/#342 的承诺（gateway/端口拒绝、
     L3 形态可用、删除倒序容错）组合起来是「唯一可用形态的撤销路径缺失」。
1b【低但同族】**删 ACL 只清 ACL 绑定，伴随 macip 残留**：紧接上面 `delete acls r142-acl`（rev 1558）→
   `show acl-plugin acl` 空（ACL 本体已删、ACL 绑定已解），但 `show acl-plugin macip interface` 仍
   `sw_if_index 2: 0`（`nfvis-nonip-permit` macip ACL 与绑定留下，直到 VPP 重启；残渣对账也不覆盖）。
2【高（条件性）】**#354 探活上界不生效：libvirt 楔死 → 状态机静默卡死**
   - 复现：`kill -STOP <libvirtd pid>`（socket 可连、零响应 = 与 round129 同族的楔死形态）→ 75s 后：
     `show alarms active` **无 `COMPUTE_UNAVAILABLE`**、`systemctl is-active nfvis` = active（WatchdogSec=30 未触发）、
     journal 90s 内**零**探活/中断/复连记录；期间 `show virtual-machine-functions sem-vm` **挂到
     客户端 90s 超时**（实测 100s 被 `timeout` 杀掉）。`kill -CONT` 后立即恢复、仍无任何告警/日志。
   - 代码根因：`async_connect.go:243-250` 的 `withTimeout` 是同步调用（只有被调方尊重 ctx 才有界）；
     `conn_libvirt.go:253-265` 的 `StateReason` 只在入口查一次 `ctx.Err()`，随后 `DomainLookupByName` 无超时
     阻塞（go-libvirt `getResponse` 裸等、全模块无 deadline）。对照：VPP 探针有 goroutine+timer 硬兜底
     （`vpp.go:372-387`、`main.go:1130-1143`）——libvirt 探活两样都没有。
   - 影响链：状态机永不返回 ⇒ 不探活/不复连/不告警；15s 巡检持 `recoveryMu` 永久阻塞 ⇒ VPP 恢复收敛与
     commit 路径连带挂起；`/metrics` 与历史采样同族停摆；systemd 看门狗救不了（喂狗协程独立存活）。
3【中，#359】**幂等 Sync 清空应答的以太源 MAC**
   - 复现：启用 `dhcp-server`（rev 1552）后等一轮 15s 巡检 → 从第二 tap 注入 DISCOVER →
     pcap 显示 OFFER 的以太源 = **`00:00:00:00:00:00`**（应为内核 tap MAC `02:fe:…`）。
   - 代码根因：`dhcpserver.go:321` 每次 Sync 用配置规格覆盖 `rt.spec`（`tapMAC` 恒为零值），而
     `rt.spec.tapMAC = tr.MAC()`（`:343`）只在**打开内核 tap 的那一次**执行（幂等 Sync 在 `:327` 早退）。
   - 影响：投递不受影响（目的 MAC=chaddr），但 BD 会学到 `00:00:00:00:00:00` bogon 表项（实测有）；
     任何做 L2 源过滤/端口安全的环境会丢帧；与决策行「服务器 L2 源用 tap MAC」不符。
4【中，#359 + 观测】**停用/删除的回收顺序与索引身份**
   - 已执行复现（子智能体故障注入）：`teardown` 先删内存登记、`deleteTap` 失败只记错误，随后**仍删租约文件**
     （`dhcpserver.go:374-378`）⇒ 「同一次提交后序失败回滚」或「tap 删除失败」场景下租约表被抹、客户端仍用旧地址
     ⇒ 地址可被重复分配（v1 无冲突检测），且无告警。
   - `reset()` 不清 `tapIndex`（`:235-247`）⇒ VPP 重启后、下一次 Sync 成功前，端口读视图按**旧索引**过滤，
     `teardown` 也按旧索引发 `TapDelete`（索引是否被复用属真机待验；若复用可能误删/误滤用户接口）。
   - punt 注册失败时（`:300` 早退）tap 已建、已入 BD、但**未登记** ⇒ `TapIndexes()` 为空 ⇒ 内置 tap
     出现在用户端口视图（`source=runtime`，且用户删不掉）——与决策 ⑦ 相反。
