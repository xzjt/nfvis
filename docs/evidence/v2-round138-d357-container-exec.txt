## §0 能力前提核实（动手前，真机 spike — #338 的教训）

先在真机**直接打 Docker Engine API**（Docker 29.1.3，curl --unix-socket），确认三种形态都成立才写实现：

- `POST /containers/sem-ct/exec`（`AttachStdout/AttachStderr=true, Tty=false, Cmd=[...]`）⇒ 拿到 exec id；
- `POST /exec/{id}/start`（`Detach=false, Tty=false`）⇒ **多路复用流**，`xxd` 实证：
  `01 00 00 00 00 00 00 04 "out\n"` 紧跟 `02 … "err\n"`（`01`=stdout、`02`=stderr，后跟 4 字节大端长度）；
- `GET /exec/{id}/json` ⇒ `{"ExitCode":7,...}`；
- TTY 形态（`Tty=true`）⇒ `Content-Type: application/vnd.docker.raw-stream` + 裸 body。

⇒ 能力可用，据此写实现（`demuxDockerStream` 纯函数按实测帧格式写）。

## §1 作用效果（独立事实源＝`docker exec` 直跑）

```
$ nfvis-cli -c 'request container-functions sem-ct exec "ip addr"'
退出码: 0（耗时 55ms）
--- stdout ---
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
    inet 127.0.0.1/8 scope host lo
    ...
--- stderr ---
（无输出）
```

- **逐字对照**：产品 stdout 段与 `docker exec sem-ct ip addr` 的输出**完全一致**（Python 字符串比对 `True`）。
- **退出码对照**：`sh -c 'echo out; echo err 1>&2; exit 7'` ⇒ 产品报 `退出码: 7`、stdout=`out`、stderr=`err`；
  `docker exec` 直跑同命令 `rc=7` ⇒ 一致。
- stderr 与 stdout **分流**正确（两块分开渲染，各自「（无输出）」）。

## §2 生命周期

- `restart` 后 exec 仍可用：`exec "cat /etc/hostname"` ⇒ 容器 ID `5cc2f35882b1`（alpine）。
- **停机后如实拒绝**（CLI 与 REST 同款文案，且指向下一步）：
  ```
  %% 容器未处于运行态: sem-ct（当前 exited）；先 request container-functions sem-ct start
  ```
  REST 同场景 **409**，`message` 与 CLI 逐字一致。
- 再 `start` 回来即可用（无需重启 nfvisd）。

## §3 跨对象组合

`exec "ps -o pid,comm"` ⇒ `PID 1 sleep` / `13 ps` —— 看到的是**容器自己**的进程视图（不是宿主），
与容器编排（Entrypoint/Cmd）在配置里的声明一致。

## §4 对抗性

**① 超时（`sleep 60` + `timeout 3`）**：rc=1，输出
`%% 命令在 3s 内未结束（已停止等待；容器内进程可能仍在运行，退出码未知）`，**不报退出码**（未知 ≠ 0）。
**并且验证了这句文案是实话**（独立事实源）：超时后 `docker exec sem-ct ps | grep -c "sleep 60"` = **1**
⇒ 容器内进程确实仍在运行（Docker 无 exec 中止接口）。

**② 大输出（1 MiB）**：置 `truncated` 并标注「已截断：…超过 256 KiB 上限」，输出文件 ≈262 KB
（256 KiB 上限 + 头部），未撑爆内存、命令仍跑完（退出码 0）。

**③ 命令不存在**：`exec nope-xyz` ⇒ `退出码: 127`、stderr 回 `/bin/sh: nope-xyz: not found`，
而**本操作成功**（rc=0）——退出码是**结果**不是失败。

**④ 参数误用**：`exec ip addr`（忘加引号）⇒ `%% 命令是一个整体：含空格请加引号（如 exec "ip addr"）；
要加超时用 … <command> timeout <seconds>`；`timeout 999` ⇒ `%% timeout 须在 1..300 秒之间（缺省 30）`。

**⑤ S 档拒绕（临时建 `op-probe` operator 账号，验后已删）**：

| 面 | 命令/端点 | 结果 |
|---|---|---|
| CLI | `request container-functions sem-ct exec "id"`（operator） | `%% 无权限执行该命令` |
| CLI（对照） | `request container-functions sem-ct log last 2`（operator） | 正常返回 |
| REST | `POST …/sem-ct:exec`（operator token） | **403** |
| REST（对照） | `GET …/sem-ct/logs`（同一 token） | **200** |

**⑥ REST 状态码矩阵**：无 token **401** / 未知容器 **404** / 停机 **409** / 空命令 **400** /
`timeout_seconds=999` **400** / 正常 **200**（响应含 `exit_code`/`stdout`/`stderr`/`duration_ms`）。

**首跑实测发现套件夹具问题并已修**：`cli-ct2` 的命令是 `command /bin/sh`（无参）——容器 start 后
**立刻退出**，于是 `exec` 正控必然撞「未处于运行态」（首跑 240/2/15）。修法是给夹具补
`args -c "sleep 3600"` 让容器**常驻**（否则只有「拒绝」没有「能执行」，正控缺失）；
`command`→Entrypoint、`args`→Cmd，即 `/bin/sh -c "sleep 3600"`。

**夹具修好后又撞两次（都如实入册）**：
① 脚本块内写 `#` 注释会被**当成命令**执行（`-c` 逐行）⇒ 整个阶段块中止、`cli-ct2` 没建出来，
   阶段 4 级联 9 条假红——注释已挪到块外；
② `args -c "sleep 3600"` 的内层引号被**外层 bash 双引号吃掉**（退化成 `sh -c sleep`，sleep 报缺操作数
   后容器立刻退出）⇒ 改用**无引号**形态 `command /bin/sleep` + `args 3600`。
（两次都是「先看级联关系、再怀疑产品」才定位到的——round36 的同款纪律。）

**跑套件时撞到的环境事故（如实登记）**：我早前用 `op-probe` 口令做 CLI 验证时**忘了 `-u op-probe`**，
于是那几次失败登录被计到 **admin** 头上，叠加阈值后 **admin 被锁定 15 分钟**
（`% 登录失败: 连续失败次数过多，账号已锁定：14:01:45 前禁止登录`，决策 #76 的口令策略按设计生效）。
**教训**：换身份验证必须显式给 `-u`；失败登录是**有代价**的（累计到阈值即锁号），别拿真账号试口令。
（锁定窗口结束后复跑，结果见 §7 补记。）
