===== V1 收尾第七十二轮：控制台顶栏「我的账号」（只读账号可用的自助改密入口，决策 #147）=====
日期：2026-09-24；分支 `feat/console-self-service-password`（main `bca77ff` 之上）

----- 1. 起因与交付 -----
起因（round70 登记、本轮处置）：改口令的表单原先只在「用户与权限」页（`#/system/users`），而该页自决策 #145
起对 `read-only` 角色隐藏（导航不列、页内写入口隐藏）⇒ **只读用户在界面上无处改自己的口令**。服务端本来就
允许：`POST /api/v1/system/login-users/{name}:change-password` 注册为 **ClassReadOnly**（本人 + 验旧口令，
见 `internal/api/server.go` 与 `resources_w5.go` 的 `handleChangePassword`）——即缺口纯在界面侧。

| 文件 | 改了什么 |
|---|---|
| `internal/api/ui/index.html` | 顶栏加 `#account-btn`「我的账号」（`topbar-right`，**不带 `data-write`**）；新增只含「当前口令 / 新口令」的小对话框 `#acct`（`#acct-who`/`#acct-old`/`#acct-new`/`#acct-msg`/`#acct-close`/`#acct-submit`，同样**整块不带 `data-write`**），置于 `#modal` 之前（确认框叠在它上面） |
| `internal/api/ui/app.js` | 新增「我的账号」段：`acctMsg`（消息落在本框）、`openAcct`（每次打开先清空口令控件）、`closeAcct`；绑定 `#account-btn` → `openAcct`、`#acct-close` → `closeAcct`、`#acct-submit` → 读值后调 `usrMyPassword` 并随即清空；`#acct` 点遮罩与 Esc 也算取消（Esc 先给叠在上面的确认框）。`usrMyPassword` / `usrPrecheck` 各加一个**消息去处**参数（缺省＝用户页的 `#usr-msg`），顶栏这条的提示因此落在自己的框里——**一条处理器两个入口**，没有第二份实现 |

| `docs/NFViS-用户手册.md` | §10.12 补两处**操作者可见**的说明（随包文档 = 发布件的一部分，R48-5 的教训：新交付的界面入口必须写进手册）：顶栏右上有「我的账号」；以及一段「改自己的口令」——**所有账号可见**（含只读账号）、高危档确认、改完用新口令重新登录（不会自动登出）、用户页那条表单仍保留。**未改**其余段落 |

设计要点（逐条对应本轮要求）：
1. **免构建**：原生 HTML/CSS/JS，无 npm、无打包步骤（Go `embed`）。
2. **入口与对话框都不带 `data-write`**——这正是本条的**目的**：只读账号要看得见、用得上（带了就会被
   `body.role-readonly [data-write]` 的 CSS 规则隐藏，本入口白加）。入口给了稳定 id `account-btn` 便于守护断言。
3. **分级确认按高危档**（与用户页那条一致）：确认词＝**当前登录用户名**、默认 10 秒倒计时、只读回显
   `request system password change`、影响面四条（立即生效 / 服务端验旧口令 / 新口令按本机策略 / 可回退）。
4. **改完不自动登出**：只提示「口令已修改——请用新口令重新登录。」；框可取消（点「取消」、点遮罩、按 Esc）。
5. **口令控件不在别处留值**：只在提交那一刻读值、随后立即清空；开框时也先清空（不把上次的输入带进来）。
6. **契约与服务端一字未改**（REST 路径、注册 class 都不动）；用户页那条表单**保留**（两个入口同源、行为一致）。

**§3.6 一处行为观察（如实记录，非缺陷）**：首次尝试改密时被服务端拒绝——
`修改口令失败：candidate 会话锁被占用: 由 admin@api 持有`，界面**如实回显**该原因、未谎报成功。
根因是产品既有语义：login-users 的写路径走**配置事务**（取编辑锁 → 写候选 → 立即提交，见决策 #141 刀 4b 的核实），
而当时我用于建探针账号的 admin REST 会话**没有登出**、仍持有编辑锁；按决策 #119 的口径 `POST /logout`
释放锁后即成功。**结论**：自助改密会被**别人的**编辑锁挡住是既有设计（FR-CFG-001 的会话锁），
界面表现正确（把服务端原话给操作者）；已记入本证据备查。
**同批查出的一条既有缺陷（登记，未在本刀修）**：`login-users` 的写路径（`internal/api/resources_w5.go` 的
`mutateLoginUsers`）是「取编辑锁 → 写候选 → 立即提交」，而 `Engine.Commit` **不释放锁**——只有 `Release`/`Discard`/
空闲超时（`internal/config/engine.go` 的 `releaseLocked` 调用点）才释放。控制台**配置页**的提交是**客户端**显式收尾
（`app.js` 的 `cfgEndSession()`「已生效：释放会话锁」），所以那边没有这个问题；但**用户管理/自助改密**这条路径
提交后**仍持有全局编辑锁**，直到该会话登出（决策 #119 的 `POST /logout`）或空闲超时 ⇒ 其它会话的配置写会被
409「candidate 会话锁被占用: 由 X 持有」挡住。本轮验收里两次撞到（admin 建完探针没登出、acct-tmp 改完口令后
我用 admin 删账号得 409）。**判据**：这条对**所有** login-users 写（建/删/改 class/改口令）都成立，属既有行为、
非本刀引入；修法是在 `mutateLoginUsers` 提交成功后按 `cfgEndSession` 的同款语义释放锁 + 用例（变异验证）。
已登记在 `docs/V1-收尾待办.md` §2.3 与本文件。
