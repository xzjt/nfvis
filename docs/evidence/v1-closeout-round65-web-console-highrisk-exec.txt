----- 6. 附带发现：只读账号（read-only）的角色行为（**设计 §8 未实现**）-----
顺手做的角色行为实测（同一个开发态实例，另建 `netop-ro`/read-only 账号登入浏览器）：

| 观察面 | 结果 |
|---|---|
| 导航 | **21 个导航项一个不少**（含「配置」「用户与权限」「证书」「内核基线」这些写页） |
| 各页写入口 | **全部可见**：VM 页「启动/停止/重启」、用户页「创建用户/修改我的口令」、证书页「安装并立即生效/重签自签证书」、内核页「写入基线/回退上一次基线」、配置页「开始编辑」、运维页「安装升级包/回退到上一版本/从所选归档恢复配置/**恢复出厂**/**重启主机**/关机」、抓包页「开始抓包/停止并导出」 |
| 服务端判定 | **拦得住**：点「开始编辑」→ 页内如实回「配置（无法进入编辑：当前 class 无权执行该操作）」；`#/system/users` 整页「以下数据读取失败：/system/login-users（当前 class 无权执行该操作）」；配置库无任何变化 |
| 浏览器 JS | 无异常（`errs=[]`） |

**结论**：**服务端 class 判定是真边界（有效）**，但**界面没有按角色隐藏写入口**——设计 §8 的
「`read-only` 只见只读页…写按钮**隐藏**（不是禁用）」与骨架计划 Step 2 的验收项「只读账号看不到写入口」
**均未实现**（`internal/api/ui/app.js` 里除用户管理页外没有任何 class 判定）。本轮**只登记不改**
（跨 ~20 个页面的入口分类 + 需要浏览器复验，属独立一刀）；影响面是**体验与误导**（点下去才被拒），
不是越权。清理：该账号已删，配置库内容回到动作前（cfgsha 逐字节一致）。
