§0 结论
- **#386：DNS「管理网侧转发」＝不建（产品口径关闭）**——技术可行（产品管理地址的 UDP/53 空闲、
  #345 的转发核心可直接复用），但按产品口径关闭：管理网卡依 FR-NET-002「专用于 SSH/API/syslog/Prometheus」、
  设备本机解析已由宿主解析器覆盖、域内解析已由 #345 覆盖、对外提供解析只新增攻击面。
  **如需**：先改 FR 再立项（实现路线与工作量见 §3）。
- **#387：ACL 逐规则命中计数＝维持依赖底座（不投入）**——三条路线逐条评估：a) 待底座递增（唯一正当路线）；
  b) 退用 err 族总数——**实测粒度是「全局节点总量」**（无法归属到规则/接口），挂到某 ACL 名下即**误导性读数**，不采用；
  c) 自研计数通道——工程量大、需求不迫切，暂不立项。**重启条件**＝底座递增 或 产品提出明确需求。

§2 取证（round168 真机只读，两条）
- **DNS 侧（可行性事实）**：目标机 `ss -lnup` 的 UDP/53 监听者只有 systemd-resolved（`127.0.0.53%lo`、`127.0.0.54`）
  与 libvirt 自带 dnsmasq（`192.168.122.1`，virbr0 网络）；**产品管理地址（192.168.155.129）的 :53 空闲** ⇒
  若建，绑定不成问题（systemd 259 亦支持 `DNSStubListenerExtra`，但本定裁不走该路——见 §3 备注）。
- **ACL 侧（计数面事实）**：`acl_plugin.so` 的计数相关字符串仅两类——
  `/acl/%d/matches%c`（逐规则组合计数；#118 实测：启用 `acl_stats_intf_counters_enable` 并重绑定后**仍恒 0**）
  与 `Stats counters enabled for interface ACLs: %d`（全局开关的显示位）；节点 err 计数
  （`acl-plugin-in-ip4-fa` 等节点的 checked/permit/deny）为**节点级聚合**，无 per-interface、更无 per-rule。
  产品读视图现状：`show acls` 为配置视图（`internal/api/cli_net_show.go` 注释写明「运行态字段（ACL 命中计数…）
  属 M3，此处先呈现配置视图」），输出中不含计数列、不编造 0 命中。

§3 #386 的执行路径评估（若将来改 FR 立项；含方案比选）
- **方案 A（本定裁首选的将来路线）：复用 #345 转发核心 + 管理侧监听器**——绑**管理地址**（不绑通配）UDP/53；
  上游单一真源＝`set system dns server` 列表；显式开关语句（缺省关）；三面读视图；边界照 #345 口径如实
  （TCP 不在覆盖、无缓存、nfvisd 不在即中断）。工作量：中等（与 #345 同量级：契约 + 监听器/单测 + 真机四维 + 文档）。
- **方案 B（不采用）：systemd-resolved 的 `DNSStubListenerExtra=<管理地址>`**——最省（一行配置），
  但把宿主解析器整体暴露到管理网络，解析行为（缓存/上游切换/访问控制）脱离产品契约，与「契约可控、可如实告知」
  的口径不符，故不采用（仅作为事实登记）。
- **方案 C（不做，本定裁）**：现状即「设备自身走宿主解析器、域内走 #345、管理网客户端用既有 DNS 基础设施」。
- 前置（任何将来立项共同要求）：FR-NET-002（或新增 FR）需先改写为包含「对外 DNS 解析」——本产品管理网卡
  的用途是**规格书明文列举**的，新增服务须先动规格。
