§7 发现（登记待裁；按严重度排序）
--------------------------------------------------------------------------------
- **R84-1（P1，假成功 + 套件假绿）非交互脚本模式对「需确认」命令静默无操作且退出码 0**
  现象：`nfvis-cli -c "request system reboot"` 只打印
  「重启 nfvis 将中断全部业务。Restart the system? [yes,no]」→ rc=0，什么都没做；
  `request system software rollback`、`request images delete name …`、`request system zeroize`、
  `request interfaces <口> bind-dpdk|unbind-dpdk`、`delete virtual-machine-functions|containers|images`
  同理（凡服务端以 `[yes,no]` 结尾问询的都在内）。
  根因：确认流程只在交互 REPL 里实现（internal/cli/repl.go 的 `strings.HasSuffix(out,"[yes,no]")`
  分支读一行并追加 `--yes` 重发）；`runScript`（cmd/nfvis-cli/main.go）**完全不处理**问询文本，
  既不报错也不置 failed。
  连带：`contrib/scripts/cli-fulltest.sh` 的判定只看行首 `%`/`校验失败` 与 rc，
  于是把「问了没做」判成 ✓（本轮日志实见 `✓ request system software rollback`、
  `✓ request images delete name naming-test.tar`）——**套件覆盖是假的**。
  建议：runScript 检测到 `[yes,no]` 时按错误处理（`%% 需交互确认：非交互模式请显式追加 --yes`）
  并置 failed；套件对这些行显式加 `--yes` 或改判为「预期报错」。
  手工规避：命令尾加 `--yes`（本轮实测可用）。

- **R84-2（P1，配置完整性 + 数据面残留）CLI 删 L3 交换机不清同名 VRF（CLI⇄REST 不一致）**
  现象：`delete virtual-switches vs-l3` + commit 后，`show configuration` 里仍留
  `vrfs vs-l3 { name vs-l3; }`；`display set` 反推不出它（空 VRF 无语句形态，操作者看不见）；
  `vppctl show ip table` 里 `vs-l3` 表**跨 VPP 重启与 nfvisd 重启持久存在**，`show vrfs` 一直列出；
  CLI **无任何命令可清除**（`delete vrfs` = 无效命令；再 `delete virtual-switches vs-l3` = 「无匹配配置」）。
  根因：REST `DELETE /virtual-switches/{name}` 明确连同名 Vrf 一并删
  （resources.go，注释「L3 交换机与同名 VRF 条目互为映射（附录 B），一并删除」）；
  而 CLI 走 `applyTokens` 通用删除路径，只有 `delete virtual-switches <n> type` 这类别名规则
  才调 `removeVrf`（cli_aliases_net.go），整节点删除没有对应清理。
  建议：把「删虚拟交换机 → 同时删同名 Vrf」落到两侧共同依赖处（CLI 侧补等价清理），并补守护用例。
  规避：先 `set virtual-switches <名> type l2`（触发 removeVrf）再删对象。

- **R84-3（P2，假成功 + 误诊）接口统计在 VPP 重启后永久不可用（= R83-7 复现 + 根因）**
  现象：`show interfaces ens192 detail` 的 RxPkts/TxPkts 为 `-`；
  `show interfaces ens192 statistics` → `%% 接口 ens192 统计运行态不可用（stats 未接入）`；
  REST `GET /interfaces/{name}` 只回 `{"name":"ens192"}`（契约声明含 statistics）；
  控制台接口详情页据此显示「读取失败：该口当前取不到计数（数据面未连接或口不在数据面）」。
  同刻独立事实源有值：`vppctl show interface ens192` rx packets=174418、CLI 列表视图 RxPkts=62。
  根因：internal/orchestrator/network/stats_linux.go 的 `statsConn.conn` 进程内**只建一次**，
  VPP 重启后 stats segment 换了，`GetInterfaceStats` 失败 → `InterfaceCounters` 永久返回 false，
  且不重连；恢复只能 `systemctl restart nfvis`。
  **决定性证据（本轮实测）**：`systemctl restart nfvis` 后同一请求立刻恢复——
  `GET /interfaces/ens192` → `{"description":"cli-pre","name":"ens192","statistics":{"rx_packets":1,…}}`，
  `show interfaces ens192 statistics` → `interface ens192 statistics: {1 0 60 0 0 0 0 0}`；
  重启前同一请求只有 `{"name":"ens192"}`。⇒ 不是「stats 未接入」，是连接陈旧。
  建议：取数失败时重连一次并重建连接（或与 VPP 重连回调联动）；文案别再说「stats 未接入」。

- **R84-4（P2，假成功）`request vpp restart` 无起后健康校验（= R83-6 复现）**
  现象：把 2M 池运行期置 0（`echo 0 > …/hugepages-2048kB/nr_hugepages`）后走产品路径
  `request vpp restart` → 回「已按 committed 配置重启 VPP 并触发恢复收敛。」，
  而 VPP 实际 `failed (Result: core-dump)`、`code=dumped, signal=SEGV`、Mem peak 2.1M、
  `vppctl` Connection refused；`show interfaces` 会如实标注「VPP 未连接」。
  根因：requestVPP 的 restart 分支在 `vppRestart(ctx)` 返回 nil 即报成功（cli_compute_oper.go），
  不等起后健康校验。
  建议：restart 后短轮询校验 VPP 存活（binary API 可连），失败即 `%%` 报错并指出「VPP 未起来」；
  另可重启前按 startup.conf 需求预检大页池尺寸。

- **R84-5（P2，不可达指引）`show system kernel` 的「一致性」把运行期池增长判成基线未生效**
  现象：cmdline 已是 `hugepages=1`、配置期望也是 1，但运行实际 2 →
  输出「一致性：与配置期望不一致（需写入 GRUB 基线并重启生效）：大页 1G：期望 1，实际 2
  （cmdline 启动参数需生效并重启）」，并引导 `request system kernel apply` → `request system reboot`。
  实测重启 + `request vpp restart` 后 1G 仍是 2/1（VPP 运行期把池顶大后内核不回收），
  **照提示做永远不一致**；向导结尾与手册 §5.4 第 1 步「重启后应显示一致」因此不可达。
  根因：internal/system/kernel.go 的 `Compare` 用运行实际池大小与期望比对（不是 cmdline 与期望），
  而提示文案说的是 cmdline 未生效。
  建议：大页一致性按 cmdline（基线）比对；运行实际大于声明时另作说明（不判不一致），
  仅当运行实际小于声明（分配失败）才告警。控制台同源显示一并受益。

- **R84-6（P2，可诊断性）镜像下载中断后状态长期停在 downloading**
  现象：`request images download …` 直连 CDN 约 1.7MB/min，8.5MB 后停滞；`show images` 一直
  `downloading`，`detail` 无进度字段，journal 无任何相关日志，`index.json` 里 `.part` 留在原地；
  超过 client 的 10 分钟超时后仍显示 downloading（未验证到 failed 状态），操作者无进度/无错误/无重试指引。
  建议：进度写进 meta（`show images <名> detail` 可见）、超时/中断即落 `failed` 并在 CLI 报错、
  重试走断点续传（.part 已在，机制已有）。注：本轮最终用代理 curl + upload 绕过。

- **R84-7（P2，提示与实现不一致）容器镜像可用名：文案指错方向（#160 收口不完整）**
  现象：`set image alpine:3.20`（tar 内嵌 tag）与 `set image alpine.tar:latest`（产品重打的 tag）
  都被拒：`仓库中不存在镜像 "…"；仓库现有：alpine.qcow2、alpine.tar、debian-…。
  注意：容器镜像的可用名是 docker load 落地的 tar 内嵌 tag；上传目录项名与它不一致时，两个名字都用不了`；
  实际**只有仓库项名 `alpine.tar` 能通过**（commit 成功 rev 23/25）。
  建议：要么让校验同时接受 docker 里真实存在的引用（`alpine:3.20`），要么把文案改成
  「配置里请写上传的目录项名 <名>」，并让 `?`/Tab 候选直接列出仓库项名（现在候选是自由文本）。

- **R84-8（P3，易错点）`request images upload` 的 file 只认绝对路径**
  现象：`request images upload name alpine.qcow2 type vm-image file alpine.qcow2`（候选描述是
  「incoming 内的文件路径」）→ `%% 文件 alpine.qcow2 必须位于 /data/incoming 内（先经 scp/sftp 传入）`；
  根因是相对路径按**守护进程 CWD** 解析成 `/alpine.qcow2`。写 `/data/incoming/alpine.qcow2` 才成功。
  建议：相对路径按 IncomingDir 解析，或错误文案点明「请给绝对路径」。

- **R84-9（P3，文档漂移）手册 §5.3 的 wizard 输出样例与实现不符**
  样例写 `top`，实现打印 `exit`，且顺序在 commit 之前；另样例未含「内核基线已写入/pending_reboot」
  两段实际输出。建议随发布轮重拍该样例。

- **R84-10（P3，显示与判定口径不一致）新装无阈值时 `show system hardware` 显示「阈值 0%」**
  现象：`root-used 15.6%（阈值 0%）` 同时 `越限:（无）`。判定侧 `Evaluate` 把 `limit<=0`
  当「未设置→ok」（internal/system/hardware.go），显示侧直接把 0 打出来，读起来像「任何占用都越限」。
  建议：未设置时显示「未设置」而不是 0%。

- **R84-11（P3，日志噪音 + 文案不一致）**
  ① VPP 重连时 govpp 告警把**整个二进制结构体 dump** 进 journal（数十行/次，
  正常重连路径上刷屏，本轮多次重启 VPP 现场明显）；建议降级/截断。
  ② 同一处语法错误在两条路径文案不同：`-c` 下 `request images delete <名>` 回

接 §11 的 R84-14/R84-15，本轮把两条都收敛了——**其中 R84-15 是 P1，也是 round84 走查里

**#170 / R84-14（apply 撤销缺口）`delete bonds <名>` 后 VPP 里 BondEthernet0 残留**
- 根因：`internal/orchestrator/apply.go` 的 `plan()` **从未生成 `del-bond` 操作**（删除段只有
  ct/vm/bd/vrf/span/qos/acl），而收敛路径又只「补齐不摘除」；于是删 bond 要等 `request vpp restart`
  才清。残留期间该口同时是 bond 成员与 BD 成员（实测 VPP 允许这种并存——正是它把上一轮的
  VNF 排障带偏）。
- 做法：新增 `del-bond[<名>]` 计划操作（镜像 `del-vrf`，排在 BD/VRF 之后）；新增
  `BondProvider.PruneBonds`（收敛时按 `sw_interface_bond_dump` 枚举数据面现存 bond、跳过声明集，
  对残留项**先按数据面实况逐成员 `bond_detach_member`、再 `bond_delete`**）；`DeleteBond` 未命中
  登记表时按接口名反查数据面。
- 真机复验（1.1.41~dev1，用 ens224 以免动基线）：`set bonds bond0 members 0 ens224` + commit →
  `show bond details` 有 BondEthernet0/ens224；`delete bonds bond0` + commit → **立刻**为空、
  ens224 回普通口；随即把它作为交换机端口声明 → BD 立刻列出（**无需 vpp restart**）；
  手工在 VPP 里加的残留 bond 在 `systemctl restart nfvis` 收敛后同样被拆掉，声明中的 bond 不受影响。

**#171 / R84-15（P1）VNF 的 vhost 口从未挂进 bridge domain——两条「等价」声明其实不等价**
- 现象（1.1.40 实机）：`show interface vh-<vm>-eth0` 恒为 `rx N / drops N (100%)`；
  `show bridge-domain 6252701 details` 成员**只有** bvi0 + ens192；`show l2fib` 学不到 guest MAC；
  连锁＝guest 拿不到 DHCP → cloud-init 卡在 `systemd-networkd-wait-online` → user-data 脚本从未执行
  → BVI ping 100% 丢包，**全程零报错**。
- 反向定位（决定性）：手工 `vppctl set interface l2 bridge vh-rc84b-probe-1-eth0 6252701` 后重启 VM
  → ens192 立刻有 tx、**125µs 后**收到 `192.168.155.254 → 192.168.155.140` 的 DHCP Reply、
  vhost 口 tx 7、L2FIB 学到 guest MAC、guest 拿到地址 ⇒ 断点在产品侧，不在上游也不在 guest。
  同时排除了 `l2-fwd Reflection Drop` 计数与 ens192 rx drops 的干扰（那是 VMware NAT 把邻机
  SSH 泛洪进 BD、VPP 正当拒绝原路回弹）。
- 根因：`internal/orchestrator/network/l2.go` 的 `desiredMembers` 只遍历 `vs.Ports`；而
  `set virtual-machine-functions <n> interfaces <nic> virtual-switch <vs>`（**手册 §9.2 用的写法**）
  只把交换机名存在 VNF 对象上——**全仓没有任何生产代码给 `model.VSwitchPort.Vnf/VnfInterface` 赋值**，
  故 `l2.go` 里处理 VNF 端口的分支与 `portIndex` 是**不可达死代码**。只有交换机侧的写法
  `set virtual-switches <vs> ports <n> vnf <vm> interface <nic>` 才真的生效。
  （这解释了为什么早前轮次「看起来能通」：那时的配置里两种写法都写了。）
- 做法：在 orchestrator 的 `plan()` 与 `EnsureConsistent` 层，用新增的 `SwitchMembersOf`（以
  `VnfPortsOf` 为唯一真源）把 VNF/容器侧声明投影进交换机端口集合的**副本**（显式端口优先、
  不改写调用方配置、**不物化进配置库**，故 `show configuration` 不变）；双向覆盖——声明存在即挂进 BD，
  改挂/删 VNF/删交换机即摘除（摘除排在删 vNIC 之前，单测断言顺序），收敛路径同样重放；
  `desiredMembers` 解析失败改为如实上报（进未收敛清单）而不是静默跳过——这条静默正是缺陷藏了
  这么久的原因。
- **真机端到端（round84 一直缺的那条证据终于拿到）**：探针 VNF 仅用 VNF 侧声明
  （交换机侧端口只有 ens192）→ `show bridge-domain 6252701 details` 成员出现 `vh-rc84c-probe-1-eth0`
  → `show l2fib verbose` 学到 `52:54:5b:5f:23:6e → vh-rc84c-probe-1-eth0`（此前 learned=0）
  → **`vppctl ping 192.168.100.10 source bvi0 repeat 5` 连续三次 5/5 0% 丢包**
  （空闲后首个 ICMP 丢 1 个是已登记的既有环境现象）；
  漂移验证：手工把该口挂到别的 BD → `systemctl restart nfvis` → 自动挂回 6252701、ping 复通 5/5。

**§12 新登记（未修，供下轮裁）**：
- **R84-16（P3，读视图缺口）**：VNF 侧声明的端口**不会**出现在 `show virtual-switches <vs> ports`
  这类**配置来源**的读视图里（BD 成员关系只在运行态可见）。要一致就得在模型归一化层物化进
  `vs.Ports`——但那会把合成端口写进配置库、改变 `show configuration` 的形状，**属需先决策的改动**，
  本轮只做到「运行态正确」。
- **R84-17（P3）**：删 VNF 后 `VNF_PORT_DOWN` 告警不自动消（进程内告警表，重启即清）。
- **R84-18（P3）**：`cross-connect` 端口数不足时**静默无操作**（既有测试把「缩减到 1 端口」定义为合法）。
- 容器 memif 的同一投影路径只过了单测（机上容器未声明 vNIC）。

§14 round84 追加现场：用户点名的「VNF 的 eth0 走 NFViS NAT 拿 IP 并 ping Windows 宿主」测试
--------------------------------------------------------------------------------
**结论：当前产品的 NAT 功能对该场景不可用**——`nfvis-cli` 侧配置能提交、VPP 侧 NAT44-EI 也确实
在位（`show nat44 ei interfaces` = `ens192 in` / `ens224 out`、池地址在位），但 **VNF 的 vNIC
接不进 NAT 的 inside 转发域**，实测 guest 侧 100% `Destination Host Unreachable`。

拓扑与配置（全部走产品路径，rev 118~122）：
```
vs-nat (L3): l3-interface ens192 192.168.200.1/24     # inside 转发域
vs-wan (L3): l3-interface ens224 192.168.155.61/24    # outside 出接口
nat rules 10 match source 192.168.200.0/24 virtual-switch vs-nat
            action interface ens224 + action source-pool pool-a(192.168.155.62)
vnf-dhcp: interfaces eth0 virtual-switch vs-nat
guest: 192.168.200.10/24 gw 192.168.200.1（cloud-init 静态，无 DHCP 服务端）
```
- VPP 侧核对：`show nat44 ei interfaces` → `ens192 in` / `ens224 out`；`show nat44 ei addresses` →
  `192.168.155.62`（池）+ `192.168.155.61`（出接口地址，VPP 自动纳入）⇒ **NAT 特性本身配起来了**。
- guest 侧实测（串口两轮一致）：
  `2: enp1s0 inet 192.168.200.10/24` + `default via 192.168.200.1`，
  而 `ping 192.168.155.1` → `From 192.168.200.10 icmp_seq=1 Destination Host Unreachable` ×3，
  **3 packets transmitted, 0 received, 100% packet loss**。
- 断点：**guest 的网关 ARP 无人应答**。ARP 请求从 vhost 口进来，而 `192.168.200.1` 配在
  `l3-interface ens192` 上——VPP 只为「接收接口自己所拥有的地址」作答，同 VRF 但另一接口的地址不代答。

**根因（两条，都在产品侧）**
1. **NAT 的 inside 接口集合永远不含 VNF 的 vNIC**：`internal/orchestrator/network/l3.go` 的
   `SetVnfTable`（VNF vNIC 进 L3 交换机，FR-NET-020 的 L3 场景）只调 `sw_interface_set_table`
   把接口置入 VRF 表，**不登记进 `p.ifaces[tableID]`**；而 NAT inside 的解析走
   `AttachedIfaces()`（只读该登记集合，`provider.go` 里 `SetInsideResolver(n.l3.AttachedIfaces)`）
   ⇒ vNIC 拿不到 `nat44-ei-in2out` 特性，其流量不会被转换。实测 VPP 里 inside 只有 ens192。
2. **vNIC 无法承载网关地址**：决策 #41 规定 L3 交换机的 vNIC「置表、不配 IP」；而校验层
   （`internal/model/validate.go`）明确拒绝把 vNIC/任何非物理口当 l3-interface——
   `vrfs[vs-nat].l3_interfaces[vh-vnf-dhcp-eth0]: L3 接口 "vh-vnf-dhcp-eth0" 不存在或不是物理口/bond/vlan 子接口`；
   本轮顺带实测**连 VPP tap 也被同一条校验拒**（`l3_interfaces[tap0]` 同样报错），
   即 M5 证据里「tap 作 inside」的做法在当前校验下已不可复现。
   两条叠加 ⇒ guest 在自己的口上既没有可 ARP 的网关、也不会被 NAT 命中。
- 附带的三个 NAT 相关缺陷（本轮实测，未修）：
  - **R84-20（P2，下发不幂等）**：重放时 `nat44_ei_add_del_interface_addr`（规则不带 source-pool 时）
    与 `nat44_ei_add_del_address_range` 会对 VPP 重复下发并收到 `VPPApiError: Value already exists (-81)`，
    **整个 `ApplyNAT` 中止**（表现为一条 WARN + 未收敛项），而配置与 `show nat` 看起来完全正常（误导）。
    实测：把池地址与出接口地址错开、且池不带出接口自身地址时，首次下发可成功；`p.ifaddr/p.pools`
    这类进程内状态一丢（重启 nfvisd）就会重放失败。
  - **R84-21（P2，进程内状态不随 VPP 失效）**：带外 `systemctl restart vpp` 后，产品仍认为 NAT
    已下发（`p.enabled/p.features/p.pools` 都在）→ 跳过重放 → `show nat44` 空、NAT 静默失效，
    必须 `systemctl restart nfvis` 才恢复。与 R84-3（stats 连接只建一次）同族，但影响的是 apply 状态。
  - **R84-22（P3，顺序）**：恢复收敛里把 vNIC 置入 L3 VRF 可能早于该 VRF 建表 →
    `VNF 接口 … 置入 VRF vs-nat 的 IPv4 表: VPPApiError: No such FIB / VRF (-3)` 未收敛项，
    再重放一次才成功（本轮 commit 与守护进程重启各见一次）。
- 操作者注记：NAT 试验期间我用 cloud-config 给 guest 写了 `/etc/netplan/99-nfvis-static.yaml`（静态地址），
  **该文件随 guest 磁盘持久**——把 user-data 换回 DHCP 后 guest 仍按旧静态地址跑（于是宿主 ping 不通，
  看着像数据面坏了）。清理办法是再推一个 `rm -f /etc/netplan/99-nfvis-static.yaml && netplan apply`
  的 user-data 并重启（本轮即如此复原）。**改 guest 网络配置时优先用脚本改运行态，别写持久化 netplan**。
- 复原：已把拓扑退回用户上一轮验证过的形态（`vs-vnf` L2 + `ports 1 ens192` + BVI 192.168.100.1/24，
  VNF eth0 回 `vs-vnf`，user-data 回 DHCP 报告脚本），并复验 **宿主 → guest `192.168.155.143` 4/4 0% 丢失 <1ms**、
  `nfvis-vm → guest` 3/3 0%、`show l2fib` 学到 guest MAC。
- **能给用户的可用路径**：要「guest 拿 192.168.155.x 并 ping 通 Windows 宿主」，当前版本请用
  **L2 桥接**（guest 的 vNIC + `ens192` 同挂一个 L2 交换机，DHCP 由上游网段给）——即 §13 与本轮复原后的形态；
  **经 NFViS NAT 的路径要等上面两条根因修掉**（建议：把 vNIC 登记进 inside 解析集合 + 允许 vNIC 承载
  L3 地址，或为 L3 交换机提供自动的 vNIC 网关）。


§15 round84 终章之二：VNF 的 eth0 走 NFViS NAT 打通（决策 #172~#174）
--------------------------------------------------------------------------------
承接 §14 的两条根因，本轮把「VNF 的 eth0 经 NFViS NAT 拿地址并 ping 通 Windows 宿主」跑通了。
终态配置（全部产品路径）：
```
vs-nat (L3): l3-interface vh-vnf-dhcp-eth0 ip address 192.168.200.1/24   # vNIC 自己当有地址的 L3 接口
vnf-dhcp:    interfaces eth0 type vhost-user virtual-switch vs-nat
vs-wan (L3): l3-interface ens224 ip address 192.168.155.61/24
nat rules 10: match source 192.168.200.0/24 virtual-switch vs-nat action interface ens224
guest:       192.168.200.10/24 gw 192.168.200.1
```
**guest 侧（串口，1.1.42~dev3 实机）**：
```
PING 192.168.155.1 (192.168.155.1) 56(84) bytes of data.
64 bytes from 192.168.155.1: icmp_seq=1 ttl=127 time=1.99 ms
64 bytes from 192.168.155.1: icmp_seq=2 ttl=127 time=0.294 ms
64 bytes from 192.168.155.1: icmp_seq=3 ttl=127 time=0.325 ms
```
**VPP 侧（`show nat44 ei sessions detail`，跨 VRF 会话）**：
```
i2o 192.168.200.10 proto icmp port 516 fib 1
o2i 192.168.155.61 proto icmp port 11570 fib 2
     total pkts 6, total bytes 504      dynamic translation
（同一时刻 3 条动态转换，thread vpp_wk_0）
```
* 副作用：`show nat44 ei interfaces` = `vh-vnf-dhcp-eth0 in` / `ens224 out`；`show interface address` 里
  `vh-vnf-dhcp-eth0` 持有 `192.168.200.1/24`（table = vs-nat），guest 的网关 ARP 由该口自己作答
  （修前是 100% `Destination Host Unreachable`）。

**本轮修的三件事（决策 #172~#174）**
- **#172 允许「已声明的 vNIC 口」作 L3 接口**：口名规则（`vh-<vm>-<nic>`、>63 字节回退 FNV-1a、
  容器 `mf-…`）从 `internal/orchestrator` **下沉到 `internal/model`**（避免两处漂移；
  `orchestrator.VnfIfaceName/MemifIfaceName` 变薄封装、签名不变），校验层按**同一份配置**枚举
  已声明的 vNIC 并放行其确定性口名（随机名字/tap/未声明口仍拒）。
  这解决了 §14 根因二：guest 的网关终于落在它自己的口上。
- **#173 NAT inside 覆盖 vNIC + VPP 重连后按配置重建登记**：`SetVnfTable` 现在把 vNIC 计入该 VRF 的
  inside 集合（`AttachedIfaces` 合并 `ifaces` ∪ `vnfs`，按 idx 去重）；恢复收敛在 **VRF 落地之后、
  ApplyNAT 之前**按 committed 配置重建三类登记（`ifaces`/`ifaceTable`/`vnfs`），使
  `InvalidateRuntimeState()`（VPP 重连时清进程内缓存）之后 NAT 仍能算出 inside/outside；
  另加守卫：规则声明了 virtual-switch 却解析不出 inside 时**不删**既有 inside 特性（避免「算不出就关插件」）。
  **真机复验**：`systemctl restart vpp` + `systemctl restart nfvis` 后
  `show nat44 ei interfaces` 仍是 `vh-vnf-dhcp-eth0 in` / `ens224 out`、池地址在、无未收敛项。
- **#174 NAT 下发幂等 + 地址池带 VRF**：地址池/接口地址/静态映射的 add 方向容忍
  `-81 Value already exists`、移除方向容忍 `-6 No such entry`/`-81`/`-169 Feature already disabled`
  （此前一次重放就会让整个 `ApplyNAT` 中止，只留一条 WARN + 未收敛项，而 `show nat` 看着正常）；
  地址池下发改带上 outside 转发域的 VRF（`nat44_ei_add_del_address_range` 的 `VrfID`，此前恒为 0），
  删除时用登记里的旧 VRF（换域要先删旧表）。

**仍未解决（新登记，供下轮裁）**
- **R84-24（P2）显式 `source-pool` 在跨 VRF 场景下分配不出端口**：带 `action source-pool` 时
  guest 的包**进了 NAT**（`nat44-ei-in2out-slowpath` 计数在涨）但会话建不起来：
  `vppctl show errors` → `nat44-ei-in2out-slowpath  out of ports`，`show nat44 ei sessions` = 0。
  实测把池地址的 tenant VRF 从 0 改成 outside VRF 后**仍然**如此；**去掉池、只留 `action interface`
  （由出接口地址承担外部地址）则立刻通了**（即上面那组成功证据）。
  怀疑池的 tenant VRF 语义与 inside/outside 的对应关系还需与 VPP 源码核对（可能与 inside VRF 或
  会话租户绑定，而不是 outside VRF）。**现状给操作者的口径：跨 VRF NAT 请用 `action interface`
  （不带 source-pool）**；这条已在手册 §8.8 写明。
- **R84-25（P3）`delete nat rules <seq> action source-pool <name>` 会连带删掉整条规则**（本轮两次
  踩到：只想摘掉池引用，结果 `show nat` 里规则整条消失）。我未逐句隔离验证其语义（是循环删除还是叶子删除），
  但两次现象一致，建议下轮用最小用例确认并给出「只删叶子」的写法或明确文档。
- **R84-26（P3）`show configuration | display set` 在「空 `nat;` 节点」上反推失败**：
  输出 `%% display set 内部错误：生成语句未能完整还原配置——请改用 show configuration / | display json 并报告缺陷`
  （自校验诚实报错是好的，但操作者拿不到 display set；触发场景：删光 NAT 规则后配置里留下空 `nat` 节点）。
- 另：本轮为验证在 VNF 上用了「运行期脚本设 IP」（不走 netplan），避免 §14 那类持久化 netplan 残留；
  该脚本每次改 user-data 文件名触发 cloud-init 重放，属既有机制（§0 红线 12）。
- **机器终态**：拓扑停在 §15 这套 NAT 配置（guest 在 192.168.200.0/24、经 NAT 出 ens224），
  VNF `vnf-dhcp` running；如需回到「guest 直接桥到上游网段」，把 VNF 的 eth0 指回一个 L2 交换机
  （端口含 ens192）并让 guest 走 DHCP 即可（§13 的形态）。


§16 round84 终章之三：R84-24/25/26 三条收口（决策 #175/#176）
--------------------------------------------------------------------------------
- **R84-24 已修（决策 #175）**：显式 `source-pool` 在跨 VRF 下建不起会话的根因是**池的 tenant VRF 取错了域**。
  真机 + VPP 26.06 源码定位：池地址带 FIB 索引，in2out 慢路径只从「接收接口所在表」或「VRF-independent」的
  地址里挑端口；池被登记到 outside 表 → 永远没有候选地址 → `nat44-ei-in2out-slowpath  out of ports`、会话恒 0。
  实测同一地址按 **inside 表（8922296）** 下发后立刻可用。修后**真机验收（1.1.43~dev2，带池配置）**：
  `show nat44 ei addresses` → `192.168.155.62 / tenant VRF: 8922296`；
  `show nat44 ei sessions detail` → `i2o 192.168.200.10 … fib 1` / `o2i 192.168.155.62 … fib 2`（12+ 条动态转换）；
  guest 串口 `64 bytes from 192.168.155.1: icmp_seq=… ttl=127`（首轮偶发 33% 丢包＝已登记的空闲首包现象）；
  `out of ports` 冻结在 6 不再增长。

§17 round84 终章之四：R84-27 收口（决策 #177）——`show nat` 会话答非所问
--------------------------------------------------------------------------------
- **根因**：VPP 26.06 的 `nat44_ei_user_session_dump` 是**按用户** dump；产品的 `NATSessions()` 发的是
  `0.0.0.0 / vrf 0` → 永远 0 条，于是 NAT 明明在跑（`vppctl` 有会话、guest 经 NAT ping 通宿主），
  `show nat` 却说「（无 NAT 会话）」。
- **真机探针**：`nat44_ei_user_dump` → `192.168.200.10 vrf_id=8922296 nsessions=13`（8922296 = `TableID("vs-nat")` 租户表，
  **不是**会话里的 fib 1）；按该值 dump 得 13 条，按 `0.0.0.0/vrf 0` 得 0 条。
- **修法**：先 `nat44_ei_user_dump` 收齐用户，再逐用户 `nat44_ei_user_session_dump{IP, VrfID 取自 user_dump}` 汇总；
  空用户表如实返回空、dump 失败原样上抛（**不做静默降级**——退回旧口径正是缺陷成因）。
- **真机验收（1.1.44~dev1 实装）**：造流量后立即查，`show nat` 输出 3 行配置 + 表头 + **25 条会话**
  （如 `192.168.200.10  570  192.168.155.62  19948  1  6`），与 `vppctl show nat44 ei sessions detail`
  **逐条对照 25 vs 25、双向差异 0**；`show nat sessions` 等价写法同结果。
- 附注：产品侧会话字段与契约 `NatSession`（inside_ip/inside_port/outside_ip/outside_port/protocol/bytes/packets）
  本就一致，CLI 表头未变——只修了「取哪份事实」。
