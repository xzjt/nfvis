§7 发现（登记待裁；按严重度排序）
--------------------------------------------------------------------------------
- **R84-1（P1，假成功 + 套件假绿）非交互脚本模式对「需确认」命令静默无操作且退出码 0**
  现象：`nfvis-cli -c "request system reboot"` 只打印
  「重启 nfvis 将中断全部业务。Restart the system? [yes,no]」→ rc=0，什么都没做；
  `request system software rollback`、`request images delete name …`、`request system zeroize`、
  `request interfaces <口> bind-dpdk|unbind-dpdk`、`delete virtual-machine-functions|containers|images`
  同理（凡服务端以 `[yes,no]` 结尾问询的都在内）。
  根因：确认流程只在交互 REPL 里实现（internal/cli/repl.go 的 `strings.HasSuffix(out,"[yes,no]")`
  分支读一行并追加 `--yes` 重发）；`runScript`（cmd/nfvis-cli/main.go）**完全不处理**问询文本，
  既不报错也不置 failed。
  连带：`contrib/scripts/cli-fulltest.sh` 的判定只看行首 `%`/`校验失败` 与 rc，
  于是把「问了没做」判成 ✓（本轮日志实见 `✓ request system software rollback`、
  `✓ request images delete name naming-test.tar`）——**套件覆盖是假的**。
  建议：runScript 检测到 `[yes,no]` 时按错误处理（`%% 需交互确认：非交互模式请显式追加 --yes`）
  并置 failed；套件对这些行显式加 `--yes` 或改判为「预期报错」。
  手工规避：命令尾加 `--yes`（本轮实测可用）。

- **R84-2（P1，配置完整性 + 数据面残留）CLI 删 L3 交换机不清同名 VRF（CLI⇄REST 不一致）**
  现象：`delete virtual-switches vs-l3` + commit 后，`show configuration` 里仍留
  `vrfs vs-l3 { name vs-l3; }`；`display set` 反推不出它（空 VRF 无语句形态，操作者看不见）；
  `vppctl show ip table` 里 `vs-l3` 表**跨 VPP 重启与 nfvisd 重启持久存在**，`show vrfs` 一直列出；
  CLI **无任何命令可清除**（`delete vrfs` = 无效命令；再 `delete virtual-switches vs-l3` = 「无匹配配置」）。
  根因：REST `DELETE /virtual-switches/{name}` 明确连同名 Vrf 一并删
  （resources.go，注释「L3 交换机与同名 VRF 条目互为映射（附录 B），一并删除」）；
  而 CLI 走 `applyTokens` 通用删除路径，只有 `delete virtual-switches <n> type` 这类别名规则
  才调 `removeVrf`（cli_aliases_net.go），整节点删除没有对应清理。
  建议：把「删虚拟交换机 → 同时删同名 Vrf」落到两侧共同依赖处（CLI 侧补等价清理），并补守护用例。
  规避：先 `set virtual-switches <名> type l2`（触发 removeVrf）再删对象。

- **R84-3（P2，假成功 + 误诊）接口统计在 VPP 重启后永久不可用（= R83-7 复现 + 根因）**
  现象：`show interfaces ens192 detail` 的 RxPkts/TxPkts 为 `-`；
  `show interfaces ens192 statistics` → `%% 接口 ens192 统计运行态不可用（stats 未接入）`；
  REST `GET /interfaces/{name}` 只回 `{"name":"ens192"}`（契约声明含 statistics）；
  控制台接口详情页据此显示「读取失败：该口当前取不到计数（数据面未连接或口不在数据面）」。
  同刻独立事实源有值：`vppctl show interface ens192` rx packets=174418、CLI 列表视图 RxPkts=62。
  根因：internal/orchestrator/network/stats_linux.go 的 `statsConn.conn` 进程内**只建一次**，
  VPP 重启后 stats segment 换了，`GetInterfaceStats` 失败 → `InterfaceCounters` 永久返回 false，
  且不重连；恢复只能 `systemctl restart nfvis`。
  **决定性证据（本轮实测）**：`systemctl restart nfvis` 后同一请求立刻恢复——
  `GET /interfaces/ens192` → `{"description":"cli-pre","name":"ens192","statistics":{"rx_packets":1,…}}`，
  `show interfaces ens192 statistics` → `interface ens192 statistics: {1 0 60 0 0 0 0 0}`；
  重启前同一请求只有 `{"name":"ens192"}`。⇒ 不是「stats 未接入」，是连接陈旧。
  建议：取数失败时重连一次并重建连接（或与 VPP 重连回调联动）；文案别再说「stats 未接入」。

- **R84-4（P2，假成功）`request vpp restart` 无起后健康校验（= R83-6 复现）**
  现象：把 2M 池运行期置 0（`echo 0 > …/hugepages-2048kB/nr_hugepages`）后走产品路径
  `request vpp restart` → 回「已按 committed 配置重启 VPP 并触发恢复收敛。」，
  而 VPP 实际 `failed (Result: core-dump)`、`code=dumped, signal=SEGV`、Mem peak 2.1M、
  `vppctl` Connection refused；`show interfaces` 会如实标注「VPP 未连接」。
  根因：requestVPP 的 restart 分支在 `vppRestart(ctx)` 返回 nil 即报成功（cli_compute_oper.go），
  不等起后健康校验。
  建议：restart 后短轮询校验 VPP 存活（binary API 可连），失败即 `%%` 报错并指出「VPP 未起来」；
  另可重启前按 startup.conf 需求预检大页池尺寸。

- **R84-5（P2，不可达指引）`show system kernel` 的「一致性」把运行期池增长判成基线未生效**
  现象：cmdline 已是 `hugepages=1`、配置期望也是 1，但运行实际 2 →
  输出「一致性：与配置期望不一致（需写入 GRUB 基线并重启生效）：大页 1G：期望 1，实际 2
  （cmdline 启动参数需生效并重启）」，并引导 `request system kernel apply` → `request system reboot`。
  实测重启 + `request vpp restart` 后 1G 仍是 2/1（VPP 运行期把池顶大后内核不回收），
  **照提示做永远不一致**；向导结尾与手册 §5.4 第 1 步「重启后应显示一致」因此不可达。
  根因：internal/system/kernel.go 的 `Compare` 用运行实际池大小与期望比对（不是 cmdline 与期望），
  而提示文案说的是 cmdline 未生效。
  建议：大页一致性按 cmdline（基线）比对；运行实际大于声明时另作说明（不判不一致），
  仅当运行实际小于声明（分配失败）才告警。控制台同源显示一并受益。

- **R84-6（P2，可诊断性）镜像下载中断后状态长期停在 downloading**
  现象：`request images download …` 直连 CDN 约 1.7MB/min，8.5MB 后停滞；`show images` 一直
  `downloading`，`detail` 无进度字段，journal 无任何相关日志，`index.json` 里 `.part` 留在原地；
  超过 client 的 10 分钟超时后仍显示 downloading（未验证到 failed 状态），操作者无进度/无错误/无重试指引。
  建议：进度写进 meta（`show images <名> detail` 可见）、超时/中断即落 `failed` 并在 CLI 报错、
  重试走断点续传（.part 已在，机制已有）。注：本轮最终用代理 curl + upload 绕过。

- **R84-7（P2，提示与实现不一致）容器镜像可用名：文案指错方向（#160 收口不完整）**
  现象：`set image alpine:3.20`（tar 内嵌 tag）与 `set image alpine.tar:latest`（产品重打的 tag）
  都被拒：`仓库中不存在镜像 "…"；仓库现有：alpine.qcow2、alpine.tar、debian-…。
  注意：容器镜像的可用名是 docker load 落地的 tar 内嵌 tag；上传目录项名与它不一致时，两个名字都用不了`；
  实际**只有仓库项名 `alpine.tar` 能通过**（commit 成功 rev 23/25）。
  建议：要么让校验同时接受 docker 里真实存在的引用（`alpine:3.20`），要么把文案改成
  「配置里请写上传的目录项名 <名>」，并让 `?`/Tab 候选直接列出仓库项名（现在候选是自由文本）。

- **R84-8（P3，易错点）`request images upload` 的 file 只认绝对路径**
  现象：`request images upload name alpine.qcow2 type vm-image file alpine.qcow2`（候选描述是
  「incoming 内的文件路径」）→ `%% 文件 alpine.qcow2 必须位于 /data/incoming 内（先经 scp/sftp 传入）`；
  根因是相对路径按**守护进程 CWD** 解析成 `/alpine.qcow2`。写 `/data/incoming/alpine.qcow2` 才成功。
  建议：相对路径按 IncomingDir 解析，或错误文案点明「请给绝对路径」。

- **R84-9（P3，文档漂移）手册 §5.3 的 wizard 输出样例与实现不符**
  样例写 `top`，实现打印 `exit`，且顺序在 commit 之前；另样例未含「内核基线已写入/pending_reboot」
  两段实际输出。建议随发布轮重拍该样例。

- **R84-10（P3，显示与判定口径不一致）新装无阈值时 `show system hardware` 显示「阈值 0%」**
  现象：`root-used 15.6%（阈值 0%）` 同时 `越限:（无）`。判定侧 `Evaluate` 把 `limit<=0`
  当「未设置→ok」（internal/system/hardware.go），显示侧直接把 0 打出来，读起来像「任何占用都越限」。
  建议：未设置时显示「未设置」而不是 0%。

- **R84-11（P3，日志噪音 + 文案不一致）**
  ① VPP 重连时 govpp 告警把**整个二进制结构体 dump** 进 journal（数十行/次，
  正常重连路径上刷屏，本轮多次重启 VPP 现场明显）；建议降级/截断。
  ② 同一处语法错误在两条路径文案不同：`-c` 下 `request images delete <名>` 回
