## 0.1 round14（R13-E/R13-F 收口，决策 #458/#459）

- **#458（R13-F）**：VM 内存必须是生效页尺寸的**正整数倍**，提交期拒绝（改前提交放行、`start` 才由 QEMU
  报裸错）。真机两态：`512`+`1G`、`1536`+`1G` 均提交即拒；`1024`+`1G` 放行。
- **#459（R13-E）**：内核基线**为每个已声明页尺寸各挂一个** hugetlbfs 挂载点（主挂载点 `/dev/hugepages`
  保持旧口径、另一尺寸 `/dev/hugepages-<size>`）。真机：`request system kernel apply` 写出两条挂载行，
  2M 的 VM 从「无可用挂载点」变为 `running`；**顺带修掉** apply/show 的「一致（无需重启）」不含挂载点
  这处不实陈述（现把「已声明但未挂载」并入 pending/一致性差异）。

  走 2M、1G 留给 VNF），3×1G-only 不是目标形态，故**不改编排**；「1G 池声明 N ⇒ VNF 可用 N−1」作为
  明示边界保留（决策 #347 / 手册 §6.2），不再作为待办。

  跑前必须先解决的六件事见该证据 §1；套件脚本已留在 VM `/root/suites/`。
- **观察③ 已收口**（**round15，决策 #460**）：读视图/手册把 1G 池数据面固定占的那 1 页说成「VPP 主堆」，
  真机取证**不是**——`/proc/<vpp>/smaps` 里唯一的 1G 页映射是 **DPDK EAL 段 `memfd:seg_0-0`**，而
  `vppctl show memory` 的 main heap `page stats` 是 `page-size 2M`（512×2M=1G）。页数口径不变、**只改解释**；
  CLI/REST（同源 note）/Web/向导注释/手册/命令全表五处措辞已更正。真机（`dev6`）CLI 与 REST 均带新归属。
- **观察① 已收口**（**round16，决策 #461**）：Web VM 详情「资源」块 vCPU 绑定/绑定核/内存后端/大页大小
  恒「—」而运行态有事实——根因是**字段级**（三处「未声明即回显空值」+ `vcpu.cores_assigned` 契约声明了
  从未发出）。修后读视图给**有效值**（pin⇒true、backing⇒hugepage、页尺寸⇒主池）并按**账本**发
  `cores_assigned`；`numa_node` 按设计仍「—」（未声明＝无 NUMA 亲和）。真机三面（CLI/REST/Web）复核过，
  截图 `docs/images/v3-round16-web-vm-resources-effective.png`。
- **`unbind-dpdk` 「不自动重探」已口径收口**（**round17**，非缺陷）：本平台内核**确实不会**在清
  `driver_override` + `rescan` 后自动交还原生驱动（**停 VPP 后**实测，3s 内无驱动；模块与 alias 都在位）
  ⇒ 产品「先试 + 失败如实报错 + 给 `to-driver` 提示」是正确行为。⚠️ 教训：**对仍被 VPP 持有的设备写
  sysfs 会阻塞**（本次第一次实验就挂住了）——产品那条「仍在数据面占用」守卫的文案与实测一致。
  证据 `docs/evidence/v3-round17-unbind-dpdk-reprobe-confirmed.txt`。

  会话」且报文已丢。按**文案明示**落地：CLI 三处（start 提示 / stop 后果 / export 无会话的照做提示）+

  逐个跑，api 测试单次约 8 分钟）。
- **「改完必须真机过一遍」**：本轮 3 处细化都是真机才暴露的（govpp 错误形状、delete 幂等、人话文案）。
- **交叉编译换装二进制**是快路径，但**正式发版仍须 deb 两次逐字节一致 + 四套件**。
- **lab 拓扑坑**：L2 域的 BD 含物理口接 VMnet8 时，guest 的 DHCP 广播会被外置 DHCP 抢先应答（产品侧
  租约如实记录，别误判为产品缺陷）。
