# NFViS v3：数据面可切换（VPP / Linux 内核网络）设计

> 生成日期：2026-10-07。契约先行：本文件先于实现落盘，实现与本文件不一致时以本文件为准并同步修订。
> 决策记录见 `docs/NFViS-系统产品需求与目标架构规格书.md` 附录 A #404。

## 1. 目标与口径

产品新增**数据面实现的选择**：同一套配置模型、同一套 CLI/REST/Web 交互，数据面可以由
**VPP**（既有）或 **Linux 内核网络**（v3 新增）承担，由 `system.dataplane` 开关决定。

四条口径（用户裁定）：

1. **整机单数据面**：同一时刻只启用一种。切换需重启 nfvisd 生效（与 `resource-pools`
   同档的「需重启」语义），切换时不做在线迁移。
2. **安装期与运行期都能选**：安装器 `--dataplane vpp|kernel`、首次初始化向导问一句、
   运行期 `set system dataplane <vpp|kernel>`。三处**写的是同一个事实源**（committed 配置），
   安装器与向导只是把它代写进配置。
3. **缺省 = vpp**：未配置时回落 VPP，与引入该开关之前的行为逐字一致——既有安装升级后
   不会莫名其妙换数据面。
4. **不留假功能**：内核数据面尚不实现的能力，在**提交期直接拒绝**（不是「配了不生效」），
   命令与读数**如实报不支持**（不是「VPP 未连接」这种会误导排查的措辞）。

## 2. 架构

### 2.1 选择点

`cmd/nfvisd/main.go` 在装配网络编排之前读一次 committed 配置的 `system.dataplane`
（`committedDataPlaneMode`，读不到一律回落 vpp），据此装配其一：

| 装配项 | `vpp` | `kernel` |
|---|---|---|
| 网络编排 | `*network.L2Network`（VPP 客户端族） | `*netkernel.Provider`（`ip`/`bridge`/`nft`） |
| VPP 连接管理 / 拉起 / DPDK 接管 / startup.conf | 全量 | **不创建、不拉起** |
| 计算编排的 vNIC 形态 | vhost-user socket | virtio 网卡 + 宿主 tap + vhost-net |
| VPP 控制面（`show vpp` / `request vpp restart`） | 真实控制器 | 如实回报「当前数据面为内核网络」 |
| 运行态聚合（`state.Runtime`） | VPP stats segment | 无（读视图省略运行态字段） |
| 诊断（ping/traceroute） | `vppctl` | 宿主网络栈（`ip vrf exec` 支持 VRF 作用域） |

### 2.2 方法面：两种实现同形

装配层与恢复巡检不按数据面分叉——两者实现**同一个方法面**（`main.netRuntime` =
`orchestrator.NetworkProvider` + 恢复巡检 + 运行态读视图）：

- VPP 侧：`*network.L2Network`（既有）；
- 内核侧：`*netkernel.Provider`（新增，编译期断言 `var _ netRuntime = (*network.L2Network)(nil)`
  与 netkernel 包内的对应断言把「方法面一致」钉在编译期）。

内核侧对**能给出内核等价物**的读视图给真值（MAC 表、路由、bridge 成员、接口状态、端口清单），
对**内核数据面无对应物**的（LLDP 邻居、NAT 会话、DHCP 租约）如实报不可用；
风暴抑制/端口安全的「数据面实况」块已改读**内核事实**（tc/nft）——此前把真话塞进说明字段、
消费方按 VPP 字段读不到，会显示成「未收敛」，与事实相反。

## 3. 能力映射与支持矩阵

### 3.1 已实现（v3 第一期）

| 配置对象 | VPP 实现 | 内核实现 |
|---|---|---|
| `interfaces[]` | DPDK 接管物理口 + sw_interface | 物理口留在内核（MTU/描述/管理状态用 `ip link`） |
| `bonds[]` | bond（静态 / LACP） | 内核 bonding（无 lacp → `balance-xor`；有 → `802.3ad`） |
| `virtual-switches[]`（l2） | bridge domain | 内核 bridge（`vlan_filtering`；access/trunk/native → `bridge vlan`） |
| 交换机网关（BVI） | BVI 接口 + 网关 VRF | 地址落在 bridge 上，bridge 入网关 VRF（`vr-<交换机名>`） |
| `vrfs[]`（l3 交换机） | VRF / IP 表 | 内核 VRF（`ip link type vrf`，表号由名字确定性派生） |
| l3-interface（含 vlan 子接口） | subif + 地址 | `ip link type vlan` + `ip addr` |
| `routes[]` | FIB | `ip route`（VRF 表内，`metric` = distance） |
| `nat` | nat44 插件 | nftables（`table inet nfvis-nat`：snat / masquerade / dnat） |
| `vxlan-tunnels[]` | vxlan 插件 | 内核 vxlan 设备 |
| VNF vNIC | vhost-user socket | virtio 网卡 + 宿主 tap + **vhost-net**（`<interface type='bridge'>`） |
| `sriov.vf-count` | sysfs（本就内核侧） | 同（不变） |
| 抓包 / 诊断 | VPP pcap trace / `vppctl ping` | 诊断走宿主网络栈；抓包走宿主 `tcpdump`（命令与端点数据面中立同名——`show capture` / `request capture …` / `/capture`；`count` 语义随数据面：VPP 为环形缓冲深度、内核为达到即停） |

### 3.2 第二批（已实现）

| 配置对象 | VPP 实现 | 内核实现 |
|---|---|---|
| `acls[]` + `l3-interface acl-in` | acl 插件（macip 槽） | nftables 独立表 `netdev nfvis-acl`：每个 ACL 一条链（按 seq 顺序、末尾无条件 `drop` ＝ 隐式拒绝），绑定＝按设备一条 ingress 链 + `jump`；绑定前先放行非 IP（ARP）——VPP 侧踩过的坑在这里同样成立 |
| `qos-policies[]` + 接口入/出向绑定 | policer 入向/出向特性 | tc `clsact` + `matchall action police rate <cir>bit burst <cbs> drop`，入/出向各自独立 |
| `port-mirroring[]` | span 插件 | tc `mirred egress mirror dev <分析口>`（ingress/egress/both） |
| `interfaces[].storm-control` | policer + L2 classify | tc 按目的 MAC 分类（广播 `ff:ff:ff:ff:ff:ff`、组播 I/G 位掩码）各一条 police |
| `interfaces[].port-security` | macip ACL | 桥口 `learning off` + nftables `netdev` 表按源 MAC 白名单丢弃 |

**共享 `clsact` 的 pref 分配表**（`tc.go` 的 `tcPref*`，单一真源）：QoS 10 / 镜像 20 /
风暴广播 30 / 风暴组播 40。真机集成测试抓到过 pref 撞号的缺陷（QoS 与风暴都用 10，
风暴的撤除把刚下发的限速 policer 删了）——新增族必须从这张表取号。

**同接口多族共存的口径**（内核语义：同一 chain 按 prio 升序遍历，**首个判决 ≥0 的 filter 即终止
遍历**）：QoS/风暴的 police 判决写成 `conform-exceed drop/continue`（超限丢、未超限**继续遍历**
后续 filter），端口镜像的 mirred 尾随 `continue`——于是**同一接口上 QoS + 风暴 + 镜像可共存**，
任一族都不再静默屏蔽后续族。风暴两档：**广播档不继续遍历**（与 VPP 侧一致：广播帧只落广播档），
只配组播档时广播帧按目的 MAC 的 I/G 位落入组播档。

### 3.2b 第三批（已实现）：DHCP 中继（自研用户态中继实例，决策 #437）

| 配置对象 | VPP 实现 | 内核实现 |
|---|---|---|
| `virtual-switches[].dhcp_relay_server` | VPP dhcp proxy（按 rx-VRF，源地址重写、giaddr=0） | **nfvisd 内的用户态中继实例**（每台声明了中继的 L2 交换机一个；零外部依赖，不引入 dhcrelay/dnsmasq 一类守护进程） |

**报文口径**（与 VPP 侧同口径，round113 真机实证的形态）：收该交换机内核 bridge（`LinkName(vs.Name)`）
上的客户端 DHCP 请求（UDP/67）→ **源地址重写为中继源 = BVI 的 IPv4 网关地址**（socket 绑定该地址 : 67）
→ 单播到 `server:67`，**giaddr=0**、载荷**字节保真**（不插 option 82）。上行 socket 同时**绑到该域的
VRF 设备**（`SO_BINDTODEVICE`，与既有 `ip vrf exec <vrf>` 同一口径）——BVI 地址与域内路由都在
`vr-<交换机名>` 这张表里，只绑源地址时本地发起的路由查找落在主表（域内网段不在主表），connect
就会 ENETUNREACH；绑 VRF 设备后查找走该 VRF 的表，收包侧由内核按「入向设备是该 VRF 的从属」
（bridge 已 enslave 到该 VRF）匹配回本 socket。应答按
「**请求期 `xid` → 客户端 MAC**」的**短 TTL 登记表**（30s）回注——客户端此刻无 IP、不能靠路由，
故用 **AF_PACKET** 构造完整以太帧写回 bridge（由 bridge 按 fdb 单播/洪泛），以太源 = bridge 的 MAC、
IP 源 = 真实 server 地址、IP 目的 = 255.255.255.255、UDP 67→68、校验和按新头重算。

**客户端寻址依据采用契约给定的 (a)（登记表）**，不用 (b)（option 82 + server 回显）：(a) 不依赖
server 回显 option 82（VPP proxy 真机踩过的坑：不回显即静默丢弃），且不改动客户端载荷；
登记表同时是回注白名单（只有转出过的 xid 的应答才回注，来源还由连接式 UDP 限死为配置的 server:67）。
**表里找不到客户端的应答一律丢弃并计数**（`droppedNoClient`，进读视图注记），不静默。

**生命周期**（与 VPP 侧 dhcp proxy 同族）：提交随 bridge-domain 之后的伴随操作收敛（`ApplyDhcpRelay`
——新配/改 server/换网关地址重建实例、清声明停实例，起不来如实失败并使提交回滚）；交换机删除时
`DeleteBridgeDomain` **先停实例**（先解引用、后删被引用）；**恢复重放必须含 relay**（实例活在 nfvisd
进程内，进程重启后必然不在——`EnsureConsistent` 交换机段之后重放）；15s 巡检 `ReconcileProxy`
按 committed 对账（起失败被停的补启、已不声明的停掉，失败进未收敛告警）；进程退出 `Provider.Close`
停掉全部实例（socket/收发协程不残留）。

**读视图**：配置视图沿用既有 `dhcp_relay:{server}`（两数据面同形、VPP 侧逐字不变）；内核侧另加
**运行态注记 `dhcp_relay_note`**（仅详情端点，见 openapi）——机制 + 寻址依据 + 运行态/计数三面同源
（CLI `show virtual-switches <n> detail` / REST `GET /virtual-switches/{n}` / Web 详情页）。

**如实边界（v1）**：只处理**无 802.1Q 标签的 IPv4** DHCP 请求（与产品自带 DHCP 服务器同口径）；
收包面 = AF_PACKET 绑 bridge 的**本地端口**（域内广播/多播 + 目的 MAC 是 bridge 自身的单播）——
成员口之间直接交换的单播不经中继（server 与客户端同处一个二层域时应直连）；server 须在该转发域内
可达（同子网或域内静态路由，与 VPP 侧同一要求）；不挂 cBPF（按以太类型过滤到 IPv4 + 用户态判 UDP/67，
DHCP 速率极低）。

### 3.2c 第四批（已实现）：DHCP 服务器（复用既有服务器核心，只换传输面，决策 #438）

| 配置对象 | VPP 实现 | 内核实现 |
|---|---|---|
| `virtual-switches[].dhcp_server_*` | nfvisd 内的用户态服务器 + 每交换机一条内置 L2 tap（tapv2，进 BD）+ UDP/67 punt（单播续租） | **同一份用户态服务器核心**（池/租约/报文解析与构造/状态机/池耗尽告警**零复制**——`network.DHCPServerProvider`），只换两处传输面（见下） |

**两处内核专有的传输面**（其余与 VPP 侧逐字同源）：

1. **内置 tap**：每台启用的交换机建**一条内核 TUN/TAP netdev**（`ip tuntap add dev nfvisdhXXXX
   mode tap`；名沿用 `network.DHCPServerTapName`：`nfvisdh` + 8 位十六进制 = 15 字符 = IFNAMSIZ 上限），
   `ip link set dev <tap> master <该交换机的内核 bridge>` 并置 up——域内广播随 bridge 洪泛到该 tap。
   **删除按名核对身份**（严格字符集）后再删：内核接口索引会被复用，绝不按旧索引删。
   设备建好后**由产品打开 `/dev/net/tun` + `TUNSETIFF`（IFF_TAP|IFF_NO_PI）认领并长期持有该 fd**，
   以太帧收发直接读写这个 fd（read = bridge 洪泛到该端口的帧；write = 以「该端口收帧」的形态注入
   bridge），fd 与服务器实例同生共死（停用/reset/进程退出即释放持有）。
   **为什么必须持有、为什么不能用 AF_PACKET**（真机实证，务必知悉）：TUN/TAP 的 carrier 来自
   「有没有进程持有它」——`ip tuntap add` 只建**持久化设备**，此时设备是 `NO-CARRIER, state DOWN`，
   内核 bridge **不会把洪泛帧投给 carrier 为 down 的端口**，客户端 DISCOVER 永远到不了服务器
   （命令全成功、租约表恒空＝静默失效）；而 tap 的「线」就是持有它的 fd，写 tap 的 AF_PACKET 是
   「把帧交给持有者」的反方向（VPP 模式能工作正是因为那边 tap 由 VPP 持有、那条路把应答交给 VPP）。
   内置 tap 不进用户端口视图（VPP 侧按 sw_if_index 过滤，内核侧按名过滤，同一语义）。
2. **单播续租**：每交换机一个**绑到该交换机 BVI 网关地址的 UDP/67 socket**（`SO_BINDTODEVICE`
   绑该域 VRF 设备，与 §3.2b 的中继上行同法）——绑具体地址使域内广播天然不进这条路径、只走
   tap 洪泛（两条入径互补）。收到的载荷按「合成 IPv4 头 + 原载荷」交给 provider 与 VPP punt
   上行**同一解析入口**（描述符的 `SwIfIndex` 写该交换机内核 bridge 的 ifindex，经
   `SetSwitchResolver` 派发）。内核没有 punt 机制，`PuntClient` 实现为空操作：内核侧的
   「注册在不在场」由 socket 生命周期表达（socket 在＝注册在）。

**生命周期**（与 VPP 侧同族）：提交随 bridge-domain 之后的伴随操作收敛（`ApplyDHCPServer`；
启用＝建/复用，停用＝teardown：删内置 tap + 关 socket + 清租约文件）；交换机删除时
`DeleteBridgeDomain` 先停服务器（先解引用、后删被引用）；**恢复重放必须含它**（`EnsureConsistent`
交换机段之后重放：socket 活在进程内、重启后必然不在，tap 是内核对象、按名复用）；15s 巡检
`ReconcileDHCPServer` 对账（socket 按声明收敛 + 核心 Reconcile 补 tap/回收租约/复核告警）；
进程退出 `Provider.Close`（socket/收发协程不残留；tap 对象保留复用）。**起不来如实报错并进未收敛项**
（提交失败并回滚 / 恢复收敛告警并 15 秒重试）：bridge 尚未收敛、tap 建不出、BVI 地址未下发或 67
端口被占都是明确错误，不静默。

**读视图**：租约表/生效租约数与 VPP 侧**同一份**（`show virtual-switches <n> dhcp-leases` /
`GET /virtual-switches/{n}/dhcp-leases`）；内核数据面接入后该端点的「尚未收敛」503 只在真未收敛时出现。

**apply 路径不得回读配置引擎（真机自死锁实证，务必遵守）**：提交期间发动机锁
由**本次提交自己持有**，apply/Sync 路径里任何 `Provider.config()` / `Engine.Committed()` 重入读取都会
**永久阻塞**（真机 SIGQUIT 全栈：一次 `set … dhcp-server pool …` 提交把整个管理面挂死，`handleLogin` 一并卡住）。
故交换机事实（bridge 名 / 服务 VLAN）**只从调用点传下去**：`DHCPServerClient` 由 `client(sw)` 工厂按
`Sync(ctx, vs)` 的那份声明构造（VPP 侧实现收下同一参数但不使用，行为逐字不变）；巡检只用入参 `cfg`。
守护：`dhcpserver_test.go` 的「读取即阻塞的假配置源」回归用例 + 源码级 `p.config()` 扫描。

**VLAN 交换机的服务域（内核 bridge 专有的一步）**：内核 bridge 打开 `vlan_filtering` 后，广播只在
**同一 VID** 内洪泛（VPP 的 BD 没有这个概念——tap 天然与所有端口同域），故内置 tap 必须**钉到该交换机的
服务 VLAN**（`bridge vlan add dev <tap> vid <v> pvid untagged`）：服务 VLAN 取**交换机 access VLAN 或
第一个 native VLAN**（与 `vlanFilteringValue` 同一真源；未声明 VLAN 时不产生任何 VLAN 命令）。
**如实边界**：**纯 trunk**（声明了 VLAN 却没有 access/native VLAN）时服务域无法确定 ⇒ **如实报错**
（提交失败/未收敛项，文案给照做路径），不静默让客户端拿不到地址；**多 VLAN**（access + trunk）时服务器
服务 access/native 那一档，其余 VLAN 的客户端不受理（VPP 数据面不受此限）。

### 3.2d 第五批（已实现）：数据面 DNS 代理（复用自研转发核心，决策 #439）

| 配置对象 | VPP 实现 | 内核实现 |
|---|---|---|
| 全局上游（`cfg.Vpp.DNSProxyServers`）+ 各交换机按域上游（`VirtualSwitch.DNSProxyServers`） | nfvisd 内自研转发器 + VPP punt socket（收「目的 ∈ VPP 本机」的 UDP/53，按 sw_if_index 选域，回注裸 IP 包） | **同一份 DNS 报文级核心**（SERVFAIL 构造与 question 回显、上游去重、宿主栈查询——`network` 包共享导出，VPP 侧改调同一实现、行为逐字不变），只换传输面：**每个域落点一个绑具体地址的 UDP/53 socket** |

**落点集（内核侧的服务地址）**＝ L2 交换机的**全部 IPv4 网关地址** ∪ 各 VRF（`vrfs[]` 与 type=l3
交换机同名条目）`l3-interface` 的**全部 IPv4 地址**。每个落点一个 socket：`udp4` 绑**具体地址 : 53**
（不是 INADDR_ANY——只接管指向产品域内地址的查询），并 `SO_BINDTODEVICE` 绑该域的**内核 VRF 设备**
（`vr-<交换机名>` / 显式 `gateway vrf` / 同名 VRF 经 `LinkName`；与 §3.2b 的中继上行、§3.2c 的单播续租
**同一绑定法**——l3mdev 语义，真机已印证的路径）。域的 IPv4 地址在内核侧就是**本机地址**，故应答就是
普通 UDP 回包（**不需要**像 VPP 侧那样构造裸 IP 包回注）。

**报文口径（与 VPP 侧逐字同源）**：从 socket 收到查询载荷 → 按**入向 socket 所属域**选上游
（按域优先、回落全局；两者皆空 ⇒ 回 **SERVFAIL**，快速失败不静默丢弃）→ 用**宿主网络栈**向上游发
UDP（3s 超时、按声明序尝试；上游可达性要求与 VPP 侧相同＝宿主侧可达，不是域内 FIB）→ 经**同一
socket** 写回客户端（源地址自动＝落点地址、源端口 53）。**不缓存、不解析资源记录内容、纯 UDP**
（TCP 不在覆盖）——边界与 VPP 侧同口径。

**隔离/归属口径**：只接管指向产品域内地址的查询；**管理地址不在此列**（管理口不在数据面域）——
决策 #386「管理网侧不提供对外解析」的口径不受影响。**全局上游在内核数据面同样生效**：
`VppConfig.DNSProxyServers` 是数据面中立配置（#400 已确认不进 startup.conf），提交提示相应收窄为
「vpp 段里存在 DNS 代理上游之外的字段才提示不生效」。

**提交期校验（内核侧）**：删「数据面 DNS 代理尚未实现」拒绝；新增——**按域上游要求该交换机至少一个
IPv4 落点**（L2＝IPv4 网关；type=l3＝同名 VRF 的 l3-interface 至少一条 IPv4 地址），否则提交期拒绝并
给照做路径（内核侧该域没有任何可被查询的本机地址＝死配置）；VPP 侧既有口径（不要求网关）不动。

**生命周期**（与 §3.2b/§3.2c 同族）：随提交编排收敛（既有 `ApplyDNSProxy` 全局 op，位于交换机/VRF
之后；undo 回旧声明）；**恢复重放必须含它**（socket 活在 nfvisd 进程内，进程重启后必然不在——
`EnsureConsistent` 的 VRF/vxlan 段之后重放）；15s 巡检 `ReconcileDNSProxy` 对账（起失败/带外丢失的
补起、已不声明的关掉；失败如实进未收敛项与告警）；进程退出 `Close` 关全部 socket。**起不来如实报错**
（提交失败并回滚 / 未收敛告警）：地址未就绪、VRF 设备不存在、53 端口被占都是明确错误，不静默。

**读视图**：配置视图（`show dns proxy` / `GET /dns/proxy` 的 enabled/servers/switches）两数据面共用、
行为不变；内核侧**增运行态块**（机制 + 每个落点的〔域、地址、生效上游、状态〕+ 计数〔已应答 / 已回
SERVFAIL / 回包失败〕）——仅内核装配了读物时出现，VPP 侧不出现。

**apply 路径不得回读配置发动机**（与 §3.2c 同一条红线）：内核侧需要的「域落点事实」由**调用点**
（提交编排从目标配置派生）传入——`DNSProxyUpstreams` 增 `Domains` 字段；apply/Sync/巡检路径不读
`Engine.Committed()`（提交期该锁由本次提交自己持有＝重入自死锁）。守护：`dnsproxy.go` 进源码级扫描
`TestKernelApplyPathSourceHasNoEngineConfigRead`。

### 3.2e 第六批（已实现）：LLDP（自研收发代理，决策 #440）

| 配置对象 | VPP 实现 | 内核实现 |
|---|---|---|
| `protocols.lldp`（全局开关 + `advertisement-interval` + 按接口开关） | lldp 插件（`LldpConfig` 全局参数 + `LldpSetInterface` 逐口 + `LldpDump` 邻居表） | **nfvisd 内的自研收发代理**（零外部依赖，不引入 lldpd）：每启用接口一个 **AF_PACKET socket（ethertype 0x88CC）**——收＝解析 LLDPDU 基础 TLV 建邻居表（TTL 过期移除）；发＝按间隔向 `01:80:C2:00:00:0E` 发广告（TTL＝4×interval，与 VPP 侧 txHold=4 同口径） |

**口径**：`Enabled=false`/nil ⇒ 全部关闭；`Interfaces[]` 逐口开关；间隔变更只改发送节奏与 TTL。
**读视图**沿用既有三面同源（`show lldp neighbors` / `show protocols lldp neighbors` /
`GET /protocols/lldp/neighbors`），形状与 VPP 侧逐字不变；ID 渲染复用同一份 `network.LldpIDBySubtype`。
**生命周期**：提交编排（既有全局 op）、恢复重放（进程内 socket/发送协程）、15s 巡检 `ReconcileLLDP`
（补 socket/清过期邻居/复核接口消失）、进程退出关停；起不来如实报错。
**如实边界（v1）**：只解析基础 TLV（未知 TLV 跳过；不做 LLDP-MED/DCBX/管理地址）；只收无 VLAN 标签帧；
发送内容固定为本机主机名/接口名/接口 MAC（无自定义 sysname）；不做 SNMP MIB 与收发计数。**广告源 MAC 在
socket 打开时读取**——若外部（systemd-networkd 等）在运行期改接口 MAC，广告源地址会陈旧到下次重建（真机
实测：veth 被系统采用时 MAC 变化，产品随后按新 MAC 发送，属建立期之后的变化不受影响）。

**真机验证**（veth 对＋对端 netns，证据 `docs/evidence/v3-round5-d440-kernel-lldp.txt`）：发送逐 TLV 解码、
接收两读视图同源、同键刷新不新增、TTL 过期、逐口/全局关停、未声明接口提交期拒绝、`systemctl restart nfvis`
后恢复重放续发。同轮真机还抓出一条**跨族通用缺陷 R4-3 并修复**：删光 LLDP 留下空壳
（`protocols.lldp={}` / `protocols={}`）会让 `show configuration | display set` 报内部错误——修在删除合流点
（`pruneEmptySingleton` 按既有**登记制**补两层；未取通用兜底，`TestPruneEmptySingletonScope` 钉着
「未登记容器不动」的口径），守护测试两形态钉住。

### 3.3 未实现（提交期拒绝，登记 `docs/v3待做.md`）

**整族未实现**（内核侧要么没有对应物，要么需要一个常驻的用户态组件——属独立立项，
不是把现有编排换个底座）：memif 容器接入。
（DHCP 中继**不在**此列：内核侧已用自研用户态中继实例实现，见 §3.2b；DHCP 服务器同样不在
此列：复用既有服务器核心 + 内核 tap/BVI:67 socket 已实现，见 §3.2c；数据面 DNS 代理也不在
此列：复用自研转发核心、落点＝域内 IPv4 地址上的 UDP/53 socket，见 §3.2d；LLDP 同样不在
此列：自研收发代理，见 §3.2e；MAC 学习上限也不是拒绝项，而是「fdb 计数 + 阈值告警」，见 §3.2
与用户手册。）
（抓包**不在**此列：它是数据面无关的运维动作，内核侧以宿主 `tcpdump` 实现，命令与端点数据面中立同名。）

**语义不同、提交期拒绝的形态**（配置能解析，但内核侧会静默改变语义 / 恒不生效，
按「不留假功能」在提交期拒绝，文案点名对象与替代路径）：

- `cross_connect`——内核侧只有学习/泛洪形态的桥，按普通 bridge 静默处理＝改变语义；
- 静态路由**多下一跳（ECMP）**——内核侧未实现，下发期会以 iproute2 原始报错炸掉整次提交；
- **NAT 规则跨转发域**——inside 交换机与出接口不在同一转发域时，内核 nft 不区分转发域、没有跨表
  leaking，规则恒不命中（反向还会把别的域的同源前缀一并 NAT）；
- ACL **`protocol icmp` 带端口字段**——VPP 侧按 ICMP type/code 解读，内核侧表达不了、字段会被忽略；
- **vNIC 接入 `type=l3` 的交换机**——内核侧 l3 交换机不建桥，tap 无处可挂（直到起 VM 才失败）；
- **派生内核设备名撞名**——两个对象（或对象与派生的网关 VRF 名）映射到同一个内核设备名；
- **vlan 子接口派生名超过 15 字符**——`<基口名>.<vid>` 直接作内核设备名，超限内核不接受；
- **镜像源为 VNF 虚拟网卡**——宿主 tap 由 libvirt 在域启动时创建，产品没有可靠的名字映射。

`nat static`（1:1 静态映射）：**多转发域配置下提交期拒绝**（静态映射没有转发域字段、作用域无法判定
——single 域或全默认表放行；判据与替代见附录 A #419，文案点名涉及的域）。

VPP 专有口径（`show vpp *` 的按节点明细、`request vpp restart`、DPDK 接管、大页池「数据面占用」列）
在内核数据面下**按设计如实报不支持**——不是待做项，是口径。

### 3.4 内核侧的真实约束（提交期校验）

- **对象名 ≤15 字符**：交换机/bond/隧道/L3 交换机名直接用作内核接口名（IFNAMSIZ-1）。
  VPP 侧没有这个限制，故只在内核数据面下校验。
- **派生设备名互撞**：两个对象（或对象与按名字派生的网关 VRF 名）映射到同一个内核设备名时
  在提交期拒绝——内核设备名全局唯一，撞名的代价是后者下发失败、配置与数据面错位；
  派生映射的超长截断用**全宽哈希**（此前 16 位哈希可离线构造撞名反例）。
- **vlan 子接口派生名 ≤15 字符**：`<基口名>.<vid>` 超出内核接口名上限时提交期拒绝
  （VPP 侧无此限制），提示缩短基口名或改用不建子接口的形态。
- **VNF 虚拟网卡不能直接作 L3 接口**：内核侧要把它挂进 VRF，而宿主 tap 由 libvirt 在域
  启动时创建，产品侧没有可靠的挂载时点。替代拓扑是「接入一台已配网关的 L2 交换机」。
- **VNF 虚拟网卡不能接入 `type=l3` 的交换机**：内核侧 l3 交换机不建桥（只有 VRF 设备），
  静默接受会让 tap 无处可挂、直到起 VM 才失败。同样改接「已配网关的 L2 交换机」。

### 3.5 转发的前置条件（运行期，产品检测并告警）

内核数据面下产品自己就是那台路由器，「配好接口/路由」不等于「能转发」——两条前置不成立时
所有下发命令都报成功、包却全丢，故产品把它们纳入收敛与巡检：

- **转发开关**：`net.ipv4.ip_forward` 与 `net.ipv6.conf.all.forwarding` 由产品置 1 并**回读确认**
  （写不动/回读不为 1 如实报错）。缺 v6 这一条时 v6 三层地址/路由/ACL 全都「下发成功、一包不转」。
- **宿主 FORWARD 策略**：nftables/netfilter 语义下同一 hook 的多个 base chain **相互独立**——
  产品自建链（`inet nfvis-forward`，priority -10）里的 accept **不能豁免**宿主 FORWARD 策略的 drop
  （真机 A/B 已证）。故产品**检测**宿主 FORWARD 策略：为 DROP 且确有数据面设备时落
  `FORWARD_POLICY_DROP` 告警（warning，含逐对照做命令），策略恢复后自动消解；
  **产品不改宿主规则**——真正生效的放行必须写进宿主那条链。

## 4. 数据面切换的操作路径

```
# 安装期
sh nfvis-v<版本>.run -y --dataplane kernel     # 装齐两套数据面的包；把 system.dataplane 写进配置并重启生效

# 首次初始化
wizard                                          # 1/5 数据面实现 [默认 vpp]：vpp | kernel

# 运行期
configure
set system dataplane kernel
commit      # 提交输出提示「需重启服务后生效」
exit
systemctl restart nfvis
```

切换**不迁移**既有数据面对象：内核侧靠 `EnsureConsistent` 的声明式重放把 committed 配置
重新落到内核（幂等），VPP 侧靠连接事件触发的恢复收敛。切回 VPP 时 `vpp` 段配置仍在，
立即可用（切到内核时提交输出会提示它不生效）。
